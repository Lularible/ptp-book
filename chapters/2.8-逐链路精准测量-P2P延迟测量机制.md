# 2.8 逐链路精准测量：P2P延迟测量机制

## 如果每一段路都有“测速仪”

想象你在高速公路上开车，想知道从北京到上海需要多长时间。

**方法一：记录起点和终点时间**

你从北京出发时看表：8:00
你到上海时看表：24:00
总时间：16小时

但这个时间包含了：
- 真正的行驶时间
- 服务区休息时间
- 堵车等待时间
- 吃饭时间

你不知道哪一段路花了多久。

**方法二：每段路都有测速仪**

高速公路在每个路段都安装了测速仪，记录你进入和离开每段路的时间：
- 北京-天津段：2小时
- 天津-济南段：3小时
- 济南-南京段：8小时
- 南京-上海段：3小时

你可以精确知道每一段的时间，也更容易发现问题（比如济南-南京段为什么这么慢？）。

**PTP的两种延迟测量机制，就像这两种方法**：

- **E2E机制**：测量整个路径的总延迟
- **P2P机制**：逐链路测量延迟

---

## P2P机制的基本原理

### 核心思想

P2P（Peer-to-Peer，对等）机制的核心思想：**让每两个相邻端口之间相互测量链路延迟**。

不像E2E那样由从时钟测量到主时钟的整个路径，P2P让每个链路两端的设备各自测量它们之间的延迟。

### 消息交换过程

P2P机制涉及三类报文（第三类只在 two-step 时出现）：

1. **Pdelay_Req**：请求者发送，请求测量链路延迟
2. **Pdelay_Resp**：响应者回复，携带接收时间戳
3. **Pdelay_Resp_Follow_Up**：**只在响应端口是 two-step 端口时才发送**，携带发送时间戳。是否发送由响应端口自身是 one-step 还是 two-step 决定，并通过 Pdelay_Resp 头部的 `twoStepFlag` 告知请求者。

**消息交换时序**：

```
请求者（A）                             响应者（B）
    |                                       |
    |------ Pdelay_Req (t1) --------------->| (t2)
    |                                       |
    |<----- Pdelay_Resp (t4) ---------------| (t3)
    |                                       |
    |<----- Pdelay_Resp_Follow_Up (two-step)|
    |                                       |
```

**四个时间戳**：

- **t1**：请求者发送Pdelay_Req的时间
- **t2**：响应者接收Pdelay_Req的时间
- **t3**：响应者发送Pdelay_Resp的时间
- **t4**：请求者接收Pdelay_Resp的时间

### 与E2E的关键区别

| 特性 | E2E机制 | P2P机制 |
|:---|:---|:---|
| **谁发起测量** | 从时钟 | 每个端口（无论主从） |
| **测量对象** | 主时钟到从时钟的整个路径 | 两个相邻端口之间的链路 |
| **报文类型** | Sync + Delay_Req + Delay_Resp | Pdelay_Req + Pdelay_Resp + Pdelay_Resp_Follow_Up |
| **透明时钟处理** | E2E TC转发Delay_Req/Resp | P2P TC 应当（should）丢弃Delay_Req/Resp，响应Pdelay_Req |
| **适用场景** | 通用 | 需要逐链路测量，或P2P TC网络 |

## P2P机制的数学推导

### 基本公式

与E2E类似，P2P也使用四个时间戳计算延迟（标准把这式子称为**名义值**）：

```
meanLinkDelay = [(t2 - t1) + (t4 - t3)] / 2
```

**但有一个关键区别**：t1、t2、t3、t4来自**两个相邻的端口**，而不是主时钟和从时钟。

这意味着：
- t1和t4在请求者记录
- t2和t3在响应者记录

### one-step模式

在one-step模式下，Pdelay_Resp报文直接携带时间信息。

**响应者的处理**：

响应者收到Pdelay_Req时记录t2，发送Pdelay_Resp时记录t3。

Pdelay_Resp.correctionField携带：(t3 - t2)，即响应者的**周转时间**。

**请求者的计算**：

```
meanLinkDelay = [(t4 - t1) - correctedPdelayRespCorrectionField] / 2
              = [(t4 - t1) - (t3 - t2)] / 2   （delayAsymmetry 为 0 时）
              = [(t2 - t1) + (t4 - t3)] / 2
```

### two-step模式

在two-step模式下，Pdelay_Resp后跟Pdelay_Resp_Follow_Up。

**响应者的处理**：

响应者收到Pdelay_Req时记录t2，发送Pdelay_Resp时记录t3。

t2、t3 怎么放进报文，标准给了**两种可选实现** ：

- **Option A**：Pdelay_Resp 的 `requestReceiptTimestamp` 与 Pdelay_Resp_Follow_Up 的 `responseOriginTimestamp` **都置 0**，而把周转时间 (t3 − t2) 加到 **Pdelay_Resp_Follow_Up 的 correctionField** 里。
- **Option B**：Pdelay_Resp 携带 t2（`requestReceiptTimestamp`，t2 的小数纳秒部分从 correctionField 中减出），Pdelay_Resp_Follow_Up 携带 t3（`responseOriginTimestamp`，t3 的小数纳秒部分加进 correctionField）。

> linuxptp 实现的是 **Option B**：把 t2 写入 `requestReceiptTimestamp`，把 t3 写入 `responseOriginTimestamp`。

**请求者的计算**：

标准的完整式是四项相减，与 2.7 里含 correctionField 的 meanPathDelay 完整式同等严谨：

```
meanLinkDelay = [(t4 - t1)
                 - (responseOriginTimestamp - requestReceiptTimestamp)
                 - correctedPdelayRespCorrectionField
                 - Pdelay_Resp_Follow_Up.correctionField] / 2
```

其中：

- **correctedPdelayRespCorrectionField** = Pdelay_Resp.correctionField + ingressDelayAsymmetry
  （请求者用自己入口侧的 delayAsymmetry 校正所收到的 Pdelay_Resp；two-step 下 Pdelay_Resp.correctionField 本身被置 0）

代入 Option B 的 t2、t3，就得到教科书写法；再进一步，当**入口/出口 delayAsymmetry 均为 0、链路上没有透明时钟累加 correctionField** 时，后两项消失，式子退化为：

```
meanLinkDelay = [(t4 - t1) - (t3 - t2)] / 2
              = [(t2 - t1) + (t4 - t3)] / 2
```

若响应端实现的是 **Option A**，则 (responseOriginTimestamp − requestReceiptTimestamp) = 0，周转时间 (t3 − t2) 改由 `Pdelay_Resp_Follow_Up.correctionField` 这一项提供，代入完整式后结果与 Option B 相同。

### 为什么有两种模式？

**one-step模式**：
- 优点：一次单向测量只需要两个报文（Pdelay_Req + Pdelay_Resp），效率高
- 缺点：需要在发送Pdelay_Resp时精确测量t3，硬件要求高

**two-step模式**：
- 优点：可以在发送Pdelay_Resp_Follow_Up时携带精确的t3，实现简单
- 缺点：一次单向测量需要三个报文，开销大

IEEE 1588 **不规定**实现者该选哪一种，也不描述市场上哪种更普遍，本书同样不作此断言。

### 容易被忽略的前提：两端的频率必须接近

`meanLinkDelay = [(t2 - t1) + (t4 - t3)] / 2` 里，t1、t4 来自**请求者**，t2、t3 来自**响应者**，是**两套时钟**。把往返时间"对半分"，隐含假设了这两套时钟走得一样快。

如果两端频率不同，这个对半分就不成立。标准对此有明确提醒：

> 当 PTP 端口使用的时间戳时钟**不是**本地 PTP 时钟时（例如**未做频率同步的透明时钟**的端口），`<meanLinkDelay>` 的测量会因为同步化误差（syntonization error）而偏离期望值。

这恰恰是 P2P 的软肋：**P2P 要求链路上每一台设备，包括透明时钟都参与测量**，而透明时钟往往只做时间透传、不做频率同步。E2E 侧也有同样的问题，但只有主、从两端，面窄一些。

为此标准定义了两个频率比值：

- **`<neighborRateRatio>`**：链路上游 PTP 实例的本地时钟频率 ÷ 本端本地时钟频率。从测量角度，还有一个等价说法：**响应端口的时间戳时钟频率 ÷ 请求端口的时间戳时钟频率**；在该"累积频率传递"选项下，P2P 端口必须（shall）在计算 `<meanLinkDelay>` 的同时计算它。标准给的示例估计式用相隔 N 次测量的两组时间戳求增量之比（分子为响应端的 t3，分母为请求端的 t4，正是上面这个"响应÷请求"）：

  ```
  neighborRateRatio = [(t3)_N − (t3)_0] / [(t4)_N − (t4)_0]
  ```

- **`<cumulativeRateRatio>`**：Grandmaster 时钟频率 ÷ 本端本地时钟频率。

算出这个比值后，就可以把"两端频率不同"造成的测量偏差从 `<meanLinkDelay>` 中扣掉，而不是任其累积。

## 一个完整的P2P测量示例

### 场景

```
端口A ---- 链路 ---- 端口B
```

**参数**：
- 真实链路延迟：100ns（对称）
- 端口A的时间：正常
- 端口B的时间：正常（假设已经同步）

### 消息交换

**步骤1：端口A发送Pdelay_Req**

- 发送时间：t1 = 1000.000000000秒

**步骤2：端口B接收Pdelay_Req**

- 接收时间：t2 = 1000.000000100秒（100ns后）

**步骤3：端口B发送Pdelay_Resp**

- 发送时间：t3 = 1000.000001000秒（假设处理延迟900ns）

**步骤4：端口A接收Pdelay_Resp**

- 接收时间：t4 = 1000.000001100秒（t3 + 100ns）

### 计算

**四个时间戳**：

- t1 = 1000.000000000秒
- t2 = 1000.000000100秒
- t3 = 1000.000001000秒
- t4 = 1000.000001100秒

**计算meanLinkDelay**：

```
meanLinkDelay = [(t2 - t1) + (t4 - t3)] / 2
              = [(100ns) + (100ns)] / 2
              = 100ns
```

**正确！**

**注意**：响应者的周转时间（t3 - t2 = 900ns）不影响测量结果，因为被减掉了。

## P2P机制与透明时钟

### P2P透明时钟的特殊处理

P2P透明时钟（P2P TC）不仅要测量驻留时间，还要：

1. **测量链路延迟**：对每个端口，使用P2P机制测量与对端的链路延迟
2. **累加到correctionField**：转发Sync时，把驻留时间 + 入口链路延迟累加

### P2P TC的工作流程

**场景**：

```
主时钟 ---- TC_B ---- 从时钟
```

**TC_B的端口1（连接主时钟）**：

1. 定期发送Pdelay_Req给主时钟
2. 收到Pdelay_Resp，计算meanLinkDelay_1
3. 监听主时钟的Sync报文

**TC_B的端口2（连接从时钟）**：

1. 定期发送Pdelay_Req给从时钟
2. 收到Pdelay_Resp，计算meanLinkDelay_2
3. 向从时钟转发Sync报文

**转发Sync的处理**：

当Sync报文从端口1进入，从端口2离开：

```
Sync.correctionField（出口） = Sync.correctionField（入口）
                               + residenceTime
                               + meanLinkDelay_1
                               + ingressDelayAsymmetry
```

**关键**：meanLinkDelay_1是**入口链路的延迟**（主时钟→TC_B）。

## P2P vs E2E：深度对比

### 测量粒度

**E2E**：
- 测量**整个路径**的延迟
- 包含所有链路延迟 + 所有透明时钟驻留时间
- 无法区分哪一段贡献了多少延迟

**P2P**：
- 测量**每个链路**的延迟
- 可以精确知道每段链路的延迟
- 便于诊断和优化

### 不对称处理

**E2E**：
- 整个路径的不对称会影响offsetFromMaster
- 难以分别处理各段不对称
- 依赖配置的delayAsymmetry值

**P2P**：
- 每段链路的不对称独立处理
- 可以分别配置各段的不对称
- 更精细的控制

### 网络规模影响

**E2E**：
- 从时钟数量增加，Delay_Req报文数量线性增加
- 主时钟负载重
- 可能成为瓶颈

**P2P**：
- 每个端口独立测量，负载分散
- 不存在中心瓶颈
- 更适合大规模网络

### 收敛速度

**E2E**：
- 新设备加入时，需要完整的消息交换
- 收敛速度取决于Sync和Delay_Req的间隔
- 收敛时间的量级：经验值大约几秒到几十秒（**这是工程经验估计，标准没有规定任何收敛时间指标**；它主要由 `logSyncInterval` 与 `logMinDelayReqInterval` 决定）

**P2P**：
- 新设备加入时，立即开始P2P测量
- 链路**两端各自**持有一份 `<meanLinkDelay>`，网络重配置后可以**立即**做路径延迟校正，不必再等一轮端到端测量
- 收敛速度更快

### 网络拓扑要求

**E2E**：
- 对拓扑无特殊要求
- 可以有普通交换机（非PTP设备）在中间
- 兼容性好

**P2P**：
- 要求所有设备支持P2P机制
- 中间不能有普通交换机
- 要求更严格

### 报文数量

**E2E**：
- 每个从时钟：1个Delay_Req + 1个Delay_Resp
- 延迟测量报文数量 = 2 × 从时钟数量

**P2P**：
- 每条链路**两端各自**测一遍：每端 1个Pdelay_Req + 1个Pdelay_Resp（响应端是 two-step 时再加 1个Pdelay_Resp_Follow_Up）
- 延迟测量报文数量 = 4（或6）× 链路数量

**对比**：

假设：
- 网络有100个设备，形成树状拓扑
- 从时钟数量：99个
- 链路数量：99条

**E2E延迟测量报文数量**：2 × 99 = 198个

**P2P延迟测量报文数量**：4 × 99 = 396个（one-step）或 6 × 99 = 594个（two-step）

P2P的延迟报文总数是E2E的两倍甚至三倍，但：

**E2E的报文由从时钟发送**，所有Delay_Req都发往主时钟，主时钟负载重。

**P2P的报文由每个端口发送**，负载分散到整个网络。

## P2P机制的典型应用场景

### 场景一：TSN网络（时间敏感网络）

TSN（Time-Sensitive Networking）是IEEE 802.1定义的一组标准，用于在以太网上提供实时性保障。

TSN的时间同步由独立标准**IEEE 802.1AS**（业界称gPTP）规定：它不是1588定义的Profile，但基于PTP，且要求：

- 全双工以太网链路强制使用点对点（peer）延迟测量机制
- 其中继实例在同步计算上与P2P透明时钟等价，但并不完全符合1588对P2P透明时钟的规定；它自己跑BMCA，用的算法与1588的**基本相同、只是略作简化**
- 稳态下的端到端指标是：相隔7跳以内的两个实例，时间误差不超过1µs峰峰值

**为什么TSN选择P2P？**

TSN网络通常用于工业自动化、汽车电子等场景，要求：
- 快速收敛（设备加入后快速同步）
- 确定性延迟（每段链路延迟已知）
- 高可靠性（故障快速切换）

P2P机制可以满足这些要求。

### 场景二：电信网络

ITU-T定义了G.8275.1和G.8275.2 Profile，用于电信网络的时间同步。

这两个Profile各自规定哪种延迟机制，须以ITU-T原文为准：1588与802.1AS全文都未提及G.8275，本书不作断言。

### 场景三：White Rabbit

White Rabbit是一个开源的超高精度同步方案，基于PTP + SyncE（同步以太网）。

White Rabbit的规范载体是High Accuracy **Delay Request-Response** Default Profile（P2P在其中只是可选），它扩展了：
- 精确的链路延迟测量（使用DDMTD相位检测器）
- 频率同步（通过SyncE）
- 不对称校准（硬件测量光纤不对称）

可以实现**亚纳秒级同步**。

## P2P机制的实现挑战

### 挑战一：所有设备必须支持P2P

P2P机制要求网络中**所有设备**都支持P2P。

如果中间有普通交换机（不支持P2P），会发生什么？

**问题**：

普通交换机不会响应Pdelay_Req，P2P测量失败。

如果多个设备连接到同一个普通交换机，一个Pdelay_Req可能被多个设备接收，违反P2P的“一对一”假设。收到多个Pdelay_Resp属异常，标准要求必须处理：要么进入FAULTY（透明时钟则是故障条件），要么采取实现自定义的处置动作。

**解决方案**：

- 网络规划时，确保所有设备支持P2P
- 或使用边界时钟隔离不支持P2P的区域

### 挑战二：频繁的P2P测量

P2P机制要求每个端口定期发送Pdelay_Req，可能增加CPU和网络负载。

**建议**：

- 根据网络稳定性调整Pdelay_Req间隔
- 稳定网络可以用较大间隔
- 间隔下限受默认Profile约束：logMinPdelayReqInterval默认0、可配置0到5，即1秒到32秒

### 挑战三：多端口设备的资源管理

边界时钟和P2P透明时钟有多个端口，每个端口都需要：
- 独立的P2P状态机
- 独立的meanLinkDelay存储
- 独立的Pdelay报文发送/接收

**资源消耗**（以下为**工程估算**，标准不提供任何资源占用指标）：

- 每端口：状态机 + `portDS.meanLinkDelay` + 收发缓冲，量级约为几KB内存
- 每端口：独立的定时器
- 报文处理：每端口按配置的平均间隔收发Pdelay报文（默认 Profile 下平均间隔为 1 s～32 s），间隔越短、报文越多

对于64端口交换机，这些资源累加起来也是可观的。

## 一个完整的P2P网络示例

### 网络拓扑

```
主时钟A ---- P2P_TC_B ---- P2P_TC_C ---- 从时钟D
```

### 初始化阶段

**P2P_TC_B的端口1与主时钟A建立P2P测量**：

1. P2P_TC_B端口1发送Pdelay_Req
2. 主时钟A回复Pdelay_Resp
3. P2P_TC_B端口1计算meanLinkDelay_AB = 100ns

**P2P_TC_B的端口2与P2P_TC_C端口1建立P2P测量**：

1. P2P_TC_B端口2发送Pdelay_Req
2. P2P_TC_C端口1回复Pdelay_Resp
3. P2P_TC_B端口2计算meanLinkDelay_BC = 150ns

**P2P_TC_C的端口2与从时钟D建立P2P测量**：

1. P2P_TC_C端口2发送Pdelay_Req
2. 从时钟D回复Pdelay_Resp
3. P2P_TC_C端口2计算meanLinkDelay_CD = 120ns

### 同步阶段

**主时钟A发送Sync**：

- originTimestamp = 1000.000000000秒
- correctionField = 0

**P2P_TC_B处理Sync**：

收到Sync（端口1）：
- 记录ingress时间戳
- originTimestamp = 1000.000000000秒
- correctionField = 0

转发Sync（端口2）：
- 计算驻留时间：residenceTime_B = 5μs
- meanLinkDelay_AB = 100ns
- ingressDelayAsymmetry = 0

更新correctionField：

```
correctionField = 0 + 5μs + 100ns + 0 = 5.1μs
```

**P2P_TC_C处理Sync**：

收到Sync（端口1）：
- correctionField = 5.1μs

转发Sync（端口2）：
- 计算驻留时间：residenceTime_C = 3μs
- meanLinkDelay_BC = 150ns
- ingressDelayAsymmetry = 0

更新correctionField：

```
correctionField = 5.1μs + 3μs + 150ns + 0 = 8.25μs
```

**从时钟D接收Sync**：

- originTimestamp = 1000.000000000秒
- correctionField = 8.25μs
- meanLinkDelay_CD = 120ns（已通过P2P测量）

**计算从时钟接收Sync时刻的主时钟时间**：

```
主时钟发送时间（校正后） = originTimestamp + correctionField
                         = 1000.000000000 + 0.00000825
                         = 1000.000008250秒

路径延迟 = meanLinkDelay_CD = 120ns

从时钟接收Sync时刻的主时钟时间 = 1000.000008250 + 0.000000120
                               = 1000.000008370秒
```

offsetFromMaster = 从时钟接收Sync时刻的从时钟时间 − 从时钟接收Sync时刻的主时钟时间

从时钟可以根据这个时间调整自己的时钟。

**关键点**：从时钟**不需要发送Delay_Req**，因为路径延迟已经被P2P TC累加到correctionField中了。

## 小结：P2P机制的核心要点

**核心思想**：
- 逐链路测量延迟
- 每个端口独立测量与对端的链路延迟
- P2P TC累加链路延迟到correctionField

**消息交换**：
- Pdelay_Req：请求者发送（**链路两端各自发一份**）
- Pdelay_Resp：响应者回复
- Pdelay_Resp_Follow_Up：**只在响应端口是 two-step 时才发**（由 Pdelay_Resp 的 `twoStepFlag` 指示），携带精确时间戳

**核心公式（名义值）**：

```
meanLinkDelay = [(t2 - t1) + (t4 - t3)] / 2
```

**P2P TC的处理**：

```
Sync.correctionField += residenceTime + meanLinkDelay + ingressDelayAsymmetry
```

**与E2E的对比**：

| 特性 | E2E | P2P |
|:---|:---|:---|
| 测量对象 | 整个路径 | 每个链路 |
| 延迟测量报文数 | 2×从时钟数 | **4~6×链路数**（两端各测一遍） |
| 负载分布 | 主时钟集中 | 全网分散 |
| 网络要求 | 无特殊要求 | 所有设备支持P2P |
| 收敛速度 | 较慢 | 较快 |
| 不对称处理 | 粗粒度 | 细粒度 |

**适用场景**：
- TSN网络
- 大规模、高精度要求网络
