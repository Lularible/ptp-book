# 2.11 Where Do Nanoseconds Come From? The Mystery of Hardware Timestamps

## Software timestamps: microseconds, and that's the problem

For a PTP slave to compute the offset, it needs two accurate instants: when the Sync left the master, and when it arrived at the slave.

Where do those instants get captured?

In the simplest scheme, software timestamping, the capture happens somewhere in the OS network stack:

1. The NIC receives the frame and raises an interrupt.
2. The OS schedules the network driver.
3. The driver copies the frame and the application reads it with `recvfrom()` / `clock_gettime()`.

Every step adds delay: interrupt latency, kernel scheduling jitter, cache misses, CPU frequency scaling. The captured timestamp easily carries 10-100 µs of uncertainty.

That's catastrophic for PTP: an error of even 1 µs directly corrupts the offset computation.

Software timestamping is not precise enough.

## Hardware timestamps: capture at the PHY

Modern NICs have a PTP Hardware Clock (PHC), typically a counter driven by a high-accuracy oscillator. When a frame crosses a defined point inside the PHY, the PHC's value is latched in hardware, in parallel with the packet.

This gives:

- The exact instant the frame's first symbol crossed the reference plane.
- No interrupts, no scheduling, no software at all.
- Accuracy in the low nanoseconds.

That hardware-latched value is the hardware timestamp.

### The timestamp pipeline

```
PHY latches timestamp  →  DMA delivers the frame  →  driver attaches metadata (skb_shared_info)
     (ns accuracy)          (frame + timestamp)        (control message to userspace)
```

The application reads the timestamp through ancillary data (`SOL_SOCKET` / `SO_TIMESTAMPING` on receive; `MSG_ERRQUEUE` for transmit).

## Timestamp types in LinuxPTP

`enum timestamp_type` (util.h) distinguishes the timestamping modes:

| Type | Meaning |
|:---|:---|
| `TS_SOFTWARE` | Timestamps captured in software (kernel `SOF_TIMESTAMPING_*_SOFTWARE`). |
| `TS_HARDWARE` | Hardware timestamps from the PHC (`SOF_TIMESTAMPING_*_HARDWARE`). |
| `TS_LEGACY_HW` | Legacy hardware timestamps, reported in the system clock domain (`SOF_TIMESTAMPING_SYS_HARDWARE`). |
| `TS_ONESTEP` | One-step: the PHY inserts the timestamp directly into the on-wire frame. |
| `TS_P2P1STEP` | One-step for Pdelay_Resp in peer-to-peer mode. |

The mappings to the kernel `flags` (`SO_TIMESTAMPING_*`) were shown in section 3.8. The key pairs:

- Software RX/TX: `SOF_TIMESTAMPING_RX_SOFTWARE | TX_SOFTWARE | SOFTWARE`.
- Hardware RX/TX: `SOF_TIMESTAMPING_RX_HARDWARE | TX_HARDWARE | RAW_HARDWARE`.

## Timestamp resolution and jitter

Two figures matter:

- Resolution: how finely the PHC counts (e.g., 125 MHz → 8 ns ticks; 1 GHz → 1 ns).
- Jitter: how repeatably the same event lands on the same counter value.

A NIC with 8 ns resolution and sub-nanosecond jitter contributes ~1-2 ns of uncertainty to a PTP measurement, which is why hardware timestamping enables nanosecond sync, while software timestamping (µs-level jitter) does not.

## The timestamp point, the reference plane, and corrections

The PTP standard defines the message timestamp point (for Ethernet, the start of the first symbol after the SFD) and the reference plane (the boundary between the PTP instance and the network).

Ingress: the timestamp at the capture point inside the PHY is later than the reference-plane instant. The captured value must be corrected:

```
timestamps (RX)  = hardware timestamp − ingressLatency
```

Egress: the timestamp point is reached before the frame leaves the reference plane:

```
timestamps (TX)  = hardware timestamp + egressLatency
```

Where `ingressLatency` / `egressLatency` may be configured through `timestampCorrectionPortDS` (option 16.7).

For most PHYs with hardware timestamping, these latencies are negligible and default to zero.

## One-step clocks

In two-step mode, the precise origin is carried in a Follow_Up message. In one-step mode, the NIC itself writes the timestamp into the on-wire Sync (or Pdelay_Resp), the frame on the wire already contains its own send time.

One-step requires the hardware to:
- read the PHC,
- overwrite the originTimestamp field (and the correctionField),
- fix up any UDP checksum over the modified payload.

That's why one-step is harder to implement; most commodity NICs run two-step.

## Virtual clocks and BIND_PHC

A single PHY with one PHC can be split into several virtual clocks (vclocks). By binding a socket to a specific vclock (`SOF_TIMESTAMPING_BIND_PHC` + `bind_phc` index), applications can run multiple independent PTP domains on one NIC, each with its own disciplined time base.

## Summary

- Software timestamps: µs-level uncertainty, too coarse for precision PTP.
- Hardware timestamps: latched at the PHY, ns-level.
- Resolution and jitter decide the achievable quality.
- One-step lets the NIC write the timestamp itself.
- Latency corrections map the capture point to the reference plane.

Hardware timestamping is the first pillar of nanosecond precision in PTP.

Those timestamps ride inside specific on-wire structures. To read a Sync and find the originTimestamp, to parse the flagField and correctionField, you need to know exactly what a PTP message looks like.

A PTP message is a precisely structured header followed by a message body: Sync is 44 bytes, Announce is 64, Delay_Resp is 54...

Getting the offsets and byte order right is the difference between a working PTP implementation and garbage.
