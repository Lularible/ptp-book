# 2.12 The Ten Languages of PTP: A Full Look at Message Formats

## If PTP messages could talk

Imagine a PTP message as a courier, weaving through the network.

Each one carries a different letter:

- **Sync**: "The master clock says it's now 10:00:00.000000000 seconds."
- **Announce**: "I'm the master clock. My clockClass is 6, my clockAccuracy is 0x20."
- **Delay_Req**: "Tell me, when did you receive this message?"
- **Delay_Resp**: "I received your request at 10:00:01.000000100 seconds."

Every message has its own format and purpose. Today we'll decode the ten PTP messages.

---

## How PTP messages split

### Event messages

**Key traits**:
- They need a timestamp
- They demand high accuracy
- Hardware usually handles them

**Message types**:

| Message | Type value | Purpose |
|:---|:---|:---|
| **Sync** | 0x0 | Carries time information |
| **Delay_Req** | 0x1 | Requests a delay measurement |
| **Pdelay_Req** | 0x2 | Peer delay measurement request |
| **Pdelay_Resp** | 0x3 | Peer delay measurement response |

**Why do they need timestamps?**

These messages drive time synchronization and delay measurement, so the send and receive times must be recorded precisely.

### General messages

**Key traits**:
- They don't need a timestamp
- They carry configuration and status information
- Software can handle them

**Message types**:

| Message | Type value | Purpose |
|:---|:---|:---|
| **Follow_Up** | 0x8 | Carries the precise timestamp (two-step mode) |
| **Delay_Resp** | 0x9 | Delay measurement response |
| **Pdelay_Resp_Follow_Up** | 0xA | Precise timestamp for the peer delay measurement |
| **Announce** | 0xB | Master clock announcement |
| **Signaling** | 0xC | Signaling |
| **Management** | 0xD | Management |

> **Why the line falls exactly at 0x8**: messageType is only 4 bits wide, and the standard says, "The most significant bit of the messageType field divides this field in half between PTP event and general messages." Values with the top bit clear (0x0–0x7) are event messages; values with it set (0x8–0xF) are general messages. **0x4–0x7 and 0xE–0xF are reserved.** This event/general split decides more than whether a timestamp is needed. It also decides whether messageTypeSpecific can be used at all.

## The common message header: every message's envelope

### The common header layout (34 bytes)

Every PTP message starts with a **34-byte common message header**.

> **A note on offsets in this chapter**: From here on, "**common header**" means those 34 bytes. Every table's **Offset is a zero-based byte index**, the same convention as the Offset column in the standard's tables (no more cumulative-byte arithmetic). The common header covers offset 0–33, so the first body field after it always starts at offset 34.

| Field | Bytes | Offset | Meaning |
|:---|:---|:---|:---|
| majorSdoId + messageType | 1 | 0 | Top 4 bits: high bits of sdoId; low 4 bits: message type |
| minorVersionPTP + versionPTP | 1 | 1 | Top 4 bits: minor version; low 4 bits: major version |
| messageLength | 2 | 2 | Length of the whole message in bytes |
| domainNumber | 1 | 4 | Domain number |
| minorSdoId | 1 | 5 | Low bits of sdoId |
| flagField | 2 | 6 | Flags |
| correctionField | 8 | 8 | Correction value |
| messageTypeSpecific | 4 | 16 | Message-type-specific field: **reserved for general messages**; **event messages may use it for internal implementation**, but it must be all zeros on the wire (see below) |
| sourcePortIdentity | 10 | 20 | Identity of the sending port |
| sequenceId | 2 | 30 | Sequence number |
| controlField | 1 | 32 | Control field (obsolete) |
| logMessageInterval | 1 | 33 | Message interval |


### Key fields in detail

#### messageType

The **low 4 bits** identify the message type. The ten values are in the two tables above, under event messages and general messages.

**Top 4 bits (majorSdoId)**:

Used for domain isolation (see 2.3).

#### domainNumber + sdoId

**domainNumber** (1 byte) + **majorSdoId** (top 4 bits) + **minorSdoId** (1 byte) = the complete domain identifier.

#### flagField

A 16-bit flag field (offset 6–7, two bytes, 16 bits total). **Pay attention to the "Applies to" column**: most bits appear only in specific messages. Reading them in any other message means nothing.

| Byte | Bit | Name | Applies to | Meaning |
|:---|:---|:---|:---|:---|
| 0 | 0 | alternateMasterFlag | **Announce, Sync, Follow_Up, Delay_Resp only** | **FALSE while the sending port is in MASTER state** |
| 0 | 1 | twoStepFlag | **Sync, Pdelay_Resp only** | TRUE when the Sync has an associated Follow_Up (or the Pdelay_Resp an associated Pdelay_Resp_Follow_Up), otherwise FALSE |
| 0 | 2 | unicastFlag | ALL (all ten message types) | TRUE if the transport address is unicast, FALSE if multicast |
| 0 | 3, 4 | — (unassigned) | — | **Reserved**: unassigned flagField bits are always reserved |
| 0 | 5-6 | profileSpecific1/2 | ALL | Defined by the applicable PTP profile, otherwise FALSE |
| 0 | 7 | — (unassigned) | — | **Reserved** |
| 1 | 0 | leap61 | **Announce only** | Taken from timePropertiesDS.leap61: the last minute of the day (the current UTC day) is 61 seconds long |
| 1 | 1 | leap59 | **Announce only** | Taken from timePropertiesDS.leap59: the last minute of the day is 59 seconds long |
| 1 | 2 | currentUtcOffsetValid | **Announce only** | Taken from timePropertiesDS.currentUtcOffsetValid: the UTC offset is valid |
| 1 | 3 | ptpTimescale | **Announce only** | Taken from timePropertiesDS.ptpTimescale: TRUE means the PTP timescale |
| 1 | 4 | timeTraceable | **Announce only** | Taken from timePropertiesDS.timeTraceable: time is traceable |
| 1 | 5 | frequencyTraceable | **Announce only** | Taken from timePropertiesDS.frequencyTraceable: frequency is traceable |
| 1 | 6 | synchronizationUncertain (**optional flag**) | **Announce only** | This is an **optional** flag: if you implement the option, its value is currentDS.synchronizationUncertain |
| 1 | 7 | — (unassigned) | — | **Reserved** |

#### correctionField

An **8-byte signed integer**, the correction applied to the message.

**Unit**: `2⁻¹⁶` nanoseconds, that is, `1/65536` ns ≈ 0.01526 picoseconds.

**Conversion**:
- **correctionField → seconds**: `seconds = correctionField / (65536 × 10⁹)`
- **Nanoseconds part**: `nanoseconds = correctionField / 65536`

**Example**:

```text
correctionField = 0x0000000000028000 (decimal: 163840)
value = 163840 / 65536 = 2.5 nanoseconds
```

**Uses**:
- Carries the fractional-nanosecond part
- Transparent clocks accumulate residence time
- Path asymmetry correction

#### sourcePortIdentity

**10 bytes**:
- First 8 bytes: clockIdentity
- Last 2 bytes: portNumber

**Example**:

```text
clockIdentity = 00-1B-19-00-00-00-00-01
portNumber = 0x0001

sourcePortIdentity = 00-1B-19-00-00-00-00-01-00-01
```

#### sequenceId

**2 bytes**, the sequence number of the message.

**Uses**:
- Links Sync and Follow_Up
- Links Delay_Req and Delay_Resp
- Detects packet loss

## Each message type in detail

### Sync

**Format** (total **34+10 = 44 bytes**):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| originTimestamp | 10 | 34 |

**originTimestamp (10 bytes)**:

- 6 bytes: seconds (whole seconds)
- 4 bytes: nanoseconds

**One-step mode**:

Sync's originTimestamp carries the whole-seconds part of the send time. correctionField carries the fractional nanoseconds.

**Two-step mode**:

Sync's originTimestamp is 0 or an estimate. Follow_Up carries the precise timestamp.

---

### Follow_Up

**Format** (total **34+10 = 44 bytes**):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| preciseOriginTimestamp | 10 | 34 |

**preciseOriginTimestamp (10 bytes)**:

The precise send timestamp of the Sync.

**Association rule**:

The Follow_Up's sequenceId must match that of the corresponding Sync.

---

### Delay_Req

**Format** (total **34+10 = 44 bytes**):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| originTimestamp | 10 | 34 |

**originTimestamp**:

The standard says to set it to 0, or to an egress time estimate no worse than ±1 s (because the slave doesn't know its own exact time when it sends).

---

### Delay_Resp

**Format** (total **34+10+10 = 54 bytes**):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| receiveTimestamp | 10 | 34 |
| requestingPortIdentity | 10 | 44 |

**receiveTimestamp (10 bytes)**:

When the master clock received the Delay_Req.

**requestingPortIdentity (10 bytes)**:

The identity of the port that sent the Delay_Req (used for matching).

**Example**:

The slave sends a Delay_Req (sequenceId = 100).
The master receives it at 1000.000001000 seconds.
The master sends a Delay_Resp:
- receiveTimestamp = 1000.000001000 s
- requestingPortIdentity = the slave's portIdentity
- sequenceId = 100

---

### Pdelay_Req

**Format** (total **34+10+10 = 54 bytes**):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| originTimestamp | 10 | 34 |
| reserved | 10 | 44 |

**The reserved field**:

A 10-byte reserved field that makes the message the same length as Pdelay_Resp. The standard's reason:

> "The reserved field in the Pdelay_Req message is to make the PTP message length match the length of the Pdelay_Resp message. **In some networks and bridges, PTP messages with unequal lengths have different transit times that introduce asymmetry errors.**"

That is: **messages of unequal length have different transit times in networks and bridges**, which introduces asymmetry error. So the standard would rather waste 10 bytes than let Pdelay_Req and Pdelay_Resp differ in length.

**Purpose**:

In P2P it measures the link delay between two ports.

---

### Pdelay_Resp

**Format** (total **34+10+10 = 54 bytes**):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| requestReceiptTimestamp | 10 | 34 |
| requestingPortIdentity | 10 | 44 |

**requestReceiptTimestamp**:

When the responder received the Pdelay_Req (t2). But under the standard's other two fill options, this field is 0 and the turnaround time moves to correctionField.

**One-step mode**:

The Pdelay_Resp correctionField accumulates the turnaround time (t3 - t2), the responder's response delay.

**Two-step mode**:

The standard gives two fill options: **Option B** — Pdelay_Resp carries t2 and Pdelay_Resp_Follow_Up carries t3; **Option A** — both timestamps are 0, and the turnaround time goes into the Pdelay_Resp_Follow_Up correctionField.

---

### Pdelay_Resp_Follow_Up

**Format** (total **34+10+10 = 54 bytes**):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| responseOriginTimestamp | 10 | 34 |
| requestingPortIdentity | 10 | 44 |

**responseOriginTimestamp**:

When the responder sent the Pdelay_Resp (t3). Under Option A it is 0, and t3−t2 moves into correctionField.

---

### Announce

**Format** (total **64 bytes**):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| originTimestamp | 10 | 34 |
| currentUtcOffset | 2 | 44 |
| reserved | 1 | 46 |
| grandmasterPriority1 | 1 | 47 |
| grandmasterClockQuality | 4 | 48 |
| grandmasterPriority2 | 1 | 52 |
| grandmasterIdentity | 8 | 53 |
| stepsRemoved | 2 | 61 |
| timeSource | 1 | 63 |

**grandmasterClockQuality (4 bytes)**:

| Subfield | Bytes | Meaning |
|:---|:---|:---|
| clockClass | 1 | Clock class |
| clockAccuracy | 1 | Clock accuracy |
| offsetScaledLogVariance | 2 | Variance (log scale) |

**stepsRemoved**:

The number of PTP communication paths traversed between this instance and the Grandmaster (a slave clock directly connected to the Grandmaster sees 1).

**timeSource**:

The Grandmaster's time source type (GNSS, atomic clock, and so on).

**Purpose**:

- The master clock broadcasts its own information
- Feeds BMCA decisions
- Propagates time properties (UTC offset, leap seconds, and so on)

---

### Signaling

**Format** (fixed part **34+10 = 44 bytes**, followed by a variable-length TLV sequence):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| targetPortIdentity | 10 | 34 |
| Suffix (TLV sequence) | Variable | 44 onwards |

**Purpose**:

- Unicast negotiation
- Path trace
- Other signaling functions

**Suffix**:

One or more TLV (Type-Length-Value) entities.

---

### Management

**Format** (fixed part **34+10+1+1+1+1 = 48 bytes**, followed by the managementTLV):

| Field | Bytes | Offset |
|:---|:---|:---|
| Common header | 34 | 0 |
| targetPortIdentity | 10 | 34 |
| startingBoundaryHops | 1 | 44 |
| boundaryHops | 1 | 45 |
| reserved \| actionField | 1 | 46 |
| reserved | 1 | 47 |
| managementTLV | Variable (M) | 48 onwards |

**actionField values** (**5–F are reserved**):

- 0: GET (read)
- 1: SET (write)
- 2: RESPONSE (response)
- 3: COMMAND (command)
- 4: ACKNOWLEDGE (acknowledgement)

**Purpose**:

- Configure PTP devices
- Query status
- Fault diagnosis

---

## Message lengths at a glance

| Message | Base length (bytes) | Notes |
|:---|:---|:---|
| Sync | 44 | Can add TLVs |
| Delay_Req | 44 | Can add TLVs |
| Follow_Up | 44 | Can add TLVs |
| Delay_Resp | 54 | Can add TLVs |
| Pdelay_Req | 54 | Includes 10 reserved bytes |
| Pdelay_Resp | 54 | Can add TLVs |
| Pdelay_Resp_Follow_Up | 54 | Can add TLVs |
| Announce | 64 | Can add TLVs; includes 1 reserved byte |
| Signaling | 44+ | Header + TLV sequence |
| Management | 48+ | Header + management TLV |

## One complete message, byte by byte

### Sync (one-step)

**Hex layout** (the left column is the starting offset of each row, so you can compare byte by byte):

```text
Offset  Hex                          // Comment
00      00 12 00 2C                  // majorSdoId=0, messageType=0x0(Sync), minorVersionPTP=1, versionPTP=2, messageLength=0x002C=44
04      00 00 00 00                  // domainNumber=0, minorSdoId=0, flagField=0
08      00 00 00 00 00 00 00 00      // correctionField=0
16      00 00 00 00                  // messageTypeSpecific: for event messages it "may be used for internal implementation", but on the wire it must be all zeros
20      00 1B 19 00 00 00 00 01 00 01 // sourcePortIdentity
30      00 64                        // sequenceId=100
32      00                           // controlField=0
33      00                           // logMessageInterval=0 ⟹ multicast Sync interval 2⁰ = 1 s; for unicast Sync this byte must be 0x7F
34      00 00 00 00 03 E8            // originTimestamp seconds = 1000 (UInteger48, 6 bytes: 0x3E8=1000)
40      00 00 00 00                  // originTimestamp nanoseconds = 0 (UInteger32, 4 bytes)
```

**Reading it**:

- Message type: Sync (one-step: originTimestamp carries the send time directly; correctionField can carry fractional nanoseconds)
- PTP version: 2.1 (versionPTP=2, minorVersionPTP=1)
- Domain: 0
- Sending port: clockIdentity=00-1B-19-00-00-00-00-01, portNumber=1
- Sequence number: 100
- Send time: 1000.000000000 seconds

---

### Announce

**Hex layout (the complete 64 bytes)**:

```text
Offset  Hex                          // Comment
--- Common message header (34 bytes, offset 0-33) ---
00      0B 12 00 40                  // majorSdoId=0, messageType=0xB(Announce), minorVersionPTP=1, versionPTP=2, messageLength=0x0040=64
04      00 00 00 00                  // domainNumber=0, minorSdoId=0, flagField=0
08      00 00 00 00 00 00 00 00      // correctionField=0
16      00 00 00 00                  // messageTypeSpecific: Announce is a general message, so this field is reserved
20      00 1B 19 00 00 00 00 01 00 01 // sourcePortIdentity: clockIdentity(8) + portNumber=1(2)
30      00 64                        // sequenceId=100
32      00                           // controlField=0 (obsolete, sent as all zeros)
33      00                           // logMessageInterval=0 ⟹ multicast Announce interval 2⁰=1 s (unicast should be 0x7F)
--- Announce body (30 bytes, offset 34-63) ---
34      00 00 00 00 00 00            // originTimestamp seconds=0 (UInteger48, 6 bytes)
40      00 00 00 00                  // originTimestamp nanoseconds=0 (UInteger32, 4 bytes)
44      00 25                        // currentUtcOffset = 0x0025 = 37 s
46      00                           // reserved (1 byte)
47      0A                           // grandmasterPriority1 = 10
48      06 20 00 00                  // grandmasterClockQuality: clockClass=6, clockAccuracy=0x20(=25 ns), offsetScaledLogVariance=0
52      0A                           // grandmasterPriority2 = 10
53      00 1B 19 00 00 00 00 01      // grandmasterIdentity (8 bytes)
61      00 00                        // stepsRemoved = 0
63      20                           // timeSource = 0x20 = GNSS
```

**Reading it**:

- Message type: Announce
- Message length: 64 bytes (you can append TLVs, but messageLength must then change too)
- Sending port: clockIdentity=00-1B-19-00-00-00-00-01, portNumber=1
- Grandmaster information:
  - priority1=10, priority2=10
  - clockClass=6, clockAccuracy=0x20
  - timeSource=0x20=GNSS
- stepsRemoved=0 (the sender is the Grandmaster itself)

## Summary: the essentials of PTP messages

**Message classes**:
- Event messages: need timestamps (Sync, Delay_Req, Pdelay_Req, Pdelay_Resp)
- General messages: no timestamps (Follow_Up, Delay_Resp, Pdelay_Resp_Follow_Up, Announce, Signaling, Management)

**Common header**:
- 34 bytes
- Holds the message type, domain identifier, correctionField, sending port, and more

**Key messages**:
- Sync: time synchronization
- Announce: master clock announcement
- Delay_Req/Resp: E2E delay measurement
- Pdelay series: P2P delay measurement

**How messages link**:
- sequenceId ties related messages together
- sourcePortIdentity identifies the sender

**Length essentials**:
- Sync / Follow_Up / Delay_Req: **44 bytes** (34-byte common header + one 10-byte Timestamp)
- Delay_Resp and the three Pdelay messages (Pdelay_Req / Pdelay_Resp / Pdelay_Resp_Follow_Up): **54 bytes** (one extra 10-byte field: requestingPortIdentity; in Pdelay_Req those 10 bytes are reserved, so it matches the length of Pdelay_Resp)
- Announce: **64 bytes** (34-byte common header + 30-byte body)
- **Signaling: 44 bytes and up, always followed by a TLV sequence**; **Management: 48 bytes and up, always followed by one management TLV**. Neither has a "fixed total length"; the final length depends on the TLVs.
