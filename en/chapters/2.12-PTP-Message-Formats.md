# 2.12 The Ten Languages of PTP: A Full Look at Message Formats

## Message classification

PTP has ten message types, divided into two classes:

Event messages (require timestamps):
- Sync (0x0)
- Delay_Req (0x1)
- Pdelay_Req (0x2)
- Pdelay_Resp (0x3)

General messages (no timestamps):
- Follow_Up (0x8)
- Delay_Resp (0x9)
- Pdelay_Resp_Follow_Up (0xA)
- Announce (0xB)
- Signaling (0xC)
- Management (0xD)

The nibble `0x0-0x3` vs `0x8-0xD` distinction is exactly what a raw-socket BPF filter uses to separate event from general messages.

## The common header (34 bytes)

Every PTP message begins with the 34-byte common header:

| Offset | Field | Size |
|:--:|:--|:--:|
| 0 | majorSdoId (high nibble) + messageType (low nibble) | 1 |
| 1 | minorVersionPTP (high nibble) + versionPTP (low nibble) | 1 |
| 2 | messageLength | 2 |
| 4 | domainNumber | 1 |
| 5 | minorSdoId | 1 |
| 6 | flagField | 2 |
| 8 | correctionField | 8 |
| 16 | reserved (messageTypeSpecific) | 4 |
| 20 | sourcePortIdentity | 10 |
| 30 | sequenceId | 2 |
| 32 | controlField | 1 |
| 33 | logMessageInterval | 1 |

### Notes on key fields

- Octet 0: high nibble = majorSdoId, low nibble = messageType (e.g., `0x0B` for Announce with sdoId 0).
- Octet 1: minorVersionPTP in the high nibble, versionPTP in the low nibble. For a PTP 2.1 implementation (IEEE 1588-2019): minor=1, version=2, so the byte is 0x12.
- flagField (16 bits, big-endian):
  - byte 0 bit 0: alternateMasterFlag
  - byte 0 bit 1: twoStepFlag (a Sync will be followed by a Follow_Up)
  - byte 0 bit 2: unicastFlag
  - byte 1 bit 0: leap61
  - byte 1 bit 1: leap59
  - byte 1 bit 2: currentUtcOffsetValid
  - byte 1 bit 3: ptpTimescale
  - byte 1 bit 4: timeTraceable
  - byte 1 bit 5: frequencyTraceable
  - byte 1 bit 6: synchronizationUncertain
- correctionField: an Integer64 in units of 2⁻¹⁶ ns. E.g., 2.5 ns = 0x0000000000028000.
- sourcePortIdentity: clockIdentity (8 bytes) + portNumber (2 bytes). Port 0 is invalid/uninitialized; 0xFFFF means "all ports."

## The message bodies

### Sync / Follow_Up (44 bytes total; body 10 bytes)

```
0  messageType + sdoId
...
34 originTimestamp (Sync) / preciseOriginTimestamp (Follow_Up)
   - 6 bytes UInteger48 seconds + 4 bytes UInteger32 nanoseconds
```

- Sync body: originTimestamp.
- Follow_Up body: preciseOriginTimestamp.

### Delay_Req (44 bytes; body 10 bytes)

```
34 originTimestamp  (10 bytes)
```

### Delay_Resp (54 bytes; body 20 bytes)

```
34 receiveTimestamp           (10 bytes)
44 requestingPortIdentity     (10 bytes)
```

### Pdelay_Req (54 bytes; body 20 bytes)

```
34 originTimestamp  (10 bytes)
44 reserved         (10 bytes)
```

### Pdelay_Resp (54 bytes; body 20 bytes)

```
34 requestReceiptTimestamp    (10 bytes)
44 requestingPortIdentity     (10 bytes)
```

### Pdelay_Resp_Follow_Up (54 bytes; body 20 bytes)

```
34 responseOriginTimestamp    (10 bytes)
44 requestingPortIdentity     (10 bytes)
```

### Announce (64 bytes; body 30 bytes)

```
34 originTimestamp                 (10 bytes)
44 currentUtcOffset                (2 bytes)
46 reserved                         (1 byte)
47 grandmasterPriority1             (1 byte)
48 grandmasterClockQuality
      clockClass                    (1 byte)
      clockAccuracy                 (1 byte)
      offsetScaledLogVariance       (2 bytes)
52 grandmasterPriority2             (1 byte)
53 grandmasterIdentity              (8 bytes)
61 stepsRemoved                     (2 bytes)
63 timeSource                       (1 byte)
```

### Signaling (variant; body 10 bytes + TLVs)

```
34 targetPortIdentity  (10 bytes)
44 TLVs                (variable)
```

### Management (48 bytes + TLVs)

```
34 targetPortIdentity       (10 bytes)
44 startingBoundaryHops      (1 byte)
45 boundaryHops              (1 byte)
46 reserved | actionField    (1 byte)
47 reserved                  (1 byte)
48 management TLVs           (variable)
```

The actionField values: GET=0, SET=1, RESPONSE=2, COMMAND=3, ACKNOWLEDGE=4.

## A worked Sync example (one-step, one byte at a time)

Assume: sdoId 0, PTP 2.1, domain 0, no flags, correctionField 0, source clock 00-1B-19-00-00-00-00-01, sequenceId 100, originTimestamp = 1000 s + 0 ns.

```
00 12 00 2C    majorSdoId=0, messageType=0x0 (Sync), minorVersionPTP=1, versionPTP=2, length=44
00 00 00 00    domainNumber=0, minorSdoId=0, flagField=0
00 00 00 00 00 00 00 00    correctionField=0
00 00 00 00    reserved (messageTypeSpecific)
00 1B 19 00 00 00 00 01 00 01    sourcePortIdentity
00 64          sequenceId=100
00             controlField=0
00             logMessageInterval=0
00 00 00 00 03 E8    originTimestamp seconds=1000 (UInteger48)
00 00 00 00          originTimestamp nanoseconds=0
```

For an Announce, change octet 0 to `0x0B`, length to 64 (`00 40`), and append the 30-byte Announce body (currentUtcOffset, priority fields, identity, stepsRemoved, timeSource, see the direct Announce layout above).

## Byte order

All multi-byte fields are network byte order (big-endian). On little-endian hosts, every 16/32/48/64-bit field is byte-swapped on receipt and before transmission. Getting the byte order wrong is one of the most common implementation bugs.

## Summary

- Ten message types, two classes: event (0x0-0x3) and general (0x8-0xD).
- A 34-byte common header carries type, version, length, domain, flags, correction, IDs, sequence, control, and interval fields.
- Five message bodies repeat a pattern of timestamps and identity fields.
- Get the offsets right; get the byte order right; the rest is arithmetic.

Message formats give us the containers. But PTP is extensible, a Sync or an Announce can carry extra information in TLVs (Type-Length-Value).

TLV is where the protocol's extensibility lives: management payloads, unicast negotiation, path trace, cumulative rate ratio, PAD, authentication...

Understanding TLVs is essential before we look at management, unicast, and security.
