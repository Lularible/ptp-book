# 2.13 PTP's All-Purpose Plug-in: The TLV Extension Mechanism in Depth

## What is a TLV?

TLV (Type-Length-Value) is a generic data-encoding format:

```
┌─────────┬──────────┬───────────────────┐
│ Type    │ Length   │ Value             │
│ 2 bytes │ 2 bytes  │ Variable          │
└─────────┴──────────┴───────────────────┘

Type   : which TLV this is
Length : the number of bytes in Value (excluding Type and Length)
Value  : the actual data
```

Advantages:
- Extensible: new types don't break old implementations.
- Flexible: variable-length data.
- Easy to parse: dispatch on Type.

### Where PTP uses TLVs

- Management messages: GET/SET operations, reading/writing data sets.
- Signaling messages: unicast negotiation, event subscriptions.
- Extension TLVs: organization extensions, profile extensions.
- Optional TLVs: path trace, alternate time offset.

## TLV type ranges

IEEE 1588 allocates the 16-bit tlvType space:

| Range | Purpose |
|:---|:---|
| 0x0000-0x1FFF | Standard TLVs (mostly non-propagating) |
| 0x2000-0x3FFF | 1588-2008 security TLVs (AUTHENTICATION_2008 etc.) |
| 0x4000-0x7FFF | Propagating TLVs (organization extensions, etc.) |
| 0x8000-0xFFEF | Non-propagating / profile-specific TLVs |
| 0x7F00-0x7FFF | Experimental (propagating) |

Some TLVs outside 0x4000-0x7FFF are individually marked "Propagate", notably PATH_TRACE (0x0008) and ALTERNATE_TIME_OFFSET_INDICATOR (0x0009). Per 14.2.2.2, an unsupported propagating TLV received in an Announce shall be propagated by a boundary clock within at most three announceIntervals, preserving order.

### Key TLV values (Table 52)

| Value | TLV | Propagates? |
|:---|:---|:---|
| 0x0001 | MANAGEMENT | no |
| 0x0002 | MANAGEMENT_ERROR_STATUS | no |
| 0x0003 | ORGANIZATION_EXTENSION (deprecated) | legacy |
| 0x0004-0x0007 | REQUEST / GRANT / CANCEL / ACK (unicast) | no |
| 0x0008 | PATH_TRACE | **yes** |
| 0x0009 | ALTERNATE_TIME_OFFSET_INDICATOR | **yes** |
| 0x2000-0x2003 | 2008 security TLVs (AUTHENTICATION_2008 etc.) | no |
| 0x4000 | ORGANIZATION_EXTENSION_PROPAGATE | yes |
| 0x4001 | ENHANCED_ACCURACY_METRICS | yes |
| 0x8000 | ORGANIZATION_EXTENSION_DO_NOT_PROPAGATE | no |
| 0x8001 | L1_SYNC | no |
| 0x8002 | PORT_COMMUNICATION_AVAILABILITY | no |
| 0x8003 | PROTOCOL_ADDRESS | no |
| 0x8004-0x8006 | SLAVE_RX_SYNC_TIMING_DATA / SLAVE_RX_SYNC_COMPUTED_DATA / SLAVE_TX_EVENT_TIMESTAMPS | no |
| 0x8007 | CUMULATIVE_RATE_RATIO | no |
| 0x8008 | PAD | no |
| 0x8009 | AUTHENTICATION (2019) | no |

2019 vs 2008: L1_SYNC, CUMULATIVE_RATE_RATIO, PAD, PATH_TRACE and ALTERNATE_TIME_OFFSET all existed in 1588-2008. The genuinely new TLVs in 1588-2019 are ENHANCED_ACCURACY_METRICS (0x4001) and AUTHENTICATION (0x8009), the latter replacing the 0x2000-0x2003 security series.

## The organization extension TLV

```c
struct organization_tlv {
    Enumeration16 type;    /* TLV type */
    UInteger16    length;
    Octet         id[3];   /* organization ID (OUI) */
    Octet         subtype[3]; /* organization subtype */
    /* data follows */
};
```

The first three bytes are an IEEE-registered OUI; the next three identify a vendor-defined extension:

```c
#define IEEE_802_1_COMMITTEE  0x00, 0x80, 0xC2   /* 802.1 (AVB/TSN) */
#define IEEE_C37_238_PROFILE  0x1C, 0x12, 0x9D   /* power profile */
#define ITU_T_COMMITTEE       0x00, 0x19, 0xA7   /* ITU-T */
```

Worked example (type 0x4000, 20 data bytes: OUI + subtype + version + metricType + metricValue + 8-byte timestamp):

```
40 00 14 00 00 XX YY 00 00 01 01 01 00 00 01 00 00 00 00 00 00 00 01

40 00         tlvType = 0x4000
00 14         lengthField = 20
00 XX YY      organizationId
00 00 01      organizationSubType
01            version
01            metricType (offset)
00 00 01 00   metricValue = 256 ns
00 00 00 00 00 00 00 01   timestamp (8 bytes)
```

(Getting the lengthField to match the body byte-for-byte is the part most examples get wrong.)

## PATH_TRACE

When a boundary clock forwards an Announce carrying a PATH_TRACE TLV, it appends its own clockIdentity. The receiver can therefore reconstruct the exact path taken.

```c
struct path_trace_tlv {
    Enumeration16 type;    /* 0x0008 */
    UInteger16    length;
    struct ClockIdentity cid[0];  /* the path */
};
```

Example: three hops, 8 bytes each, length = 24 (0x0018):

```
08 00 18 00 00 1B 19 FF FE 00 00 01 00 1B 19 FF FE 00 00 02 00 1B 19 FF FE 00 00 03
```

If a clock finds its own identity already in the list, a loop has formed and the Announce is dropped.

## CUMULATIVE_RATE_RATIO

Carries the cumulative rate ratio relative to the grandmaster:

```
scaledCumulativeRateRatio = (rateRatio − 1) × 2^41
```

where rateRatio = grandmaster frequency / local frequency.

Example: rateRatio = 1.000001:

```
scaledCumulativeRateRatio = 0.000001 × 2^41 = 2199023 = 0x00218DEF
```

## ALTERNATE_TIME_OFFSET_INDICATOR

Lets a grandmaster advertise alternate time offsets (e.g., a local time scale) alongside PTP time.

Fields: currentOffset (Integer32), jumpSeconds (Integer32), timeOfNextJump (UInteger48 + nibbles), displayName (PTPText).

Because PTP time is TAI, Beijing time = PTP − 37 + 8 = PTP − 29 seconds:

```
keyField        : as advertised
currentOffset   : −29 (Beijing = TAI − 37 + 8)
displayName     : "BEIJING"

local time = PTP time + currentOffset
```

## PAD

Pads a message to a required length:

```
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes)     = 0x8008                     │
│ lengthField (2 bytes) = N                          │
│ pad (N bytes)         = all 0x00                   │
└────────────────────────────────────────────────────┘
```

Example: a profile requires the Sync to be at least 64 bytes. The Sync base is 44 bytes, so 20 bytes are needed; a PAD with lengthField 16 adds 4 + 16 = 20 bytes → 44 + 20 = 64.

## AUTHENTICATION

The 2019 security TLV (detailed in section 2.16):

```
┌────────────────────────────────────────────────────┐
│ tlvType (2) = 0x8009                               │
│ lengthField (2) = 6 + D + S + R + K                │
│ SPP (1)                                            │
│ secParamIndicator (1)                              │
│ keyID (4)                                          │
│ [disclosedKey (D)] [sequenceNo (S)] [RES (R)]      │
│ ICV (K)                                            │
└────────────────────────────────────────────────────┘
```

The secParamIndicator bits (Table 132):

```
bit 0 : RP — RES present
bit 1 : SP — sequenceNo present
bit 2 : DP — disclosedKey present
bit 3-7: reserved
```

So `0x01` means RES present, `0x02` sequenceNo, `0x04` disclosedKey.

For HMAC-SHA256-128 (K=16), the minimum TLV size is 4 + 6 + 16 = 26 bytes.

## Summary

- TLV = Type-Length-Value; PTP uses it in management, signaling, and optional extensions.
- The tlvType space is carved into propagating (0x4000-0x7FFF), non-propagating, and legacy-security ranges.
- PATH_TRACE, ALTERNATE_TIME_OFFSET, CUMULATIVE_RATE_RATIO, PAD, organization extensions and authentication are the major players.
- Watch the lengthField: it must exactly equal the number of bytes in the Value.

TLVs are the payload of the management message. The management protocol then defines who asks, who answers, and how devices get configured and monitored.

GET, SET, RESPONSE, ACKNOWLEDGE, the management message is PTP's remote-control channel.
