# 2.13 PTP's Universal Plug-in: The TLV Extension Mechanism in Depth

## A protocol's "evolution code"

IEEE 1588 moved from the 2008 edition to the 2019 edition.

The core architecture barely changed: the BMCA algorithm, the delay measurement mechanisms, the state machines. Those foundations stayed stable.

But the protocol's capabilities grew sharply:
- New security mechanisms
- New high-accuracy options
- New unicast negotiation enhancements
- New path-tracing improvements

**What's the secret?**

The answer: **the TLV extension mechanism**.

TLV (Type-Length-Value) is PTP's plug-in system. It adds new features without changing the base message format.

Just as browser plug-ins multiply what a browser can do, TLVs keep PTP evolving.

---

## From browser plug-ins to PTP extensions

### The design philosophy of browser plug-ins

A browser does only the core job: render web pages.

The plug-in system lets it extend without limit:
- An ad blocker → adds filtering
- A translation plug-in → adds translation
- Developer tools → add debugging

**The essence:**
- The browser doesn't know what a plug-in will do.
- The browser only provides a way to load plug-ins.
- Plug-ins are built independently and don't touch the browser core.

### The design philosophy of PTP TLVs

A PTP message does only the core job: carry timestamps and master-clock information.

TLVs let PTP messages extend without limit:
- PATH_TRACE TLV → adds loop detection
- AUTHENTICATION TLV → adds security authentication
- L1_SYNC TLV → adds high-accuracy synchronization

**The essence:**
- The PTP core doesn't know what a TLV will do.
- PTP only provides a way to carry TLVs.
- TLVs are designed independently and don't touch the core message format.

### The core value of TLVs

**Value one: backward compatibility**

```text
A 2008-edition PTP device receives a 2019-edition PTP message:
- Message header: fully compatible
- Message body: fully compatible
- New TLV: skipped (not understood), does not affect core functions

Result: the 2008 device keeps working (though it doesn't use the new features)
```

**Value two: progressive enhancement**

```text
Network upgrade:
Phase 1: all devices on the 2008 edition, no TLV extensions
Phase 2: some devices upgrade to 2019 and start using new TLVs
Phase 3: all devices upgraded, all features active

The whole process is a smooth transition, no one-shot upgrade needed
```

**Value three: customization**

```text
Different industry needs:
Telecom: unicast negotiation TLV + security TLV
Power: high-accuracy TLV + timestamp correction TLV
Industrial automation: path trace TLV

Each industry picks the TLVs it needs and doesn't have to load them all
```

## The basic structure of a TLV

### The three-part format

The name TLV comes from its three-part structure:

```text
┌──────────────────┬──────────────────────┬────────────────────┐
│  Type (2 bytes)  │   Length (2 bytes)   │   Value (N bytes)  │
└──────────────────┴──────────────────────┴────────────────────┘
```

**Type:**
- 2 bytes (16 bits)
- identifies the TLV's "identity"
- different types mean different functions

**Length:**
- 2 bytes (16 bits)
- the number of bytes in the Value field
- excludes Type and Length themselves

**Value:**
- N bytes (N = Length)
- the TLV's actual content
- the format is set by Type

### The length must be even

**Rule:** the total length of every TLV must be even.

```text
The standard has only one hard requirement for TLV length: an even number of bytes.
A TLV is part of the message, so it must follow this rule.

If the Value field itself is odd:
- Add 1 byte of padding.
- The Length field records the padded length.
```

**Example:**

```text
Suppose a TLV's Value needs 5 bytes:

Actual layout:
Type: 2 bytes
Length: 2 bytes
Value: 5 bytes + 1 byte padding = 6 bytes

Total length: 2 + 2 + 6 = 10 bytes (even)
Length field: 6 (total Value length, including padding)
```

### Where TLVs sit in a message

PTP message structure:

```text
PTP message as a whole:
┌────────────────────────────────────────────────────────┐
│ Message header (34 bytes)                              │
│ ────────────────────────────────────────────────────── │
│ Message body (message-type specific)                   │
│ ────────────────────────────────────────────────────── │
│ TLV 1                                                  │
│ ────────────────────────────────────────────────────── │
│ TLV 2                                                  │
│ ────────────────────────────────────────────────────── │
│ ...                                                    │
│ ────────────────────────────────────────────────────── │
│ TLV N                                                  │
└────────────────────────────────────────────────────────┘
```

**Key points:**
- TLVs are appended at the end of the message.
- One message can carry several TLVs.
- TLVs come in order and are parsed in order.

## How the tlvType space is allocated

### The "floor plan" of type values

The 16-bit tlvType space is roughly split into "floors." The picture is coarse: the real rule is a double test — the range, plus individual marks in the TLV type allocation table.

```text
tlvType floor plan:

Floor 0 (0x0000-0x3FFF): "do not propagate"
- mostly reserved
- the MANAGEMENT series
- the unicast negotiation series
- property: drop when unsupported, do not propagate (0x0008/0x0009 excepted)

Floor 1 (0x4000-0x7FFF): "propagate"
- PATH_TRACE (value is 0x0008, but marked propagate)
- ALTERNATE_TIME_OFFSET_INDICATOR (same)
- ORGANIZATION_EXTENSION_PROPAGATE
- ENHANCED_ACCURACY_METRICS
- property: must propagate when unsupported

Floor 2 (0x8000-0xFFEF): "do not propagate"
- ORGANIZATION_EXTENSION_DO_NOT_PROPAGATE
- L1_SYNC
- AUTHENTICATION
- PAD
- property: drop when unsupported, do not propagate
```

### What the propagation attribute means

**Why must some TLVs propagate?**

```text
Scenario: a boundary clock does not support a TLV

If the TLV is marked "Propagate":
The boundary clock does not understand the TLV's content,
but it must forward the TLV to its other ports
so downstream devices that support it receive it.

If the TLV is marked "Do Not Propagate":
The boundary clock does not understand the TLV's content.
It drops the TLV and does not forward it.
Downstream devices never see it.
```

**In practice:**

```text
PATH_TRACE TLV (marked propagate):
The master clock sends Announce + PATH_TRACE.
Boundary clock A supports PATH_TRACE → processes and forwards it.
Boundary clock B does not support PATH_TRACE → passes it through (no parsing, just forwarding).
The slave clock supports PATH_TRACE → receives and processes it.

Result: even with an unsupported boundary clock in the middle, PATH_TRACE still reaches the slave clock.
```

## Core TLVs in detail

### PATH_TRACE TLV

**Purpose:** detect loops and record the path an Announce takes.

**Full format:**

```text
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x0008                         │
│ lengthField (2 bytes) = 8 × N                      │
│ pathSequence[0] (8 bytes) - 1st clockIdentity      │
│ pathSequence[1] (8 bytes) - 2nd clockIdentity      │
│ ...                                                │
│ pathSequence[N-1] (8 bytes) - Nth clockIdentity    │
└────────────────────────────────────────────────────┘
```

**Fields:**

- **tlvType**: fixed value 0x0008
- **lengthField**: 8 × N, where N is the number of clockIdentity entries
- **pathSequence**: an array of ClockIdentity, 8 bytes each

**Encoding example:**

```text
Suppose the Announce travels: master clock → boundary clock A → boundary clock B

clockIdentity:
master clock: 00-1B-19-FF-FE-00-00-01
A: 00-1B-19-FF-FE-00-00-02
B: 00-1B-19-FF-FE-00-00-03

PATH_TRACE TLV encoding:
tlvType: 0x0008
lengthField: 0x0018 (24 bytes = 3 × 8)
pathSequence[0]: 00-1B-19-FF-FE-00-00-01
pathSequence[1]: 00-1B-19-FF-FE-00-00-02
pathSequence[2]: 00-1B-19-FF-FE-00-00-03

Hex:
00 08 00 18 00 1B 19 FF FE 00 00 01 00 1B 19 FF FE 00 00 02 00 1B 19 FF FE 00 00 03
```

**Boundary-clock processing:**

```c
void process_announce_with_path_trace(AnnounceMessage *msg) {
    // Step 1: parse the PATH_TRACE TLV
    PathTraceTLV *pt = find_path_trace_tlv(msg);
    if (pt == NULL) {
        // No PATH_TRACE TLV; forward as is
        forward_announce(msg);
        return;
    }

    int n = pt->lengthField / 8;   // number of pathSequence entries

    // Step 2: check whether our clockIdentity is in the list
    for (int i = 0; i < n; i++) {
        if (pt->pathSequence[i] == my_clock_identity) {
            // Loop! Drop the message
            log("Loop detected, dropping Announce");
            return;
        }
    }

    // Step 3: append our clockIdentity to the end of pathSequence
    pt->pathSequence[n] = my_clock_identity;
    pt->lengthField += 8;          // N → N+1: lengthField goes from 8N to 8(N+1)

    // Step 4: forward the Announce
    forward_announce(msg);
}
```

### CUMULATIVE_RATE_RATIO TLV

**Purpose:** carry the cumulative rate ratio so a transparent clock can compensate for frequency offset.

**Full format:**

```text
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x8007                         │
│ lengthField (2 bytes) = 4                          │
│ scaledCumulativeRateRatio (4 bytes)                │
└────────────────────────────────────────────────────┘
```

**scaledCumulativeRateRatio encoding:**

```
Definition:
scaledCumulativeRateRatio = (rateRatio - 1) × 2^41

The granularity is 2^-41, so the signed 32-bit range is about ±9.766e-4.

Where: per-hop <neighborRateRatio> = responder Timestamping Clock frequency / requester Timestamping Clock frequency
<cumulativeRateRatio> = the GM starting value × the product of every hop's <neighborRateRatio>

Encoding example:
Suppose a hop's <cumulativeRateRatio> = 1.000001 (accumulated, the upstream is 1 ppm faster than the local clock)

Calculation:
<cumulativeRateRatio> − 1 = 0.000001
0.000001 × 2^41 = 2199023.255552
Truncate toward zero to a signed integer → 2199023 (not rounded to 2199023.26,
and not truncated toward negative infinity; for a positive number this is just floor)

Hex: 0x00218DEF
```

**What it's for:**

```text
Scenario: a transparent clock handles residence time

Classic transparent clock:
Residence time goes straight into correctionField.
Frequency differences are ignored.

With CUMULATIVE_RATE_RATIO:
The transparent clock knows the frequency difference between the master clock and its local clock.
It accounts for that difference when correcting residence time.

Effect: better frequency-synchronization accuracy.
```

### AUTHENTICATION TLV

**Purpose:** provide message authentication and integrity checking.

**Full format:**

```text
┌─────────────────────────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x8009                                              │
│ lengthField (2 bytes) = 6 + D + S + R + K                               │
│ SPP (1 byte) - security parameter pointer                               │
│ secParamIndicator (1 byte) - optional-field indicator                   │
│ keyID (4 bytes) - key identifier                                        │
│ [disclosedKey] (optional, D bytes) - key disclosed for delayed security │
│ [sequenceNo] (optional, S bytes) - sequence number                      │
│ [RES] (optional, R bytes) - reserved                                    │
│ ICV (K bytes, usually 16) - integrity check value                       │
└─────────────────────────────────────────────────────────────────────────┘
```

**secParamIndicator field:**

```text
bit 0: RP - RES field present
bit 1: SP - sequenceNo field present
bit 2: DP - disclosedKey field present
bit 3-7: reserved

Examples:
secParamIndicator = 0x00 → no optional fields
secParamIndicator = 0x01 → RES present
secParamIndicator = 0x02 → sequenceNo present
secParamIndicator = 0x04 → disclosedKey present
```

**Typical configuration (immediate security):**

```text
Configuration:
Algorithm: HMAC-SHA256-128
ICV length: 16 bytes

TLV layout:
tlvType: 0x8009
lengthField: 6 + 16 = 22
SPP: 0x01
secParamIndicator: 0x00
keyID: 0x00001001
ICV: 16 bytes

Total length: 4 + 22 = 26 bytes
```

### L1_SYNC TLV

**Purpose:** L1 synchronization performance enhancement for high-accuracy sync.

**Full format:**

```text
┌──────────────────────────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x8001                                               │
│ lengthField (2 bytes) = 2 (basic format)                                 │
│ bitField (1 byte, TLV offset 4)                                          │
│   - bit 0: TCR = txCoherentIsRequired                                    │
│   - bit 1: RCR = rxCoherentIsRequired                                    │
│   - bit 2: CR  = congruentIsRequired                                     │
│   - bit 3: OPE = optParamsEnabled                                        │
│   - bit 4-7: Reserved                                                    │
│ statusField (1 byte, TLV offset 5)                                       │
│   - bit 0: ITC = isTxCoherent (this end actually achieves tx coherence)  │
│   - bit 1: IRC = isRxCoherent (this end actually achieves rx coherence)  │
│   - bit 2: IC  = isCongruent (this end is actually congruent)            │
│   - bit 3-7: Reserved                                                    │
│ [extended parameters] (optional)                                         │
└──────────────────────────────────────────────────────────────────────────┘
```

**bitField encoding:**

```text
bit 0: TCR = txCoherentIsRequired
- 1: tx coherence required
- 0: not required

bit 1: RCR = rxCoherentIsRequired
- 1: rx coherence required
- 0: not required

bit 2: CR = congruentIsRequired
- 1: congruence required
- 0: not required

bit 3: OPE = optParamsEnabled
- 1: enable extended parameters (lengthField > 2)
- 0: basic format only

Examples (all basic format, lengthField = 2):
bitField = 0x03 → require tx coherence + rx coherence
bitField = 0x07 → require tx coherence + rx coherence + congruence
bitField = 0x07 and statusField = 0x07 → all three requirements met
bitField = 0x07 and statusField = 0x01 → only tx coherence met

Full 6-byte encoding:
80 01 00 02 07 07
```

### ENHANCED_ACCURACY_METRICS TLV

**Purpose:** propagate enhanced accuracy metrics so downstream devices know the estimated synchronization accuracy.

**Full format:**

```text
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x4001                         │
│ lengthField (2 bytes)                              │
│ enhancedAccuracyMetricsMember[]                    │
└────────────────────────────────────────────────────┘
```

**Property:** marked "propagate", so it passes through even when unsupported.

```text
Scenario:
The master clock sends Sync + ENHANCED_ACCURACY_METRICS.
The boundary clock does not support it → passes the TLV through.
The slave clock supports it → receives it and parses the accuracy metrics.

Effect: the slave clock can estimate synchronization accuracy.
```

### ALTERNATE_TIME_OFFSET_INDICATOR TLV

**Purpose:** distribute offset information for an alternate time scale (local time, UTC, and so on).

**Full format:**

```text
┌────────────────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x0009                   TLV offset 0      │
│ lengthField (2 bytes) = 15 + L + M           TLV offset 2      │
│ keyField (1 byte) - time scale identifier    TLV offset 4      │
│ currentOffset (4 bytes, Integer32) - seconds TLV offset 5      │
│ jumpSeconds (4 bytes, Integer32) - seconds   TLV offset 9      │
│ timeOfNextJump (6 bytes, UInteger48)         TLV offset 13     │
│ displayName (L bytes, PTPText)               TLV offset 19     │
│ pad (M bytes)                                TLV offset 19+L   │
└────────────────────────────────────────────────────────────────┘
```

**Use case:**

```text
Scenario: compute local time from PTP time

PTP time scale: TAI (atomic time)
Local time: UTC+8 (Beijing time)

ALTERNATE_TIME_OFFSET configuration:
keyField: 0x01 (identifies "Beijing time")
currentOffset: −29   ← unit is seconds (Integer32)
displayName: "BEIJING" (7 UTF-8 bytes)

Definition of currentOffset:
  currentOffset = (time measured in the alternate time scale) − (PTP Instance Time)
                = Beijing time − TAI
                = (TAI − 37 + 8) − TAI
                = −29 seconds
  The standard also warns that this sign convention is the opposite of currentUtcOffset.
  For an arbitrary time scale (ARB), currentOffset has no fixed meaning in the standard; it is implementation-specific.

The slave clock computes:
Beijing time = PTP time + currentOffset = TAI + (−29) = TAI − 29

lengthField, byte by byte:
  Fixed part                   = 15
  displayName L = 1 + 7        =  8   (PTPText length byte + "BEIJING")
  15 + 8 = 23 → odd, violates the standard's even-length rule for TLVs
  So pad M = 1                  =  1
  lengthField = 15 + 8 + 1      = 24 = 0x0018        ✓ even
  Whole TLV = 4 + 24             = 28 bytes
```

## The organization-extension TLV

### Why organization extensions?

Standard TLVs cover PTP's core functions, but a vendor or an industry may need custom features.

**An organization-extension TLV** lets a vendor or a standards organization define its own TLV.

### Organization-extension TLV format

```text
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes)                                  │
│   - 0x4000: ORG_EXT_PROPAGATE (propagating)        │
│   - 0x8000: ORG_EXT_NO_PROP (non-propagating)      │
│ lengthField (2 bytes) = 6 + N                      │
│ organizationId (3 bytes) - organization identifier │
│ organizationSubType (3 bytes) - subtype            │
│ dataField (N bytes) - organization-specific data   │
└────────────────────────────────────────────────────┘
```

**organizationId:**
- 3 bytes
- an OUI (Organizationally Unique Identifier) or CID (Company ID)
- assigned by the IEEE RA, globally unique

**organizationSubType:**
- 3 bytes
- a subtype defined inside the organization
- organizationId + organizationSubType together guarantee global uniqueness

### Design guidelines for organization extensions

**Step one: apply for an organizationId**

```
Apply to the IEEE RA for an OUI or CID.
Get a unique 3-byte identifier.

For example:
IEEE 1588's own OUI: 00-1B-19
```

**Step two: define organizationSubType**

```text
Free allocation inside the organization.
Suggestion: define a numbering scheme.

For example:
0x000001: vendor-defined performance monitoring
0x000002: vendor-defined fault diagnostics
0x000003: vendor-defined configuration extension
```

**Step three: choose the propagation attribute**

```text
Basis for the choice:
Needs to reach the whole network → use 0x4000 (ORG_EXT_PROPAGATE)
Local use only → use 0x8000 (ORG_EXT_NO_PROP)

For example:
Network-wide performance metrics → choose 0x4000
Local debugging information → choose 0x8000
```

**Step four: design dataField**

```text
dataField content is entirely up to you.
Suggestions:
- Keep the structure simple.
- Plan for backward compatibility (reserve fields).
- Document the format.

For example:
dataField format:
- version (1 byte)
- data type (1 byte)
- data content (N bytes)
```

### Organization-extension example

**Example: a vendor-defined performance-monitoring TLV**

```text
Vendor: some company, OUI = 00-XX-YY

TLV definition:
tlvType: 0x4000 (propagating)
organizationId: 00-XX-YY
organizationSubType: 0x000001 (performance monitoring)
dataField:
  - version (1 byte): 0x01
  - metricType (1 byte): 0x01 = offset, 0x02 = delay
  - metricValue (4 bytes): the actual value
  - timestamp (8 bytes): measurement time

Full encoding example (all 24 bytes, not one byte short):
40 00 00 14 00 XX YY 00 00 01 01 01 00 00 01 00 00 00 00 00 00 00 00 01

Parsing:
tlvType: 40 00 (0x4000)
lengthField: 00 14 (20 bytes)
organizationId: 00 XX YY
organizationSubType: 00 00 01
version: 01
metricType: 01 (offset)
metricValue: 00 00 01 00 (256 nanoseconds)
timestamp: 00 00 00 00 00 00 00 01   ← 8 bytes
```

## TLV propagation rules in detail

### A boundary clock's propagation duty

A boundary clock is a key node in a PTP network and has a special duty for TLV propagation.

**Rule one: TLVs on Announce**

```text
Scenario: a boundary clock receives an Announce carrying an unsupported TLV

Handling:
- TLV marked "Do Not Propagate" → drop it, do not propagate
- TLV marked "Propagate" → must propagate, even if unsupported

How:
- Pass it through (do not parse the content; append it to the outgoing Announce)
- Propagate within at most 3 announceIntervals
```

**Rule two: TLVs on non-Announce messages**

```text
Scenario: a boundary clock receives Sync/Delay_Req and so on, carrying an unsupported TLV

Handling:
- Every unsupported TLV → drop it, do not propagate
- Only "Propagate" TLVs on Announce are mandatory to propagate
```

**Rule three: supported TLVs**

```text
Scenario: a boundary clock supports a TLV

Handling:
- Process it according to the TLV's function
- It may modify, keep, or remove the TLV
- The specific function decides
```

### Propagation delay requirement

The standard sets a limit on propagation delay:

```text
Propagation delay for a "Propagate" TLV on Announce:
At most: 3 announceIntervals

For example:
announceInterval = 2 seconds
Maximum delay = 6 seconds

Why:
Announce goes out periodically (say every 2 seconds).
Waiting at most 3 send opportunities
keeps the TLV from getting "stuck" too long.
```

### Propagation order for multiple TLVs

```text
Scenario: a boundary clock receives several Announce + TLV pairs in a short time

Handling:
- Keep them in arrival order.
- Preserve that order when appending them to the outgoing Announce.

For example:
t=0: receive Announce + TLV_A
t=1: receive Announce + TLV_B
t=2: send outgoing Announce + TLV_A + TLV_B (in order)
```

## How a transparent clock handles TLVs

### Basic behavior

A transparent clock does not change a PTP message's content. It only changes correctionField.

But what about TLVs?

**The standard says:**

```text
A TLV counts as part of the PTP message.
A transparent clock normally does not modify TLVs.
If an optional feature requires it, it may remove a TLV.
```

### Handling different TLVs

**PATH_TRACE TLV:**

```text
A transparent clock is not a boundary clock.
It does not append its clockIdentity.
It leaves PATH_TRACE unchanged.
```

**CUMULATIVE_RATE_RATIO TLV:**

```text
A transparent clock may need to read the rate-ratio information.
It uses that information to correct residence time.
It does not change the TLV content.
```

**AUTHENTICATION TLV:**

```text
A transparent clock modifies correctionField (a mutable field).
With immediate security:
- The ICV calculation covers correctionField.
- After modifying correctionField, must the transparent clock recompute the ICV?

Answer:
- Immediate security: the transparent clock modifies correctionField, and the receiver verifies using the modified value.
- Delayed security: mutable fields are not supported, so it does not apply to a transparent-clock network.
```

## TLV parsing best practices

### Parsing framework

```c
void parse_ptp_message(PTPMessage *msg) {
    // Step 1: parse the message header
    parse_header(msg);
    
    // Step 2: parse the message body
    parse_body(msg);
    
    // Step 3: parse the TLV sequence
    int offset = header_length + body_length;
    while (offset < msg->total_length) {
        TLV *tlv = parse_tlv(msg->data + offset);
        
        // Step 4: handle known TLVs
        if (is_known_tlv(tlv->tlvType)) {
            process_known_tlv(tlv);
        } else {
            // Step 5: skip unknown TLVs
            if (tlv_type_must_propagate(tlv->tlvType)) {
                mark_for_propagation(tlv);
            }
            // Skip it and keep parsing
        }
        
        // Step 6: move to the next TLV
        offset += 4 + tlv->lengthField;
    }
}
```

### Error handling

```c
TLV *parse_tlv(uint8_t *data) {
    TLV *tlv = malloc(sizeof(TLV));
    
    // Step 1: read tlvType and lengthField
    tlv->tlvType = read_uint16(data);
    tlv->lengthField = read_uint16(data + 2);
    
    // Step 2: check the length
    if (tlv->lengthField > MAX_TLV_LENGTH) {
        log_error("TLV length too large");
        return NULL;
    }
    
    // Step 3: check that the length is even
    if (tlv->lengthField % 2 != 0) {
        log_error("TLV length not even");
        return NULL;
    }
    
    // Step 4: read valueField
    tlv->valueField = malloc(tlv->lengthField);
    memcpy(tlv->valueField, data + 4, tlv->lengthField);
    
    return tlv;
}
```

### Performance optimization

```text
Optimization strategies:

Strategy one: cache TLVs
- Cache parsed TLVs.
- Avoid parsing them again.

Strategy two: fast skip
- For an unsupported TLV, read only lengthField and skip.
- Do not parse valueField.

Strategy three: filter by TLV type
- Parse only the TLV types you care about.
- Skip the rest quickly.

Strategy four: memory pool
- Allocate TLV memory from a pool.
- Avoid frequent malloc/free.
```

## TLVs and protocol evolution

### TLV changes from 2008 to 2019

**New TLVs:**

```text
A few TLVs added in the 2019 edition (examples):
- 0x8001: L1_SYNC (L1 synchronization performance enhancement)
- 0x8007: CUMULATIVE_RATE_RATIO (cumulative rate ratio)
- 0x8009: AUTHENTICATION (the 2019 security mechanism)
- 0x4001: ENHANCED_ACCURACY_METRICS (accuracy-metric propagation)

TLVs not new in this edition but still in use (examples):
- 0x8008: PAD
- 0x0008: PATH_TRACE
- 0x0009: ALTERNATE_TIME_OFFSET_INDICATOR
```

**TLVs no longer used for new extensions:**

```text
2008 edition:
- 0x0003: ORGANIZATION_EXTENSION

2019 edition:
- 0x0003 is deprecated
- Replacements: 0x4000 and 0x8000
```

**Propagation rule changes:**

```text
The 2019 propagation rule is a double rule: "range + individual marking".

Must propagate (received on Announce and unsupported locally):
- tlvType falls in 0x4000-0x7FFF, or
- it is individually marked Propagate, currently two:
    0x0008 PATH_TRACE
    0x0009 ALTERNATE_TIME_OFFSET_INDICATOR

Must not propagate:
- tlvType falls in 0x8000-0xFFEF, or
- it is individually marked Do Not Propagate
  (0x0000-0x0007, 0x000A-0x3FFF, 0x8000-0x8009, 0xFFF0-0xFFFF are all in this group)

⚠️ A common wrong simplification is "0x4000-0x7FFF propagates, everything else does not".
   That misses PATH_TRACE / ATO, the two TLVs explicitly marked Propagate.
```

### Room for future expansion

**Reserved space:**

```text
Reserved by the IEEE 1588 WG (for future WG allocation, not for vendors):
- 0x4002-0x7EFF: propagating-class reserved
- 0x800A-0xFFEF: non-propagating-class reserved

Experimental space (experimental values):
- 0x2004-0x202F: experimental (non-propagating)
- 0x7F00-0x7FFF: experimental (propagating)

Pure reserved:
- 0x000A-0x1FFF
- 0x2030-0x3FFF
- 0xFFF0-0xFFFF

TLVs left over from 1588-2008 (this edition no longer has these options; the values stay reserved and must not be reused):
- 0x2000 AUTHENTICATION_2008
- 0x2001 AUTHENTICATION_CHALLENGE
- 0x2002 SECURITY_ASSOCIATION_UPDATE
- 0x2003 CUM_FREQ_SCALE_FACTOR_OFFSET
```

**Extension advice:**

```text
If you want to define a new TLV:
1. Apply to the IEEE 1588 working group for a type value.
2. Or use the organization-extension TLV (0x4000 or 0x8000).
3. Choose the propagation attribute.
4. Design the valueField format.
5. Document it.
```

## PAD TLV: adjusting message length

### Why PAD?

Some scenarios require a PTP message to reach a minimum length.

```text
Reasons:
- Reduce length asymmetry (a delay difference caused by different message lengths in each direction)
- A profile requires a minimum length
- Some network devices require a minimum frame length
```

### PAD TLV format

```text
┌───────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x8008                        │
│ lengthField (2 bytes) = N                         │
│ pad (N bytes) - all 0x00                          │
└───────────────────────────────────────────────────┘

```

**Smallest PAD TLV:**

```text
When lengthField = 0:
Total TLV length: 4 bytes (Type + Length)
This is the smallest PAD TLV.
```

### PAD example

```
Scenario: suppose a profile requires the Sync message to be at least 64 bytes

Original Sync message: 44 bytes (PTP message length)
Needed: 20 more bytes

Add a PAD TLV:
tlvType: 0x8008
lengthField: 16 (16 bytes of pad)
Total length: 4 + 16 = 20 bytes

Final Sync: 44 + 20 = 64 bytes
```

## In practice: combining TLVs

### Scenario one: high-accuracy synchronization

```text
Announce carries:
- PATH_TRACE TLV: loop detection

Sync carries:
- CUMULATIVE_RATE_RATIO TLV: frequency transfer
```

### Scenario two: secure synchronization

```text
Every message carries:
- AUTHENTICATION TLV: authentication and integrity checking

Announce carries:
- PATH_TRACE TLV: loop detection
```

### Scenario three: telecom unicast synchronization

```text
Signaling carries:
- REQUEST_UNICAST_TRANSMISSION TLV
- or the GRANT/CANCEL/ACK TLVs

Announce carries:
- PATH_TRACE TLV: loop detection
```

## Summary: TLV essentials

**TLV structure:**
- Type (2 bytes) + Length (2 bytes) + Value (N bytes)
- Length must be even

**Propagation attribute** (double rule):
- Falls in 0x4000-0x7FFF, **or** individually marked Propagate (0x0008 PATH_TRACE, 0x0009 ATO) → must propagate (even if unsupported)
- Falls in 0x8000-0xFFEF, **or** individually marked Do Not Propagate → do not propagate (drop when unsupported)

**Core TLVs:**
- PATH_TRACE: loop detection (propagating)
- AUTHENTICATION: security authentication
- L1_SYNC: high-accuracy synchronization
- CUMULATIVE_RATE_RATIO: frequency transfer

**Organization extensions:**
- organizationId (OUI) + organizationSubType
- choose the propagation attribute (0x4000 or 0x8000)
- globally unique identifier

**PAD TLV:**
- increases message length
- 4 bytes minimum

**Parsing principles:**
- Skip unsupported TLVs.
- Propagate TLVs marked "Propagate".
- Process supported TLVs.
