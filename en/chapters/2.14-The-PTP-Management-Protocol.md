# 2.14 The Network's Remote Control: The PTP Management Protocol in Depth

## Why a management protocol?

A running PTP network needs management:

```
Common management needs:

1. Status monitoring
   - What is the current offset?
   - Who is the master?
   - How is the synchronization state?

2. Parameter configuration
   - Change the priority.
   - Adjust the send intervals.
   - Set the domain number.

3. Fault diagnosis
   - Why is it not synchronized?
   - Message statistics.
   - Error counters.

4. Operations
   - Switch the master.
   - Restart a port.
   - Update configuration.
```

IEEE 1588 defines a management protocol:
- Management messages.
- GET: read parameters.
- SET: set parameters.
- COMMAND: execute commands.

## The management message

```c
/* msg.h, lines 171-179 */

struct management_msg {
    struct ptp_header   hdr;                /* common header */
    struct PortIdentity targetPortIdentity; /* target port (10 bytes) */
    UInteger8           startingBoundaryHops;
    UInteger8           boundaryHops;
    uint8_t             flags;              /* high nibble reserved | low nibble actionField */
    uint8_t             reserved;
    /* TLVs follow */
};
```

Key fields:

```
targetPortIdentity:
- Specifies the target.
- Can be a specific port.
- An all-ones clockIdentity plus portNumber=0xFFFF broadcasts to all ports.

startingBoundaryHops and boundaryHops:
- Management messages may cross boundary clocks.
- Each BC decrements boundaryHops by one.
- At 0 the message is not retransmitted (prevents infinite propagation).

actionField (in the flags octet):
- GET: request to read.
- SET: request to set.
- RESPONSE: reply.
- COMMAND: command.
- ACKNOWLEDGE: acknowledgement.
```

## The actionField

```c
/* tlv.h, lines 58-64 */

enum management_action {
    GET,         /* read request */
    SET,         /* set request */
    RESPONSE,    /* response */
    COMMAND,     /* command */
    ACKNOWLEDGE, /* acknowledgment */
};
```

Typical flows:

```
GET operation:

client → server: GET DEFAULT_DATA_SET
server → client: RESPONSE DEFAULT_DATA_SET (data)

SET operation:

client → server: SET PRIORITY1 (value = 128)
server → client: RESPONSE PRIORITY1 (value = 128)

COMMAND operation:

client → server: COMMAND INITIALIZE
server → client: ACKNOWLEDGE INITIALIZE
```

## Boundary hops and propagation

Management messages propagate across boundary clocks per 15.3.3:

- Only multicast management messages received on a port in MASTER, SLAVE, UNCALIBRATED, or PRE_MASTER are retransmitted.
- If the received boundaryHops is 0, the message is not retransmitted.
- Otherwise the BC decrements boundaryHops by one and retransmits only via ports in those same four states.

Practical examples:

```
boundaryHops = 1: reaches directly attached ports only.
boundaryHops = 2: crosses one boundary clock.
boundaryHops = 255: nearly unlimited propagation.
```

## Management IDs

The `managementId` (an Enumeration16 inside the management TLV) selects what is read or written. Ranges:

| Range | Applies to |
|:---|:---|
| 0x0000-0x1FFF | All PTP instances |
| 0x2000-0x2FFF | Ordinary and boundary clocks |
| 0x3000-0x3FFF | Optional / vendor-specific |
| 0x4000-0x4FFF | Transparent clocks (deprecated in 2019) |
| 0x6000-0x7FFF | All clock types (delay mechanisms) |
| 0xC000-0xFFFF | LinuxPTP extensions (the "_NP" series) |

## The MANAGEMENT_ERROR_STATUS TLV

When a management request fails, the responder returns a MANAGEMENT_ERROR_STATUS TLV (type 0x0002):

```
┌─────────┬──────────┬──────────┬──────────┬───────────┐
│ tlvType │ length   │ error    │ id       │ reserved  │
│ 0x0002  │ 8(+extra)│ 2 bytes  │ 2 bytes  │ 4 bytes   │
└─────────┴──────────┴──────────┴──────────┴───────────┘
```

Error codes (Table 109):

| Error | Value |
|:---|:---|
| RESPONSE_TOO_BIG | 0x0001 |
| NO_SUCH_ID | 0x0002 |
| WRONG_LENGTH | 0x0003 |
| WRONG_VALUE | 0x0004 |
| NOT_SETABLE | 0x0005 |
| NOT_SUPPORTED | 0x0006 |
| UNPOPULATED | 0x0007 |
| GENERAL_ERROR | 0xFFFE |

## The pmc tool

`pmc` (PTP Management Client) talks to a PTP instance over the management protocol, locally via a Unix-domain socket (`-u`), or over the network (`-4`, `-6`, `-2`).

Common options:

```
-u         use the Unix-domain socket (local communication)
-b 0       boundaryHops = 0 (the local device)
-b 1       boundaryHops = 1 (one BC away)
-i <if>    network interface
-t <hex>   transportSpecific field (default 0x0)
-s <path>  UDS server address (default /var/run/ptp4l)
```

Interactive mode: `pmc -u` gives a prompt, `help` lists the recognized management IDs, and both GET/SET and abbreviated commands are accepted.

Typical commands:

```
pmc -u "GET PORT_DATA_SET"
pmc -u "GET PARENT_DATA_SET"
pmc -u "GET CURRENT_DATA_SET"
pmc -u "GET TIME_STATUS_NP"
pmc -u "SET PRIORITY1 100"
```

Version note: LinuxPTP's 1.9.2 (Ubuntu 20.04) `pmc` does not recognize the newer `_NP` TLVs (e.g., `PORT_STATS_NP`, `PORT_SERVICE_STATS_NP`, `SUBSCRIBE_EVENTS_NP`, `UNICAST_MASTER_TABLE_NP`), they report `bad command`. They require LinuxPTP 3.x.

## What pmc can't easily do

Because pmc validates against its own client-side table:

- An unknown TLV name is rejected client-side with `bad command`; it never reaches the server (e.g., `GET NON_EXISTENT_ID`).
- SETting a GET-only ID is also rejected client-side (e.g., `SET CLOCK_DESCRIPTION` → `CLOCK_DESCRIPTION only allows GET`).

So on LinuxPTP 1.9.2, a genuine server-side `MANAGEMENT_ERROR_STATUS` (NOT_SETABLE / WRONG_VALUE, etc.) is hard to trigger through pmc, the client filters out requests that are obviously invalid before sending them.

## UDS vs network transport

- UDS: point a pmc at `/var/run/ptp4l` (read/write) or `/var/run/ptp4lro` (read-only). Local, fast, permission-controlled.
- Network: `pmc -4 -i eth0 -b 1 "GET CURRENT_DATA_SET"` manages remote devices; boundaryHops controls the scope, and firewalls may block ports 319/320.

## Summary

- Management messages (with a target identity, boundary hops, and an action field) drive GET/SET/COMMAND operations.
- managementId selects the object; _NP identifiers extend LinuxPTP beyond the standard.
- Errors come back in MANAGEMENT_ERROR_STATUS TLVs (GENERAL_ERROR = 0xFFFE).
- pmc is the standard client; `-u` for local UDS, `-4`/`-6`/`-2` for the network.

Management gives us configuration and monitoring. But some deployments need the *message delivery* itself to change: unicast instead of multicast negotiation, and a record of the path.
