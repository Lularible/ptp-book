# 2.14 The Network's Remote Control: The PTP Management Protocol in Depth

## A night-shift engineer's nightmare

3 a.m. A telecom carrier's NOC (network operations center) gets an alarm.

"A base station's time synchronization is off. The offset is over 10 µs."

Wang, the engineer on duty, opens the management platform. The base station sits in a remote area, a two-hour drive away.

**The problem**:
- He needs to confirm the base station's current time offset.
- He needs to find out which master clock it follows.
- He may need to change configuration parameters.

**The old way**:
- Drive two hours to the site.
- Connect over serial or SSH.
- Read the logs, change the configuration.
- Drive two hours back.

**The PTP management protocol way**:
- Open the management software.
- Send a GET to read currentDS.
- Send a GET to read parentDS.
- Send a SET if a parameter needs changing.
- Five minutes, sitting at your desk.

That's the value of the PTP management protocol: **remote control of a PTP network**.

---

## What is the PTP management protocol?

### Core concepts

The PTP management protocol is an optional PTP feature. From a distance, a management node can:

- **Read**: query the state and configuration of a PTP device.
- **Set**: change a PTP device's configuration parameters.
- **Command**: trigger a specific operation on a PTP device.

### The SNMP analogy

If you know network management, think of the PTP management protocol as SNMP:

| SNMP concept | PTP management protocol |
|:---|:---|
| GetRequest | GET action |
| SetRequest | SET action |
| GetResponse | RESPONSE action |
| Trap | No direct equivalent (PTP uses event notification) |
| OID | managementId |
| MIB | Data set (defaultDS, currentDS, etc.) |

### Relationship to NETCONF/YANG

Modern network management is moving toward NETCONF/YANG. PTP can also be managed through a YANG model.

```text
Choosing a management approach:

Traditional approach:
PTP management protocol → dedicated to PTP
- Pros: deeply integrated with PTP
- Cons: narrow scope, manages PTP only

Modern approach:
NETCONF/YANG → general network management framework
- Pros: one framework for many protocols, transactions
- Cons: needs an extra YANG model

In practice:
Many devices support both
The PTP management protocol for quick diagnosis
NETCONF/YANG for configuration management
```

## The management protocol's basic architecture

### Management node and target device

```text
┌─────────────────┐                    ┌─────────────────┐
│ Management node │                    │  Target device  │
│  (Management    │  Management        │  (PTP device)   │
│   Instance)     │◄──── Messages ────►│                 │
│                 │                    │                 │
└─────────────────┘                    └─────────────────┘

Management node: sends management requests, receives responses
Target device: receives management requests, performs the operation, returns the result
```

**The management node is not necessarily a PTP device**:

```text
Typical deployment:

Management server (running management software)
     │
     │ management messages
     ▼
PTP boundary clock
     │
     │ management messages (boundaryHops decrements)
     ▼
PTP slave clock (target device)
```

### How management messages travel

Management messages can travel through boundary clocks, just like PTP synchronization messages.

```text
Propagation rules:

Management node → BC1 → BC2 → target device
  │            │            │           │
  │            │            │           │
  └────────────┴────────────┴───────────┘
        boundaryHops controls the range
```

## The management message format in detail

### The complete message layout

A Management message is a special PTP message (messageType = 0x0D).

```text
Management message format:
┌──────────────────────────────────────────────────────┐
│ Common header (34 bytes)                             │
│ ─────────────────────────────────────────────────────│
│ targetPortIdentity (10 bytes)                        │
│   - clockIdentity (8 bytes): target device ID        │
│   - portNumber (2 bytes): target port                │
│ ─────────────────────────────────────────────────────│
│ startingBoundaryHops (1 byte): initial hop count     │
│ boundaryHops (1 byte): remaining hops                │
│ reserved | actionField (4-bit): high 4 bits reserved │
│ reserved (1 byte): reserved                          │
│ ─────────────────────────────────────────────────────│
│ MANAGEMENT TLV (variable)                            │
│   - tlvType (2 bytes): 0x0001                        │
│   - lengthField (2 bytes)                            │
│   - managementId (2 bytes)                           │
│   - dataField (variable)                             │
└──────────────────────────────────────────────────────┘
```

### targetPortIdentity in detail

This is the "address" field. It names the target of the management message.

**clockIdentity (8 bytes)**:

```text
The target device's clockIdentity
- A specific device ID: only that device handles it
- All ones (FF-FF-FF-FF-FF-FF-FF-FF): broadcast to every device
```

**portNumber (2 bytes)**:

```text
Target port number
- A specific port number (0x0001, say): only that port handles it
- All ones (0xFFFF): "all ports"
```

**How they combine**:

| clockIdentity | portNumber | Meaning |
|:---|:---|:---|
| Specific ID | Specific port | A specific port on the target device |
| Specific ID | 0xFFFF | All ports on the target device |
| All ones | Specific port | A specific port on all devices |
| All ones | 0xFFFF | All ports on all devices |

### actionField in detail

This is the "verb". It says what to do.

| Value | Action | Meaning | Response |
|:---|:---|:---|:---|
| 0x00 | GET | Read data | RESPONSE |
| 0x01 | SET | Set data | RESPONSE |
| 0x02 | RESPONSE | Return data | - |
| 0x03 | COMMAND | Trigger a command | ACKNOWLEDGE |
| 0x04 | ACKNOWLEDGE | Confirm a command | - |

**GET flow**:

```text
Management node                             Target device
   |                                            |
   |--- Management(GET) ----------------------->|
   |    managementId = CURRENT_DATA_SET         |
   |                                            |
   |<-- Management(RESPONSE) -------------------|
   |    dataField = currentDS contents          |
```

**SET flow**:

```text
Management node                             Target device
   |                                            |
   |--- Management(SET) ----------------------->|
   |    managementId = PRIORITY1                |
   |    dataField = new priority1 value         |
   |                                            |
   |<-- Management(RESPONSE) -------------------|
   |    dataField = value after the set         |
```

**COMMAND flow**:

```text
Management node                             Target device
   |                                            |
   |--- Management(COMMAND) ------------------->|
   |    managementId = INITIALIZE               |
   |    dataField = initializationKey           |
   |                                            |
   |<-- Management(ACKNOWLEDGE) ----------------|
```

### boundaryHops in detail

This is the "TTL" field. It limits how far a management message travels.

```text
How it works:

On send:
startingBoundaryHops = initial hop count set by the sender
boundaryHops = startingBoundaryHops

At each boundary clock:
boundaryHops = boundaryHops - 1

Propagation rule:
boundaryHops > 0 → keep forwarding
boundaryHops = 0 → do not forward (the current device handles it)
```

**Example**:

```text
Topology:
Management node → BC1 → BC2 → target device

Send the management request:
startingBoundaryHops = 3
boundaryHops = 3

BC1 forwards:
boundaryHops = 2

BC2 forwards:
boundaryHops = 1

Target device receives:
boundaryHops = 1
Handles the request and responds

Response comes back:
Target device sends the response. startingBoundaryHops = 3 - 1 = 2, boundaryHops = 2
BC2 forwards, boundaryHops = 1
BC1 forwards, boundaryHops = 0
Management node receives, boundaryHops = 0
```

**Why boundaryHops?**

```text
Reason one: limit the propagation range
A large network may have hundreds of PTP devices
Broadcasting management messages can cause a broadcast storm
boundaryHops limits the range

Reason two: diagnosis
startingBoundaryHops - boundaryHops = number of boundary clocks crossed
It tells you how many hops the message has traveled
```

## Inside the MANAGEMENT TLV

### TLV format

```text
MANAGEMENT TLV format:
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x0001                         │
│ lengthField (2 bytes) = 2 + N                      │
│ managementId (2 bytes)                             │
│ dataField (N bytes)                                │
└────────────────────────────────────────────────────┘
```

**dataField length rule**:

```text
lengthField must be even
If dataField itself has odd length, pad it
```

### Management ID ranges

managementId is the "object". It says which data to read or set.

**Range layout**:

```text
managementId range allocation:

0x0000 - 0x1FFF: applies to all PTP instances
  - general operations (initialization, fault log, and so on)
  - implemented through 0x0007; 0x0008 - 0x1FFF is Reserved

0x2000 - 0x2FFF: applies to ordinary and boundary clocks
  - data sets (defaultDS, currentDS, and so on)
  - configuration parameters (priority1, domain, and so on)
  - implemented through 0x2021; 0x2022 - 0x2FFF is Reserved

0x3000 - 0x3FFF: optional management IDs (OC/BC)
  - advanced features (external configuration, holdover upgrade, and so on)
  - implemented through 0x3003; 0x3004 - 0x3FFF is Reserved

0x4000 - 0x4FFF: applies to transparent clocks
  - 0x4000 TRANSPARENT_CLOCK_DEFAULT_DATA_SET / 0x4001 TRANSPARENT_CLOCK_PORT_DATA_SET
    / 0x4002 PRIMARY_DOMAIN
  - 0x4003 - 0x4FFF is Reserved

0x5000 - 0x5FFF: reserved for optional transparent-clock management messages; the whole range is still Reserved

0x6000 - 0x7FFF: applies to ordinary clocks, boundary clocks, and transparent clocks
  - delay mechanism configuration
  - two implemented: 0x6000 DELAY_MECHANISM, 0x6001 LOG_MIN_PDELAY_REQ_INTERVAL
  - 0x6002 - 0xBFFF is Reserved

0xC000 - 0xDFFF: implementation-specific
  - vendors allocate this range themselves
  - no interoperability is expected; the management side must make sure messages reach the right device

0xE000 - 0xFFFE: assigned by an alternate PTP profile

0xFFFF: Reserved
```

**What the implementation-specific range (0xC000-0xDFFF) looks like in practice: linuxptp occupies 0xC000-0xC00B**:

```c
/* linuxptp/tlv.h, all within 0xC000-0xDFFF */
#define MID_TIME_STATUS_NP                  0xC000
#define MID_GRANDMASTER_SETTINGS_NP         0xC001
#define MID_PORT_DATA_SET_NP                0xC002   /* tlv.h:125 */
#define MID_SUBSCRIBE_EVENTS_NP             0xC003
#define MID_PORT_PROPERTIES_NP              0xC004   /* tlv.h:126 */
#define MID_PORT_STATS_NP                   0xC005   /* tlv.h:127 */
#define MID_SYNCHRONIZATION_UNCERTAIN_NP    0xC006
#define MID_PORT_SERVICE_STATS_NP           0xC007   /* tlv.h:128 */
#define MID_UNICAST_MASTER_TABLE_NP         0xC008   /* tlv.h:129 */
#define MID_PORT_HWCLOCK_NP                 0xC009   /* tlv.h:130 */
#define MID_POWER_PROFILE_SETTINGS_NP       0xC00A   /* tlv.h:131 */
#define MID_CMLDS_INFO_NP                   0xC00B   /* tlv.h:132 */
```

### General management IDs (0x0000-0x1FFF)

| managementId | Value | Allowed actions | Purpose |
|:---|:---|:---|:---|
| NULL_PTP_MANAGEMENT | 0x0000 | GET/SET/COMMAND | No-op, test connectivity |
| CLOCK_DESCRIPTION | 0x0001 | GET | Get the device description |
| USER_DESCRIPTION | 0x0002 | GET/SET | User-defined description |
| SAVE_IN_NON_VOLATILE_STORAGE | 0x0003 | COMMAND | Save the configuration to non-volatile storage |
| RESET_NON_VOLATILE_STORAGE | 0x0004 | COMMAND | Reset the configuration to defaults |
| INITIALIZE | 0x0005 | COMMAND | Initialize the device |
| FAULT_LOG | 0x0006 | GET | Read the fault log |
| FAULT_LOG_RESET | 0x0007 | COMMAND | Clear the fault log |

**CLOCK_DESCRIPTION in detail**:

This is the most commonly used diagnostic tool. It returns a full description of the device.

```text
Data returned by CLOCK_DESCRIPTION:

clockType: device type (OC/BC/E2E TC/P2P TC)
physicalLayerProtocol: physical layer protocol (such as "IEEE 802.3")
physicalAddress: physical address (such as a MAC address)
protocolAddress: protocol address (such as an IP address)
manufacturerIdentity: vendor OUI
productDescription: product description
revisionData: version information
userDescription: user description
profileIdentifier: profile identifier
```

**The INITIALIZE command**:

This is the most powerful command. It can restart a PTP instance.

```text
dataField of the INITIALIZE command:

initializationKey (2 bytes):
  0x0000: initialization event (enable the PTP instance)
  0x0001-0x7FFF: reserved
  0x8000-0xFFFF: vendor-defined

Effect:
Sets defaultDS.instanceEnable to TRUE
If it was FALSE, this "starts" the PTP instance
```

### Optional management IDs (0x3000-0x3FFF)

| managementId | Value | Allowed actions | Purpose |
|:---|:---|:---|:---|

**EXTERNAL_PORT_CONFIGURATION_ENABLED in detail**:

```text
Traditional mode: BMCA decides port state automatically
External configuration mode: the administrator sets port state by hand

After setting EXTERNAL_PORT_CONFIGURATION_ENABLED = TRUE:
- BMCA is disabled
- The administrator controls port state with ENABLE_PORT/DISABLE_PORT
- Ports no longer switch state automatically

Where it applies:
- Networks that need tight control over topology
- You don't want BMCA changing port state on its own
```

## Hands-on examples

### Example 1: Diagnosing a synchronization problem

**Scenario**: a slave clock has a bad offset, and you need to diagnose it.

**Step 1: read currentDS**

```text
Send:
Management message:
  targetPortIdentity = target device's clockIdentity + 0xFFFF
  actionField = GET
  managementId = CURRENT_DATA_SET (0x2001)

Receive:
Management message:
  actionField = RESPONSE
  dataField:
    stepsRemoved = 5
    offsetFromMaster = +15000ns (15 µs)
    meanPathDelay = 1000ns (1 µs)
```

**Analysis**:

```text
stepsRemoved = 5: crossed 5 boundary clocks
offsetFromMaster = +15µs: offset too large
meanPathDelay = 1µs: link delay normal

Preliminary conclusion:
The time offset is large, but link delay is normal
The problem may be in a relay node or the master clock
```

**Step 2: read parentDS**

```text
Send:
Management message:
  actionField = GET
  managementId = PARENT_DATA_SET (0x2002)

Receive:
Management message:
  actionField = RESPONSE
  dataField:
    parentPortIdentity = {upstream clock ID, port number}
    grandmasterIdentity = master clock ID
    grandmasterClockQuality = {class=52, accuracy=0x31}
```

**Analysis**:

```text
Master clock quality:
  clockClass = 52 (degradation alternative A: originally class 7, now beyond the profile's holdover target)
  clockAccuracy = 0x0031 (accuracy worse than 10 s)

Conclusion:
The master clock lost its external time source, degraded past its holdover target, and its accuracy dropped sharply
That may explain the slave's large offset
```

### Example 2: Changing a device's priority

**Scenario**: a device should be the master clock, but it isn't.

**Step 1: read the current priority1**

```text
Send:
Management(GET)
  managementId = PRIORITY1 (0x2005)

Receive:
Management(RESPONSE)
  dataField: priority1 = 128
```

**Step 2: set a new priority1**

```text
Send:
Management(SET)
  managementId = PRIORITY1 (0x2005)
  dataField: priority1 = 10

Receive:
Management(RESPONSE)
  dataField: priority1 = 10
```

**Step 3: save the configuration**

```text
Send:
Management(COMMAND)
  managementId = SAVE_IN_NON_VOLATILE_STORAGE (0x0003)

Receive:
Management(ACKNOWLEDGE)
```

### Example 3: Restarting a device remotely

**Scenario**: a device's configuration is a mess, and you need to restore defaults.

**Step 1: reset non-volatile storage**

```text
Send:
Management(COMMAND)
  managementId = RESET_NON_VOLATILE_STORAGE (0x0004)

Receive:
Management(ACKNOWLEDGE)
```

**Step 2: initialize the device**

```text
Send:
Management(COMMAND)
  managementId = INITIALIZE (0x0005)
  dataField: initializationKey = 0x0000

Receive:
Management(ACKNOWLEDGE)

Effect:
The device reinitializes and loads the default configuration
```

## The MANAGEMENT_ERROR_STATUS TLV

When a management operation fails, the device returns an error instead of a normal response.

### Error TLV format

```text
MANAGEMENT_ERROR_STATUS TLV format:
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x0002                         │
│ lengthField (2 bytes) = 8 + N + M                  │
│ managementErrorId (2 bytes): error code            │
│ managementId (2 bytes): ID of the request          │
│ reserved (4 bytes): reserved                       │
│ displayData (N bytes): readable error message      │
│ pad (M bytes): padding                             │
└────────────────────────────────────────────────────┘
```

### The error codes

| Error code | Value | Meaning | Typical case |
|:---|:---|:---|:---|
| RESPONSE_TOO_BIG | 0x0001 | Response too big | FAULT_LOG content too large |
| NO_SUCH_ID | 0x0002 | Unrecognized managementId | The device does not support that management ID |
| WRONG_LENGTH | 0x0003 | Wrong data length | SET data length does not match |
| WRONG_VALUE | 0x0004 | Wrong value | priority1 out of range |
| NOT_SETABLE | 0x0005 | Variable not settable | Trying to SET a read-only variable |
| NOT_SUPPORTED | 0x0006 | Operation not supported | The device does not support that action |
| UNPOPULATED | 0x0007 | Target does not exist | The specified port does not exist |
| GENERAL_ERROR | 0xFFFE | Other error | Unclassified error |

MID_NOT_SETABLE is defined but never used. The server only ever returns MID_NOT_SUPPORTED, and with pmc a read-only SET never reaches the server at all: pmc rejects the request on the client side.

### Error handling example

**Scenario**: try to set a read-only variable

```text
Send:
Management(SET)
  managementId = DEFAULT_DATA_SET (0x2000)
  dataField: priority1 = 10

Receive:
The client rejects it before sending:
  DEFAULT_DATA_SET only allows GET
```

**Analysis**:

```text
DEFAULT_DATA_SET is read-only
Use PRIORITY1 (0x2005) to set priority1
```

## How boundary clocks forward management messages

### When a boundary clock forwards

A boundary clock forwards management messages only in certain port states:

```text
Port states that forward:
- MASTER
- SLAVE
- UNCALIBRATED
- PRE_MASTER

Port states that don't:
- INITIALIZING
- FAULTY
- DISABLED
- LISTENING
- PASSIVE
```

### The forwarding flow

```text
A boundary clock handles a management message:

Step 1: check boundaryHops
if (boundaryHops == 0) {
    // don't forward, handle locally
    process_locally();
    return;
}

Step 2: check port state
if (port_state not in {MASTER, SLAVE, UNCALIBRATED, PRE_MASTER}) {
    // don't forward
    return;
}

Step 3: decrement boundaryHops
boundaryHops--;

Step 4: forward to the other ports
forward_to_other_ports();
```

### The response path

The response travels back along the reverse path.

```text
Request path:
Management node → BC1 → BC2 → target device

Response path:
Target device → BC2 → BC1 → management node

Note:
The target device starts the response fresh
startingBoundaryHops = the request's startingBoundaryHops minus the hops consumed (startingBoundaryHops - boundaryHops)
boundaryHops starts at startingBoundaryHops and decrements at each hop
boundaryHops = 0 when the response reaches the management node
```

## Security considerations

### Risks in the management protocol

**Risk 1: unauthorized access**

```text
Attack:
A malicious device sends management messages
It changes priority1 and disturbs BMCA
It disables ports and breaks synchronization

Consequence:
Network time goes haywire
Service outage
```

**Risk 2: information leak**

```text
Attack:
A malicious device sends GET requests
It reads CURRENT_DATA_SET and PARENT_DATA_SET
It learns the network topology

Consequence:
Intelligence for a follow-up attack
```

### Countermeasures

**Countermeasure 1: use the AUTHENTICATION TLV**

```text
Enable the PTP security mechanism:
Every management message carries an AUTHENTICATION TLV
The device checks the ICV before it processes the message

Effect:
Unauthorized devices can't send management messages
```

**Countermeasure 2: network isolation**

```text
Separate the management network from the PTP network:
Management messages travel only on the management VLAN
PTP devices don't expose a management interface on the service network

Effect:
Smaller attack surface
```

**Countermeasure 3: access control lists**

```text
Configure an ACL:
Only specific IP addresses may send management messages
Reject management messages from anywhere else

Effect:
Limits where management traffic can come from
```

**Countermeasure 4: read-only mode**

```text
Some deployments choose:
Allow GET only
Forbid SET and COMMAND

Effect:
Configuration can't be tampered with
Monitor only, no changes
```

## The real tool: linuxptp's pmc

### pmc in brief

The linuxptp project ships a management client: **pmc** (PTP Management Client).

```text
What pmc does:
- Sends GET/SET/COMMAND requests
- Supports only part of the standard's management IDs: 60 entries in its table, 23 unsupported
- Supports batch operations

Install:
apt install linuxptp
```

It prints no prompt. Give it a command on the command line or on stdin, and it prints the response.

### Common commands

**Get the device description**:

```bash
pmc -u -b 0 'GET CLOCK_DESCRIPTION'

Output:
	001b19.fffe.000001 seq 2 RESPONSE MANAGEMENT CLOCK_DESCRIPTION 
		clockType             0x8000
		physicalLayerProtocol IEEE 802.3
		physicalAddress       00:1b:19:00:00:01
		protocolAddress       1 192.168.1.100
		manufacturerId        00:00:00
		productDescription    Linux PTP;;
		revisionData          2.0;;
		userDescription       Server 1
```

**Get the current synchronization state**:

```bash
pmc -u -b 0 'GET CURRENT_DATA_SET'

Output:
	001b19.fffe.000001 seq 3 RESPONSE MANAGEMENT CURRENT_DATA_SET 
		stepsRemoved     2
		offsetFromMaster 125.0
		meanPathDelay    532.0
```

**Get parent clock information**:

```bash
pmc -u -b 0 'GET PARENT_DATA_SET'
```

**Set priority1**:

```bash
pmc -u -b 0 'SET PRIORITY1 10'

Output:
	001b19.fffe.000001 seq 5 RESPONSE MANAGEMENT PRIORITY1 
		priority1 10
```

**A command pmc doesn't implement**:

```bash
pmc -u -b 0 'COMMAND SAVE_IN_NON_VOLATILE_STORAGE'

Output:
sorry, SAVE_IN_NON_VOLATILE_STORAGE not supported yet
```

### pmc options

```bash
pmc [options] 'command'

Common options:
-u          use a Unix-domain socket (local)
-b 0        boundaryHops = 0 (the local device)
-b 1        boundaryHops = 1 (allow one BC; default)
-i <if>     network interface
-t <hex>    transportSpecific field (default 0x0)
-s <path>   UDS server address (default /var/run/ptp4l)

Command format:
GET <managementId>
SET <managementId> <value>
COMMAND <managementId>
```

## Summary: the essentials

**Five actions**:
- GET: read data
- SET: set data
- RESPONSE: return data
- COMMAND: trigger a command
- ACKNOWLEDGE: confirm a command

**Key management IDs**:
- 0x0001: CLOCK_DESCRIPTION (device description)
- 0x2001: CURRENT_DATA_SET (current state)
- 0x2002: PARENT_DATA_SET (parent clock information)
- 0x2005: PRIORITY1 (priority1)
- 0x200F: TIME (current time)

**Propagation control**:
- boundaryHops controls the range
- Decrement by one at each BC
- No forwarding at boundaryHops=0

**Error handling**:
- MANAGEMENT_ERROR_STATUS TLV
- Detailed error codes
- Readable error messages

**Security**:
- Enable the AUTHENTICATION TLV
- Network isolation
- Access control
