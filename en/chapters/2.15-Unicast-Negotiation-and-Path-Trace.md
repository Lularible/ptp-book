# 2.15 When Multicast Becomes a Luxury: Unicast Negotiation and Path Trace

## The telecom operator's dilemma

A large telecom operator hit a wall while deploying a 5G network.

Their core network spans several cities and has to keep the whole network in time sync. PTP is the standard choice, but there's a problem:

**Multicast doesn't work on their network.**

Multicast is technically perfectly feasible, so this is purely an **operational problem**:

```text
Problem one: multicast traffic management
Multicast messages flow into every corner of the network
The operator can't control the traffic scope precisely
Bandwidth cost is hard to account for

Problem two: security auditing
Multicast traffic is hard to trace: "who received what?"
Compliance audits require a clear sender and receiver for every flow
Multicast doesn't meet the audit requirement

Problem three: cross-domain coordination
Multicast is usually confined to a single routing domain
A 5G network spans several cities and several routing domains
Multicast can't cross routing boundaries
```

The operator's network architect asked:

"Can PTP use unicast? Like TCP, with a clear sender and receiver?"

The answer: **yes, through unicast negotiation.**

## Multicast vs unicast: an economics debate

### The case for multicast

**Efficiency**:

The core advantage of multicast: send once, many receive.

```text
Scenario: 1 master clock, 100 slave clocks

Multicast:
The master sends 1 Sync → all slaves receive it
Total traffic: 1 message

Unicast:
The master sends 100 Sync messages → each slave gets one
Total traffic: 100 messages
```

Multicast saves 99% of the bandwidth.

**Simplicity**:

Multicast doesn't need to know who the receivers are.

```text
Multicast configuration:
Master: send to multicast address 224.0.1.129
Slave: listen on multicast address 224.0.1.129
Done!

No slave addresses to configure, no receiver list to maintain
```

### The case against multicast

**Routing limits**:

Multicast messages usually don't cross a routing boundary.

```text
Default behavior of an Internet router:
Receive a multicast message → check whether it's inside this routing domain
If it crosses domains → drop it

Why:
Multicast traffic is hard to account for, so operators won't carry it
Multicast routing protocols (PIM, IGMP) are complex to configure
```

**Security tracking**:

Multicast traffic is hard to audit.

```text
Audit question:
Q: Who received the master's Sync message?
A: No idea. Every device listening on the multicast address may have received it

Compliance requirement:
Some industries (finance, government) require a clear record of sender and receiver for every flow
Multicast can't provide that record
```

**Wasted resources**:

Multicast may reach receivers that don't need it.

```text
Scenario:
100 devices in the network
Only 10 need PTP synchronization

Multicast:
All 100 devices receive the PTP messages (waste)
90 of them just "listen in" and don't take part in synchronization

Unicast:
Send only to the 10 devices that need sync
The other 90 are unaffected
```

### The case for unicast

**Precise control**:

You know exactly who sends and who receives.

```text
Unicast traffic:
Master → slave A: Sync (recorded)
Master → slave B: Sync (recorded)
Master → slave C: Sync (recorded)

Audit: a complete record of sender and receiver for every flow
```

**Cross-domain support**:

Unicast messages can cross routing boundaries.

```text
Unicast routing:
Just ordinary IP routing
Across cities and across operators, entirely feasible
```

**Security-friendly**:

Unicast is easier to encrypt.

```text
Unicast encryption:
Master → slave A: encrypted tunnel (IPsec)
Master → slave B: encrypted tunnel (IPsec)

Each tunnel has its own key, so the flows are isolated
```

### The case against unicast

**Bandwidth cost**:

More receivers means more traffic.

```text
Receiver count scales traffic linearly:
1 receiver → 1 copy
100 receivers → 100 copies
1000 receivers → 1000 copies
```

**Complex configuration**:

You need to know every receiver's address.

```text
Unicast configuration:
You need:
- each slave's IP address
- the message types each slave requests
- each slave's request interval
- each slave's grant duration

A heavy maintenance burden
```

**Scaling challenge**:

The master has to maintain a large number of unicast sessions.

```text
Master load:
One unicast session per slave
1000 slaves → 1000 sessions
High CPU and memory cost
```

### The comparison

| Feature | Multicast | Unicast |
|:---|:---|:---|
| **Bandwidth efficiency** | High (send once) | Low (N copies) |
| **Configuration complexity** | Low (no receiver knowledge) | High (configure every receiver) |
| **Cross-routing capability** | Limited (usually stays in one domain) | Good (ordinary IP routing) |
| **Security auditing** | Hard (no clear sender/receiver) | Easy (complete records) |
| **Encryption support** | Hard (multicast encryption is complex) | Easy (unicast tunnels are simple) |
| **Scalability** | Good (unlimited receivers) | Limited (the master carries the load) |
| **Where this applies** | Local networks, internal networks | Cross-domain networks, operator networks |

## PTP unicast negotiation in detail

### Key concepts

PTP unicast needs **negotiation**. Simply "sending to a different address" is nowhere near enough.

Why negotiate?

```text
Why:
The master doesn't know which slaves want unicast
The master doesn't know what send interval a slave expects
The master doesn't know how long the unicast should last

Solution:
The slave asks: "Send me unicast Sync, every 1 second, for 1 hour"
The master answers: "Granted" or "Denied"
```

### The four core TLVs

Unicast negotiation uses four TLVs. Together they form a complete request-grant-cancel mechanism.

**REQUEST_UNICAST_TRANSMISSION TLV**:

```text
Purpose: request a unicast transmission
Direction: slave → master

Format (tlv.h:283):
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x0004                         │
│ lengthField (2 bytes) = 6                          │
│ message_type (1 byte)                              │
│   - high 4 bits (bits 7-4): the requested type     │
│     encoded like the message header (SYNC=0x0,     │
│     DELAY_RESP=0x9, ANNOUNCE=0xB, PDELAY_RESP=0x3) │
│   - low 4 bits (bits 3-0): reserved                │
│   - linuxptp shifts left by 4 when sending         │
│     (message_type<<4)                              │
│ logInterMessagePeriod (1 byte)                     │
│   - interval = 2^(logInterMessagePeriod) seconds   │
│   - e.g. logInterMessagePeriod=1 → 2 s interval    │
│ durationField (4 bytes)                            │
│   - requested grant duration (seconds)             │
│   - e.g. durationField=3600 → 1 hour               │
└────────────────────────────────────────────────────┘

Note: one REQUEST asks for one message type;
to request several, send several REQUEST TLVs (one per type).
```

**GRANT_UNICAST_TRANSMISSION TLV**:

```text
Purpose: grant or deny a unicast transmission
Direction: master → slave

Format (tlv.h:169):
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x0005                         │
│ lengthField (2 bytes) = 8                          │
│ message_type (1 byte)                              │
│   - the granted message type (same as REQUEST)     │
│ logInterMessagePeriod (1 byte)                     │
│   - actual send interval (may differ from request) │
│ durationField (4 bytes)                            │
│   - actual grant duration (seconds)                │
│   - durationField=0 → deny the request             │
│ reserved (1 byte) = 0                              │
│ flags (1 byte)                                     │
│   - bit 0: GRANT_UNICAST_RENEWAL_INVITED           │
│     (invites the requester to renew)               │
└────────────────────────────────────────────────────┘
```

**CANCEL_UNICAST_TRANSMISSION TLV**:

```text
Purpose: cancel a unicast transmission
Direction: both ways (either the master or the slave can start it)

Format (tlv.h:162):
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x0006                         │
│ lengthField (2 bytes) = 2                          │
│ message_type/flags (1 byte)                        │
│   - high 4 bits (bits 7-4): the cancelled type     │
│   - bit 1: G (maintainGrant),                      │
│     TRUE = tell the grantor to keep the service    │
│   - bit 0: R (maintainRequest),                    │
│     TRUE = say I still need the service            │
│   - remaining bits: reserved                       │
│ reserved (1 byte) = 0                              │
└────────────────────────────────────────────────────┘
```

**ACKNOWLEDGE_CANCEL_UNICAST_TRANSMISSION TLV**:

```text
Purpose: acknowledge a cancel
Direction: both ways (the answer to a CANCEL)

Format (tlv.h:155):
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x0007                         │
│ lengthField (2 bytes) = 2                          │
│ message_type/flags (1 byte)                        │
│   - high 4 bits (bits 7-4): the type whose         │
│     cancel is acknowledged                         │
│   - bit 1: G (maintainGrant)                       │
│   - bit 0: R (maintainRequest)                     │
│   - remaining bits: reserved                       │
│ reserved (1 byte) = 0                              │
└────────────────────────────────────────────────────┘
```

### The full negotiation flow

**Phase one: request the unicast**

```text
Sequence:

Slave clock                                  Master clock
   |                                         |
   |--- Signaling -------------------------->|
   | REQUEST_UNICAST_TRANSMISSION TLV        |
   | message_type = Announce                 |
   | logInterMessagePeriod = 1               |
   | durationField = 300                     |
   |                                         |
   |                                         | checks:
   |                                         | - type supported?
   |                                         | - interval supported?
   |                                         | - duration supported?
   |                                         | - enough resources?
   |                                         |
   |<-- Signaling ---------------------------|
   | GRANT_UNICAST_TRANSMISSION TLV          |
   | message_type = Announce                 |
   | logInterMessagePeriod = 1               |
   | durationField = 300                     |
   |                                         |
   |                                         | (unicast starts)
```

**Phase two: the unicast transmission runs**

```text
Master → slave: unicast Announce (every 2 s)
Master → slave: unicast Sync (if it was requested too)
Master → slave: unicast Delay_Resp (if it was requested too)
```

**Phase three: the grant expires**

```text
Timeline:
t=0     the slave requests, the master grants, duration=300 s
t=300   the grant expires

Slave behavior:
Before expiry (say at t=280), send the REQUEST again
So unicast doesn't stop when the grant expires
```

**Phase four: request renewal**

```text
Slave clock                                  Master clock
   |                                         |
   |--- REQUEST_UNICAST_TRANSMISSION ------->|
   | (renewal, same or different parameters) |
   |                                         |
   |<-- GRANT_UNICAST_TRANSMISSION ----------|
   | (the new grant replaces the old one)    |
```

**Phase five: cancel on purpose**

```text
Scenario: the slave no longer needs unicast, or the master is short of resources

Slave → master:
CANCEL_UNICAST_TRANSMISSION
Master → slave:
ACKNOWLEDGE_CANCEL_UNICAST_TRANSMISSION
(unicast stops)

Or the other way round:

Master → slave:
CANCEL_UNICAST_TRANSMISSION
Slave → master:
ACKNOWLEDGE_CANCEL_UNICAST_TRANSMISSION
(unicast stops)
```

### The key rules in detail

**Rule one: a request must get an answer**

```text
The standard says: any PTP Port with the unicast negotiation option
enabled that receives a REQUEST_UNICAST_TRANSMISSION must send a
GRANT_UNICAST_TRANSMISSION (grant or deny), regardless of its own
port state.
(The grantor may itself be in SLAVE state; only INITIALIZING/FAULTY/
DISABLED and the transparent clock fault condition are exempt.)

It cannot stay silent!
```

**Rule two: duration=0 means denied**

```text
durationField in the GRANT:
> 0: granted, for duration seconds
= 0: request denied
```

**Rule three: a new grant replaces the old one**

```text
Scenario:
The slave first requests Announce unicast, duration=300 s
At t=100 s it requests Announce unicast again, duration=600 s

Result:
The old grant is cancelled
The new grant takes effect and runs for 600 s from the moment the
grant message is sent
```

**Rule four: one active grant per direction and message type**

```text
Limit:
A slave can't hold two "Announce unicast grants" in the same direction
A master can't hold two "Sync unicast grants" in the same direction

Why:
Avoid duplicate transmissions and wasted resources
```

**Rule five: the message interval may vary by ±30%**

```text
The standard says:
The master's actual send interval should stay within ±30% of the mean

For example:
Granted interval: logInterMessagePeriod=1 → expect 2 s
Allowed band: 2 s × 0.7 = 1.4 s
              2 s × 1.3 = 2.6 s
At least 90% of actual intervals land in 1.4-2.6 s.
An occasional one may fall outside, but none should exceed 4 s
(twice the period).
```

### Message-type combinations

A slave can request unicast for several message types:

```text
Common combinations:

Combination one: full synchronization (3 REQUEST TLVs)
Request: Sync + Delay_Resp + Announce (one REQUEST each)
Result: the master sends all three messages by unicast

Combination two: time synchronization only (2 REQUEST TLVs)
Request: Sync + Delay_Resp
Result: the master sends Sync and Delay_Resp by unicast
Announce stays multicast

Combination three: master discovery only (1 REQUEST TLV)
Request: Announce
Result: the master sends Announce by unicast
Sync and Delay_Resp stay multicast
```

**message_type field values** (one REQUEST asks for one message type):

```text
Request Sync:        message_type = 0x0 (linuxptp on-wire byte 0x00)
Request Delay_Resp:  message_type = 0x9 (linuxptp on-wire byte 0x90)
Request Announce:    message_type = 0xB (linuxptp on-wire byte 0xB0)
Request Pdelay_Resp: message_type = 0x3 (linuxptp on-wire byte 0x30)
```

## Unicast negotiation in practice

### A telecom operator deployment case

> The scenario and scale figures below (3 cities, 500 base stations, the 100/150/250 split) are all a **constructed case for teaching, not measured data from any operator**. They show how an engineering constraint like "multicast can't cross routing domains" pushes a design toward unicast. The magnitudes are indicative; don't copy the numbers.

**Scenario**:

A 5G network covering 3 cities, 500 base stations in total.

```text
Network topology:
City A core network
    |
    ├── City A base stations (100)
    |
City B core network (connected to city A over the IP backbone)
    |
    ├── City B base stations (150)
    |
City C core network (connected to city A over the IP backbone)
    |
    ├── City C base stations (250)
```

**The problem with multicast**:

```text
The IP backbone doesn't carry multicast traffic
City A's PTP master can't reach cities B and C over multicast
Each city would need its own master → high cost
```

**The unicast plan**:

```text
Deployment:
City A: GPS-synchronized master clock
Cities B and C: slaves, synchronized to the city A master over unicast

Unicast negotiation:
Each base station sends a REQUEST to the master when it starts up
The master grants unicast Sync/Delay_Resp/Announce
Synchronization continues
```

**Configuration example**:

```
Master configuration (IP: 10.0.0.1):
[global]
hybrid_e2e 1
inhibit_multicast_service 1
unicast_listen 1

Slave configuration (each base station):
[global]
unicast_req_duration 3600

[unicast_master_table]
table_id 1
logQueryInterval 2
UDPv4 10.0.0.1

[eth0]
unicast_master_table 1
```

### The unicast renewal mechanism

**Problem**: what happens when a grant expires?

```text
Timeline:
t=0      the slave requests, the master grants duration=300 s
t=300    the grant expires

Without renewal:
t=300    the master stops sending unicast
t=300+   the slave loses synchronization
```

**Solution**: renew ahead of time.

```text
Slave logic:
Receive the grant (duration=D)
Compute the renewal time: t_renew = D - margin (margin is implementation-defined; the standard only requires "renew before expiry")
At t_renew, send a new REQUEST

Example:
duration = 300 s
margin = 60 s
Renew at t=240 s
The new grant runs 300 s from the moment the grant message is sent
```

linuxptp renews at three-quarters of the granted duration.

**When renewal fails**:

```text
Scenario: the master denies the renewal

Slave behavior:
Try again (possibly asking for a longer interval or a shorter duration)
If it keeps failing, switch to multicast (if available)
Or switch to holdover
```

### Master clock resource management

**Challenge**: the master may receive a large number of unicast requests.

```text
Scenario (illustrative, not measured data): 500 slaves, each requesting 3 message types

Master load:
Unicast sessions: 500 × 3 = 1500
Messages sent per second:
- Announce every 2 s → 250 per second
- Sync every 0.125 s → 4000 per second (with a high rate)
- Delay_Resp on demand → possibly several thousand per second

Heavy CPU and memory pressure
```

**What the master can do**:

```text
Suggestion one: cap the number of sessions and deny new requests above the cap

Suggestion two: if the requested "interval × duration" looks unreasonable,
shorten the grant duration first rather than lowering the message rate
(that's the direction the standard gives)

Suggestion three: allocate by customer priority
High-priority customers → satisfy the request
Low-priority customers → shorten the duration or deny
```

## Unicast and security working together

### Unicast is easier to encrypt

**The challenge with multicast encryption**:

```text
Multicast encryption problems:
Several receivers share one key
Key distribution is complex (needs protocols such as GDOI)
A key leak affects every receiver
```

**The advantage of unicast encryption**:

```text
Unicast encryption:
A separate IPsec tunnel per slave
A separate key per tunnel
A key leak affects only one slave
```

**Deployment example**:

```text
Master ←→ slave A: IPsec tunnel (key K_A)
Master ←→ slave B: IPsec tunnel (key K_B)
Master ←→ slave C: IPsec tunnel (key K_C)

Good isolation, high security
```

### Auditing unicast traffic

**The audit requirement**:

Some industries require a record of all time-synchronization traffic.

```text
Finance industry requirement (illustrative; compliance rules differ by industry and this book cites no specific regulation):
Every time-synchronization message must have a clear sender and receiver
Record the timestamp and the message contents
For compliance audits and dispute resolution
```

**Unicast supports auditing naturally**:

```text
Unicast message properties:
A clear source IP and destination IP
The sender and receiver of every message can be recorded

Sample log (format illustrative; implementations differ):
2024-01-01 10:00:00.000
Master (10.0.0.1) → slave A (10.1.0.1): Sync
Master (10.0.0.1) → slave B (10.1.0.2): Sync
...
```

## Path trace: an Announce's travel log

### Why does Announce need tracing?

Announce messages travel through the PTP network, carrying the master clock's information.

**Normal propagation**:

```text
Topology: master → boundary clock A → boundary clock B → slave

Announce path:
master sends → A forwards → B forwards → slave receives

Each boundary clock adds 1 to stepsRemoved
```

**The loop problem**:

```text
Topology: A → B → C → A (a loop)

Announce propagation:
A sends → B forwards → C forwards → A receives it!

Problem:
A receives its own Announce (after going around through B and C)
stepsRemoved can keep climbing
The BMCA may make the wrong decision
```

**Why loops hurt**:

```text
Harm one: endless circulation
Announce keeps travelling around the loop
Wasted bandwidth

Harm two: BMCA errors
stepsRemoved keeps climbing
May trip the maxStepsRemoved limit
Or affect master selection

Harm three: malicious Announce
See the standard's suppression of rogue Announce messages
Stale Announce messages in a loop can disturb a healthy BMCA
```

### The PATH_TRACE TLV mechanism

**The idea**:

Have each Announce carry a "travel log" recording every boundary clock it passed.

```text
PATH_TRACE TLV format:
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x0008                         │
│ lengthField (2 bytes)                              │
│ pathSequence[]                                     │
│   - list of ClockIdentity                          │
│   - each ClockIdentity is 8 bytes                  │
└────────────────────────────────────────────────────┘
```

**How it works**:

```text
Step one: the master sends an Announce
PATH_TRACE = [master clockIdentity]

Step two: boundary clock A receives the Announce
Check whether its own clockIdentity is in PATH_TRACE
If not → append A's clockIdentity, forward
If yes → loop detected, drop

Step three: boundary clock B receives the Announce
Same check and append logic

Step four: the slave receives the Announce
PATH_TRACE = [master, A, B]
The whole propagation path is recorded
```

### Loop detection by example

**Scenario one: normal propagation**

```text
Topology:
master (ID=M) → A (ID=A) → B (ID=B) → slave (ID=S)

Announce propagation:
M sends: PATH_TRACE = [M]
A forwards: PATH_TRACE = [M, A]
B forwards: PATH_TRACE = [M, A, B]
S receives: PATH_TRACE = [M, A, B]

Normal operation
```

**Scenario two: loop detected**

```text
Topology:
A (ID=A) → B (ID=B) → C (ID=C) → A (a loop)

Announce propagation:
A sends: PATH_TRACE = [A]
B forwards: PATH_TRACE = [A, B]
C forwards: PATH_TRACE = [A, B, C]
A receives: PATH_TRACE = [A, B, C]

A checks: its own clockIdentity (A) is in PATH_TRACE
Conclusion: a loop!
Action: drop the Announce, do not forward
```

**Scenario three: a complex loop**

```text
Topology:
M → A → B → C → D → B (a loop, from D back to B)

Announce propagation:
M sends: PATH_TRACE = [M]
A forwards: PATH_TRACE = [M, A]
B forwards: PATH_TRACE = [M, A, B]
C forwards: PATH_TRACE = [M, A, B, C]
D forwards: PATH_TRACE = [M, A, B, C, D]
B receives: PATH_TRACE = [M, A, B, C, D]

B checks: its own clockIdentity (B) is in PATH_TRACE
Conclusion: a loop!
Action: drop
```

### PATH_TRACE has nothing to do with the BMCA

PATH_TRACE takes no part in the BMCA comparison; the standard only requires pathSequence to be maintained for the current parent's Announce.

**Use one: loop detection**

The main use, as described above.

**Use two: path quality assessment**

```text
PATH_TRACE length = number of boundary clocks crossed

Suppose:
Announce A: PATH_TRACE = [M, A, B] (length 3)
Announce B: PATH_TRACE = [M, C] (length 2)

That may mean:
Announce B's path is shorter, with lower delay
Operationally it's a clue for path selection and troubleshooting
```

**Use three: fault location**

```text
Scenario: the slave sees an abnormal offset

Check PATH_TRACE:
PATH_TRACE = [M, A, B, C]

Suppose C is a newly added boundary clock
C's clock may be the problem

Operations can locate the fault
```

### The path trace dataset

The standard defines the pathTraceDS dataset:

```c
struct PathTraceDS {
    Boolean enable;              // whether path trace is enabled
    ClockIdentity list[];        // the PATH_TRACE list this port sends in Announce
};
```

**Configuration example**:

```text
Boundary clock configuration:
[global]
path_trace_enabled 1

Once enabled, the boundary clock will:
- check the PATH_TRACE of every Announce it receives
- append its own clockIdentity
- forward the Announce
```

## Mixed multicast/unicast operation

### Why mix?

All-unicast is a heavy load; all-multicast has limits. Hybrid mode is the compromise. Announce stays multicast, Delay_Req and Delay_Resp go unicast, and Sync can go either way.

**The hybrid strategy**:

```
Announce: multicast
- discovers the master clock, no encryption needed
- multicast is efficient

Sync: unicast
- time synchronization needs precise control
- unicast is easier to encrypt and audit

Delay_Resp: unicast
- answers the slave's request
- it's naturally unicast
```

### Hybrid mode configuration

```
Master configuration:
[global]
hybrid_e2e           1
unicast_listen       1

Slave configuration:
[global]
unicast_req_duration 3600

[unicast_master_table]
table_id 1
logQueryInterval 2
UDPv4 10.0.0.1

[eth0]
unicast_master_table 1
```

**Effect**:

```
The slave receives:
- Announce: multicast (discovers the master clock)
- Sync/Delay_Resp: unicast (precise time synchronization)

Notes:
In LinuxPTP the slave uses [unicast_master_table] to send REQUESTs
for Sync/Announce/Delay_Resp to the masters in the table automatically;
Announce is received multicast (the default hybrid mode), while Sync
and the rest go unicast as requested.
```

## Rogue Announce suppression (IEEE 1588-2019)

Path trace cooperates with the mechanism the standard describes as **Suppression of rogue Announce messages (informative)**.

### What a rogue Announce is

> "Rogue Announce messages are PTP Announce messages that can circulate out-of-date information endlessly in a loop. These messages typically contain information used by the BMCA but characterize a Grandmaster PTP Instance that **no longer exists in the network**…"

That is, **it isn't necessarily someone attacking you**. More often the cause is this: the real master clock is gone (unplugged, demoted), but the Announce describing it keeps circling the loop with no way out. The standard is explicit: a rogue Announce can come from a fault or a spanning-tree protocol transient, or from a malicious device. The test is the same either way: **stepsRemoved climbs by one every lap**.

```text
Signs:
- stepsRemoved keeps increasing (plus one per boundary clock)
- stepsRemoved itself is a UInteger16 and can reach 65535,
  so "climbing by laps" fits the field just fine
- but the qualification limit is 255: the standard says
  an Announce with stepsRemoved ≥ 255 shall not be qualified;
  defaultDS.maxStepsRemoved can tighten the limit further
- carries stale master clock information
```

In one sentence: **"can it exceed 255" and "does it reach the BMCA table" are two different things.** The field holds 65535, but once stepsRemoved ≥ min(255, maxStepsRemoved), the message is no longer qualified and takes no part in the BMCA. 255 is the standard's last line of defense; maxStepsRemoved is how operations can move that line forward.

### Three suppression mechanisms

**Mechanism one: PRE_MASTER state**

A boundary clock waits in PRE_MASTER for a while before entering MASTER.

```text
Effect:
The wait may give looped Announce messages time to die out

Result:
The standard names two drawbacks.
"it helps but does not guarantee elimination of rogue Announce
messages, and it introduces considerable delay in reconfiguring
systems in the event of a change in the Grandmaster Clock or
topology."
So it's only an aid, and it slows reconvergence when the GM changes
```

**Mechanism two: path trace (the most effective)**

Use the PATH_TRACE TLV to detect loops and drop looped Announce messages.

```text
Effect:
The boundary clock scans pathSequence and finds its own clockIdentity
in it → loop → drop

Result:
The most effective, because "it becomes operative on the first pass
around a loop", and "does not disrupt long chains of Boundary Clocks"
(it doesn't hurt long chains).

But the standard states two preconditions you need to know in the field:
1) "all PTP Instances in a path need to accept, modify, and pass on
   the TLV for the method to work". If one device on the path
   doesn't implement the option, loop detection fails for the
   whole path;
2) if appending its own clockIdentity would push the Announce past
   the maximum frame length, it doesn't append it. The trace is cut
   short, so a loop "above a certain size" goes undetected and never
   clears.
```

**Mechanism three: the maxStepsRemoved threshold**

Set an upper limit on stepsRemoved; drop anything above it.

```text
Configuration:
defaultDS.maxStepsRemoved is optional and configurable per instance,
"need not be the same for each PTP Instance in the domain"

Behavior:
stepsRemoved ≥ min(255, maxStepsRemoved) → the Announce is not
qualified, is dropped, and takes no part in the BMCA

Example:
with maxStepsRemoved=10, an Announce that went 10 hops →
stepsRemoved=10 → dropped
```

The standard's trade-off: the hard floor of 255 "always works", but a lap adds several hops, so clearing a loop that way is slow. Tightening the limit shortens the clearing time, at the cost of possibly killing legitimate paths. So the standard gives two selection principles: **a) get rogue Announce messages in a loop cleared as fast as possible; b) don't block legitimate Announce messages from reaching other instances in the network.**

**Choosing maxStepsRemoved**:

```text
Star topology:
min(maxStepsRemoved) ≥ 9
Why: with the GM at the farthest leaf, the opposite boundary clock
sees stepsRemoved=8; qualification drops on "greater than or equal",
so the limit must be >8

Linear chain topology:
Set it from the chain length
Don't let legitimate Announce messages get killed by mistake
```

## Summary: the core points of unicast negotiation

**The four phases of unicast negotiation**:
1. REQUEST: the requester (grantee) asks for unicast
2. GRANT: the grantor grants or denies (duration=0 means deny)
3. CANCEL: either side cancels the unicast
4. ACKNOWLEDGE: confirms the cancel

**Where unicast applies**:
- networks that cross routing domains
- operator networks
- scenarios that need security auditing
- scenarios that need precise traffic control

**Where multicast applies**:
- local networks
- internal networks
- large deployments (many receivers)
- scenarios with simple configuration

**The core of path trace**:
- the PATH_TRACE TLV records the propagation path
- boundary clocks check it and append their clockIdentity
- loops are detected and looped Announce messages dropped
- it works with maxStepsRemoved to suppress rogue Announce messages
