# 2.15 When Multicast Becomes a Luxury: Unicast Negotiation and Path Trace

## Why unicast?

PTP normally uses multicast: the master sends Announce/Sync/Delay_Resp to a well-known group address, and every slave listens.

But some networks are built differently:

- Low-latency or high-reliability links where the multicast forwarding machinery is undesirable.
- Subnet topologies where multicast isn't available (e.g., routed WAN segments).
- Scaled infrastructure in which the operator wants each path explicitly granted and accounted.

For those, PTP defines unicast negotiation: a slave explicitly asks the master, per message type, to send it a unicast stream at a given rate for a given duration.

## The negotiation TLVs

Four TLVs drive unicast negotiation (standard section 16.1):

| TLV | Value | Direction |
|:---|:---|:---|
| REQUEST_UNICAST_TRANSMISSION | 0x0004 | slave → master |
| GRANT_UNICAST_TRANSMISSION | 0x0005 | master → slave |
| CANCEL_UNICAST_TRANSMISSION | 0x0006 | either |
| ACKNOWLEDGE_CANCEL_UNICAST_TRANSMISSION | 0x0007 | either |

### REQUEST_UNICAST_TRANSMISSION

```
┌────────────────────────────────────────────────────┐
│ tlvType (2)      = 0x0004                          │
│ lengthField (2)  = 6                               │
│ message_type (1)                                   │
│   - high nibble (bits 7-4): the requested type     │
│     (values match the header messageType:          │
│      SYNC=0x0, DELAY_RESP=0x9, ANNOUNCE=0xB,       │
│      PDELAY_RESP=0x3)                              │
│   - low nibble (bits 3-0): reserved                │
│ logInterMessagePeriod (1)                          │
│   - interval = 2^logInterMessagePeriod seconds     │
│ durationField (4)                                  │
│   - requested grant duration in seconds            │
└────────────────────────────────────────────────────┘
```

One REQUEST asks for one message type. To request several types, send one REQUEST per type.

### GRANT_UNICAST_TRANSMISSION

```
┌────────────────────────────────────────────────────┐
│ tlvType (2)      = 0x0005                          │
│ lengthField (2)  = 8                               │
│ message_type (1)     (as requested)                │
│ logInterMessagePeriod (1)                          │
│ durationField (4)     (0 means the request is denied)│
│ reserved (1)                                        │
│ flags (1)          bit 0 = GRANT_UNICAST_RENEWAL_INVITED│
└────────────────────────────────────────────────────┘
```

The `R` (Renewal Invited) bit tells the requestor its repeated request will likely be granted again.

### CANCEL / ACKNOWLEDGE_CANCEL

```
┌────────────────────────────────────────────────────┐
│ tlvType (2)      = 0x0006 / 0x0007                 │
│ lengthField (2)  = 2                               │
│ message_type/flags (1)                             │
│   - high nibble (bits 7-4): message type           │
│   - bit 1: G (maintainGrant)                       │
│   - bit 0: R (maintainRequest)                     │
│   - other bits: reserved                           │
│ reserved (1)                                       │
└────────────────────────────────────────────────────┘
```

- `R` (maintainRequest) TRUE means "I still need this service."
- `G` (maintainGrant) TRUE means "I will keep providing this service."
- Both FALSE means "cancel the service."

## The negotiation flow

```
Requester (slave)                 Grantor (master)
        |                                  |
        |-- Signaling (REQUEST) ---------->|
        |   message_type = Announce        |
        |   logInterMessagePeriod = 1      |
        |   durationField = 300            |
        |                                  | check:
        |                                  | - type supported?
        |                                  | - interval feasible?
        |                                  | - duration acceptable?
        |<-- Signaling (GRANT) ------------|
        |   message_type = Announce        |
        |   logInterMessagePeriod = 1      |
        |   durationField = 300            |
        |                                  |
        |<-- Announce (unicast) ----------- (for the granted duration)
```

With hybrid operation, Announce can stay multicast while Sync/Delay_Resp are unicast, or everything can go unicast.

## Message-type encoding, concretely

With the message type carried in the high nibble, the on-wire bytes are:

```
request Sync:        0x00   (SYNC = 0x0 << 4)
request Announce:    0xB0   (ANNOUNCE = 0xB << 4)
request Delay_Resp:  0x90   (DELAY_RESP = 0x9 << 4)
request Pdelay_Resp: 0x30   (PDELAY_RESP = 0x3 << 4)
```

LinuxPTP exactly matches this: it stores `message_type << 4` (unicast_client.c).

## LinuxPTP configuration

Master (reference `configs/UNICAST-MASTER.cfg`):

```ini
[global]
hybrid_e2e               1
inhibit_multicast_service 1
unicast_listen           1

[eth0]
priority1 128
priority2 128
```

Slave (reference `configs/UNICAST-SLAVE.cfg`):

```ini
[global]
unicast_req_duration 3600

[unicast_master_table]
table_id 1
logQueryInterval 2
UDPv4 192.168.1.11
UDPv4 192.168.1.22

[eth0]
unicast_master_table 1
```

Notes:
- A master advertising unicast service uses `hybrid_e2e` + `inhibit_multicast_service` + `unicast_listen`.
- In the slave's master table, `UDPv4 <address>` / `UDPv6` / `L2` are the per-master entries. (There is no `master_address` option and no `logDelayReqInterval`; the Delay_Req interval item is `logMinDelayReqInterval`.)
- `unicast_req_duration` is the requested grant duration in seconds.
- Older LinuxPTP didn't expose the master table via `GET UNICAST_MASTER_TABLE_NP`; that TLV is a 3.x feature.

## Path trace

When loop-free path verification matters, boundary clocks can append their clockIdentity to an Announce's PATH_TRACE TLV as they forward it.

```
master A:                    path = [A]
boundary clock B forwards:   path = [A, B]
boundary clock C forwards:   path = [A, B, C]
slave receives:              path = [A, B, C]  → A → B → C → slave
```

If a clock sees its own identity already in the list, a loop exists, and it drops the message.

Enabling it in LinuxPTP:

```ini
[global]
path_trace_enabled 1
maxStepsRemoved 20
```

## Summary

- Unicast negotiation replaces multicast with per-type, per-rate, per-duration unicast grants.
- REQUEST/GRANT/CANCEL/ACK carry the message type in the high nibble and flags (maintainRequest/maintainGrant) where applicable.
- LinuxPTP's master side uses `unicast_listen`; the slave side uses `unicast_master_table`.
- PATH_TRACE lets every node reconstruct the exact path, and detect loops.

Negotiation and management assume a trusted network. But PTP networks are sometimes hostile.
