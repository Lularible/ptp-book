# 2.16 Guarding the Vault of Time: PTP Security in Depth

## Why does PTP need security?

PTP was designed for benign networks, a laboratory, a factory floor, a carrier domain. But a time-stamping network is a valuable attack surface:

- Spoofing: inject a forged Announce claiming a better clock, and every slave re-disciplines to your time.
- Manipulation: alter Sync or Follow_Up timestamps; the offsets glide to wherever the attacker wants.
- Delay attacks: hold a message longer than you should; the measured path delay changes and the clock looks wrong, the single hardest attack to detect.
- Replay: replay old messages; clocks jump back to a previous time.

In a world running 5G, smart grids, and high-frequency trading off PTP, a malicious time map means dropped base stations, grid instability, and mispriced trades.

IEEE 1588-2019's answer is a multipronged approach (Annex P): several security prongs working together rather than a single mechanism.

## The prongs (Annex P)

| Prong | Mechanism | Scope |
|:---|:---|:---|
| **A** | PTP integrated security (AUTHENTICATION TLVs) | protoco-level, per message |
| **B** | External transport security (IPsec, MACsec) | protects the link/transport |
| **C** | Architecture mechanisms (redundancy, monitoring) | design-level robustness |
| **D** | Monitoring and management (intrusion detection, telemetry) | operational oversight |

Further precautions: disable unused features, whitelist/access control, secure network management, prefer two-step operation, compartmentalize.

## Prong A: the AUTHENTICATION TLV

### The TLV format (section 16.14)

```
┌────────────────────────────────────────────────────┐
│ tlvType (2)      = 0x8009                          │
│ lengthField (2)                                     │
│ SPP (1)            security parameter/policy index  │
│ secParamIndicator (1)                               │
│ keyID (4)                                           │
│ [disclosedKey (D)] [sequenceNo (S)] [RES (R)]       │
│ ICV (K) – the integrity check value                 │
└────────────────────────────────────────────────────┘

lengthField = 6 + D + S + R + K
```

The secParamIndicator bits (Table 132):

```
bit 0 : RP — RES present
bit 1 : SP — sequenceNo present
bit 2 : DP — disclosedKey present
bit 3-7: reserved
```

D, S, R, and K are even numbers of octets. For HMAC-SHA256-128 (K = 16), the minimum TLV is 4 + 6 + 16 = 26 bytes.

### Immediate vs delayed security

- Immediate security: the ICV covers the message as sent; the receiver validates on arrival. Mutable fields must be handled per policy (e.g., the correctionField may be zeroed for validation).
- Delayed security: the key is disclosed in a *later* message (TESLA-style). The receiver buffers messages until the key arrives, then validates. This survives delay attacks better but needs buffering and clock-discipline discipline.

### What the ICV covers

The ICV (typically HMAC-SHA-256 truncated to 16 bytes) covers:
1. The PTP header.
2. The message body.
3. The preceding TLVs.
4. The AUTHENTICATION TLV itself, up to (but not including) the ICV.

Mutable fields are negotiated between sender and receiver.

## Key management

The sender and receiver share security associations, each identified by:
- a Security Parameter Pointer (SPP),
- a key ID,
- associated key material and policy.

Annex P discusses both automated and manual key management, covering immediate and delayed processing, and the security association update rules.

## TESLA-style key disclosure

Delayed processing can use a one-way hash chain:

```
K_N      = fresh random
K_{N-1}  = H(K_N)
K_{N-2}  = H(K_{N-1})
...
K_0      = H(K_1)
```

Because K_i = H(K_{i+1}), knowing K_i lets you *verify* K_{i+1}, but not the reverse. The sender discloses K_0, then K_1, then K_2..., and the receiver checks messages from earlier periods once the corresponding key arrives.

## The AcceptableMaster table (17.5)

For networks that want an explicit whitelist of masters, IEEE 1588-2019 defines the acceptable master mechanism: a table of `AcceptableMaster` entries (port identity + alternate priority), and when enabled, only masters on the list qualify.

Note: LinuxPTP (both 1.9.2 and 4.x) does not implement the AcceptableMaster table or the corresponding management TLV. The configuration snippet below is a conceptual sketch, not a LinuxPTP option:

```ini
# conceptual; not implemented in LinuxPTP
[acceptableMasterTable]
acceptablePortIdentity 00-1B-19-FF-FE-00-00-01
alternatePriority1 128
```

In the 2008 edition, acceptable masters were identified by protocol address; 1588-2019 deprecates that in favor of port identity.

## Bandwidth and operations costs

- AUTHENTICATION TLV for a 16-byte ICV + base fields: minimum about 26 bytes per secured message.
- On typical Sync rates this is a modest fraction of the frame, but every message crossing a secure domain carries it.
- Delayed security needs buffering; key rotation adds management traffic.

## Prong B and beyond

- MACsec (802.1AE) authenticates (and optionally encrypts) frames at the link layer, protecting the entire frame transparently.
- IPsec authenticates (and optionally encrypts) at the IP layer, but doesn't protect the raw-L2 PTP transport.
- Architecture (Prong C): redundant masters, master-role restrictions, monitoring.
- Monitoring (Prong D): guard the grandmaster's attributes; alarm on unexpected master switches; log jump events.

## Summary

- PTP security is multipronged (Annex P prongs A-D).
- Prong A: AUTHENTICATION TLVs with ICVs, SPPs, and key IDs; immediate or delayed (TESLA-style) processing.
- Prong B: external transport security (MACsec/IPsec).
- Prongs C & D: architecture and monitoring.
- The AcceptableMaster table whitelists masters, but it's a 1588-2019 feature LinuxPTP doesn't implement.

The protocol is covered end to end. The remaining frontier is how far the art can be pushed: absolute synchronization, sub-nanosecond, across kilometers of fiber.

PTP gives you nanoseconds; White Rabbit hunts picoseconds, with DDMTD phase detection, SyncE frequency, and hardware time-of-day.
