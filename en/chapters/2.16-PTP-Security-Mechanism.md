# 2.16 Guarding the Vault of Time: PTP Security in Depth

## A hypothetical: an attacker plugs in a rogue master clock

**Suppose** a financial trading system uses PTP for time synchronization.

One day an attacker connects a device and keeps broadcasting Announce messages. It claims to be a high-accuracy GPS-synchronized clock with clockClass=6.

Its quality parameters look slightly better than the real master clock, so BMCA picks it as the new master without hesitation.

Every slave clock in the network, the trading servers included, switches to the attacker's device.

If the attacker shifts that device's time by 50 microseconds, the error is enough to reorder trades, trip the risk controls, and cause serious losses.

**What this shows**: PTP was designed on the assumption that the network is trusted. It has no built-in authentication. That's one of the core security threats PTP faces.

## A time network is a vault

If a PTP network is a financial system, **time is the money**.

What does a bank vault need?

**Layer one: walls and guards**
- Physical isolation: only authorized people get in
- PTP equivalent: VLAN isolation, firewalls, ACLs

**Layer two: identity checks**
- Before anyone enters the vault, you check their ID against the list
- PTP equivalent: acceptable master table, whitelisting

**Layer three: tamper evidence**
- The vault door has a seal that shows if someone has pried at it
- PTP equivalent: AUTHENTICATION TLV, ICV integrity checks

**Layer four: monitoring and alarms**
- Cameras inside the vault; anything unusual trips an alarm
- PTP equivalent: performance monitoring, anomaly detection

**Layer five: backup and redundancy**
- The vault has a standby system that takes over when the main one fails
- PTP equivalent: multiple master clocks, multiple domains, voting algorithms

PTP's security mechanisms are exactly that **layered defense**.

IEEE 1588-2019's security annex calls it a "multi-pronged approach". The standard's security clause is normative; the security annex is informative, and the clause points to it. Both references are legitimate. The annex groups the defenses into four prongs: A, message-level protection; B, link- and network-layer security such as MACsec or IPsec; C, architectural measures; D, performance monitoring.

## The threat landscape

### Threat one: rogue grandmaster

**Attack**:

A malicious device joins the network and sends carefully crafted Announce messages:

```text
Announce message:
clockClass = 6        // "better" than the real master clock
clockAccuracy = 0x21  // 100 ns accuracy
priority1 = 128       // a plausible priority
```

When BMCA receives this Announce, it compares the data sets:

```text
Malicious device: priority1=128, clockClass=6
Real master:      priority1=128, clockClass=7

Comparison: clockClass 6 < 7
Result: the malicious device wins
```

**Consequences**:
- Network time is wrong (off by tens of microseconds, maybe milliseconds)
- Services that depend on precise time fail
- Security holes can open up (authentication tokens may be judged expired when they are not)

**Real-world analogy**:

Picture a stranger walking into a bank with a "senior manager" badge that outranks the real manager's. The guard never checks whether the badge is genuine, so the stranger takes over the bank.

### Threat two: man-in-the-middle

**Attack**:

The attacker controls a node in the middle of the network, a switch for example, and intercepts and modifies PTP messages.

```text
Normal flow:
Master → Sync (t1=1000.000000000) → Slave

Attack flow:
Master → Sync → attacker modifies → Slave
                   ↓
            t1 changed to 999.999950000
```

The slave computes its offset from the tampered t1 and gets the wrong answer.

**Consequences**:
- Synchronization accuracy drops sharply
- BMCA decisions can be influenced (by tampering with Announce messages)
- Hard to detect (the attacker can keep the error small and controlled)

### Threat three: replay attack

**Attack**:

The attacker captures a Sync message and sends it again later.

```text
Timeline:
10:00:00.000  Master sends Sync (t1=1000.000000000)
10:00:00.001  Slave receives it, computes a normal offset
10:00:05.000  Attacker sends the same Sync again
10:00:05.001  Slave receives it, sees t1 far from local time
```

**Consequences**:
- The clock jumps
- The servo goes unstable
- Holdover may kick in

### Threat four: delay attack

**Attack**:

The attacker leaves the message contents alone and only adds delay in transit.

```text
Normal delay: 100 ns
After the attack: asymmetric delay, 100 ns out, 500 ns back
```

PTP cannot detect asymmetric delay; both E2E and P2P assume symmetry. So the slave computes a wrong offset.

**Why it's hard to see**:

This is the stealthiest attack. The attacker changes no message content, only the forwarding timing.

**Consequences**:
- A systematic time error
- It can persist for a long time without being noticed
- It is especially dangerous for high-accuracy applications such as 5G

### Threat five: denial of service

**Attack**:

The attacker floods the network with PTP messages and exhausts bandwidth or CPU.

```text
Normal Announce interval: 2 s
Attack: 1000 Announce messages per second
```

**Consequences**:
- Devices overload and cannot process real PTP traffic
- The network congests
- Synchronization stops

## PTP's built-in security mechanism

IEEE 1588-2019 defines **PTP integrated security**, built around the AUTHENTICATION TLV.

### The structure of the AUTHENTICATION TLV

```text
AUTHENTICATION TLV format:
┌────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x8009                         │
│ lengthField (2 bytes)                              │
│ SPP (1 byte) - security parameter pointer          │
│ secParamIndicator (1 byte) - optional-field flags  │
│ keyID (4 bytes) - key identifier                   │
│ disclosedKey (optional) - key revealed later       │
│ sequenceNo (optional) - not used in this version   │
│ RES (optional) - reserved                          │
│ ICV (16 bytes or more) - integrity check value     │
└────────────────────────────────────────────────────┘
```

**Fields**:

| Field | Meaning |
|:---|:---|
| **SPP** | Security Parameter Pointer, points to a security association in the SAD |
| **secParamIndicator** | Says which optional fields are present (disclosedKey, sequenceNo, RES) |
| **keyID** | Identifies the key in use |
| **disclosedKey** | The key the sender discloses in delayed security |
| **ICV** | Integrity Check Value |

The `lengthField` counts the fixed fields, the optional disclosedKey (D), sequenceNo (S), and RES (R) bytes, and the ICV (K): `lengthField = 6 + D + S + R + K`. With no optional fields and a 16-byte ICV, the TLV is 26 bytes.

### How the ICV is computed

The ICV is the heart of the whole mechanism. Here's a concrete example.

**Assumptions**:
- Key: 32 bytes, for example `0x01020304...` (32 bytes in total)
- Algorithm: HMAC-SHA256-128 (the recommended algorithm)
- PTP message: an Announce, say

**What goes into the calculation**:

The ICV covers the following, concatenated in order:

```text
1. PTP header (34 bytes)
2. Message body (the Announce body)
3. Preceding TLVs (if any)
4. The AUTHENTICATION TLV itself (excluding the ICV field)
```

**One special case**: some fields need handling before they go into the ICV.

**Mutable fields** (fields that may change in transit):

| Field | Treatment |
|:---|:---|
| correctionField | Immediate security: included normally; delayed security: set to zero |
| sourcePortIdentity | Policy may restrict it |
| domainNumber | Policy may restrict it |
| messageType | Policy may restrict it |
| portIdentity of the receiving port | Policy may restrict it |

**Steps (pseudocode)**:

```c
// Step 1: prepare the buffer for the calculation
uint8_t buffer[2048];  // large enough
int offset = 0;

// Step 2: copy the PTP header (handle mutable fields per policy)
memcpy(buffer + offset, ptp_header, 34);
offset += 34;

// Step 3: copy the message body
memcpy(buffer + offset, ptp_body, body_length);
offset += body_length;

// Step 4: copy the preceding TLVs (if any)
for (each TLV before AUTHENTICATION TLV) {
    memcpy(buffer + offset, tlv_data, tlv_length);
    offset += tlv_length;
}

// Step 5: copy the AUTHENTICATION TLV (without the ICV)
memcpy(buffer + offset, auth_tlv, auth_tlv_length - icv_length);
offset += auth_tlv_length - icv_length;

// Step 6: compute HMAC-SHA256
uint8_t hmac_result[32];
hmac_sha256(key, key_length, buffer, offset, hmac_result);

// Step 7: take the first 16 bytes as the ICV (HMAC-SHA256-128)
memcpy(icv, hmac_result, 16);
```

**Why HMAC-SHA256-128 and not full SHA256?**

Full SHA256 produces 32 bytes, but PTP needs only 128 bits (16 bytes) of security. Truncating to the first 16 bytes is standard industry practice: it keeps the security and saves bandwidth.

### The Security Policy Database (SPD) and the Security Association Database (SAD)

PTP security relies on two core databases.

**SPD (Security Policy Database)**:

It defines which messages need authentication.

```text
SPD example (illustrative; the standard does not define the SPD structure):
┌──────────────┬───────────────────┬─────────┐
│ Message type │ Requirement       │ SA used │
├──────────────┼───────────────────┼─────────┤
│ Sync         │ Must authenticate │ SA_1    │
│ Delay_Req    │ Must authenticate │ SA_1    │
│ Delay_Resp   │ Must authenticate │ SA_1    │
│ Announce     │ Must authenticate │ SA_1    │
│ Pdelay_Req   │ Must authenticate │ SA_2    │
│ Management   │ Optional          │ SA_3    │
└──────────────┴───────────────────┴─────────┘
```

**SAD (Security Association Database)**:

It stores the keys and security parameters.

```text
SAD example:
┌─────────────┬───────┬────────────────────┬─────────────┐
│ SA ID (SPP) │ keyID │ Key                │ Algorithm   │
├─────────────┼───────┼────────────────────┼─────────────┤
│ 1           │ 1001  │ 0x01... (32 bytes) │ HMAC-SHA256 │
│ 2           │ 1002  │ 0x02... (32 bytes) │ HMAC-SHA256 │
│ 3           │ 1003  │ 0x03... (32 bytes) │ HMAC-SHA256 │
└─────────────┴───────┴────────────────────┴─────────────┘
```

**The workflow**:

```text
Sender:
1. Check the SPD: does this message type need authentication?
2. If so, check the SAD: which SA applies?
3. Get the key and compute the ICV
4. Build the AUTHENTICATION TLV and append it to the message

Receiver:
1. Receive the message and check for an AUTHENTICATION TLV
2. Read the SPP, look up the key in the SAD
3. Compute the ICV and compare it with the one in the message
4. If they match, accept the message; otherwise drop it
```

### Immediate security processing

**Traits**: real-time verification, keys distributed in advance.

**Flow**:

```text
Sender                              Receiver
   |                                    |
   | 1. Look up SPD/SAD                 |
   | 2. Compute ICV                     |
   |                                    |
   |---- message + AUTH TLV ----------->|
   |                                    | 3. Read SPP
   |                                    | 4. Look up key in SAD
   |                                    | 5. Compute ICV
   |                                    | 6. Compare ICVs
   |                                    | 7. Pass or fail
```

**Advantages**:
- Real-time verification; the message is processed or dropped immediately
- Mutable fields work (correctionField can be used normally)
- Fits transparent-clock networks (a transparent clock can change correctionField)

**Drawbacks**:
- Keys must be distributed to every device in advance
- Key leakage is a risk
- Key management gets complicated on multicast

**Where it fits**:
- Boundary-clock networks
- Transparent-clock networks (E2E TC or P2P TC)
- Anything that needs real-time processing

### Delayed security processing

**Traits**: keys disclosed late, store first and verify later.

**Core idea** (from TESLA):

The sender does not publish the key up front. Instead:
1. It sends the message with its ICV
2. It waits
3. It discloses the key
4. The receiver uses that key to verify the stored message

**Flow**:

```text
Sender                              Receiver
   |                                    |
   |---- message + ICV (key K1) ------->| store, do not verify
   |                                    |
   |---- message + ICV (key K2) ------->| store, do not verify
   |                                    |
   |---- message + ICV (key K3) ------->| store, do not verify
   |                                    |
   |---- disclose key K1 -------------->| verify message 1 with K1
   |                                    |
   |---- disclose key K2 -------------->| verify message 2 with K2
   |                                    |
```

**The key point**:

The key must be disclosed late enough that the attacker cannot forge a message before it arrives.

```text
Security condition:
disclosure time > message travel time + attacker processing time
```

**Advantages**:
- Supports multicast source authentication (only the real source can produce a valid ICV)
- No long-term key for every pair of nodes; a receiver needs the chain anchor once
- Tolerates packet loss (you can skip the verification of one interval)

**Drawbacks**:
- Verification is delayed (messages cannot be processed immediately)
- Mutable fields are not supported (correctionField must be zero during verification)
- It does not suit transparent-clock networks

**Where it fits**:
- Multicast networks
- Networks without transparent clocks
- Cases where source authentication matters more than latency

linuxptp v4.4 implements this integrated security, with OpenSSL, GnuTLS, and Nettle back-ends plus a GnuPG-based variant. It's the one concrete implementation you can run today.

## External transport security

PTP integrated security is optional. Many deployments choose **external security** instead.

### MACsec (IEEE 802.1AE)

**How it works**: encryption and authentication at Layer 2, on each link.

**Advantages**:
- Fully compatible with PTP: a transparent clock can change correctionField, and MACsec doesn't care
- Every MAC frame is encrypted and authenticated
- Hardware acceleration is available

**Deployment**:

```text
Network topology:
Master → MACsec switch → transparent clock → MACsec switch → Slave

MACsec configuration:
- separate key per link
- encryption algorithm: GCM-AES-128
- authentication algorithm: built into GCM
```

**Caveat**:

MACsec needs switch support and adds deployment cost. But for high-security sites such as financial networks, it often makes the shortlist.

### IPsec

**How it works**: encryption and authentication at Layer 3.

**Two modes**:

**Mode one: no PTP clock in the middle**

```text
Master → router → ... → router → Slave

IPsec configuration:
- ESP (Encapsulating Security Payload)
- an IPsec tunnel directly between master and slave
```

**Mode two: with a boundary or transparent clock**

```text
Master → IPsec tunnel → boundary clock → IPsec tunnel → Slave

Challenge: the boundary clock has to decrypt, process, and re-encrypt.
```

**The problem**:

With IPsec tunnels, an intermediate PTP clock (a boundary clock) has to:
1. decrypt the message
2. process the PTP contents
3. re-encrypt and forward it

That adds complexity and latency.

**Workaround**:

Some deployments:
- use IPsec only at the network edge
- leave the PTP domain unencrypted and rely on physical isolation

## Architecture and monitoring

### Architectural redundancy

**Multiple master clocks**:

```text
Deployment:
Master A (GPS)   Master B (GPS)
     |                |
     └─────┬──────────┘
           |
      Boundary clock
           |
         Slave

BMCA picks the better master automatically.
If master A fails, the network switches to master B.
```

**Multiple domains**:

```text
Domain 0: Master A → slave group 1
Domain 1: Master B → slave group 2

The two domains run independently and cross-check each other.
```

**Voting algorithm**:

Used to detect delay attacks.

```text
A slave belongs to both domain 0 and domain 1:
domain 0 computes offset = +50 ns
domain 1 computes offset = +200 ns

Difference 150 ns, outside the normal range → anomaly detected
```

**How it works**:

If the attacker affects only one domain, the other gives a reference. A large difference between the two offsets suggests something is wrong.

### Performance monitoring (prong D of the multi-pronged approach)

The security annex's monitoring guidance defines these parameters, and they can detect attacks.

**What to watch**:

| Metric | Normal | Warning sign |
|:---|:---|:---|
| **offsetFromMaster** | Stable, small fluctuations | A sudden jump |
| **meanPathDelay** | Stable | A large change (delay attack) |
| **frequency drift** | No more than the local oscillator can explain | Large drift |
| **master switch count** | Rare | Frequent switching |

**Anomaly detection example**:

```python
# Monitor offset changes. The 1000 / 500 here are only illustrative thresholds, not values from the standard.
def detect_offset_anomaly(history):
    # offset should change slowly under normal conditions
    for i in range(1, len(history)):
        delta = abs(history[i] - history[i-1])
        if delta > 1000:  # sudden jump over 1 microsecond
            alert("anomaly: offset jumped")
    
    # check the trend in the mean
    mean_delay = calculate_mean(history)
    if abs(mean_delay - baseline) > 500:
        alert("anomaly: link delay changed a lot")
```

## The acceptable master table

This is the simplest security mechanism, and a very effective one.

### Data structure

```c
struct AcceptableMasterTable {
    uint16_t tableSize;           // number of entries
    AcceptableMaster table[];     // entry array
};

struct AcceptableMaster {
    PortIdentity acceptablePortIdentity;  // acceptable master port identity
    uint8_t alternatePriority1;           // replacement priority1 (optional)
};
```

### How it works

```text
Flow:
1. The administrator configures the list of acceptable masters
   for example:
   - 00-1B-19-FF-FE-00-00-01 (master A)
   - 00-1B-19-FF-FE-00-00-02 (master B)
   
2. A slave receives an Announce

3. Before BMCA runs, check whether the sender is on the list

4. If it is not:
   - it does not enter the BMCA comparison
   - the Announce is ignored

5. If it is:
   - it takes part in BMCA normally
   - if that master's alternatePriority1 is >0, it replaces the grandmasterPriority1 in the remote Announce (=0 means no effect)
```

### Where it fits

**Case one: stopping a rogue master**

The core use. Even if the attacker sends a high-quality Announce, it is ignored when it isn't on the whitelist.

This is filtering, not authentication. clockIdentity is visible on the wire, so anyone can copy a legitimate one, and a forged Announce can still win first-message-wins master selection, which is a denial-of-service surface. Real protection comes from the security mechanism.

**Case two: controlling master switches**

Configure a whitelist of several masters, and BMCA chooses only among them.

**Case three: operations**

Operators can control exactly which masters the network accepts.

### Configuration example (LinuxPTP)

> Note: the acceptable master table is an IEEE 1588 concept, and **LinuxPTP (1.9 and 4.4) does not implement these configuration keys**. What follows shows the intended semantics only; in practice you configure it on equipment that supports the feature, for example a telecom switch.

```ini
# /etc/linuxptp/ptp4l.conf (illustrative; LinuxPTP does not support this yet)

[global]
# acceptable master configuration
acceptableMasterTableEnabled 1
acceptableMasterTableSize 2

[acceptableMasterTable]
# master A
acceptablePortIdentity 00-1B-19-FF-FE-00-00-01
alternatePriority1 128

# master B
acceptablePortIdentity 00-1B-19-FF-FE-00-00-02
alternatePriority1 130
```

## Key management protocols

PTP security depends on key management. IEEE 1588-2019 gives two examples of automated key management.

### GDOI (Group Domain of Interpretation)

**RFC 6407 defines it**, for multicast key management.

**Core concepts**:

- **Group**: every device in a PTP domain
- **Key server**: generates and distributes keys
- **Group member**: a PTP device

**Workflow**:

```text
Key server              PTP device A   PTP device B
    |                       |             |
    |<- registration -------|             |
    |<- registration ---------------------|
    |                       |             |
    |---- group key push -->|             |
    |---- group key push ---------------->|
    |                       |             |
    |                       | compute ICV with the key
    |                       |---- secured PTP message -->|
    |                       |             | verify ICV
```

**Rekeying**:

The key server pushes new keys periodically. This is called "Rekey".

```text
Key lifetime:
Key A: in use for a while
Key B: takes over from key A
Key C: takes over from key B
...

When to push:
push the new key before the old one expires
every device switches over smoothly
```

**Advantages**:
- Scales to large multicast networks
- Central management, easy operations
- Automatic rekeying

**Drawbacks**:
- Needs a key server
- The key server is a single point of failure
- Fairly complex

### TESLA (Timed Efficient Stream Loss-tolerant Authentication)

**RFC 4082 defines it**, specifically for multicast source authentication.

**Core idea**:

Use a time gap to authenticate: disclose the key late.

**Key chain**:

The sender pre-generates a chain of keys:

```
Key chain (one-way hash chain; the start is a fresh random seed that stays secret, the end is the published anchor):
K_N = random seed
K_{N-1} = hash(K_N)
K_{N-2} = hash(K_{N-1})
...
K_0 = hash(K_1)

Note: K_i = hash(K_{i+1}), so someone with K_{i+1} can compute hash(K_{i+1}) = K_i and verify it,
but cannot invert K_i to get K_{i+1};
the sender discloses keys one interval at a time in the order K_0 → K_1 → K_2 ...
```

The chain is one-way: `K_{i-1} = F(K_i)`. Knowing `K_i` lets you walk backwards to `K_{i-1}`, an older key, but never forward to `K_{i+1}`, the next one. That is the whole point: a disclosed key cannot be used to forge future messages.

**Workflow**:

```
Interval   Key sent            Key verified
T0         K1 (discloses K0)   none
T1         K2 (discloses K1)   verify T0 messages with K1
T2         K3 (discloses K2)   verify T1 messages with K2
T3         K4 (discloses K3)   verify T2 messages with K3
...

Security guarantee:
A message sent in T0 uses K1 to compute its ICV.
At T0 the attacker does not know K1 and cannot forge the message.
K1 is disclosed at T1, and the receiver verifies the T0 message.
By then the attacker can no longer change it; that interval is over.
```

The key disclosed in one interval is the key from the previous interval.

**Time synchronization requirement**:

TESLA requires loose time synchronization between sender and receiver.

PTP already provides exactly that.

**Advantages**:
- Strong multicast source authentication
- No long-term key for every pair of nodes; a receiver needs the chain anchor once
- Loss tolerant (you can skip verification for one interval)

**Drawbacks**:
- Verification delay
- Mutable fields are not supported
- It depends on time synchronization

TESLA still needs a key-distribution center. That center delivers the chain anchor, and it is what makes the receiver's verification meaningful.

## Best-practice checklist

### Network-layer protection

**VLAN isolation**:
```text
Create a dedicated VLAN that carries only PTP traffic:
VLAN 100: PTP domain 0
VLAN 101: PTP domain 1

Keep all other traffic out of the PTP VLAN
```

**ACL**:
```text
Allow: PTP ports (UDP 319/320, or Ethernet type 0x88F7)
Deny: everything else
```

**Physical isolation**:
```text
High-security sites: a dedicated network, never shared with business traffic
```

### PTP-layer protection

**Enable the acceptable master table**:
```text
Configure a whitelist of every legitimate master
This is the cheapest effective defense you can deploy
```

**Enable the AUTHENTICATION TLV**:
```text
High-security sites: turn on PTP integrated security
Choose immediate security if you use transparent clocks
Choose delayed security if you only need source authentication
```

### Monitoring-layer protection

**Real-time monitoring**:
```text
Metrics:
- offsetFromMaster
- meanPathDelay
- master switch events
- (optional) message-rate counters, to spot DoS

Alarm clues (the standard gives qualitative hints only, no thresholds):
- offset takes an unexpected jump
- the correction shows a frequency drift beyond what the local oscillator can explain
- P2P link delay changes a lot
```

**Log audit**:
```text
Record everything:
- Announce reception (sender information)
- BMCA decisions
- master switch events
```

### Architecture-layer protection

**Redundant deployment**:
```text
At least two masters
Different paths (avoid shared network segments)
```

**Multi-domain verification**:
```text
Deploy two PTP domains
A slave synchronizes to both
Cross-check the results
```

## Summary: layered defense for PTP security

**Layer one: network isolation**
- VLANs, ACLs, firewalls
- Physical isolation (the strongest)

**Layer two: PTP authentication**
- Acceptable master table (whitelist)
- AUTHENTICATION TLV (ICV verification)

**Layer three: external security**
- MACsec (Layer 2)
- IPsec (Layer 3)

**Layer four: architectural redundancy**
- Multiple masters
- Multiple domains
- Voting algorithms

**Layer five: monitoring and alarms**
- Performance metrics
- Anomaly detection
- Log audit

## The cost of security

Security isn't free.

**Compute cost**:
- ICV: the algorithm is at least HMAC-SHA256-128
- This book won't give a number: it depends on whether the CPU has hardware HMAC/AES acceleration, the message rate, and whether traffic passes through a transparent clock

**Bandwidth cost**:
- AUTHENTICATION TLV: at least 26 bytes (tlvType + length 4 bytes + SPP/secParam/keyID 6 bytes + ICV 16 bytes)
- Every message gets longer
- 26 bytes is 59% of a 44-byte Sync, and 41% of a 64-byte Announce

**Complexity cost**:
- Key management: GDOI or TESLA deployment
- Configuration upkeep: SPD/SAD updates
- Training: people have to understand the mechanisms

**How to choose**:

Security level scales with cost. Match it to your threat model:

- **Low threat**: acceptable master table + VLAN isolation
- **Medium threat**: + AUTHENTICATION TLV + monitoring
- **High threat**: + MACsec + multi-domain redundancy + voting
