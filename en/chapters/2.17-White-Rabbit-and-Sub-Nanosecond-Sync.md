# 2.17 Chasing the Speed of Light: White Rabbit and Sub-Nanosecond Synchronization

## CERN's crazy requirement

Around the time the Large Hadron Collider (LHC) was built — first beam in 2008 — CERN faced a challenge that looked impossible.

The LHC is a 27-kilometer ring. It has to collide two proton beams at close to the speed of light.

For the collisions to work, the control system has to time thousands of accelerating components precisely.

**The question**: how precise is "precise"?

Proton speed: 299792458 m/s × 0.999999991 = 299792 km/s (close to the speed of light).

In one nanosecond, a proton travels: 299792 × 10^-9 = **0.3 meters**.

If the control system's timing error is 1 ns, the two beams miss each other by 0.3 m, and the collision fails completely.

**The synchronization accuracy CERN needed**: sub-nanosecond, ideally picosecond.

The mainstream time synchronization of the day:
- NTP: milliseconds
- PTP: microseconds (a few hundred nanoseconds at best)

Neither could meet the LHC's needs.

CERN's engineers decided: **build one themselves**.

---

## The birth of White Rabbit

### Starting the project

CERN started the White Rabbit project and gradually opened it up. The name comes from *Alice in Wonderland* — the white rabbit who is always on time, pocket watch in hand.

**Core goals**:
- Synchronization accuracy: sub-nanosecond (<1 ns)
- Reach: built from multiple fiber spans
- Nodes: large-scale networking
- Cost: under control (you can't put a cesium clock at every node)

### Choosing the technical path

The engineers looked at where existing PTP ran into trouble:

**Bottleneck one: software timestamping**

Traditional PTP generates timestamps in the OS kernel. Between the NIC receiving a frame and the kernel processing it, there is:
- NIC DMA delay
- PCI bus delay
- kernel interrupt handling delay
- software scheduling delay

Add those up and you get at least tens of nanoseconds — and it's unstable (jitter can reach hundreds of nanoseconds).

**The fix**: hardware timestamping, stamped directly at the PHY layer.

**Bottleneck two: frequency drift**

PTP leans on the slave's local oscillator. Even with precise hardware timestamps, if the local oscillator's frequency is off, error accumulates between two Sync messages.

Say:
- Sync interval: 2 seconds
- Local oscillator error: 100 ppm (parts per million)

Accumulated error: 2 s × 100 × 10^-6 = **200 microseconds**.

That is far past a nanosecond target.

**The fix**: physical-layer frequency synchronization (SyncE).

**Bottleneck three: phase measurement resolution**

Even with the frequency synchronized, how do you measure a nanosecond-scale phase offset?

The traditional way: a counter. The counter adds one every clock cycle.

At 125 MHz, one cycle is 8 ns, so the resolution is 8 ns.

**The fix**: a DDMTD phase detector, which pushes phase resolution into the picosecond range.

### White Rabbit's three-horse team

White Rabbit builds on PTP but adds three key enhancements:

**First horse: Synchronous Ethernet (SyncE)**
- Recovers the clock from the physical layer
- Delivers frequency synchronization and removes drift

**Second horse: the DDMTD phase detector**
- Picosecond phase measurement
- Resolution around 0.5 ps

**Third horse: precise link delay measurement**
- Measures fiber asymmetry
- Measures delays inside the equipment
- Calibrates the whole link

## First horse: Synchronous Ethernet (SyncE)

### Clock recovery in ordinary Ethernet

Ethernet is an asynchronous transport. Sender and receiver don't need to share a clock in advance.

So how does the receiver decode the data?

**The method**: recover the clock from the data signal.

The Ethernet physical layer uses special encoding (8b/10b or 64b/66b, for example) so the data signal has enough transitions for the receiver to recover the clock with a PLL.

```
Sender                     Receiver
  |                         |
  |--- data (with clock) -->|
  |                         | PLL recovers the clock
  |                         | decode data with that clock
```

### SyncE's core idea

The receiver already recovers a clock from the physical layer. Why not use that clock as the local clock?

**That's the core of SyncE**: turn Ethernet's "clock recovery" into "clock synchronization".

```
Ordinary Ethernet:
Receiver recovers clock → used only to decode data → thrown away

SyncE:
Receiver recovers clock → used to decode data → also used as the local clock reference
```

### The SyncE clock chain

```
Master clock (GPS-synced)   SyncE switch         Slave clock
     |                          |                     |
     |--- Ethernet signal ----->|                     |
     |                          | PLL recovers clock  |
     |                          | recovered clock drives the local system
     |                          |                     |
     |                          |---Ethernet signal ->|
     |                          |                     | PLL recovers clock
     |                          |                     | recovered clock drives local system
```

**Effect**:

The slave's local clock now comes straight from the master's physical-layer clock. Frequency offset is gone (zero in theory; in practice limited by PLL precision).

### SyncE vs PTP frequency synchronization

| Feature | PTP frequency sync | SyncE frequency sync |
|:---|:---|:---|
| **Method** | Messages carry frequency information; software adjusts | The physical layer passes the clock signal directly |
| **Precision** | Depends on oscillator quality, ppm | PLL precision, ppb (parts per billion) |
| **Stability** | Affected by network jitter | Physical layer, no jitter |
| **Delay** | Message processing delay | Hardware PLL delay |
| **Cost** | Software | Needs a SyncE PHY chip |

**SyncE's strengths**:

High precision, good stability, immune to network load.

**SyncE's limitation**:

It synchronizes frequency only, not phase (phase needs PTP).

That's why White Rabbit needs **SyncE + PTP**: SyncE handles frequency, PTP handles phase.

## Second horse: the DDMTD phase detector

### The trouble with ordinary phase measurement

Suppose you want to measure the phase difference between two clocks.

The simplest method: a counter.

```
Clock A: counter +1 every cycle
Clock B: counter +1 every cycle
Compare the two counter values
```

The problem: resolution is limited by the clock frequency.

**Example**:

125 MHz → one cycle is 8 ns → 8 ns resolution.

Measure a 1 ns phase difference? No chance. The counters either match (0 ns apart) or differ by one (8 ns apart).

### DDMTD's magic

DDMTD (Digital Dual-Mixer Time Difference) uses a clever trick: **turn a high-frequency phase difference into a low-frequency one, and gain resolution**.

**The principle**:

Say:
- Input clock: 125 MHz (f_in)
- An auxiliary clock slightly below it: 124.992371 MHz (f_PLL)

```
f_PLL = N/(N+1) × f_in

where N is a large integer (the example implementation uses N = 2^14 = 16384)
```

Work it out:
```
f_PLL  = 16384/16385 × 125 MHz = 124.992371 MHz
beat   = f_in − f_PLL = 125 MHz − 124.992371 MHz
       = 125 MHz/16385 ≈ 7.6289 kHz ≈ 7.63 kHz
```

That beat is the DDMTD output: **about 7.63 kHz**.

### Why does this improve resolution?

The key insight: the phase difference gets "amplified".

```
Input phase difference:  Δφ_in
Output phase difference: Δφ_out

Amplification: N+1 = 16385

Δφ_out = (N+1) × Δφ_in
```

**Example**:

Say the input phase difference is 1 ps.

```
Δφ_in = 1 ps
Δφ_out = 16385 × 1 ps = 16.385 ns
```

Measuring a 16.385 ns phase difference is much easier than measuring 1 ps.

**Working backwards**:

The standard says: the example implementation uses a counter driven by f_in (125 MHz) to measure the output phase difference x_out, so x_out's resolution is one clock period — 8 ns:
```
Input phase resolution = output phase resolution / (N+1)
                       = 8 ns / 16385
                       = 0.488251 ps
```

That's the power of DDMTD: **picosecond resolution**.

### DDMTD in hardware

```
Principle:

Clock A ──┬─── mixer 1 ───┬─── counter ─── digital processing
          │               │
Clock B ──┴─── mixer 2 ───┴

Auxiliary clock (f_PLL = N/(N+1) × f_in)
drives both mixers
```

**What the mixers do**:

A mixer compares an input clock with the auxiliary clock and produces a beat signal.

```
Mixer 1 output: (Clock A − auxiliary clock) → 7.63 kHz, phase carries Clock A
Mixer 2 output: (Clock B − auxiliary clock) → 7.63 kHz, phase carries Clock B
```

The phase difference between the two beat signals is the phase difference between Clock A and Clock B — amplified 16385 times.

### White Rabbit's actual parameters

The example implementation in the standard gives these concrete numbers (it comes from CERN's open-source White Rabbit implementation):

```
Input clock: 125 MHz
Auxiliary clock: N = 2^14 = 16384
Beat output: f_out = f_in/(N+1) ≈ 7.63 kHz
Output (coarse) phase resolution: 8 ns (one 125 MHz period)
Input phase resolution: 8 ns / 16385 = 0.488251 ps
             (the standard gives this exact value; elsewhere it says "about 0.5 ps")

Timestamp precision: ±4 ps ("the timestamping precision … is ±4 ps";
            "The measured precision is ±4 ps")
```

**±4 ps** is the timestamp precision the example implementation reaches. Note that the standard gives **precision**, not accuracy; it says only "sub-nanosecond" for synchronization **accuracy**.

## Third horse: precise link delay measurement

### Three layers of delay measurement

White Rabbit breaks delay down into components and measures each one.

**Layer one: dynamic delay**

Delay that changes at run time, such as phase shift.

```
Sources:
- phase changes inside the PHY chip
- temperature-driven delay changes
- supply voltage fluctuations

Handling:
- DDMTD measures it in real time
- dynamic correction
```

**Layer two: semi-static delay**

Fixed when the link comes up, then almost never changes.

```
Sources:
- bitslide: the delay from the PHY adjusting its receive window
- the link negotiation process

Handling:
- measured when the link comes up
- stored as a semi-static parameter
```

**Layer three: static delay**

Almost constant for the whole life of the device.

```
Sources:
- fiber length (about 5 ns per meter of fiber)
- fixed delay inside the equipment
- PCB trace delay

Handling:
- measured by calibration
- stored as a static parameter
```

### Measuring fiber asymmetry

This is White Rabbit's most critical calibration.

**The problem**:

A fiber's "outbound" and "return" delays can differ:

```
Causes:
- asymmetry in the optical transceiver
- wavelength difference (bidirectional single-fiber uses different wavelengths)
- temperature difference

Effect:
- one-way propagation delay is about 5 ns/m (1 m ≈ 5 ns, 100 m ≈ 500 ns)
- medium asymmetry is only a small part of it, about [α/(α+2)]×<meanDelay> (α is the asymmetry coefficient)
```

**White Rabbit's solution**:

Use a special optical module: **1000BASE-BX10**, bidirectional over a single fiber.

```
Wavelength assignment:
the two directions use different wavelengths
over one single-mode fiber

Asymmetry measurement:
1. Prepare two lengths of the same medium, one short and one long
2. Synchronize with each and measure the time difference of the reference signals
3. Compute the medium's relative delay coefficient α

delayAsymmetry = constantAsymmetry + [α/(α+2)] × meanDelay
```

The example implementation in the standard says:

> With 1000BASE-BX10 single-fiber bidirectional, work out α and <delayAsymmetry> from the dynamic asymmetry correction.

### The calibration procedure (informative, recommended)

The standard's calibration annex is informative: its steps are recommendations, not requirements. High-precision devices can calibrate this way.

**Calibration steps**:

**Step one: build a calibrator**

Use two identical PTP instances to build a "calibrator", or use an off-the-shelf calibrator that has already been absolutely calibrated.

```
Calibrator requirements:
- provides a reference output outside PTP (such as 1PPS)
- internal delay is constant within the required uncertainty
```

**Step two: calibrate the PTP port**

Use the calibrator to calibrate each PTP port:

```
Method:
1. First set the calibrated port's timestamp correction to a coarse value or zero
2. Synchronize the instance under test to the calibrator over a short medium
3. Measure the time difference between the two reference outputs (such as 1PPS)
4. From that, compute the port's timestamp correction parameters
```

**Step three: medium asymmetry calibration**

Measure the medium's relative delay coefficient α:

```
Method:
1. Prepare two lengths of the same medium (cableshort / cablelong)
2. Synchronize two instances over the short and long medium
3. Measure the time difference between the two reference outputs
4. Compute the relative delay coefficient α
```

**Storing the results**:

```
Store per port:
- timestampCorrectionPortDS.egressLatency / .ingressLatency: transmit/receive timestamp correction
- asymmetryCorrectionPortDS.constantAsymmetry: constant asymmetry
- asymmetryCorrectionPortDS.scaledDelayCoefficient: scaled asymmetry coefficient (α = value / 2^62)
```

## Writing physical-layer cooperation into the standard: the Layer-1 synchronization enhancement

IEEE 1588-2019 defines the normative **Layer-1 synchronization enhancement (L1Sync)**, and the example implementation above is built on it.

### Key concepts

**Coherent clocks**:

The **change** in phase offset between two clocks is bounded by a performance limit.

```
If Clock A and Clock B are coherent:
change in phase offset < performance limit (the standard gives no number)

Note: the phase offset can be a constant, as long as the change stays within the limit
```

**Tx coherent port**:

The L1 transmit clock is coherent with the Local PTP Clock.

```
Meaning:
the clock the PHY uses to transmit is sourced from the PTP clock
→ transmit timestamps are precise
```

**Rx coherent port**:

The L1 receive clock is coherent with the Local PTP Clock.

```
Meaning:
the clock the PHY recovers from the link is coherent with the PTP clock
→ receive timestamps are precise
```

**Congruent port**:

L1 frequency synchronization and PTP synchronization run in the same timing direction.

```
Meaning:
the frequency sync direction (master → slave) matches the PTP sync direction
→ avoids a frequency loop conflict
```

### The L1Sync state machine

The standard defines a state machine for L1Sync ports:

```
State sequence:

DISABLED → IDLE → LINK_ALIVE → CONFIG_MATCH → L1_SYNC_UP
```

**The states**:

| State | Meaning | Behavior |
|:---|:---|:---|
| **DISABLED** | L1Sync is off, or an L1SYNC_RESET has occurred | No L1_SYNC TLV is sent; all dynamic members return to their initial values |
| **IDLE** | L1Sync is on | Sends L1_SYNC TLV, waits for a response |
| **LINK_ALIVE** | A valid L1_SYNC TLV arrived | Checks configuration compatibility |
| **CONFIG_MATCH** | Configurations are compatible | Requests the required relationship (tx/rx coherent, congruent) |
| **L1_SYNC_UP** | The required relationship is applied | The synchronization enhancement takes effect; the accuracy gain is live |

**Transition conditions**:

```
POWERUP           → DISABLED: power-on
any state         → DISABLED: L1SyncEnabled = FALSE or L1SYNC_RESET
DISABLED → IDLE: L1SyncEnabled = TRUE (L1_SYNC_ENABLED event)
IDLE → LINK_ALIVE: LINK_OK (a valid L1_SYNC TLV arrived from the peer)
LINK_ALIVE → CONFIG_MATCH: CONFIG_OK (configurations match, txCoherentIsRequired, etc.)
CONFIG_MATCH → L1_SYNC_UP: STATE_OK (required relationship applied, indicated by the dynamic members)
L1_SYNC_UP → CONFIG_MATCH: !STATE_OK (required relationship lost)
CONFIG_MATCH → LINK_ALIVE: !CONFIG_OK (configurations no longer match)
LINK_ALIVE → IDLE: !LINK_OK (the link is no longer alive)
```

### L1_SYNC TLV format

```
L1_SYNC TLV format:
┌──────────────────────────────────────────────────────────┐
│ tlvType (2 bytes) = 0x8001                               │
│ lengthField (2 bytes)                                    │
│ bitField (1 byte):                                       │
│   - bit 0: txCoherentIsRequired                          │
│   - bit 1: rxCoherentIsRequired                          │
│   - bit 2: congruentIsRequired                           │
│   - bit 3: optParamsEnabled                              │
│ statusField (1 byte): ITC/IRC/IC coherence status bits   │
│ (optional) extension parameters                          │
└──────────────────────────────────────────────────────────┘
```

### How the L1Sync enhancement works

**The flow**:

```
Step one: the port enables L1Sync
- sends L1_SYNC TLV declaring its requirements (for example, it needs rx coherence)
- state: IDLE

Step two: the peer responds
- the peer receives the L1_SYNC TLV and checks whether it can meet the requirements
- if it can, it sends its own L1_SYNC TLV (declaring its requirements)
- state: LINK_ALIVE

Step three: configurations match
- both sides check compatibility
- state: CONFIG_MATCH

Step four: apply the relationship
- both sides configure their PLLs so the clocks are coherent
- state: L1_SYNC_UP

Effect: timestamp precision moves from nanoseconds to picoseconds
```

## The high-accuracy default profile in detail

IEEE 1588-2019 defines three default profiles. One is the **high-accuracy default profile**. Its delay mechanism is delay request-response (E2E); peer-to-peer is only an option there.

### Profile identifier

```
profileNumber  : 3
primaryVersion : 1
revisionNumber : 0
ProfileIdentifier: 00-1B-19-03-01-00
```

### Mandatory options

The profile **requires** these options:

| Option | Meaning |
|:---|:---|
| **Layer-1 synchronization enhancement** | Must implement L1Sync |
| **External configuration mechanism** | Must implement, but off (inactive) by default; once enabled, port state comes from outside, otherwise the hierarchy still follows the default BMCA |
| **Timestamp correction** | Must implement hardware delay correction |
| **Asymmetry correction** | Must implement path asymmetry correction |

### Frequency accuracy requirement

```
Frequency accuracy: within 4.6 ppm of the second defined by the master's time scale
```

Note that 4.6 ppm is far tighter than ordinary PTP's 100 ppm.

### The clock model

The high-accuracy default profile defines a special clock model:

```
Clock model:

Local PTP Clock ──────┬─── timestamping clock
                      │
                      │ (frequency sync)
                      │
L1 clock recovery ────┴─── physical-layer clock

Key points:
- Local PTP Clock and the L1 clock are frequency-synchronized
- the timestamping clock is the Local PTP Clock (there is no separate "local clock")
```

**Why design it this way?**

The traditional PTP clock model:
```
local clock ←→ Local PTP Clock ←→ timestamping clock
```

The local clock may have its own oscillator, running at a different frequency from the PTP clock, which causes drift.

The high-accuracy profile's clock model:
```
Local PTP Clock = timestamping clock
L1 clock frequency-synced → Local PTP Clock frequency
```

Frequency comes straight from the physical layer, so drift is gone.

## White Rabbit vs standard PTP

### Technical comparison

| Feature | Standard PTP (hardware timestamping) | White Rabbit |
|:---|:---|:---|
| **Frequency sync** | PTP messages | SyncE (physical layer) |
| **Phase measurement resolution** | Nanoseconds (limited by clock frequency) | Picoseconds (DDMTD) |
| **Timestamp precision** | Nanoseconds | ±4 ps |
| **Synchronization accuracy** | Sub-microsecond | Sub-nanosecond |
| **Link calibration** | Limited (hardware-dependent) | Complete (dynamic + semi-static + static) |
| **Fiber asymmetry** | Configured as a static value | Measured and calibrated dynamically |
| **Cost** | Ordinary NIC + FPGA | Dedicated WR node hardware |

### Where each applies

**Standard PTP fits**:
- 5G base stations (with a defined end-to-end time error budget)
- financial trading (with regulatory timestamp requirements)
- power systems (phasor measurement and similar)
- industrial automation

**White Rabbit fits**:
- particle accelerators
- radio telescope arrays
- scientific experiments (speed-of-light measurement, gravitational-wave detection)
- applications that need sub-nanosecond precision

### The cost difference

**Standard PTP hardware**:
- a NIC that supports hardware timestamping
- a PTP switch
- total cost: acceptable

**White Rabbit hardware**:
- a WR node (dedicated development board): open-source hardware
- WR switches
- fiber: single-fiber bidirectional, which costs more
- calibration equipment: extra cost

**The verdict**:

White Rabbit hardware doesn't necessarily cost much more than high-end PTP equipment, but deployment is more complex (calibration, special fiber).

## The key elements of sub-nanosecond synchronization

### Element one: hardware timestamping

Timestamps **must** be generated at the physical layer.

```
Where to timestamp:
best: inside the PHY chip (before the MII/RGMII interface)
next best: at the MAC layer (at the MII interface)

Precision needed:
sub-nanosecond sync: better than 1 ns resolution
picosecond precision: dedicated high-resolution phase measurement
```

### Element two: frequency synchronization

Physical-layer frequency synchronization is **required**.

```
Options:
SyncE: Ethernet physical-layer clock recovery
pros: precise, stable

Alternative:
a high-precision local oscillator (rubidium, cesium)
pros: no SyncE network needed
cons: expensive, needs periodic calibration
```

### Element three: phase measurement

High-resolution phase measurement is **required**.

```
Options:
DDMTD: picosecond resolution (White Rabbit)
pros: extreme precision

Alternative:
a high-frequency counter (a 1 GHz clock gives 1 ns resolution)
pros: simple to implement
cons: resolution is limited
```

### Element four: link calibration

Full link calibration is **required**.

```
What to calibrate:
- dynamic delay: measured in real time (DDMTD)
- semi-static delay: measured when the link comes up
- static delay: calibrated at the factory
- fiber asymmetry: measured and corrected
```

### Element five: environmental control

Environmental factors **must** be controlled.

```
Contributors:
- temperature: affects crystal frequency (typically 1 ppm/°C)
- temperature: affects fiber delay and the medium asymmetry coefficient α
- vibration: affects crystal stability
- supply noise: affects clock jitter

Countermeasures:
- oven-controlled crystal (OCXO): more stable than an ordinary crystal
- temperature-controlled room: limits temperature swings
- vibration isolation: reduces vibration
- low-noise supply: reduces supply interference
```

## Summary: the price of extreme precision

White Rabbit proved that PTP with the high-precision options can reach sub-nanosecond precision on a well-designed network.

**What does it cost?**

**Hardware cost**:
- special PHY chips (DDMTD-capable)
- FPGA implementation
- single-fiber bidirectional optics
- calibration equipment

**Deployment cost**:
- full link calibration
- environmental control
- specialist operations

**Knowledge cost**:
- understanding SyncE
- understanding DDMTD
- understanding the calibration procedure

**How to decide**:

```
If your application needs only sub-microsecond precision:
→ standard PTP + hardware timestamping is cheaper

If your application needs sub-nanosecond precision:
→ White Rabbit is the best-known publicly available option today

If your application needs femtosecond precision:
→ White Rabbit isn't enough; you need more extreme techniques (optical synchronization, for example)
```
