# 2.18 The Art of Following Rules: PTP Profiles and Conformance

## If there were no rulebook

Imagine an international football match with no shared rulebook.

**The scene**:

```
Referee A (from Europe): offside per UEFA rules
Referee B (from South America): offside per CONMEBOL rules
Player C (from Asia): thinks handling the ball is allowed (he plays beach football)
Player D (from Africa): thinks the match should run 120 minutes

What's the result?
- Constant arguments
- No way to decide who won
- The match can't go on
```

PTP has the same problem.

```
Device A (Huawei): P2P delay mechanism, Sync interval 125 ms
Device B (Cisco): E2E delay mechanism, Sync interval 1000 ms
Device C (ZTE): requires L1Sync
Device D (Nokia): requires unicast

Connect these devices together:
- A and B can't talk (different delay mechanisms)
- C thinks the network is broken (no L1Sync)
- D can't send anything (the others expect multicast)

Result: the network collapses.
```

This is why PTP needs a **profile**.

A profile is the rulebook for a PTP network. Every device has to follow the same one before anything works.

---

## What is a profile?

### Definition

**Profile**: a document a standards body writes on top of IEEE 1588-2019. It names the PTP feature set and the attribute values that suit one application.

### What it does

**Job one: constrain the options**

PTP has hundreds of optional parameters and dozens of optional features. A profile says which are required, which are optional, and which are forbidden.

```
Example: what the ITU-T G.8275.1 profile specifies

Required:
- Delay mechanism: P2P
- SyncE: required
- Clock types: ordinary clock, boundary clock

Optional:
- Unicast negotiation: optional
- Security mechanisms: optional

Forbidden:
- E2E delay mechanism: forbidden
- Transparent clock: forbidden (in the telecom access network)
```

**Job two: specify the defaults**

A profile sets the default value and the allowed range for each parameter.

```
Example: what the default profile specifies

logSyncInterval:
  Default: 0 (1 second)
  Allowed range: -1 to +1

logAnnounceInterval:
  Default: 1 (2 seconds)
  Allowed range: 0 to 4

priority1:
  Default: 128
  Allowed range: 0 to 255
```

**Job three: guarantee interoperability**

Devices that follow the same profile can talk to each other and synchronize.

```
Interoperability guarantee:

Device A (vendor X, profile P) + Device B (vendor Y, profile P)
→ they work together

Device A (profile P1) + Device B (profile P2)
→ they may not
```

### What a profile contains

A complete profile should define:

| Item | Meaning | Example |
|:---|:---|:---|
| **BMCA option** | Which BMCA version to use | the default BMCA |
| **Configuration management** | How a device is configured | management protocol or external configuration |
| **Path delay mechanism** | E2E or P2P | P2P |
| **Configurable attribute ranges** | Allowed range of each parameter | logSyncInterval: -1 to +1 |
| **Transport mechanism** | Which transport to use | UDP/IPv4, IEEE 802.3 |
| **PTP instance types** | Which clock types are allowed | OC and BC only |
| **Option requirements** | Required, optional, forbidden | L1Sync: optional |
| **Traceability uncertainty** | Time accuracy required | as the application needs |
| **Observation interval τ** | Performance measurement interval | 1.0 s |

## The main profiles in detail

### IEEE 802.1AS: time-sensitive networking (TSN)

**Body**: IEEE 802.1 Working Group

**Where it's used**: audio/video bridging, industrial automation, automotive networks

**Core traits**:

```
Required:
- Delay mechanism: P2P
- Frequency synchronization: gPTP messages (neighborRateRatio/rateRatio)
- BMCA: a custom BMCA
- Time scale: PTP timescale

Traits:
- Fast convergence (a few milliseconds)
- Redundancy support
- Sub-microsecond accuracy
```

**Profile identifier**: 00-80-C2-00-02-00

**Technical details**:

```
How 802.1AS differs from standard PTP:

1. Custom BMCA:
   Doesn't use the standard BMCA
   Uses the "Grand Master" concept
   Supports hot standby

2. Frequency synchronization:
   Carried by gPTP messages (neighborRateRatio/rateRatio)
   Physical-layer synchronization (such as SyncE) is neither required nor prohibited

3. Fast convergence:
   Uses "pDelay" instead of "delay"
   Shorter measurement intervals

4. Multiple transports:
   IEEE 802.3 (Ethernet)
   IEEE 802.11 (Wi-Fi)
   AVB (audio/video bridging)
```

**Where this applies**:

```
- Professional audio and video production
- Automotive Ethernet
- Industrial automation (high-accuracy work)
- Data center networks
```

### ITU-T G.8275.1: telecom time synchronization

**Body**: ITU-T (International Telecommunication Union)

**Where it's used**: telecom networks, 5G base stations, mobile backhaul

**Core traits**:

```
Required:
- Delay mechanism: P2P
- SyncE: required
- Time scale: PTP timescale
- Accuracy: the profile sets an end-to-end time error budget

Clock types:
- Ordinary clock (OC)
- Boundary clock (BC)
- Telecom grandmaster (Telecom Grandmaster)

Profile identifier (the value linuxptp reports): 00-19-A7-01-02-03
```

**Clock classes defined**:

```
Clock classes defined by ITU-T G.8275.1:

PRTC (Primary Reference Time Clock):
- Accuracy: set by the relevant ITU-T recommendations
- Gets time from a GNSS receiver
- The top-level clock in the network

T-GM (Telecom Grandmaster):
- Meets the PRTC requirements
- Can connect to GNSS directly
- Or synchronize from a PRTC

T-BC (Telecom Boundary Clock):
- Synchronizes from an upstream T-GM or T-BC
- Distributes time downstream
- Must support SyncE

T-TSC (Telecom Slave Clock):
- A slave clock
- Used in terminal equipment such as base stations
```

**Architecture example**:

```
A typical telecom time synchronization architecture:

GNSS satellite
   │
   ▼
PRTC/T-GM (core site)
   │
   │ SyncE + PTP
   ▼
T-BC (aggregation site)
   │
   │ SyncE + PTP
   ▼
T-BC (access site)
   │
   │ SyncE + PTP
   ▼
T-TSC (base station)

Accuracy guarantee:
Each clock class carries its share of the time error budget
The end-to-end error still has to fit the budget the profile sets
```

**Where this applies**:

```
- 5G base station synchronization (TDD needs high accuracy)
- Mobile backhaul networks
- Telecom core networks
```

### ITU-T G.8275.2: telecom time synchronization (IP layer)

How it differs from G.8275.1:

```
G.8275.1:
- Layer 2 (Ethernet)
- SyncE required
- Boundary clock mode

G.8275.2:
- Layer 3 (IP)
- SyncE not required
- Transparent clocks supported
- Can cross routers

Where each applies:
G.8275.1: inside one operator's network
G.8275.2: across operators and domains
```

### IEC 62439-3: industrial network redundancy

**Body**: IEC (International Electrotechnical Commission)

**Where it's used**: industrial automation, process control

**Core traits**:

```
Traits:
- Redundancy (PRP, HSR)
- Accuracy: microseconds
- High availability
- E2E and P2P supported

Profile identifier: defined by the implementation
```

**Redundancy mechanisms**:

```
PRP (Parallel Redundancy Protocol):
- Two networks in parallel
- Zero switchover time
- Two interfaces per device

HSR (High-availability Seamless Redundancy):
- Ring network
- Zero switchover time
- Suits substations

Relationship to PTP:
- PTP messages travel over the redundant network
- Duplicates need special handling
```

### The IEEE 1588 default profiles

IEEE 1588-2019 defines three default profiles.

**The default end-to-end profile (E2E)**

```
Traits:
- Delay mechanism: E2E
- For general-purpose networks

Configuration:
domainNumber: 0
logAnnounceInterval: 1 (2 seconds)
logSyncInterval: 0 (1 second)
priority1: 128
priority2: 128

Profile identifier: 00-1B-19-01-01-00
```

**The default peer-to-peer profile (P2P)**

```
Traits:
- Delay mechanism: P2P
- Has its own P2P-side parameters

Profile identifier: 00-1B-19-02-01-00
```

**The high-accuracy default profile (delay request-response)**

```
Traits:
- L1 synchronization enhancements required
- Must implement an external configuration mechanism (off by default)
- Timestamping correction required
- Asymmetry correction required
- Stricter limits on the clock's frequency adjustment range

Profile identifier: 00-1B-19-03-01-00

Where it applies:
- High-accuracy applications
- Implementations in the White Rabbit class
- Scientific experiments
```

## The profile identifier in detail

### Structure

A profile identifier is a 6-byte value:

```
┌──────────────────────┬────────────────────────┬──────────────────────────┐
│ OUI/CID (3 bytes)    │ profileNumber (1 byte) │ profileVersion (2 bytes) │
└──────────────────────┴────────────────────────┴──────────────────────────┘
```

**OUI/CID**:
- 3 bytes
- organizationally unique identifier
- assigned by the IEEE RA
- keeps profiles from different organizations from colliding

**profileNumber**:
- 1 byte
- the profile's number within the organization
- 0-255, assigned by the organization itself

**profileVersion**:
- 2 bytes
- the profile's version number
- primaryVersion (major) + revisionNumber (revision)

### Examples

**IEEE 802.1AS**:

```
OUI: 00-80-C2 (the IEEE 802.1 Working Group)
profileNumber: 00
profileVersion: 02-00

Full identifier: 00-80-C2-00-02-00
```

**ITU-T G.8275.1**:

```
OUI: 00-19-A7
profileNumber: 01
profileVersion: 02-03 (the value linuxptp reports)

Full identifier: 00-19-A7-01-02-03
```

**The default profiles**:

```
OUI: 00-1B-19 (IEEE 1588's own OUI)
profileNumber: 01/02/03
profileVersion: 01-00

E2E default profile: 00-1B-19-01-01-00
P2P default profile: 00-1B-19-02-01-00
High-accuracy profile: 00-1B-19-03-01-00
```

### How the profile identifier gets used

**profileIdentifier in Announce**:

```
Announce carries no profileIdentifier
To find out which profile a peer follows, you go through the management protocol below

Profiles are isolated by domainNumber and sdoId:
Domains with different sdoId never interoperate,
and there's no profile field in the message to compare
```

**profileIdentifier in the management protocol**:

```
CLOCK_DESCRIPTION returns profileIdentifier
An administrator can query a device's profile remotely
```

## Conformance requirements in detail

### The levels of conformance

```
Conformance levels:

Level one: protocol conformance
- Must meet every mandatory requirement of IEEE 1588-2019
- Optional clauses, if implemented, must meet the specification

Level two: transport conformance
- If a standard transport is used (such as UDP/IPv4)
- It must meet that transport's specification

Level three: profile conformance
- Must meet every requirement of the declared profile
- Anything the profile doesn't specify uses the default
```

### The conformance statement

A device vendor has to declare which profile the product follows.

```
Example conformance statement:

"This device conforms to IEEE 1588-2019 and follows the ITU-T G.8275.1 profile (telecom time synchronization)."

Specifically:
- It implements every function the profile requires
- Parameter ranges match the profile
- It interoperates with other devices on the same profile
```

### Conformance testing

Conformance testing checks that a device does what it declared.

**What testing covers**:

```
- The required functions
- Optional functions the device implemented
- Synchronization accuracy and convergence time
- Behavior next to other vendors' equipment
```

**Testing bodies**:

```
Independent test houses:
- Offer PTP conformance testing
- Issue test reports

Other bodies:
- National certification bodies
- Industry alliances
```

### When things don't line up

**Case one: mixed profiles**

```
Problem:
Device A follows G.8275.1 (P2P)
Device B follows the default profile (E2E)

Result:
They can't interoperate
The delay mechanisms don't match
```

**Case two: mismatched parameters**

```
Problem:
Device A: logSyncInterval = 0 (1 second)
Device B: expects logSyncInterval = -3 (125 ms)

Result:
Device B receives Sync too slowly
Synchronization accuracy drops
```

**Case three: unsupported option**

```
Problem:
The profile requires L1Sync
The device doesn't support L1Sync

Result:
It doesn't conform to the profile
It may not work properly
```

## QSDO and sdoId

### What QSDO means

**QSDO (Qualified Standards Development Organization)**.

**Qualification conditions**:

```
Condition one: multiple parties
Members come from several companies or academic/government bodies

Condition two: not dominated
No single entity controls it

Condition three: formal process
Profiles are approved by member vote or a normal operating procedure
```

### Examples of QSDOs

```
Recognized QSDOs:
- IEEE (Institute of Electrical and Electronics Engineers)
- IEC (International Electrotechnical Commission)
- ITU-T (ITU Telecommunication Standardization Sector)
- IETF (Internet Engineering Task Force)
- ANSI (American National Standards Institute)

Industry consortia (may qualify as QSDOs):
- Industry alliances
- Standards organizations
```

### sdoId allocation

**Purpose**: isolate profiles from different standards bodies.

```
sdoId allocation:

0x000: non-QSDO
- Organizations without QSDO status
- Uses the default value

0x001-0x0FF: reserved
- Not allowed, for backward compatibility

0x100: IEEE 802.1
- Time-sensitive networking

0x101-0x1FF: reserved
- Not allowed, for backward compatibility

0x200: common mean-link-delay service

0x300-0xFFC: QSDO
- Assigned to qualified standards organizations

0xFFD-0xFFE: experimental
- Experimental use

0xFFF: IEEE 1588
- The PTP Working Group
```

**How sdoId is used**:

```
sdoId in the PTP message header:

domainNumber (1 byte) + majorSdoId (high 4 bits) + minorSdoId (1 byte)

Together they form the full domain identity

Devices with different sdoId never interoperate, even with the same domainNumber
That gives profile-level isolation
```

### Applying for an sdoId

```
Application process:

Step one: confirm QSDO status
- Prepare the organization's charter
- Show multiple-party participation
- Show a formal process

Step two: apply to the IEEE RA
- Submit the application
- Wait for review

Step three: receive the allocation
- The IEEE RA assigns a unique sdoId
- Use it in the profile
```

## How to choose a profile

### Decision factors

**Factor one: the application**

```
Application map:

Telecom network (5G base station):
→ ITU-T G.8275.1 (L2) or G.8275.2 (L3)

Industrial automation (high accuracy):
→ IEEE 802.1AS or IEC 62439-3

Audio/video bridging:
→ IEEE 802.1AS

Scientific experiments (sub-nanosecond):
→ the high-accuracy default profile or White Rabbit

General purpose:
→ the default profile (E2E or P2P)
```

**Factor two: accuracy**

```
Accuracy map:

±100 ns:
→ the high-accuracy profile plus hardware support

±1 µs:
→ IEEE 802.1AS or ITU-T G.8275.1

±10 µs:
→ the default profile plus hardware timestamping

±1 ms:
→ the default profile; software timestamping is acceptable
```

**Factor three: network conditions**

```
Network conditions map:

SyncE available:
→ ITU-T G.8275.1, IEEE 802.1AS

No SyncE:
→ the default profile, ITU-T G.8275.2

Multicast available:
→ the default multicast mode

No multicast:
→ a unicast profile or unicast negotiation

Crossing routers:
→ ITU-T G.8275.2 (L3)
```

**Factor four: device capabilities**

```
Device capability map:

Supports P2P:
→ a P2P profile

E2E only:
→ an E2E profile

Supports L1Sync:
→ the high-accuracy profile

No L1Sync:
→ the standard profile
```

### The selection process

```
Profile selection decision tree:

Start
  │
  ├─ Is it a telecom network?
  │     │
  │     ├─ yes → does it have SyncE?
  │     │         │
  │     │         ├─ yes → ITU-T G.8275.1
  │     │         │
  │     │         └─ no → ITU-T G.8275.2
  │     │
  │     └─ no
  │           │
  │           ├─ industrial or audio/video?
  │           │     │
  │           │     ├─ yes → IEEE 802.1AS
  │           │     │
  │           │     └─ no
  │           │           │
  │           │           ├─ need sub-nanosecond accuracy?
  │           │           │     │
  │           │           │     ├─ yes → the high-accuracy profile
  │           │           │     │
  │           │           │     └─ no → the default profile
  │           │           │
  │           │           └─ E2E or P2P?
  │           │                 │
  │           │                 ├─ transparent clocks present → P2P
  │           │                 │
  │           │                 └─ none → E2E
```

## Version compatibility

### IEEE 1588 version history

```
Version history:

IEEE 1588-2002:
- First edition
- versionPTP = 1
- Not compatible with later editions

IEEE 1588-2008:
- Second edition
- versionPTP = 2
- Major improvements

IEEE 1588-2019:
- Third edition
- versionPTP = 2
- minorVersionPTP = 1
- Mostly compatible with 2008
```

### 2008 and 2019 compatibility

**What's compatible**:

```
Most options are compatible:
- Unicast negotiation: compatible
- Path trace: compatible
- Alternate time scales: compatible
- Timestamp correction: compatible
- Asymmetry calculation: compatible
```

**What isn't**:

```
Incompatible options:

1. Cumulative frequency transfer:
   - 2019 adds the CUMULATIVE_RATE_RATIO TLV
   - 2008 devices don't recognize it
   - Mixing them causes synchronization errors

2. PTP integrated security:
   - 2019 adds the AUTHENTICATION TLV
   - Using it breaks devices that don't use it
   - The combination of topology and security policy can cause problems
```

**What to watch out for**:

```
Warning cases:

1. Acceptable master table:
   - With transparent clocks in the path, a 2008 device may misbehave
   - Why: the transparent clock changes the source address, and 2008 matches on protocol address

2. CMLDS (common mean link delay service):
   - Mixing old and new devices may fail
   - Why: 2008 devices don't support it

3. L1 synchronization enhancements:
   - Performance is suboptimal with 2008 devices present
   - Why: 2008 devices don't support L1Sync
```

### Best practice for compatibility

```
Advice for mixing 2008 and 2019 devices:

1. Avoid incompatible options:
   - Don't use cumulative frequency transfer
   - Don't use PTP integrated security

2. Configure consistently:
   - Every device on the same profile
   - The same parameter values

3. Test it:
   - Test the mixed scenario in the lab
   - Verify synchronization accuracy

4. Write it down:
   - Record device versions
   - Record the options in use
```
