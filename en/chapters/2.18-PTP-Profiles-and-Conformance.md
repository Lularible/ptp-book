# 2.18 The Art of Following Rules: PTP Profiles and Conformance

## Why profiles?

IEEE 1588 is a toolkit, offering choices: delay mechanism (E2E or P2P), message intervals, timestamps, optional features, security... A vendor that picks its favorites may never interoperate with another vendor's implementation.

A PTP profile resolves the ambiguity: it fixes the defaults and the allowed ranges so that conforming devices interoperate.

IEEE 1588-2019's default profiles live in Annex I. Each carries a 6-octet profileIdentifier used in the clock description.

## The default profiles (Annex I)

| Profile | Annex | profileIdentifier | Delay mechanism |
|:---|:---|:---|:---|
| Delay Request-Response Default PTP Profile | I.3 | 00-1B-19-01-01-00 | E2E (delay request-response) |
| Peer-to-Peer Default PTP Profile | I.4 | 00-1B-19-02-01-00 | P2P |
| High-Accuracy Delay Request-Response Default PTP Profile | I.5 | 00-1B-19-03-01-00 | E2E + L1 sync (Annex L) |

The I.5 (high-accuracy) profile is the one that captures White Rabbit's approach: L1-based synchronization (Annex L) is required and enabled, external port configuration (17.6) is required, timestamp corrections (16.7) and link asymmetry (16.8) must be implemented, masterOnly mode is required, and profile isolation (16.5) is prohibited. Its grandmaster frequency must stay within 4.6 ppm (I.5.6.1), and it supports ±4.6 ppm of frequency adjustment.

The other default profiles impose:

```
defaultDS.domainNumber:                    default 0
portDS.logAnnounceInterval:                default 1, range 0..4
portDS.logSyncInterval:                    default 0, range −1..+1
portDS.logMinDelayReqInterval:             default 0, range 0..5
portDS.announceReceiptTimeout:             default 3, range 2..10
defaultDS.priority1 / priority2:           default 128
defaultDS.slaveOnly:                       default FALSE
τ (time observation window):               100 s
defaultDS.sdoId:                           0x000 (or the standard default)
```

Plus frequency-accuracy limits: the grandmaster's second shall deviate no more than 0.01% (100 ppm) from its timescale's second (I.3.4.1 / I.4.4.1).

## Profiles from other bodies

- IEEE 802.1AS (gPTP): profileIdentifier 00-80-C2-00-00-01, the P2P profile used for time-sensitive networking.
- ITU-T G.8275.1 / G.8275.2: telecom profiles for phase/time and frequency, using the ITU-T OUI 00-19-A7; LinuxPTP's identifiers are 00-19-A7-01-02-03 (G.8275.1) and 00-19-A7-02-01-02 (G.8275.2).
- IEC 62439-3 (industrial redundancy, PRP/HSR) uses PTP for its time synchronization.
- IEC 61588 / C37.238 (power profile) and others exist for their domains.

There are also optional mechanisms a profile may invoke: unicast negotiation (16.1), PATH_TRACE, enhanced accuracy metrics, and the AcceptableMaster table.

## profileIdentifier structure

A profileIdentifier is 6 octets:

```
[OUI/CID (3)] [profileNumber (1)] [version major (1)] [version minor (1)]
```

- The first three octets are an IEEE OUI (or a company ID).
- The fourth is the profile number.
- The last two are the profile's major/minor version, in order.

Example: 00-1B-19 01 01 00. OUI 00-1B-19, profile number 1, version 1.0 (the I.3 profile).

## sdoId: what a profile carries along

Profiles that need stronger isolation register an sdoId (12-bit). IEEE 1588-2019 Table 2 allocation:

| sdoId | Permission |
|:---|:---|
| 0x000 | 1588-2008 legacy / basic |
| 0x100 | IEEE 802.1 |
| 0x200 | Common Mean Link Delay Service |
| 0x300-0xFFC | PTP profiles from registered QSDO organizations |
| 0xFFD, 0xFFE | Experimental |
| 0xFFF | IEEE 1588 WG reserved |

Combinations of sdoId/domainNumber not listed in Table 2 are reserved.

## The version byte

The common header carries both major and minor version:

```
octet 1: minorVersionPTP (high nibble) | versionPTP (low nibble)
```

- `versionPTP` = 1 → 1588-2002.
- `versionPTP` = 2, `minorVersionPTP` = 0 → 1588-2008.
- `versionPTP` = 2, `minorVersionPTP` = 1 → 1588-2019, byte 0x12.

A profile must specify which version(s) it uses; mixing 2008 and 2019 devices in one domain needs care because the minor version and new data-set members differ.

## Conformance and interoperability

- A device claiming conformance to a profile must implement all of its required members and respect every allowed range/default.
- `descriptionPortDS.profileIdentifier` reports the implemented profile.
- Profiles may restrict (never expand) the domain-number ranges; the profileIdentifier scheme gives every profile a unique identity for interoperation.
- For a "high accuracy" claim, the I.5 profile demands the L1 sync, calibration, and asymmetry-correction plumbing, not just fancier PTP messages.

## Practical guidance

- Choose a profile before building: E2E for generality, P2P for TSN/per-link measurement, I.5 for WR-grade.
- Set priorities and intervals from the profile's table, not ad hoc.
- Verify the version byte, sdoId, and profileIdentifier in CLOCK_DESCRIPTION to catch cross-profile interference.

## Summary

- A profile fixes defaults, ranges, and options so products interoperate.
- Annex I gives the three IEEE default profiles (E2E, P2P, high-accuracy) with identifiable profileIdentifiers.
- Other bodies (802.1, ITU-T, power) add their own profiles, each with its own OUI-backed identifier.
- Version, sdoId, and profileIdentifier are the concrete tokens of profile identity on the wire.
