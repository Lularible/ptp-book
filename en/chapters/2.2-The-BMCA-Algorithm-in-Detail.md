# 2.2 Bringing the Conductor to Life: The BMCA in Detail

## A true story: who gets to be the master clock?

In 2019, a telecom operator's 5G base-station network started behaving bizarrely.

The network had 12 core switches, each with a GPS antenna, and in theory any of them could serve as a time source. The engineers' reasoning: great, if one GPS fails, the others take over. Redundant design, high reliability.

But in reality, after the network had run for a while, some base stations' time suddenly jumped, and synchronization accuracy collapsed from sub-microsecond to millisecond level. Even weirder, the jumps were random, with no pattern.

It took two months of troubleshooting to find the culprit: the master clock election.

All 12 switches were sending Announce messages, each claiming "I am the master." Downstream base stations received multiple Announces and didn't know whom to follow. Worse, some switches decided at certain moments "I'm better," switched state, then a moment later discovered "someone else is better" and switched back.

It was like an orchestra where twelve musicians all stood up saying "I'll conduct," then started deferring to each other. The ensemble collapses into chaos.

Root cause: misconfigured BMCA (Best Master Clock Algorithm).

## What is BMCA? A "democratic election" without ballots

In a PTP network, who gets to be the master clock is a central question.

If you designate it manually, two problems arise:
1. When the topology changes (say, the master fails), human intervention is required.
2. In a large network, manual configuration is impractical.

PTP's answer: let the devices choose.

That is the BMCA, an algorithm that automatically elects a master clock. Its hallmarks:
- Distributed: each device runs it independently; no central controller.
- Deterministic: identical inputs produce identical outputs.
- Self-healing: when the master fails, a new master is elected automatically.

BMCA's core idea: every device knows its own "quality," and learns everyone else's quality through Announce messages. Then everyone chooses the highest-quality device as the master.

It's as if:
- Every musician knows his own skill level.
- Every musician can hear the others play.
- Everyone automatically picks the finest player as the conductor.

## What determines the "quality" of a master clock?

BMCA compares a set of objective clock quality attributes, nothing to do with "who's most popular."

### Clock quality attributes: the master clock's "résumé"

When a PTP device sends an Announce message, it carries the following "résumé information":

#### 1. priority1: the first-priority (administrative) weight

- Type: UInteger8 (0-255)
- Meaning: the administrative priority set by the administrator.
- Rule: the smaller the value, the higher the priority.
- Purpose: lets an administrator manually influence the master election.

Example:

You have two GPS clocks: clock A and clock B. Clock A is paired with a high-accuracy rubidium clock; clock B is a plain GPS unit. You want A to be the master and B to be the backup.

You can set:
- Clock A: priority1 = 10
- Clock B: priority1 = 20

BMCA will then prefer clock A. When A fails, B takes over automatically.

Default: 128 (the middle value, neither favored nor disadvantaged).

Configuration guidance:
- Core master clock: 10-50
- Primary backup: 51-100
- Secondary backup: 101-150
- Ordinary device: 128 (default)
- Slave-only device: 200-255

#### 2. clockClass: the clock's grade (accuracy and traceability)

- Type: UInteger8 (0-255)
- Meaning: the clock's accuracy grade and traceability.
- Rule: the smaller the value, the higher the grade.
- Purpose: indicates the clock's time quality and state.

Key values explained:

| Value | Meaning | Notes |
|:---|:---|:---|
| **6** | Primary reference clock, PTP timescale | Synchronized directly to GPS/atomic clock, traceable to international standards, will never be a slave |
| **7** | Formerly class 6, lost sync, holdover | Lost GPS, but the local atomic clock is still holding time, accuracy still high |
| **13** | Application-specific time source, ARB timescale | Uses a dedicated time source (e.g., a lab internal clock), not traceable |
| **14** | Formerly class 13, lost sync, holdover | Lost the external signal, holding locally |
| **52** | Degradation alternative A (downgraded from class 7) | Formerly class 7, but holdover has exceeded specification; can no longer be master |
| **58** | Degradation alternative A (downgraded from class 14) | Formerly class 14, but holdover exceeded; can no longer be master |
| **187** | Degradation alternative B (from class 7, slave-capable) | Lost sync, may become a slave |
| **193** | Degradation alternative B (from class 14, slave-capable) | Lost sync, may become a slave |
| **248** | Default | The default class when nothing else is specified |
| **255** | Slave-only | This device will never become a master |

Key rules:

clockClass < 128: the device considers itself accurate enough and should not become a slave.

clockClass ≥ 128: the device may become a slave, or a master (if nothing better exists).

Typical scenarios:

Scenario 1: a core equipment room

A telecom core room has one high-accuracy clock, connected to both GPS and a rubidium clock.

Normal state:
- Receiving GPS, clockClass = 6.
- Highest priority, becomes the master.

GPS signal lost, but the rubidium clock keeps working:
- clockClass changes from 6 to 7.
- Still able to be master, but accuracy drops slightly.

Rubidium drift exceeds specification:
- clockClass changes from 7 to 52.
- Should no longer be master; yield to the backup clock.

Scenario 2: a slave device

A 5G base station need not provide time to anyone; it only needs to sync from an upstream clock.

Configuration: clockClass = 255, slaveOnly = TRUE.

This base station will never become a master.

#### 3. clockAccuracy: clock accuracy

- Type: Enumeration8
- Meaning: expected accuracy when acting as a master.
- Rule: the smaller the value, the higher the accuracy.

Key values:

| Value (hex) | Accuracy | Typical device |
|:---|:---|:---|
| **0x17** | ≤ 1 ps | Optical clock, lab equipment |
| **0x1B** | ≤ 100 ps | High-end scientific instruments |
| **0x1E** | ≤ 2.5 ns | White Rabbit |
| **0x20** | ≤ 25 ns | Carrier-grade master clock |
| **0x22** | ≤ 250 ns | Industrial master clock |
| **0x23** | ≤ 1 µs | Ordinary GPS clock |
| **0x24** | ≤ 2.5 µs | Ordinary crystal oscillator (XO) |
| **0x25** | ≤ 10 µs | Oven-controlled crystal oscillator (OCXO) |
| **0x26** | ≤ 25 µs | Standard crystal oscillator |
| **0x27** | ≤ 100 µs | Low-end crystal oscillator |
| **0x28** | ≤ 250 µs | Uncompensated crystal oscillator |
| **0x29** | ≤ 1 ms | Internal oscillator |
| **0x2A** | ≤ 2.5 ms | Internal oscillator |
| **0x2B** | ≤ 10 ms | Internal oscillator |
| **0x2C** | > 10 ms | Unknown accuracy |
| **0xFE** | Unknown | Cannot determine accuracy |
| **0xFF** | Reserved |: |

The range is wide because PTP must support everything from "extreme precision" to "good enough."

Research: particle accelerators, radio telescopes need picosecond sync. Using atomic/optical clocks, clockAccuracy = 0x17.

Telecom: 5G base stations and core networks need nanosecond sync. Using GPS + rubidium, clockAccuracy = 0x20.

Industry: automation and robot coordination need microsecond sync. Using GPS + TCXO, clockAccuracy = 0x24.

IoT: sensor networks are fine with milliseconds. Using internal oscillators, clockAccuracy = 0x29.

#### 4. offsetScaledLogVariance: clock stability

- Type: UInteger16
- Meaning: a measure of clock frequency stability (based on the Allan variance).
- Rule: the smaller the value, the better the stability.

A quick intro to the Allan variance:

The Allan variance is a statistic for measuring oscillator frequency stability. In short, it answers: if I measure an oscillator's frequency at two different moments, how much do the readings differ?

PTP represents stability as a log-scaled Allan variance:

1. Measure the oscillator's Allan variance (units: s²).
2. Take its base-2 logarithm.
3. Multiply by 256 (scaling).
4. Add 0x8000 (convert to an unsigned integer).

Example:

A typical quartz crystal's Allan variance is about 10⁻¹⁸ s² (for a 1-second observation window).

log₂(10⁻¹⁸) ≈ −60

Scaled: −60 × 256 = −15360

Converted to unsigned: −15360 + 32768 = 17408 (0x4400)

Key point:

This value need not be set by hand. The device computes it automatically from its local oscillator's specification.

For most applications, engineers need not deeply understand the Allan variance, just know: this is an objective, mathematically rigorous measure of stability.

#### 5. priority2: the second-priority tie-breaker

- Type: UInteger8 (0-255)
- Meaning: used to break ties when all other attributes are equal.
- Rule: the smaller the value, the higher the priority.

Purpose:

When two devices have the same priority1, clockClass, clockAccuracy, and offsetScaledLogVariance, priority2 decides.

If priority2 is also equal, the clockIdentity decides.

Typical scenario:

You have two identical GPS clocks, both paired with identical rubidium oscillators, same priority1, clockClass, clockAccuracy, offsetScaledLogVariance.

You want clock A to be the master and clock B the backup.

Configuration:
- Clock A: priority1 = 10, priority2 = 10
- Clock B: priority1 = 10, priority2 = 20

Clock A will then be preferred. When A fails, B takes over.

#### 6. stepsRemoved: hops to the grandmaster

- Type: UInteger16
- Meaning: number of boundary-clock hops from the current device to the Grandmaster.
- Rule: the smaller the value, the closer to the master.

How it works:

- The Grandmaster itself: stepsRemoved = 0
- A slave directly attached to the Grandmaster: stepsRemoved = 1
- The next level down: 2
- And so on.

Purpose:

When two devices have the same grandmaster (same grandmasterIdentity), stepsRemoved determines who is closer to the master. The one closer to the master is preferred as the local master.

Preventing infinite propagation:

stepsRemoved has an upper limit: 255.

When a device receives an Announce with stepsRemoved ≥ 255, it drops it. This prevents Announce messages from propagating forever (e.g., through a loop).

## The BMCA algorithm: three steps to elect a master

The BMCA has three steps:

### Step 1: collect candidates (dataset comparison)

Each PTP port maintains a foreignMasterList.

When a port receives an Announce:
1. Validate the message (not sent by itself, stepsRemoved < 255, etc.).
2. Add the master's information to the foreignMasterList.
3. Within a time window (4 announceIntervals by default), require at least 2 Announces from the same master before considering it valid.

At least two are required to avoid phantom masters. If a faulty device happens to send one bad Announce, believing it from a single message could cause frequent master switching. Receiving two or more shows the master is working stably.

### Step 2: pick the best candidate (the Ebest computation)

Each PTP port picks its local best master (Ebest) from the foreignMasterList.

The election rule compares attributes in this order; the first tie-breaker to differ wins.

The comparison flow (dataset comparison algorithm):

```
compare priority1
  ↓
compare clockClass
  ↓
compare clockAccuracy
  ↓
compare offsetScaledLogVariance
  ↓
compare priority2
  ↓
compare stepsRemoved (only when grandmasterIdentity is the same)
  ↓
compare clockIdentity (final tie-breaker)
```

Example:

Devices A and B both send Announces; compare their attributes:

| Attribute | Device A | Device B | Result |
|:---|:---|:---|:---|
| priority1 | 10 | 10 | tie |
| clockClass | 6 | 7 | **A wins** |

Result: device A becomes the Ebest.

Note: once an attribute decides the winner, later attributes are not compared.

### Step 3: decide port states (the state decision)

The whole PTP instance (not each port) picks the global best master from all ports' Ebests.

Then, based on that global best master, it decides each port's state.

The state-decision algorithm:

```
Who is the global best master?
  │
  ├── Case 1: I myself am the best
  │     │
  │     └── I become the master
  │           all ports enter MASTER state
  │
  └── Case 2: someone else (Ebest) is better
        │
        └── I am not the master
              │
              ├── for each port:
              │     is this port's Ebest the global best?
              │       │
              │       ├── Yes: this port enters SLAVE
              │       │     (sync from the best master)
              │       │
              │       └── No: this port enters PASSIVE
              │             (neither master nor slave; pruned)
              │
              └── special case: clockClass < 128
                     even if others are better, may force itself master
```

The state decision codes:

The PTP standard defines six state decision codes:

| Code | Meaning | Notes |
|:---|:---|:---|
| **M1** | Become MASTER | clockClass 1-127, quality good enough |
| **M2** | Become MASTER | clockClass ≥ 128, but nothing better exists |
| **M3** | Become MASTER | a MASTER port on a non-master device |
| **S1** | Become SLAVE | sync from the best master |
| **P1** | Become PASSIVE | passive port on a clockClass 1-127 device (pruning) |
| **P2** | Become PASSIVE | passive port on a clockClass ≥ 128 device (pruning) |

## A complete BMCA election example

A full example shows how the BMCA works.

Topology:

```
Device A (GPS+rubidium) ---+
                            |
Device B (GPS+rubidium) ---+--- BC C --- Device D (ordinary clock)
                            |
Device E (ordinary clock) --+
```

Device attributes:

| Device | priority1 | clockClass | clockAccuracy | priority2 | clockIdentity |
|:---|:---|:---|:---|:---|:---|
| A | 10 | 6 | 0x20 | 10 | 00-1B-19-00-00-00-00-01 |
| B | 10 | 6 | 0x20 | 20 | 00-1B-19-00-00-00-00-02 |
| C | 128 | 248 | 0xFE | 128 | 00-1B-19-00-00-00-00-03 |
| D | 128 | 255 | 0xFE | 128 | 00-1B-19-00-00-00-00-04 |
| E | 128 | 248 | 0xFE | 128 | 00-1B-19-00-00-00-00-05 |

The election:

Step 1: BC C receives Announces from A, B, and E.

Step 2: compare A and B (both clockClass 6, both priority1 10):
- priority1: tie
- clockClass: tie
- clockAccuracy: tie
- priority2: A is 10, B is 20 → A wins

Step 3: compare A and E:
- priority1: A is 10, E is 128 → A wins

Step 4: BC C sets Ebest = device A.

Step 5: BC C's port states:
- Port 1 (connected to A/B/E): Ebest = A, enters SLAVE
- Port 2 (connected to D): enters MASTER, becomes D's master

Step 6: Device D receives BC C's Announces, determines C is the best master, enters SLAVE.

Final result:

- Grandmaster: device A (GPS+rubidium, clockClass=6)
- Master Clock (for device D): BC C
- Slaves: BC C (syncs from A), device D (syncs from C), device E (syncs from A)

If device A fails:

1. BC C stops receiving A's Announces.
2. After the timeout (announceReceiptTimeout × announceInterval), BC C re-runs BMCA.
3. Now the candidates are only B and E.
4. Compare B and E: B's clockClass=6, E's = 248 → B wins.
5. Port 1 of BC C switches to SLAVE and syncs from B.
6. The whole network transparently switches to the new grandmaster (device B).

Switchover speed depends on two defaults:

- Default announceInterval: 2 s (logAnnounceInterval=1 → interval = 2¹ = 2 s)
- Default announceReceiptTimeout: 3
- Timeout: 3 × 2 = 6 seconds

After device A fails, within at most 6 seconds the network switches to device B.

## BMCA's key design principles

### 1. Atomicity

After computing all ports' recommended states, update all port states atomically.

Atomicity matters because if port 1 updates to SLAVE before port 2 updates to MASTER, the whole PTP instance is momentarily inconsistent.

PTP requires: compute all recommended states → update all port states in one step → no interruption in between.

### 2. Symmetry

If two devices receive each other's Announces, they derive the same master-slave relationship.

BMCA is deterministic: same input, same output.

Example:

Devices A and B send Announces to each other. Both run BMCA; both discover A is better. Then:
- A decides: I am MASTER.
- B decides: I am SLAVE (sync from A).

Both sides agree, no "we both think we're master" conflict.

### 3. Fast convergence

BMCA is designed to converge quickly. On a stable network, the master is typically elected within one announceInterval.

Factors affecting convergence time:

- announceInterval
- announceReceiptTimeout
- Network size (number of devices)
- Topology depth

Optimization suggestions:

For scenarios needing fast switching (e.g., telecom), you can:
- Reduce logAnnounceInterval (e.g., 0 → −1, interval from 1 s to 0.5 s).
- But don't set it too small, it increases traffic and CPU load.

## BMCA's pitfalls and best practices

### Pitfall 1: many devices with equal priority

Problem:

Ten devices in the network all use the default configuration: priority1=128, priority2=128.

Result: BMCA falls back to clockIdentity, and the device with the smallest clockIdentity becomes master. That could be an unexpected device.

Solution:

Give the core master devices a lower priority1 (e.g., 10-50), explicitly designating master priority.

### Pitfall 2: forgetting slaveOnly

Problem:

An end device (e.g., a workstation) doesn't need to provide time to others, but slaveOnly=TRUE (or clockClass=255) was forgotten.

Result: if this device mistakenly believes it's the best (say, the master fails), it switches to MASTER and broadcasts time signals, possibly disturbing other devices.

Solution:

For pure slave devices, set:
- slaveOnly = TRUE
- or clockClass = 255

### Pitfall 3: path asymmetry from transparent clocks

Problem:

BMCA assumes Announce propagation paths are symmetric. If the network contains many transparent clocks with asymmetric delay, BMCA decisions can become inconsistent.

Solution:

- Use boundary clocks instead of transparent clocks (boundary clocks terminate and regenerate Announces).
- Or use the PATH_TRACE TLV (the option in 16.2) to detect loops.

### Pitfall 4: unreasonable announce timeout

Problem:

- Timeout too small (e.g., announceReceiptTimeout=2): ordinary packet loss triggers switching, causing frequent master flapping.
- Timeout too large (e.g., announceReceiptTimeout=10): after a master failure, switching takes too long.

Solution:

Choose the timeout to fit network reliability:
- Reliable networks (wired, dedicated): 2-3
- Typical networks (wired, shared): 3-5
- Unreliable networks (wireless, interference): 5-10

## Summary: BMCA's core points

BMCA is one of the most elegant algorithms in PTP. Its rules deliver:
- Automatic election: no human intervention.
- Fast convergence: election completes in seconds.
- Self-healing: automatic switchover when the master fails.
- Determinism: identical inputs, identical outputs.

Key attribute comparison order:

```
priority1 → clockClass → clockAccuracy → offsetScaledLogVariance → priority2 → clockIdentity
```

State decision rules:
- I am the best → MASTER
- Someone else is better, and this port is the best → SLAVE
- Someone else is better, but this port isn't the best → PASSIVE

Best practices:
- Give core master devices a lower priority1.
- Set slaveOnly=TRUE on pure slaves.
- Choose announceReceiptTimeout sensibly.
- Use boundary clocks to isolate network regions.

Master election is settled.
