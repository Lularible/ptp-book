# 2.4 The Memory of a Time Machine: A Full Look at PTP Data Sets

## If a PTP device had a brain, where would its memory live?

A PTP device has to remember several things.

It remembers:
- Who I am (clockIdentity)
- What state I'm in (MASTER or SLAVE)
- Who my master is (grandmasterIdentity)
- How far I am from my master (offsetFromMaster)
- How often I should send Sync (logSyncInterval)

This information lives in data sets.

PTP data sets are like the device's "memory bank," storing all the state information the protocol needs to run.

## The three kinds of data-set memory

Data-set members fall into three classes.

### Static members: decided at the factory, never change

Definition: determined when the device is designed; they don't change during operation.

Characteristics:
- Usually bound to hardware.
- Require no runtime computation.
- Are never modified by the protocol.

Typical examples:
- `clockIdentity`: the device's unique identity, determined by hardware.
- `numberPorts`: how many PTP ports the device has, determined by hardware.

Analogy: like your DNA, decided at birth, never changes.

### Dynamic members: auto-updated as the protocol runs

Definition: updated automatically during protocol operation, based on received messages or measurement results.

Characteristics:
- Change in real time.
- Need no human intervention.
- Controlled by the protocol's algorithms.

Typical examples:
- `offsetFromMaster`: the slave's offset from the master, updated after every synchronization.
- `portState`: the port's current state, decided by the BMCA.
- `meanDelay`: the average path delay, updated after every measurement.

Analogy: like your heart rate, adjusts automatically to your body's condition, with no effort from you.

### Configurable members: an administrator can change them

Definition: modifiable through a management interface (SNMP, NETCONF, CLI, etc.).

Characteristics:
- Require the administrator to set them actively.
- Usually have defaults.
- May change at runtime (if the administrator reconfigures).

Typical examples:
- `priority1`, `priority2`: BMCA priorities, adjustable by the administrator.
- `domainNumber`: the domain number, settable by the administrator.
- `logSyncInterval`: the Sync interval, adjustable by the administrator.

Analogy: like your haircut, you decide how to cut it, and you can change it any time.

## A detailed look at the core data sets

PTP defines several data sets, each responsible for one class of information.

### 1. defaultDS: the default data set

Role: stores the PTP instance's identity and global configuration.

Scope: one per PTP instance.

#### Key members in detail

##### 1. clockIdentity: who I am

- Type: ClockIdentity (8 bytes)
- Classification: static
- Meaning: the PTP instance's unique identifier
- Generation: based on a MAC address, EUI-64, or other unique identifier

clockIdentity matters in three scenarios.

Scenario 1: BMCA tie-breaking

When two devices are equal in every priority attribute, BMCA compares clockIdentity. The smaller one wins.

Scenario 2: loop detection

When a boundary clock forwards an Announce, it can record the list of clockIdentities it traversed in a PATH_TRACE TLV. If a boundary clock finds its own clockIdentity already in the list, a loop has formed.

Scenario 3: diagnosis

An administrator can quickly locate a faulty device by clockIdentity.

##### 2. numberPorts: how many ports do I have?

- Type: UInteger16
- Classification: static
- Meaning: the number of ports of the PTP instance
- Values:
  - Ordinary clock: 1
  - Boundary clock: ≥2
  - Transparent clock: ≥1

numberPorts matters because in the management protocol an administrator needs to know how many ports a device has, in order to query the state of each.

##### 3. clockQuality: how good is my clock?

- Type: a structure (clockClass + clockAccuracy + offsetScaledLogVariance)
- Classification: dynamic
- Meaning: the clock's quality metrics

clockQuality's three members:

clockClass:
- The clock's grade, indicating its accuracy and traceability.
- The smaller the value, the higher the grade.
- Key values: 6 (primary reference), 7 (holdover), 248 (default), 255 (slave-only).

clockAccuracy:
- The clock's expected accuracy.
- The smaller the value, the better.
- Key values: 0x20 (≤25 ns), 0x22 (≤250 ns), 0x23 (≤1 µs).

offsetScaledLogVariance:
- Clock stability, based on the Allan variance.
- The smaller the value, the better the stability.

clockQuality changes with the clock's condition.

Normal state:
- Device connected to GPS, clockClass = 6.
- clockAccuracy set from GPS accuracy, e.g., 0x20.

GPS lost, but a local atomic clock holds time:
- clockClass changes from 6 to 7.
- clockAccuracy may degrade slightly.

Local clock drift exceeds specification:
- clockClass changes from 7 to 52.
- The device is no longer fit to be a master.

##### 4. priority1 and priority2: my priority

- Type: UInteger8 (0-255)
- Classification: configurable
- Meaning: the BMCA election priority
- Rule: the smaller the value, the higher the priority

priority1 vs. priority2:

- priority1: the primary priority, typically distinguishing devices of different "tiers."
- priority2: the secondary priority, typically distinguishing devices within the same "tier."

Configuration strategy:

| Device type | Recommended priority1 | Recommended priority2 |
|:---|:---|:---|
| Core master (GPS + atomic clock) | 10 | 10 |
| Primary backup (GPS + rubidium) | 20 | 10-20 |
| Secondary backup (GPS + TCXO) | 30 | 10-30 |
| Ordinary device | 128 | 128 |
| Slave-only device | 200-255 | 128 |

##### 5. domainNumber: my domain

- Type: UInteger8 (0-255)
- Classification: configurable
- Meaning: the domain number of the PTP instance
- Default: 0

##### 6. slaveOnly: can I only be a slave?

- Type: Boolean
- Classification: configurable
- Meaning: whether the PTP instance can only act as a slave
- Values:
  - TRUE: can never become a master
  - FALSE: may become a master

slaveOnly=TRUE suits these devices:

- End devices (workstations, servers)
- Devices that don't provide time to others
- Devices that only need to synchronize, not be synchronized by

Note: when slaveOnly=TRUE, clockClass must be set to 255.

##### 7. sdoId: my profile

- Type: UInteger16 (low 12 bits valid, 0-4095)
- Classification: configurable
- Meaning: identifies the profile used by the PTP instance
- Default: 0x000

### 2. currentDS: the current data set

Role: stores the PTP instance's current synchronization status.

Scope: one per PTP instance.

#### Key members in detail

##### 1. stepsRemoved: how far am I from the grandmaster?

- Type: UInteger16
- Classification: dynamic
- Meaning: the number of boundary-clock hops to the Grandmaster
- Values:
  - The Grandmaster: 0
  - A slave directly attached to the Grandmaster: 1
  - One level farther: 2
  - And so on.

It is updated as follows:

I'm a master (M1/M2 decision):
- stepsRemoved = 0

I'm a slave (S1 decision):
- stepsRemoved = Ebest.stepsRemoved + 1

Example:

```
Grandmaster A (stepsRemoved = 0)
    ↓
Boundary Clock B (stepsRemoved = 1)
    ↓
Boundary Clock C (stepsRemoved = 2)
    ↓
Slave Clock D (stepsRemoved = 3)
```

What stepsRemoved does:

Purpose 1: BMCA decisions

When two devices share the same grandmasterIdentity, compare stepsRemoved. The smaller one wins.

Purpose 2: prevent unbounded propagation

When stepsRemoved ≥ 255, drop the Announce, preventing loop-induced infinite propagation.

##### 2. offsetFromMaster: how far am I from the master?

- Type: TimeInterval (unit: 2⁻¹⁶ ns internally, ≈15.26 fs resolution)
- Classification: dynamic
- Meaning: slave time − master time
- Values:
  - Positive: the slave is ahead of the master
  - Negative: the slave is behind the master
  - Zero: fully synchronized

The offsetFromMaster formula, derived in section 1.4, is:

```
offsetFromMaster = t₂ − originTimestamp − meanDelay − correctionField
```

Where:
- t₂: the Sync receive timestamp
- originTimestamp: the Sync send timestamp
- meanDelay: the average path delay
- correctionField: the sum of various corrections

What offsetFromMaster does:

Purpose 1: phase correction

The slave adjusts its time based on offsetFromMaster. If offsetFromMaster = +1 µs, the slave is 1 µs fast and must subtract 1 µs.

Purpose 2: sync-quality monitoring

The administrator can watch offsetFromMaster to judge sync quality. Violent fluctuation suggests an unstable network or a faulty clock.

##### 3. meanDelay: the average delay

- Type: TimeInterval (2⁻¹⁶ ns)
- Classification: dynamic
- Meaning: the average path delay or average link delay
- Depends on the delay mechanism:
  - E2E: meanDelay = meanPathDelay (end-to-end path delay)
  - P2P: meanDelay = meanLinkDelay (peer link delay)
  - No delay mechanism: meanDelay = 0

The meanPathDelay formula, derived in section 1.4, is:

```
meanPathDelay = [(t₂ − t₁) + (t₄ − t₃)] / 2
```

Where:
- t₁: the Sync send timestamp
- t₂: the Sync receive timestamp
- t₃: the Delay_Req send timestamp
- t₄: the Delay_Req receive timestamp

### 3. parentDS: the parent data set

Role: stores information about the parent PTP instance (the upstream master).

Scope: one per PTP instance.

#### Key members in detail

##### 1. parentPortIdentity: who is my superior?

- Type: PortIdentity (clockIdentity + portNumber)
- Classification: dynamic
- Meaning: the parent clock's port identity

Example:

If a slave receives time from boundary clock B's port 2, then:
- parentPortIdentity.clockIdentity = B's clockIdentity
- parentPortIdentity.portNumber = 2

##### 2. grandmasterIdentity: who is the ultimate master?

- Type: ClockIdentity (8 bytes)
- Classification: dynamic
- Meaning: the Grandmaster's identity

parentPortIdentity vs. grandmasterIdentity:

```
Grandmaster A
    ↓
Boundary Clock B (port 2)
    ↓
Slave Clock C
```

For slave clock C:
- parentPortIdentity = the identity of B's port 2
- grandmasterIdentity = A's clockIdentity

##### 3. grandmasterClockQuality: the grandmaster's quality

- Type: a structure (clockClass + clockAccuracy + offsetScaledLogVariance)
- Classification: dynamic
- Meaning: the Grandmaster's clock quality

The slave needs to know the Grandmaster's quality so it can propagate it downstream in its own Announces.

##### 4. grandmasterPriority1 and grandmasterPriority2

- Type: UInteger8
- Classification: dynamic
- Meaning: the Grandmaster's BMCA priorities

### 4. timePropertiesDS: the time properties data set

Role: stores the timescale and traceability information.

Scope: one per PTP instance.

#### Key members in detail

##### 1. currentUtcOffset: TAI minus UTC

- Type: Integer16
- Classification: dynamic (configurable at the master)
- Meaning: the current value of TAI − UTC
- As of 2026: 37 seconds

It is updated as follows:

- Master: extracted from GPS signals, or set manually.
- Slave: obtained from Announce messages, or set manually.

##### 2. currentUtcOffsetValid: is the UTC offset valid?

- Type: Boolean
- Classification: dynamic
- Meaning: whether currentUtcOffset is valid
- Values:
  - TRUE: valid
  - FALSE: invalid, should not be used

It is FALSE when:

- The master loses GPS and cannot obtain the latest leap-second information.
- The master's time source is unreliable.

##### 3. leap59 and leap61: leap-second notices

- Type: Boolean
- Classification: dynamic
- Meaning:
  - leap59=TRUE: the last minute of the month will have 59 seconds (a negative leap second)
  - leap61=TRUE: the last minute of the month will have 61 seconds (a positive leap second)

Note: leap59 and leap61 cannot both be TRUE.

##### 4. ptpTimescale: which timescale?

- Type: Boolean
- Classification: dynamic (configurable at the master)
- Meaning:
  - TRUE: the PTP timescale (TAI)
  - FALSE: the ARB timescale

##### 5. timeTraceable: is the time traceable?

- Type: Boolean
- Classification: dynamic
- Meaning: whether the time is traceable to international standards

##### 6. frequencyTraceable: is the frequency traceable?

- Type: Boolean
- Classification: dynamic
- Meaning: whether the frequency is traceable to international standards

##### 7. timeSource: the type of time source

- Type: Enumeration8
- Classification: dynamic
- Meaning: the type of source the master clock's time comes from
- Typical values:
  - 0x20: GNSS (GPS, etc.)
  - 0x10: ATOMIC_CLOCK
  - 0x50: NTP
  - 0xA0: INTERNAL_OSCILLATOR

### 5. portDS: the port data set

Role: stores each PTP port's state and configuration.

Scope: one per PTP port.

#### Key members in detail

##### 1. portIdentity: the port's identity

- Type: PortIdentity (clockIdentity + portNumber)
- Classification: static
- Meaning: the port's unique identity

##### 2. portState: the port's state

- Type: Enumeration8
- Classification: dynamic
- Meaning: the port's current state
- Values:
  - 0x01: INITIALIZING
  - 0x02: FAULTY
  - 0x03: DISABLED
  - 0x04: LISTENING
  - 0x05: PRE_MASTER
  - 0x06: MASTER
  - 0x07: PASSIVE
  - 0x08: UNCALIBRATED
  - 0x09: SLAVE

##### 3. logAnnounceInterval: the Announce interval

- Type: Integer8
- Classification: configurable
- Meaning: the Announce send interval, in log-base-2 seconds
- Formula: interval = 2^logAnnounceInterval seconds
- Default: 1 (i.e., 2 seconds)
- Typical range: −3 to +4 (125 ms to 16 s)

Example:

| logAnnounceInterval | Interval |
|:---|:---|
| -3 | 125 ms |
| -2 | 250 ms |
| -1 | 500 ms |
| 0 | 1 s |
| 1 | 2 s (default) |
| 2 | 4 s |
| 3 | 8 s |
| 4 | 16 s |

##### 4. announceReceiptTimeout: the Announce timeout

- Type: UInteger8
- Classification: configurable
- Meaning: the timeout multiple for consecutive missed Announces
- Formula: timeout = announceReceiptTimeout × 2^logAnnounceInterval
- Default: 3
- Typical range: 2-10

Example:

With logAnnounceInterval=1 (2 s interval) and announceReceiptTimeout=3:
- Timeout = 3 × 2 = 6 seconds

If no Announce is received within 6 seconds, the ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES event fires.

##### 5. logSyncInterval: the Sync interval

- Type: Integer8
- Classification: configurable
- Meaning: the Sync send interval, in log-base-2 seconds
- Formula: interval = 2^logSyncInterval seconds
- Default: 0 (i.e., 1 second)
- Typical range: −7 to +1 (7.8 ms to 2 s)

The Sync interval is usually smaller than the Announce interval because Sync drives time synchronization, where a higher rate improves accuracy (within limits).

Announce is used for the BMCA; it need not be so frequent, saving bandwidth.

##### 6. logMinDelayReqInterval: the minimum Delay_Req interval

- Type: Integer8
- Classification: dynamic (advertised by the master)
- Meaning: the slave's minimum Delay_Req interval, in log-base-2 seconds
- Formula: interval = 2^logMinDelayReqInterval seconds
- Default: 0 (i.e., 1 second)

The master advertises it because it knows its own processing capacity. If processing power is limited, it can ask slaves to reduce Delay_Req frequency to avoid overload.

##### 7. delayMechanism: the delay measurement mechanism

- Type: Enumeration8
- Classification: configurable
- Meaning: the delay measurement mechanism used by the port
- Values:
  - 0x01: E2E (end-to-end)
  - 0x02: P2P (peer-to-peer)
  - 0x03: COMMON_P2P (common P2P)
  - 0x04: SPECIAL (special port)
  - 0xFE: NO_MECHANISM (no delay mechanism)

Key rule:

- All ports on the same PTP communication path must use the same delayMechanism.
- Mixing E2E and P2P prevents correct delay measurement.

##### 8. versionNumber and minorVersionNumber: the PTP version

- Type: UInteger4
- Classification: configurable
- Meaning: the PTP protocol version
- IEEE 1588-2019: versionNumber=2, minorVersionNumber=1

## The relationships between data sets

### Relationship diagram

```
PTP instance
├── defaultDS (identity and configuration)
├── currentDS (current sync status)
├── parentDS (parent clock information)
├── timePropertiesDS (time properties)
└── portDS[] (one per port)
    ├── portDS[1]
    ├── portDS[2]
    └── ...
```

### Data flow

Master clock sends Announce:

```
Master's data sets → Announce message
├── defaultDS.clockIdentity → sourcePortIdentity.clockIdentity
├── defaultDS.clockQuality → grandmasterClockQuality
├── defaultDS.priority1 → grandmasterPriority1
├── defaultDS.priority2 → grandmasterPriority2
├── currentDS.stepsRemoved → stepsRemoved
├── timePropertiesDS.currentUtcOffset → currentUtcOffset
└── ...
```

Slave receives Announce:

```
Announce message → slave's data sets
├── sourcePortIdentity → parentDS.parentPortIdentity
├── grandmasterIdentity → parentDS.grandmasterIdentity
├── grandmasterClockQuality → parentDS.grandmasterClockQuality
├── grandmasterPriority1 → parentDS.grandmasterPriority1
├── stepsRemoved + 1 → currentDS.stepsRemoved
└── ...
```

## Data set update rules

### M1/M2 decision (I become the master)

When BMCA decides I am the master, update the data sets as follows:

currentDS:
- stepsRemoved = 0
- offsetFromMaster = 0
- meanDelay = 0

parentDS:
- parentPortIdentity.clockIdentity = defaultDS.clockIdentity
- parentPortIdentity.portNumber = 0
- grandmasterIdentity = defaultDS.clockIdentity
- grandmasterClockQuality = defaultDS.clockQuality
- grandmasterPriority1 = defaultDS.priority1
- grandmasterPriority2 = defaultDS.priority2

timePropertiesDS:
- Update the properties from the external time source (e.g., GPS).

### S1 decision (I become the slave)

When BMCA decides I am the slave, update the data sets as follows:

currentDS:
- stepsRemoved = Ebest.stepsRemoved + 1

parentDS:
- parentPortIdentity = Ebest.sourcePortIdentity
- grandmasterIdentity = Ebest.grandmasterIdentity
- grandmasterClockQuality = Ebest.grandmasterClockQuality
- grandmasterPriority1 = Ebest.grandmasterPriority1
- grandmasterPriority2 = Ebest.grandmasterPriority2

timePropertiesDS:
- currentUtcOffset = Ebest.currentUtcOffset
- leap59 = Ebest.leap59
- leap61 = Ebest.leap61
- ptpTimescale = Ebest.ptpTimescale
- timeTraceable = Ebest.timeTraceable
- frequencyTraceable = Ebest.frequencyTraceable
- timeSource = Ebest.timeSource

## A complete example

A complete example shows how data sets work.

Scenario:

```
Master clock A (GPS-fed)
    ↓
Boundary clock B
    ↓
Slave clock C (5G base station)
```

Initial state:

Master A's data sets:

| Data set | Member | Value |
|:---|:---|:---|
| defaultDS | clockIdentity | 00-1B-19-00-00-00-00-01 |
| defaultDS | clockClass | 6 |
| defaultDS | clockAccuracy | 0x20 |
| defaultDS | priority1 | 10 |
| defaultDS | priority2 | 10 |
| defaultDS | slaveOnly | FALSE |
| currentDS | stepsRemoved | 0 |
| timePropertiesDS | ptpTimescale | TRUE |
| timePropertiesDS | currentUtcOffset | 37 |
| timePropertiesDS | timeTraceable | TRUE |
| timePropertiesDS | frequencyTraceable | TRUE |
| timePropertiesDS | timeSource | 0x20 (GNSS) |

Master A sends Announce:

| Field | Value |
|:---|:---|
| sourcePortIdentity | 00-1B-19-00-00-00-00-01, portNumber=1 |
| grandmasterIdentity | 00-1B-19-00-00-00-00-01 |
| grandmasterClockQuality | {class:6, accuracy:0x20, variance:...} |
| grandmasterPriority1 | 10 |
| grandmasterPriority2 | 10 |
| stepsRemoved | 0 |
| currentUtcOffset | 37 |
| ptpTimescale | TRUE |
| timeTraceable | TRUE |
| frequencyTraceable | TRUE |
| timeSource | 0x20 |

Boundary clock B receives the Announce:

Boundary clock B updates its data sets:

| Data set | Member | Updated value |
|:---|:---|:---|
| currentDS | stepsRemoved | 0 + 1 = 1 |
| parentDS | parentPortIdentity | A's port 1 |
| parentDS | grandmasterIdentity | 00-1B-19-00-00-00-00-01 |
| parentDS | grandmasterPriority1 | 10 |
| timePropertiesDS | currentUtcOffset | 37 |
| timePropertiesDS | timeTraceable | TRUE |

Boundary clock B forwards Announce:

| Field | Value |
|:---|:---|
| sourcePortIdentity | B's clockIdentity, portNumber=2 |
| grandmasterIdentity | 00-1B-19-00-00-00-00-01 |
| grandmasterClockQuality | {class:6, accuracy:0x20, variance:...} |
| grandmasterPriority1 | 10 |
| stepsRemoved | 1 (was 0, +1) |
| currentUtcOffset | 37 |

Slave clock C receives the Announce:

Slave clock C updates its data sets:

| Data set | Member | Updated value |
|:---|:---|:---|
| currentDS | stepsRemoved | 1 + 1 = 2 |
| parentDS | parentPortIdentity | B's port 2 |
| parentDS | grandmasterIdentity | 00-1B-19-00-00-00-00-01 |
| timePropertiesDS | currentUtcOffset | 37 |

In slave clock C's application:

The application queries time information:

```
Question 1: Which master am I synced to?
Answer: parentDS.grandmasterIdentity = 00-1B-19-00-00-00-00-01 (master A)

Question 2: How far am I from the master?
Answer: currentDS.stepsRemoved = 2 (two boundary clocks)

Question 3: How far am I from my immediate superior?
Answer: currentDS.offsetFromMaster = +125 ns (assuming the current measurement)

Question 4: What's UTC right now?
Answer: PTP time − timePropertiesDS.currentUtcOffset
       = (current PTP time) − 37
```

## Summary: the core points of data sets

Data set classification:
- defaultDS: identity and global configuration
- currentDS: current synchronization status
- parentDS: parent clock information
- timePropertiesDS: time properties
- portDS: port state and configuration

Member classification:
- Static: decided at the factory, never changes.
- Dynamic: auto-updated as the protocol runs.
- Configurable: an administrator can modify.

Key members:
- defaultDS.clockIdentity: unique device identity
- defaultDS.clockQuality: clock quality
- currentDS.offsetFromMaster: time offset
- currentDS.stepsRemoved: hops to the grandmaster
- parentDS.grandmasterIdentity: the master's identity
- timePropertiesDS.currentUtcOffset: the leap-second offset

Data flow:
- Master sends Announce: data sets → message
- Slave receives Announce: message → data sets

That covers how PTP devices store and manage information.

The remaining question is the nine port states: how they transition and what events trigger those transitions.

The next section covers the port state machine, PTP's "heart": a complete set of state transition rules that keep the protocol running correctly.

The "intermediate states" INITIALIZING, PRE_MASTER, and UNCALIBRATED exist for a reason, and the protocol cannot jump straight from LISTENING to MASTER or SLAVE.

These intermediate states are the key to protocol stability. Skip them, and multiple devices might simultaneously claim to be master, or a slave might start working before it's stable.
