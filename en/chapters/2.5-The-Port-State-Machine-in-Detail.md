# 2.5 The Nine Lives of a Clock: The Port State Machine in Detail

## A PTP port's "life journey"

Imagine a PTP port as a living organism passing through different "life stages."

Sometimes it rests, waiting for a signal.
Sometimes it prepares, gathering strength.
Sometimes it is the "conductor," sending time signals.
Sometimes it is the "follower," receiving time signals.

The PTP standard defines nine port states, each with clear behavioral rules.

A PTP port's "life cycle" deserves a close look, the way a biologist watches an organism.

## The nine states: at a glance

| State | English | Core behavior | What messages can it send? |
|:---|:---|:---|:---|
| **Initializing** | INITIALIZING | Initializing | No messages |
| **Fault** | FAULTY | Something broke | Only responds to management |
| **Disabled** | DISABLED | Manually disabled | Only responds to management |
| **Listening** | LISTENING | Waiting for Announce | May send Pdelay messages |
| **Pre-Master** | PRE_MASTER | Preparing to be master | No timing messages |
| **Master** | MASTER | Already the master | Sends all messages |
| **Passive** | PASSIVE | Passive, not participating in sync | Pdelay / Signaling / management responses |
| **Uncalibrated** | UNCALIBRATED | Calibrating | May send Delay_Req |
| **Slave** | SLAVE | Already synchronized | Sends Delay_Req |

> **An easily overlooked premise: not all nine states are mandatory.**
> INITIALIZING, MASTER, PASSIVE, and SLAVE always exist; the other five exist "on demand."

## States in detail: the meaning of each "life"

### State 1: INITIALIZING

Meaning: the port has just powered up or been reset and is initializing.

Behavior:
- Initialize all data-set members.
- Initialize hardware (such as the timestamp generator).
- Send no PTP messages.

Exit conditions:
- Initialization completes (`INITIALIZATION_COMPLETE`) → enter LISTENING.
- A fault is detected (`FAULT_DETECTED`) → enter FAULTY.
- Disabled via the management interface (`DESIGNATED_DISABLED`, that is, portEnable written FALSE) → enter DISABLED. This is **not** a branch of "initialization complete": the standard lets DISABLED be entered from **any** state by that event, and linuxptp's `ptp_fsm()` in the INITIALIZING branch handles only `EV_FAULT_DETECTED` and `EV_INIT_COMPLETE`.

Analogy: like a newborn who must learn to breathe, see, and hear before socializing.

Typical duration: a few milliseconds to a few seconds, depending on hardware initialization speed.

### State 2: FAULTY

Meaning: the port has detected a fault and cannot work normally.

Behavior:
- Sends no PTP messages proactively (management excepted).
- May respond to management messages for the administrator to diagnose.

Entry reasons:
- Hardware fault (e.g., damaged PHY).
- Software fault (e.g., memory exhaustion).
- Configuration error (e.g., out-of-range parameters).
- The P2P mechanism detected multiple responders.

Exit conditions:
- The administrator clears the fault via the management interface → enter INITIALIZING.
- Or fix the fault and restart the device.

Analogy: like a person who is ill and needs treatment; they can't work normally.

Fault diagnosis:

The administrator can query fault information via a management interface (SNMP, CLI, etc.):
- `faultLogDS`: fault log.
- `portDS.portState`: current state.

### State 3: DISABLED

Meaning: the port has been manually disabled and does not participate in the PTP protocol.

Behavior:
- Sends no PTP messages except management responses.
- Drops all received PTP messages (management excepted).

Entry reasons:
- The administrator disables the port via the management interface.
- The configuration file marks this port disabled.

Exit conditions:
- The administrator enables the port via the management interface → enter INITIALIZING.

Analogy: like a person on an extended leave, voluntarily not working.

Uses:

Scenario 1: maintenance

A device attached to a port needs maintenance; the administrator can temporarily disable the port to avoid disturbing the PTP network.

Scenario 2: topology control

When the network has redundant paths, the administrator can control PTP topology by disabling certain ports.

### State 4: LISTENING

Meaning: the port is listening to the network, waiting for Announce messages.

Behavior:
- Listen for Announce messages.
- May send Pdelay_Req/Pdelay_Resp (if the P2P mechanism is configured).
- May send Signaling and management messages.

Entry reasons:
- After INITIALIZING completes.
- Falling back to LISTENING from other states due to a BMCA re-decision or role revocation.

Exit conditions:
- Valid Announce received → based on the BMCA decision, enter PRE_MASTER, UNCALIBRATED, or PASSIVE.
- announceReceiptTimeout expires → enter MASTER.

Analogy: like a new employee on the first day, observe first, listen to others, learn the lay of the land.

The key timeout:

A port in LISTENING starts the `announceReceiptTimeout` timer. If it expires, the port enters MASTER directly (deeming itself the best master); only when the BMCA actively recommends it to be master (`EV_RS_MASTER` in linuxptp, recommended state = BMC_MASTER in the standard, decisions M1/M2/M3) does it first enter PRE_MASTER to await confirmation.

LISTENING acts as the port's "waiting room". In this state, the port first observes whether a better master already exists on the network, rather than rushing to become master.

This avoids the "jumping the gun" problem: if every port began sending Announce the moment it powered up, several ports might simultaneously claim to be master, causing chaos.

### State 5: PRE_MASTER

Meaning: the port is preparing to be master but is still waiting for final confirmation.

Behavior:
- Sends no Announce, Sync, or Delay_Resp.
- May send Pdelay_Req/Pdelay_Resp (if P2P is configured).
- May send Signaling and management messages.

Entry reasons:
- BMCA decision: I should become master (M1/M2/M3 decision)...
- ...but I must wait out the qualificationTimeout to be sure no better master appears.

Exit conditions:
- The qualificationTimeout expires (`EV_QUALIFICATION_TIMEOUT_EXPIRES`) with no better Announce seen → enter MASTER.
- A better Announce is received → if the BMCA now recommends slave, enter **UNCALIBRATED** (SLAVE only after the servo settles); if it recommends passive, enter PASSIVE.

Analogy: like someone elected a leader, waiting for the "publicity period" to end before formally taking office.

The PRE_MASTER state exists to solve a specific problem:

Suppose two devices exist on the network: A and B.

A powers up first; BMCA decides A becomes master. A immediately enters MASTER and starts sending Announces.

B powers up later, and B's clockQuality is better than A's. In LISTENING, B receives A's Announce; BMCA decides B should be master. B enters PRE_MASTER.

If B immediately switched to MASTER, A would receive B's Announce, see that B is better, and switch to SLAVE, while B sends Announces and becomes master.

In practice, though, in that switching instant the network may briefly contain two masters, confusing downstream devices.

PRE_MASTER's solution:

After B enters PRE_MASTER, it waits out the `qualificationTimeout`, which is **N × announceInterval**: N = 0 for an **M1/M2 decision**, and N = stepsRemoved + 1 for an **M3 decision** (a MASTER port on a non-master device).

During the wait:
- If B receives a better Announce (say C comes online), B abandons becoming master.
- If B receives nothing better, B confirms the network is stable and enters MASTER.

This avoids frequent master switching.

### State 6: MASTER

Meaning: the port has become the master and sends time signals to the network.

Behavior:
- Sends Announce (per logAnnounceInterval).
- Sends Sync (per logSyncInterval).
- Sends Follow_Up (if two-step mode).
- Responds to Delay_Req with Delay_Resp.
- Responds to Pdelay_Req with Pdelay_Resp (if the P2P mechanism is used).

Entry reasons:
- PRE_MASTER's timeout expires, confirming the role.
- BMCA decision: I should be master.

Exit conditions:
- A better Announce received → per the BMCA decision, enter UNCALIBRATED (then SLAVE after calibration) or PASSIVE.
- The administrator disables the port → enter DISABLED.
- A fault is detected → enter FAULTY.

Analogy: like someone formally becoming a leader and issuing orders.

The MASTER state's duties:

Duty 1: send time signals

The master periodically sends Sync messages, telling slaves "what time it is."

Duty 2: respond to delay-measurement requests

Slaves send Delay_Req; the master must respond with Delay_Resp, telling them "your request was received at such-and-such a time."

Duty 3: broadcast master information

The master periodically sends Announce, telling the network "who I am and how good I am."

Duty 4: maintain time quality

The master must keep its clock quality (clockClass, clockAccuracy) consistent with reality. If it loses GPS, it should downgrade its clockClass.

### State 7: PASSIVE

Meaning: the port doesn't participate in master-slave relationships; it's in a "pruned" state.

Behavior:
- Sends no Announce, Sync, or Delay_Resp.
- Receives Sync but **discards it without using it for synchronization**: a port not in SLAVE or UNCALIBRATED must discard Sync.
- May send Pdelay_Req/Pdelay_Resp (if P2P is configured), plus Signaling and management messages.

Entry reasons:
- BMCA decision: this port should be neither master nor slave.

Exit conditions:
- A better Announce received → per the BMCA decision, enter **UNCALIBRATED** if the port should be a slave (not SLAVE directly; calibration comes first), or PRE_MASTER if it should be master.
- announceReceiptTimeout expires (`EV_ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES`) → enter MASTER. A PASSIVE port also starts this timer, and the standard lists LISTENING, PASSIVE, UNCALIBRATED, and SLAVE together as states that upgrade to MASTER on timeout.
- Topology change → enter another state (including LISTENING).

Analogy: like being "muted" at a meeting, neither speaking nor taking a stance.

The purpose of PASSIVE is loop pruning. Consider a triangular topology:

```
Device A ---- Device B
  |        /
  |       /
  |      /
Device C ----
```

Suppose A is master.

If a link also exists between B and C:
- B syncs from A, entering SLAVE.
- C syncs from A, entering SLAVE.
- But B and C might also establish a master-slave relationship between themselves.

Suppose B syncs from C, and C syncs from A:

```
A (MASTER) → C (SLAVE) → B (SLAVE)
```

B indirectly syncs from A, seems fine.

But the problem: if the link between B and C breaks, B must re-sync from A, and the switchover may be slow.

PTP's approach: prune the redundant B-C link. Pruning happens at the **port**, and both ends are never PASSIVE at once: a PASSIVE port sends no timing messages, so if both ends stayed silent, the standard would upgrade them to MASTER when announceReceiptTimeout expires. The BMCA's steady-state result is one designated port on the link (MASTER, still forwarding time from A) and the other end PASSIVE, outside synchronization.

If the A→C link breaks, the port on the PASSIVE side (say C's port to B) can quickly move through **UNCALIBRATED** to SLAVE and sync from B instead.

What PASSIVE does:
- Prevents synchronization loops.
- Provides a redundant path for fast fault switchover.

### State 8: UNCALIBRATED

Meaning: the port is calibrating; synchronization isn't stable yet.

Behavior:
- May send Delay_Req.
- May receive Sync.
- The clock servo is initializing and adjusting.

Entry reasons:
- Before moving from LISTENING (or another state) into SLAVE.

Exit conditions:
- The master clock is selected (`EV_MASTER_CLOCK_SELECTED`), the servo locks, and sync stabilizes → enter SLAVE.
- A better Announce received → enter another state.
- The servo cannot lock → it does **not** return to LISTENING. The full state machine has no UNCALIBRATED-to-LISTENING edge, and the standard's port state transition diagram has none either. In linuxptp, `ptp_fsm()` in the UNCALIBRATED branch can only go to DISABLED, FAULTY, MASTER, SLAVE, PRE_MASTER, PASSIVE (plus linuxptp's private, non-standard tenth state `PS_GRAND_MASTER`; the standard has nine port states, linuxptp has ten), or stay put. Only the simplified `ptp_slave_fsm()` used when `defaultDS.slaveOnly = TRUE` sends UNCALIBRATED back to LISTENING on announce timeout (`EV_ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES`) or when the port is recommended master or passive.

Analogy: like a student just beginning to learn, still fumbling, grades unstable.

UNCALIBRATED exists to solve a specific problem:

A port moves from LISTENING into SLAVE and starts applying time synchronization immediately.

But if the slave's local clock differs greatly from the master (say, seconds), the servo needs time to adjust. During adjustment, the slave's time can jump violently.

If applications use PTP time during this period, problems can occur (e.g., log timestamps going backwards).

UNCALIBRATED's solution:

The port first enters UNCALIBRATED, waits for the servo to lock initially and the offset to drop to a reasonable range, then enters SLAVE.

This gives the application layer a clear signal: "time is not stable yet, don't rely on it."

### State 9: SLAVE

Meaning: the port has become a slave, syncing time from the master.

Behavior:
- Receives Sync, adjusts the local clock.
- Sends Delay_Req (E2E mechanism).
- Receives Delay_Resp.
- May send Pdelay_Req/Pdelay_Resp (P2P mechanism).

Entry reasons:
- BMCA decision: I should be slave (S1 decision).
- UNCALIBRATED, sync stable.

Exit conditions:
- A better Announce received → per the BMCA decision, enter another state.
- A synchronization fault (`EV_SYNCHRONIZATION_FAULT`, that is, the implementation detects that it must run through the initialization in UNCALIBRATED again) → fall back to UNCALIBRATED.
- Master lost (announceReceiptTimeout expiry) → an ordinary port enters MASTER directly (taking over); a slaveOnly port returns to LISTENING.
- The administrator disables the port → enter DISABLED.
- A fault is detected → enter FAULTY.

Analogy: like a student formally enrolled, following the teacher.

The SLAVE state's duties:

Duty 1: receive time signals

Receive the master's Sync, extract timestamps, compute the offset.

Duty 2: measure path delay

Send Delay_Req (E2E) or participate in P2P delay measurement, determining the path delay to the master.

Duty 3: adjust the local clock

Run the clock servo to adjust the local clock's phase and frequency based on the offset.

Duty 4: monitor sync quality

Watch offsetFromMaster and meanDelay to judge sync quality, raising alarms if deviation grows too large.

## State transitions: a PTP port's "turning points"

### The complete state transition diagram

```
POWERUP / INITIALIZE
        ↓
   INITIALIZING
        ├── INITIALIZATION_COMPLETE ──→ LISTENING
        ├── FAULT_DETECTED ──→ FAULTY
        └── DESIGNATED_DISABLED ──→ DISABLED

   LISTENING
        │  ← STATE_DECISION_EVENT: BMCA gives the recommended state
        ├── recommends BMC_MASTER (decisions M1/M2/M3) ──→ PRE_MASTER
        ├── recommends BMC_SLAVE (decision S1) ──→ UNCALIBRATED
        ├── recommends BMC_PASSIVE (decisions P1/P2) ──→ PASSIVE
        └── ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES ──→ MASTER (direct promotion, bypassing PRE_MASTER)

   PRE_MASTER
        │  ← on entry, the announceReceiptTimeout timer is stopped and not restarted
        ├── QUALIFICATION_TIMEOUT_EXPIRES ──→ MASTER
        ├── recommends BMC_SLAVE ──→ UNCALIBRATED
        └── recommends BMC_PASSIVE ──→ PASSIVE

   UNCALIBRATED
        ├── MASTER_CLOCK_SELECTED ──→ SLAVE
        ├── ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES ──→ MASTER
        ├── recommends BMC_MASTER ──→ PRE_MASTER
        └── recommends BMC_PASSIVE ──→ PASSIVE

   PASSIVE
        ├── ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES ──→ MASTER
        ├── recommends BMC_SLAVE ──→ UNCALIBRATED (SLAVE only after calibration settles)
        ├── recommends BMC_MASTER ──→ PRE_MASTER
        └── topology change ──→ LISTENING or another state

   SLAVE
        ├── ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES ──→ MASTER
        │        (a slaveOnly port returns to LISTENING)
        ├── SYNCHRONIZATION_FAULT ──→ UNCALIBRATED
        ├── recommends BMC_SLAVE and old and new masters differ ──→ UNCALIBRATED
        └── recommends BMC_PASSIVE ──→ PASSIVE

   MASTER
        ├── recommends BMC_SLAVE ──→ UNCALIBRATED
        └── recommends BMC_PASSIVE ──→ PASSIVE

   ── two edges triggerable from "any state" ──
   DESIGNATED_DISABLED ──→ DISABLED
   FAULT_DETECTED ──→ FAULTY
   ── exits from the two "dead-end" states ──
   DISABLED ──DESIGNATED_ENABLED──→ INITIALIZING
   FAULTY ──FAULT_CLEARED──→ INITIALIZING
```

### Typical state transition scenarios

#### Scenario 1: an ordinary clock powering up

```
Power on
  ↓
INITIALIZING (initialize data sets, check hardware)
  ↓
LISTENING (listen for Announce)
  ↓
  ├── Announce received, BMCA decision: I am a slave
  │     ↓
  │   UNCALIBRATED (servo initializing)
  │     ↓
  │   SLAVE (sync complete)
  │
  ├── timeout, no Announce (announce expiry)
  │     ↓
  │   MASTER (promote to master directly, skips PRE_MASTER)
  │
  └── Announce received, BMCA decision: I am the master
        ↓
      PRE_MASTER (waiting for confirmation)
        ↓
      MASTER (becomes master)
```

#### Scenario 2: the master fails and the slave is promoted

```
Initial state:
- Master A: MASTER
- Slave B: SLAVE (syncs from A)

Master A fails (power loss or GPS lost)
  ↓
Slave B no longer receives A's Announces
  ↓
announceReceiptTimeout expires (about 6 seconds later)
  ↓
Slave B's port receives EV_ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES
  ↓
ptp_fsm: SLAVE enters MASTER directly (master lost, takes over)
  ↓
Slave B begins sending Announce, becoming the new master
  ↓
(if a better master later appears, B falls back to SLAVE through UNCALIBRATED)
```

Switchover time: roughly announceReceiptTimeout ≈ 6 seconds.

Note: the timeout path from SLAVE goes directly to MASTER, not through PRE_MASTER. PRE_MASTER appears only when a port actively competes to become master (`EV_RS_MASTER` from the BMCA; it enters PRE_MASTER and waits for the qualificationTimeout).

#### Scenario 3: loop detection and pruning

```
Initial state (triangular topology):
- Device A: MASTER (grandmaster)
- Device B: SLAVE (syncs from A)
- Device C: SLAVE (syncs from A)

There is a redundant link between B and C.

BMCA runs:
- B checks: the best master is A
- C checks: the best master is A
- But the B-C link is only redundant: each one's best path to A is the direct link, with no need to go through the other

BMCA decision (assume the comparison reaches the last layer, "port identity," and B wins, becoming the designated port for this link):
- B's port to C: MASTER (still announces and syncs in the name of root=A)
- C's port to B: PASSIVE; C's best Announce (Ebest) comes from A and does not use this port, while B's Announce on this link is one hop worse than Ebest, so the BMCA gives PASSIVE (decision code P1 or P2)
- Both ends are never PASSIVE at once: a PASSIVE port sends no timing messages, and if both ends were silent, the standard would upgrade them to MASTER when announceReceiptTimeout expires

Result:
- The link between B and C is "pruned" (the PASSIVE end is what gets cut)
- If the A→C link breaks, C's port to B can quickly move through UNCALIBRATED to SLAVE and sync from B
```

## The state machine's key design principles

### Principle 1: determinism

Identical inputs must produce identical outputs.

The PTP state machine is deterministic: given a current state and an event, the next state is fixed.

This guarantees predictability and testability.

### Principle 2: stability

The state machine is designed for stability, avoiding frequent switching.

Example: the PRE_MASTER state

Before becoming master, a port enters PRE_MASTER and waits. This avoids the frequent master switching caused by "jumping the gun."

### Principle 3: atomicity

State decisions are atomic.

When the BMCA computes all ports' recommended states, it updates all port states atomically in one step, not one by one.

This guarantees state consistency.

### Principle 4: fast convergence

The state machine is designed to converge quickly.

On a stable network, transitions typically complete within one announceInterval.

## slaveOnly mode: the simplified state machine

If a device's `defaultDS.slaveOnly = TRUE`, it uses a simplified state machine.

### The simplified state machine

```
INITIALIZING → LISTENING → UNCALIBRATED → SLAVE
```

Key restrictions:
- Never enters PRE_MASTER, MASTER, or PASSIVE.
- clockClass must be 255.
- `ptp_slave_fsm()` still handles INITIALIZING, FAULTY, and DISABLED; on its master-side events it assigns LISTENING rather than ignoring them.

Applications:
- End devices (workstations, servers).
- Devices that don't provide time to others.

Benefits:
- Simpler implementation.
- Less resource consumption.
- No accidental promotion to master.

## State machine implementation notes

### Note 1: event processing order

A state machine may receive several events at once. For example:
- An Announce has arrived.
- A timer expired.
- A management command arrived.

The implementation must define a clear event-priority order.

Typical priority (high to low):
1. Management commands (e.g., DISABLE_PORT).
2. Fault events.
3. Announce processing.
4. Timer events.

### Note 2: resource management

Different states need different resources:
- MASTER: must send Announce, Sync, Delay_Resp.
- SLAVE: must send Delay_Req and receive Sync.
- LISTENING: only needs to listen.

Implementations can allocate/release resources dynamically on transitions.

### Note 3: clock servo initialization

Entering UNCALIBRATED requires initializing the clock servo. This may involve:
- Clearing historical data.
- Setting initial parameters.
- Waiting for enough samples.

Implementations must account for initialization time and resource use.

## Summary: the state machine's core points

The nine states:
- INITIALIZING: initializing
- FAULTY: fault
- DISABLED: disabled
- LISTENING: listening
- PRE_MASTER: pre-master
- MASTER: master clock
- PASSIVE: passive
- UNCALIBRATED: uncalibrated
- SLAVE: slave clock

Key transitions:
- INITIALIZING → LISTENING: initialization complete
- LISTENING → PRE_MASTER: I should be master
- PRE_MASTER → MASTER: confirmed as master
- LISTENING → UNCALIBRATED → SLAVE: I should be slave
- LISTENING → PASSIVE: neither master nor slave

Key timeouts:
- announceReceiptTimeout: timeout for missing Announces.
- qualificationTimeout: the PRE_MASTER confirmation timeout.

Key principles:
- Determinism: same input, same output.
- Stability: avoid frequent switching.
- Atomicity: state updates complete atomically.
- Fast convergence: transitions complete in seconds.

> **Left hanging for 2.6**
>
> You may wonder how a transparent clock improves sync accuracy when it doesn't join the BMCA and keeps no state machine.
>
> The answer is one key concept: **residence time**.
>
> When a PTP message passes through a transparent clock, the transparent clock records the ingress and egress timestamps, computes the residence time, and writes it into the message's correctionField.
>
> Downstream devices then know "how long this message was held up along the way," and can subtract that residence-time part of the delay (subtract it, not eliminate it completely; the accuracy of the subtraction is also limited by timestamp quality and by the rate difference between the timestamping clocks at the two ends).
