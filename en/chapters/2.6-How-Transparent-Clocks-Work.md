# 2.6 The Relay Station That Doesn't Lie: How Transparent Clocks Work

## An "honesty" question

Suppose you mail a letter to a friend.

The letter departs from Beijing, passes through three transit points: Shanghai, Guangzhou, and Shenzhen, and finally reaches your friend.

When your friend receives the letter, he wants to know how long it was in transit. But he can only see the postmarks on the envelope: mailed in Beijing on January 1, received on January 5. That 4-day gap includes both the actual shipping time and the time the letter sat in the transit points.

The question: will the transit points honestly tell you how long the letter stayed there?

In a traditional postal system, the answer is: usually not.

But in a PTP network, there's a device that will proactively, precisely, and honestly tell you: the Transparent Clock (TC).

## A transparent relay station

### The transparent clock's core task

A transparent clock has exactly one core task: measure how long PTP messages stay inside it, and tell the downstream devices.

That sounds easy, but it matters enormously.

### Why do we need transparent clocks?

Scenario 1: without transparent clocks

```
Master ---- Switch A ---- Switch B ---- Switch C ---- Slave
```

Suppose:
- True propagation delay from master to slave (light in fiber): 100 ns
- Each switch's processing delay: 1 µs to 10 µs, highly variable
- Three switches, total processing delay: 3 µs to 30 µs, a 27 µs spread

The slave measures path delay as: 100 ns + (3 µs to 30 µs) = 3.1 µs to 30.1 µs.

The problem:
- Path-delay jitter: 27 µs
- That 27 µs jitter lands directly on offsetFromMaster
- Sync accuracy is capped at roughly 27 µs

Scenario 2: with transparent clocks

```
Master ---- TC_A ---- TC_B ---- TC_C ---- Slave
```

A transparent clock will:
1. Record the message's ingress timestamp.
2. Record the egress timestamp.
3. Compute the residence time.
4. Write the residence time into the message's correctionField.

When the slave receives the message, it knows:
- True propagation delay: 100 ns
- Residence at TC_A: 5.2 µs
- Residence at TC_B: 3.8 µs
- Residence at TC_C: 6.1 µs
- Total residence: 15.1 µs

When the slave computes offsetFromMaster, it subtracts this 15.1 µs.

The result:
- The residence time is measured and compensated precisely.
- The remaining uncertainty is only the timestamp accuracy itself (typically < 10 ns).
- Sync accuracy can approach the timestamp accuracy (nanosecond level).

## Transparent clock vs. boundary clock

A boundary clock can do this too, but at a different cost and with a different effect.

### What a boundary clock does

A boundary clock will:
1. Receive the upstream Sync.
2. Adjust its own local clock.
3. Generate new Sync messages for downstream.

Problems:
- A boundary clock needs a high-accuracy local clock (expensive).
- A boundary clock must participate in the BMCA (complex).
- A boundary clock becomes a new "master," adding a hierarchy tier.

Advantages:
- It can isolate error accumulation.
- It can bridge different networks.

### What a transparent clock does

A transparent clock will:
1. Receive the Sync.
2. Record ingress and egress timestamps.
3. Write the residence time into the correctionField.
4. Forward the Sync (no new message generated).

Advantages:
- No high-accuracy local clock needed (cheap).
- No BMCA participation (simple).
- No added hierarchy tier.

Disadvantages:
- Cannot isolate error accumulation.
- Cannot bridge different networks.

### How to choose

| Scenario | Recommendation |
|:---|:---|
| Small network, low cost | Transparent clock |
| Need to isolate error accumulation | Boundary clock |
| Need to bridge different networks | Boundary clock |
| Existing ordinary switches, upgrading to PTP | Transparent clock |
| Carrier-grade, high-accuracy network | Boundary clock + transparent clock |

## The two types of transparent clocks

PTP defines two kinds of transparent clocks:

### End-to-End Transparent Clock (E2E TC)

Characteristics:
- Supports all PTP message types.
- Forwards Announce, Sync, Follow_Up, Delay_Req, Delay_Resp, etc.
- Measures only residence time, not link delay.

How it works:

Handling Sync:

1. Sync enters the E2E TC; record the ingress timestamp (t1).
2. Sync leaves the E2E TC; record the egress timestamp (t2).
3. Compute the residence time: residenceTime = t2 − t1.
4. Update the correctionField: correctionField += residenceTime.
5. Forward the Sync.

Handling Delay_Req:

Same as Sync, measure residence time and update the correctionField.

Key formula:

```
Sync.correctionField (egress) = Sync.correctionField (ingress) + residenceTime
```

Note: if the ingress and egress messages differ in twoStepFlag, the handling is more complex (detailed later).

### Peer-to-Peer Transparent Clock (P2P TC)

Characteristics:
- Supports a subset of message types: Announce, Sync, Follow_Up, Signaling, Management.
- Drops Delay_Req and Delay_Resp.
- Measures both residence time and link delay.

How it works:

Handling Sync:

1. Sync enters the P2P TC; record the ingress timestamp (t1).
2. Sync leaves the P2P TC; record the egress timestamp (t2).
3. Compute the residence time: residenceTime = t2 − t1.
4. Obtain the ingress link delay: meanLinkDelay (measured via the P2P delay mechanism).
5. Update the correctionField: correctionField += residenceTime + meanLinkDelay.
6. Forward the Sync.

Handling Delay_Req:

Dropped, not forwarded.

Key formula:

```
Sync.correctionField (egress) = Sync.correctionField (ingress) + residenceTime + meanLinkDelay
```

A P2P TC drops Delay_Req because the P2P mechanism measures delay link by link. Each P2P TC already knows the delay of the links on both sides (the meanLinkDelay).

When a P2P TC forwards a Sync, it writes "residence time + ingress link delay" into the correctionField.

Downstream devices then have no need to send Delay_Req to measure the whole path delay, the path delay has already been accumulated segment by segment into the correctionField.

An E2E TC keeps Delay_Req because the E2E mechanism measures delay end to end. The slave must send Delay_Req and the master must reply Delay_Resp to measure the whole path.

An E2E TC only measures residence time and doesn't participate in delay measurement, so it must forward Delay_Req and Delay_Resp.

## Residence-time measurement: the details decide the accuracy

### The key to timestamp generation

Residence-time accuracy depends on timestamp accuracy.

The timestamping point:

The PTP standard requires timestamps to be generated when the message's message timestamp point passes the reference plane.

The message timestamp point:
- For Ethernet: the start of the first symbol after the Start-of-Frame Delimiter (SFD).

The reference plane:
- The boundary between the PTP instance and the network.
- Usually at the PHY (physical layer).

The ideal case:

Generate timestamps at the PHY, with no software latency.

The real case:

Some devices can't timestamp at the PHY and do it at the MAC or higher. Those need to measure and correct the latency.

### Timestamp correction

If the timestamp is generated at the MAC layer, there's a latency between it and the PHY reference plane that must be corrected:

```
Actual timestamp (reference plane) = captured timestamp + correction delay
```

Measuring the correction delay:

The manufacturer must measure:
- ingressLatency: the latency from the reference plane to the MAC.
- egressLatency: the latency from the MAC to the reference plane.

These latencies can be measured through calibration and written into the `timestampCorrectionPortDS` data set.

## Handling the correctionField: the art of accumulation

### What the correctionField means

The correctionField is an 8-byte field in the PTP message header that carries various corrections.

Units: 2⁻¹⁶ nanoseconds

Typical contents:
- The fractional-nanosecond part (a supplement to originTimestamp).
- The transparent clock's residence time.
- Path asymmetry corrections.

### The E2E TC's correctionField handling

#### For Sync

One-step mode (the Sync itself carries the timestamp):

```
Sync.correctionField (egress) = Sync.correctionField (ingress) + residenceTime + ingressAsymmetry
```

Two-step mode (Sync followed by Follow_Up):

Case 1: ingress twoStepFlag=FALSE, egress twoStepFlag=TRUE

The TC must "upgrade" to two-step:
- Set Sync.twoStepFlag to TRUE.
- Create a Follow_Up carrying residenceTime + ingressAsymmetry.

Case 2: ingress twoStepFlag=TRUE, egress twoStepFlag=TRUE

The TC must associate the Sync and Follow_Up:
- On receiving Sync, record its correctionField and sequenceId.
- On receiving the matching Follow_Up, update Follow_Up.correctionField.
- Forward the Follow_Up.

Case 3: ingress twoStepFlag=TRUE, egress twoStepFlag=FALSE

The TC must "downgrade" to one-step:
- Wait for the Follow_Up to arrive.
- Merge Sync.correctionField and Follow_Up.correctionField.
- Set Sync.twoStepFlag to FALSE.
- Forward the Sync.

Case 4: ingress twoStepFlag=FALSE, egress twoStepFlag=FALSE

The simplest case:
- Update Sync.correctionField directly.
- Forward the Sync.

#### For Delay_Req

The key difference: Delay_Req uses the egressAsymmetry (egress asymmetry); the ingress asymmetry is applied to Sync.

Formula:

```
Delay_Req.correctionField (egress) = Delay_Req.correctionField (ingress) + residenceTime − egressAsymmetry
```

Why the opposite sign?

- Sync: master→slave direction; the ingress asymmetry is part of the forward delay and must be added.
- Delay_Req: slave→master direction; the egress asymmetry must be subtracted to obtain the true delay.

### The P2P TC's correctionField handling

#### For Sync

```
Sync.correctionField (egress) = Sync.correctionField (ingress) + residenceTime + ingressAsymmetry + meanLinkDelay
```

Key point: the P2P TC adds the ingress link delay (meanLinkDelay).

Thus, a Sync received by a downstream device carries in its correctionField:
- the residence times of all upstream transparent clocks,
- the delays of all upstream links.

The downstream device only needs to:
- Extract the timestamp from the Sync.
- Subtract the correctionField.
- Obtain the master's true send time.

No Delay_Req is needed.

## Path asymmetry correction

### What is asymmetry?

Definition: the delay from master to slave differs from the delay from slave to master.

Causes:
- Different fiber lengths (different directions on different fibers).
- Different wavelengths (WDM, different wavelengths travel at different speeds).
- Different switch processing delays.
- Different uplink/downlink bandwidths on wireless links.

### The effect of asymmetry

When PTP computes path delay, it assumes symmetry:

```
meanPathDelay = [(t2 − t1) + (t4 − t3)] / 2
```

If asymmetric:
- t_ms (master→slave) ≠ t_sm (slave→master)
- But the formula still computes the average.

Result: the computed meanPathDelay does not equal the true delay.

### How do transparent clocks handle asymmetry?

E2E TC:
- Adds ingressAsymmetry to Sync.
- Subtracts egressAsymmetry from Delay_Req.

P2P TC:
- Adds ingressAsymmetry to Sync.
- The meanLinkDelay measurement must also account for asymmetry.

Sources of the asymmetry value:
- Configured: set by the administrator through a management interface.
- Profile-defined: a default for a specific application.
- Dynamically computed: some media support dynamic computation (e.g., option 16.8 of IEEE Std 1588-2019).

## A complete transparent-clock processing example

### Scenario

```
Master A ---- TC_B ---- TC_C ---- Slave D
```

Parameters:
- Master A sends Sync at time t1 = 1000.000000000 s
- TC_B residence time: 5 µs
- TC_C residence time: 3 µs
- A→B link delay: 100 ns
- B→C link delay: 150 ns
- C→D link delay: 120 ns
- Optical propagation delay (ignored here): ~5 ns/m

### The P2P TC's handling

TC_B:

Receives the Sync:
- originTimestamp = 1000.000000000 s
- correctionField = 0 (initial)

Measures:
- residenceTime = 5 µs
- meanLinkDelay (A→B) = 100 ns
- ingressAsymmetry (assumed) = 0

Updates the correctionField:

```
correctionField = 0 + 5 µs + 0 + 100 ns = 5.1 µs
```

Forwards the Sync.

TC_C:

Receives the Sync:
- originTimestamp = 1000.000000000 s
- correctionField = 5.1 µs

Measures:
- residenceTime = 3 µs
- meanLinkDelay (B→C) = 150 ns
- ingressAsymmetry (assumed) = 0

Updates the correctionField:

```
correctionField = 5.1 µs + 3 µs + 0 + 150 ns = 8.25 µs
```

Forwards the Sync.

Slave D:

Receives the Sync:
- originTimestamp = 1000.000000000 s
- correctionField = 8.25 µs
- Receive timestamp: t2 = 1000.000008470 s (assumed)

Computes:

```
Corrected master send time = originTimestamp + correctionField
                           = 1000.000000000 + 0.00000825
                           = 1000.000008250 s

Path delay (C→D) = 120 ns (measured by the P2P mechanism)
Time at D's sync point under the master clock = 1000.000008250 + 0.000000120 = 1000.000008370 s

offsetFromMaster = t2 − the master-clock time at D's sync point
                 = 1000.000008470 − 1000.000008370
                 = 100 ns
```

Slave D learns: it is 100 ns ahead of the master and must subtract 100 ns.

### What if there are no transparent clocks?

Suppose TC_B and TC_C are ordinary switches that measure no residence time and accumulate nothing into the correctionField.

Slave D still computes in the P2P way:

Receives the Sync:
- originTimestamp = 1000.000000000 s
- correctionField = 0 (ordinary switches added nothing)
- Receive timestamp: t2 = 1000.000008470 s

Slave D measures the peerDelay (the direct C→D link):
- peerDelay = 120 ns

Computes offsetFromMaster (P2P formula):

```
offsetFromMaster = t2 − t1 − correctionField − peerDelay
                 = 1000.000008470 − 1000.000000000 − 0 − 0.000000120
                 = 8.35 µs
```

But in fact, the true offsetFromMaster should be 100 ns: the Sync actually arrived at 1000.000008370 s, and t2 = 1000.000008470 s means the slave is only 100 ns ahead.

Error: 8.35 µs − 100 ns = 8.25 µs

That error is precisely what the ordinary switches failed to accumulate into the correctionField:
- A→B link delay: 100 ns
- B residence time: 5 µs
- B→C link delay: 150 ns
- C residence time: 3 µs

Totaling 8.25 µs. P2P delegates the accumulation of the whole middle path's delays entirely to the transparent clocks along the route; once the TCs are absent, that entire slice of delay simply vanishes from the offset computation.

Strictly speaking, an ordinary switch C won't answer a Pdelay_Req, so this peerDelay could not even be measured. We assume the 120 ns of the last hop is known here purely to make the numbers comparable. In reality, a network of ordinary switches must fall back to E2E delay measurement (see section 2.7).

## Key challenges in implementing a transparent clock

### Challenge 1: timestamp accuracy

Residence-time accuracy depends directly on timestamp accuracy.

Requirements:
- Timestamp resolution: at least nanosecond-level.
- Timestamp jitter: < 10 ns.
- Timestamp clock: may be a free-running Local Clock.

Solutions:
- Use hardware timestamps (PHY layer).
- Use high-resolution counters.
- Correct internal latency.

### Challenge 2: message association

In two-step mode, the TC must associate the Sync and Follow_Up messages.

Association criteria:
- Same sourcePortIdentity.
- Same sequenceId.

Implementation:
- Maintain a cache table of the Sync messages' information.
- When a Follow_Up arrives, look up the matching Sync.
- Update Follow_Up.correctionField, then forward it.

Note: the cache needs a timeout-based cleanup to avoid memory leaks.

### Challenge 3: correctionField overflow

The correctionField is a 64-bit signed integer with units of 2⁻¹⁶ ns (the smallest tick ≈ 15.26 femtoseconds); its theoretical range is about ±1.4×10¹⁴ ns, i.e., about ±39 hours.

If there are very many transparent clocks or very long residence times, overflow is theoretically possible (in practice, very hard to reach).

Solutions:
- Use a large enough integer type for intermediate results.
- Detect overflow and drop the message or raise an alarm.

### Challenge 4: asymmetry measurement

A P2P TC must measure the link delay (meanLinkDelay), but that measurement can itself be affected by asymmetry.

Solutions:
- For the P2P mechanism, asymmetry largely cancels out (see the analysis in IEEE Std 1588-2019, 11.4.2).
- But if utmost accuracy is required, an explicit asymmetry correction is still needed.

## Summary: the transparent clock's core points

What a transparent clock does:
- Measures the residence time of PTP messages.
- Updates the correctionField.
- Eliminates switch-processing-delay uncertainty.

Two types:
- E2E TC: forwards all messages, measures residence time.
- P2P TC: drops Delay_Req, measures residence time + link delay.

Key formulas:

E2E TC:
```
Sync.correctionField += residenceTime + ingressAsymmetry
Delay_Req.correctionField += residenceTime − egressAsymmetry
```

P2P TC:
```
Sync.correctionField += residenceTime + ingressAsymmetry + meanLinkDelay
```

Key challenges:
- Timestamp accuracy.
- Message association (two-step mode).
- CorrectionField overflow.
- Asymmetry measurement.

A transparent clock measures residence time and link delay.

How the slave measures the path delay to the master is a separate question.

Section 2.7 covers the E2E delay measurement mechanism, where four timestamps measure end-to-end path delay.

You may wonder why four timestamps (t1, t2, t3, t4) are needed rather than two.

Because the master and slave clocks aren't aligned yet.

If they were already aligned, two timestamps would suffice. But the very point of PTP is to align them, and *before* alignment, the two clocks differ.

The four-timestamp design sidesteps this elegantly: even without knowing the offset, you can compute the path delay.
