# 2.8 Measuring Each Link Precisely: The P2P Delay Measurement Mechanism

## If every segment of the road had a radar gun

Imagine driving a long highway route and wanting to know how long the whole trip takes.

Method 1: record the start and end times

You check your watch at the start: 8:00.
You check it at the destination: 24:00.
Total time: 16 hours.

But that total includes:
- the actual driving time,
- rest-stop breaks,
- traffic-jam waits,
- meal stops.

You have no idea which segment took how long.

Method 2: a radar gun on every segment

The highway authority installs radar guns on each segment, recording when you enter and leave:
- Segment 1: 2 hours
- Segment 2: 3 hours
- Segment 3: 8 hours
- Segment 4: 3 hours

Now you know each segment precisely, and it's easier to spot problems (why is segment 3 so slow?).

PTP's two delay measurement mechanisms are like these two methods:

- The E2E mechanism: measures the total delay over the whole path.
- The P2P mechanism: measures delay link by link.

## The basic principle of the P2P mechanism

### The core idea

The core idea of the P2P (peer-to-peer) mechanism: let every pair of adjacent ports measure the link delay between them.

Unlike E2E, where the slave measures the whole path to the master, P2P has the devices at each end of every link measure the delay between themselves.

### The message exchange

The P2P mechanism involves three message types (the third appears only in two-step):

1. Pdelay_Req: sent by the requester, asking to measure the link delay.
2. Pdelay_Resp: replied by the responder, carrying the receive timestamp.
3. Pdelay_Resp_Follow_Up: sent only when the responding port is a two-step port, carrying the send timestamp. Whether it is sent is decided by the responding port itself, and the requester is told through the `twoStepFlag` in the Pdelay_Resp header.

The exchange sequence:

```
Requester (A)                            Responder (B)
    |                                       |
    |------ Pdelay_Req (t1) --------------->| (t2)
    |                                       |
    |<----- Pdelay_Resp (t4) ---------------| (t3)
    |                                       |
    |<----- Pdelay_Resp_Follow_Up (two-step)|
    |                                       |
```

The four timestamps:

- t1: when the requester sent Pdelay_Req.
- t2: when the responder received Pdelay_Req.
- t3: when the responder sent Pdelay_Resp.
- t4: when the requester received Pdelay_Resp.

### The key difference from E2E

| Feature | E2E | P2P |
|:---|:---|:---|
| **Who initiates** | The slave clock | Every port (master or slave) |
| **What is measured** | The whole path, master to slave | The link between two adjacent ports |
| **Message types** | Sync + Delay_Req + Delay_Resp | Pdelay_Req + Pdelay_Resp + Pdelay_Resp_Follow_Up |
| **Transparent clock handling** | E2E TC forwards Delay_Req/Resp | P2P TC should drop Delay_Req/Resp and answer Pdelay_Req |
| **Applications** | General | Per-link measurement, or P2P TC networks |

## The math behind P2P

### The basic formula

Like E2E, P2P uses four timestamps to compute the delay. The standard calls this expression a **nominal value**:

```
meanLinkDelay = [(t2 − t1) + (t4 − t3)] / 2
```

But there's a key difference: t1, t2, t3, and t4 come from two adjacent ports, not the master and slave.

That means:
- t1 and t4 are recorded by the requester.
- t2 and t3 are recorded by the responder.

### One-step mode

In one-step mode, the Pdelay_Resp carries the time information directly.

The responder's handling:

The responder records t2 when it receives Pdelay_Req and t3 when it sends Pdelay_Resp.

Pdelay_Resp.correctionField carries (t3 − t2): the responder's turnaround time.

The requester's computation:

```
meanLinkDelay = [(t4 − t1) − correctedPdelayRespCorrectionField] / 2
              = [(t4 − t1) − (t3 − t2)] / 2   (delayAsymmetry = 0)
              = [(t2 − t1) + (t4 − t3)] / 2
```

### Two-step mode

In two-step mode, the Pdelay_Resp is followed by a Pdelay_Resp_Follow_Up.

The responder's handling:

The responder records t2 when it receives Pdelay_Req and t3 when it sends Pdelay_Resp.

There are **two options** for putting t2 and t3 into the messages:

- **Option A**: set both `requestReceiptTimestamp` in the Pdelay_Resp and `responseOriginTimestamp` in the Pdelay_Resp_Follow_Up to 0, and add the turnaround time (t3 − t2) to the **Pdelay_Resp_Follow_Up.correctionField**.
- **Option B**: the Pdelay_Resp carries t2 (`requestReceiptTimestamp`, with t2's fractional-nanosecond part subtracted from correctionField), and the Pdelay_Resp_Follow_Up carries t3 (`responseOriginTimestamp`, with t3's fractional-nanosecond part added to correctionField).

> linuxptp implements **Option B**: it writes t2 into `requestReceiptTimestamp` and t3 into `responseOriginTimestamp`.

The requester's computation:

The standard's full expression subtracts four terms, as rigorous as the complete meanPathDelay formula with correctionField in 2.7:

```
meanLinkDelay = [(t4 − t1)
                 − (responseOriginTimestamp − requestReceiptTimestamp)
                 − correctedPdelayRespCorrectionField
                 − Pdelay_Resp_Follow_Up.correctionField] / 2
```

where:

- **correctedPdelayRespCorrectionField** = Pdelay_Resp.correctionField + ingressDelayAsymmetry
  (the requester corrects the received Pdelay_Resp with the `delayAsymmetry` on its own ingress side; in two-step, Pdelay_Resp.correctionField itself is set to 0)

Plug in Option B's t2 and t3 and you get the textbook form. Go one step further: when **both ingress and egress delayAsymmetry are 0 and no transparent clock has accumulated correctionField along the link**, the last two terms vanish, and the expression reduces to:

```
meanLinkDelay = [(t4 − t1) − (t3 − t2)] / 2
              = [(t2 − t1) + (t4 − t3)] / 2
```

If the responder implements **Option A**, then (responseOriginTimestamp − requestReceiptTimestamp) = 0, and the turnaround time (t3 − t2) comes from the `Pdelay_Resp_Follow_Up.correctionField` term instead. Plugging that into the full expression gives the same result as Option B.

### Why two modes?

One-step mode:
- Advantage: only two messages, efficient.
- Disadvantage: must precisely measure t3 when sending Pdelay_Resp; demanding on hardware.

Two-step mode:
- Advantage: can carry a precise t3 in the Pdelay_Resp_Follow_Up; simpler to implement.
- Disadvantage: three messages; more overhead.

IEEE 1588 does **not** say which one an implementer should choose, and it does not describe which is more common in the market. This book makes no such claim either.

### The easily overlooked premise: the two ends' frequencies must be close

In `meanLinkDelay = [(t2 − t1) + (t4 − t3)] / 2`, t1 and t4 come from the **requester** and t2 and t3 from the **responder**, so they are **two different clocks**. Cutting the round trip in half assumes both clocks run at the same rate.

If the two ends' frequencies differ, that halving doesn't hold. The standard warns explicitly:

> When the timestamping clock used by a PTP port is **not** the local PTP clock (for example, a port of a **transparent clock that has not been frequency-synchronized**), the measurement of `<meanLinkDelay>` will deviate from the expected value because of syntonization error.

This is P2P's weak spot: **P2P requires every device on the link, including transparent clocks, to take part in the measurement**, and transparent clocks often only pass time through without frequency synchronization. E2E has the same issue, but only between master and slave, so its scope is narrower.

For this, the standard defines two frequency ratios:

- **`<neighborRateRatio>`**: the local clock frequency of the upstream PTP instance divided by this end's local clock frequency. From the measurement point of view there is an equivalent statement: the timestamping clock frequency of the responding port divided by that of the requesting port. Under the "cumulative frequency transfer" option, a P2P port shall compute it alongside `<meanLinkDelay>`. The standard's example estimate takes two sets of timestamps N measurements apart and forms the ratio of the increments (numerator is t3 at the responder, denominator is t4 at the requester, exactly the "responder ÷ requester" above):

  ```
  neighborRateRatio = [(t3)_N − (t3)_0] / [(t4)_N − (t4)_0]
  ```

- **`<cumulativeRateRatio>`**: Grandmaster clock frequency divided by this end's local clock frequency.

Once you have this ratio, you can subtract the measurement error caused by "different frequencies at the two ends" from `<meanLinkDelay>` instead of letting it accumulate.

## A complete P2P measurement example

### Scenario

```
Port A ---- link ---- Port B
```

Parameters:
- True link delay: 100 ns (symmetric).
- Port A's time: normal.
- Port B's time: normal (assumed already synchronized).

### The message exchange

Step 1: port A sends Pdelay_Req

- Send time: t1 = 1000.000000000 s

Step 2: port B receives Pdelay_Req

- Receive time: t2 = 1000.000000100 s (100 ns later)

Step 3: port B sends Pdelay_Resp

- Send time: t3 = 1000.000001000 s (assume 900 ns processing delay)

Step 4: port A receives Pdelay_Resp

- Receive time: t4 = 1000.000001100 s (t3 + 100 ns)

### Computation

The four timestamps:

- t1 = 1000.000000000 s
- t2 = 1000.000000100 s
- t3 = 1000.000001000 s
- t4 = 1000.000001100 s

Compute meanLinkDelay:

```
meanLinkDelay = [(t2 − t1) + (t4 − t3)] / 2
              = [(100 ns) + (100 ns)] / 2
              = 100 ns
```

Correct!

Note: the responder's turnaround time (t3 − t2 = 900 ns) has no effect on the result, because it cancels out.

## The P2P mechanism and transparent clocks

### The P2P transparent clock's special handling

A P2P transparent clock (P2P TC) measures residence time and also:

1. Measures link delay: for each port, uses the P2P mechanism to measure the link delay to the peer.
2. Accumulates into the correctionField: when forwarding Sync, adds residence time + ingress link delay.

### The P2P TC's workflow

Scenario:

```
Master ---- TC_B ---- Slave
```

TC_B's port 1 (toward the master):

1. Periodically sends Pdelay_Req to the master.
2. Receives Pdelay_Resp, computes meanLinkDelay_1.
3. Listens for the master's Sync.

TC_B's port 2 (toward the slave):

1. Periodically sends Pdelay_Req to the slave.
2. Receives Pdelay_Resp, computes meanLinkDelay_2.
3. Forwards the Sync to the slave.

Handling the forwarded Sync:

When a Sync arrives at port 1 and leaves port 2:

```
Sync.correctionField (egress) = Sync.correctionField (ingress)
                               + residenceTime
                               + meanLinkDelay_1
                               + ingressDelayAsymmetry
```

Key point: meanLinkDelay_1 is the ingress link's delay (master → TC_B).

## P2P vs. E2E: a deep comparison

### Measurement granularity

E2E:
- Measures the delay over the whole path.
- Includes all link delays + all transparent-clock residence times.
- Cannot tell which segment contributed how much.

P2P:
- Measures each link's delay.
- Knows every segment's delay precisely.
- Easier to diagnose and optimize.

### Asymmetry handling

E2E:
- Asymmetry over the whole path affects offsetFromMaster.
- Hard to handle each segment's asymmetry separately.
- Relies on a configured delayAsymmetry.

P2P:
- Each segment's asymmetry is handled independently.
- Can configure each segment's asymmetry separately.
- Finer-grained control.

### Effect of network size

E2E:
- As the number of slaves grows, Delay_Req volume grows linearly.
- Heavy master load.
- Can become a bottleneck.

P2P:
- Every port measures independently; load is spread out.
- No central bottleneck.
- Better suited to large networks.

### Convergence speed

E2E:
- A new device needs a full message exchange to join.
- Convergence depends on the Sync and Delay_Req intervals.
- Order of magnitude: by rule of thumb, a few seconds to tens of seconds (**this is an engineering estimate; the standard specifies no convergence-time metric**; it is mainly determined by `logSyncInterval` and `logMinDelayReqInterval`).

P2P:
- A new device begins P2P measurement immediately.
- Each end of the link holds its own `<meanLinkDelay>`, so after a network reconfiguration it can correct the path delay **immediately**, without waiting for another end-to-end measurement round.
- Faster convergence.

### Topology requirements

E2E:
- No special topology requirements.
- Ordinary switches (non-PTP devices) can sit in the middle.
- Good compatibility.

P2P:
- Requires all devices to support the P2P mechanism.
- No ordinary switches in the middle.
- Stricter requirements.

### Message volume

E2E:
- Per slave: 1 Delay_Req + 1 Delay_Resp.
- Volume = 2 × number of slaves.

P2P:
- Each end of every link measures once: per end 1 Pdelay_Req + 1 Pdelay_Resp (plus 1 Pdelay_Resp_Follow_Up when the responder is two-step).
- Volume = 4 (or 6) × number of links.

Comparison:

Suppose:
- The network has 100 devices in a tree topology.
- Number of slaves: 99.
- Number of links: 99.

E2E message volume: 2 × 99 = 198.

P2P message volume: 4 × 99 = 396 (one-step) or 6 × 99 = 594 (two-step).

P2P's total delay-message count is two or even three times E2E's, but consider the distribution:

E2E's messages originate at the slaves, every Delay_Req heads to the master, putting load on it.

P2P's messages originate at every port, load is spread across the whole network.

## Typical applications of P2P

### Scenario 1: TSN networks (time-sensitive networking)

TSN (Time-Sensitive Networking) is a set of IEEE 802.1 standards delivering real-time guarantees over Ethernet.

TSN's time synchronization is specified by a separate standard, **IEEE 802.1AS** (known in the industry as gPTP). It is not a profile defined by 1588, but it is based on PTP, and it requires:

- full-duplex Ethernet links to use the peer-delay measurement mechanism,
- the relay instance to be mathematically equivalent to a P2P transparent clock for synchronization calculations, though it does **not** fully conform to 1588's specification for P2P transparent clocks; it runs its own BMCA, with an algorithm that is **largely identical to 1588's, only somewhat simplified**,
- a steady-state end-to-end metric: two instances within 7 hops have a time error of no more than 1 µs peak to peak.

**Why does TSN choose P2P?**

TSN networks usually serve industrial automation and automotive electronics, which demand:
- fast convergence (quick sync when a device joins),
- deterministic delay (each segment's delay known),
- high reliability (fast fault switchover).

The P2P mechanism meets these requirements.

### Scenario 2: telecommunications

ITU-T defines the G.8275.1 and G.8275.2 profiles for telecom network time synchronization.

Which delay mechanism each profile specifies must be taken from the ITU-T text itself: neither 1588 nor 802.1AS mentions G.8275, and this book makes no assertion.

### Scenario 3: White Rabbit

White Rabbit is an open-source, ultra-high-precision synchronization solution built on PTP + SyncE (synchronous Ethernet).

White Rabbit's specification carrier is the High Accuracy **Delay Request-Response** Default Profile (P2P is only optional in it). It extends it with:
- precise link-delay measurement (using DDMTD phase detectors),
- frequency synchronization (through SyncE),
- asymmetry calibration (hardware measurement of fiber asymmetry).

It achieves **sub-nanosecond synchronization**.

## Implementation challenges of P2P

### Challenge 1: all devices must support P2P

The P2P mechanism requires every device in the network to support P2P.

An ordinary switch (P2P-incapable) in the middle causes a problem: it won't answer Pdelay_Req, so P2P measurement fails.

If multiple devices connect to the same ordinary switch, a single Pdelay_Req can be received by multiple devices, violating P2P's "one-to-one" assumption. Receiving more than one Pdelay_Resp is abnormal, and the standard **requires** action: an ordinary or boundary clock enters FAULTY (a transparent clock signals a fault condition), or the implementation takes its own measures.

Solutions:

- Plan the network so every device supports P2P.
- Or use boundary clocks to isolate P2P-incapable regions.

### Challenge 2: frequent P2P measurement

P2P requires every port to send Pdelay_Req periodically, which can raise CPU and network load.

Suggestions:

- Adjust the Pdelay_Req interval to the network's stability.
- A stable network can use a larger interval.
- The lower bound is set by the default profile: `logMinPdelayReqInterval` defaults to 0 and can be configured from 0 to 5, that is, 1 second to 32 seconds.

### Challenge 3: resource management on multi-port devices

Boundary clocks and P2P transparent clocks have multiple ports; each port needs:
- an independent P2P state machine,
- independent meanLinkDelay storage,
- independent Pdelay message send/receive.

**Resource consumption** (the following is an **engineering estimate**; the standard provides no resource-usage metrics):

- Per port: state machine + `portDS.meanLinkDelay` + send/receive buffers, on the order of a few KB of memory.
- Per port: an independent timer.
- Message processing: each port sends and receives Pdelay messages at the configured average interval (under the default profile, the average interval is 1 s to 32 s); shorter intervals mean more messages.

On a 64-port switch, all this adds up.

## A complete P2P network example

### Topology

```
Master A ---- P2P_TC_B ---- P2P_TC_C ---- Slave D
```

### The initialization phase

P2P_TC_B's port 1 establishes P2P measurement with master A:

1. Port 1 sends Pdelay_Req.
2. Master A replies Pdelay_Resp.
3. Port 1 computes meanLinkDelay_AB = 100 ns.

P2P_TC_B's port 2 establishes P2P measurement with P2P_TC_C's port 1:

1. Port 2 sends Pdelay_Req.
2. P2P_TC_C's port 1 replies Pdelay_Resp.
3. Port 2 computes meanLinkDelay_BC = 150 ns.

P2P_TC_C's port 2 establishes P2P measurement with slave D:

1. Port 2 sends Pdelay_Req.
2. Slave D replies Pdelay_Resp.
3. Port 2 computes meanLinkDelay_CD = 120 ns.

### The synchronization phase

Master A sends Sync:

- originTimestamp = 1000.000000000 s
- correctionField = 0

P2P_TC_B processes the Sync:

Receives the Sync (port 1):
- Records the ingress timestamp.
- originTimestamp = 1000.000000000 s
- correctionField = 0

Forwards the Sync (port 2):
- Computes the residence time: residenceTime_B = 5 µs
- meanLinkDelay_AB = 100 ns
- ingressAsymmetry = 0

Updates the correctionField:

```
correctionField = 0 + 5 µs + 100 ns + 0 = 5.1 µs
```

P2P_TC_C processes the Sync:

Receives the Sync (port 1):
- correctionField = 5.1 µs

Forwards the Sync (port 2):
- Computes the residence time: residenceTime_C = 3 µs
- meanLinkDelay_BC = 150 ns
- ingressAsymmetry = 0

Updates the correctionField:

```
correctionField = 5.1 µs + 3 µs + 150 ns + 0 = 8.25 µs
```

Slave D receives the Sync:

- originTimestamp = 1000.000000000 s
- correctionField = 8.25 µs
- meanLinkDelay_CD = 120 ns (already measured via P2P)

Compute the master-clock time at the instant D receives the Sync:

```
Corrected master send time = originTimestamp + correctionField
                           = 1000.000000000 + 0.00000825
                           = 1000.000008250 s

Path delay = meanLinkDelay_CD = 120 ns

Master-clock time at D's Sync receipt = 1000.000008250 + 0.000000120
                                       = 1000.000008370 s
```

offsetFromMaster = the slave-clock time at Sync receipt − the master-clock time at Sync receipt

The slave can then adjust its clock accordingly.

Key point: the slave does not need to send Delay_Req, because the path delay has already been accumulated into the correctionField by the P2P TCs.

## Summary: the P2P mechanism's core points

Core ideas:
- Measure delay link by link.
- Each port independently measures the delay to its peer.
- P2P TCs accumulate link delays into the correctionField.

Message exchange:
- Pdelay_Req: sent by the requester (**each end of the link sends its own**).
- Pdelay_Resp: replied by the responder.
- Pdelay_Resp_Follow_Up: sent **only when the responding port is two-step** (indicated by the Pdelay_Resp's `twoStepFlag`); carries the precise timestamp.

Core formula (**nominal value**):

```
meanLinkDelay = [(t2 − t1) + (t4 − t3)] / 2
```

The P2P TC's handling:

```
Sync.correctionField += residenceTime + meanLinkDelay + ingressAsymmetry
```

Comparison with E2E:

| Feature | E2E | P2P |
|:---|:---|:---|
| Measurement target | The whole path | Each link |
| Message volume | 2 × #slaves | **4–6 × #links** (each end measures once) |
| Load distribution | Concentrated at the master | Spread across the network |
| Network requirements | None special | All devices must support P2P |
| Convergence speed | Slower | Faster |
| Asymmetry handling | Coarse-grained | Fine-grained |

Applications:
- TSN networks
- Large, high-accuracy networks
