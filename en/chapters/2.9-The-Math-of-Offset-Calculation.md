# 2.9 The Math of Offset Calculation: From Timestamps to Clock Adjustment

## A deceptively simple question: how do you "set the watch"?

Suppose your watch is 5 minutes fast relative to standard time.

How do you fix it?

Simply turn the hands back 5 minutes. Problem solved.

That is phase adjustment: correcting the clock's time value in one step.

A PTP slave faces the same question:

- It knows offsetFromMaster (say, +50 ns).
- How should it adjust the local clock?

The question here is narrow: how to adjust the clock to the correct time.

## What is phase offset?

Phase offset: at a given instant, the difference between the slave-clock time and the master-clock time.

Symbol: offset, or θ

Units: time (seconds, nanoseconds, etc.)

Analogy: like two runners, at some instant, one is 5 meters ahead of the other. That 5-meter gap is the phase offset.

Phase offset can be eliminated with a one-time adjustment: let the lagging runner sprint 5 meters forward, and the two are side by side.

## The complete PTP time-offset formula

### Review of the basic formula

Sections 2.7 and 2.8 derived the basic formula:

```
offsetFromMaster = [(t2 − t1) − (t4 − t3)] / 2
```

### The real formula: accounting for the correctionField

One-step mode:

```
offsetFromMaster = t2 − originTimestamp − meanDelay − correctedSyncCorrectionField
```

Two-step mode:

```
offsetFromMaster = t2 − preciseOriginTimestamp − meanDelay
                   − correctedSyncCorrectionField − Follow_Up.correctionField
```

Where:

```
meanDelay = meanPathDelay (E2E), or meanLinkDelay (P2P), or 0

correctedSyncCorrectionField = Sync.correctionField + ingressDelayAsymmetry
```

### A complete worked example

Input data:

- t2 = 1000.000000150 s (the slave's Sync receive time)
- preciseOriginTimestamp = 1000.000000000 s
- meanDelay = 100 ns
- Sync.correctionField = 5 µs (accumulated by transparent clocks)
- Follow_Up.correctionField = 0.5 ns (fractional part)
- ingressDelayAsymmetry = 0

Computation:

```
correctedSyncCorrectionField = 5 µs + 0 = 5 µs

offsetFromMaster = t2 − preciseOriginTimestamp − meanDelay
                   − correctedSyncCorrectionField − Follow_Up.correctionField

                 = 1000.000000150 − 1000.000000000 − 0.000000100
                   − 0.000005000 − 0.0000000005

                 = −0.0000049505 s

                 = −4950.5 ns
```

Interpretation: the slave is 4,950.5 ns behind the master; it needs to move forward 4,950.5 ns.

## Phase adjustment: directly modifying the clock value

### The simplest method: the step adjustment

Step adjustment: directly add to or subtract offsetFromMaster from the local clock.

```
new local time = current local time − offsetFromMaster
```

Example:

```
offsetFromMaster = −4950.5 ns (slave is 4950.5 ns behind)
current local time = 1000.000000150 s
new local time = 1000.000000150 + 0.0000049505 = 1000.0000051005 s
```

Adjustment complete; the slave is aligned with the master.

### The problems with step adjustment

Problem 1: time going backwards

If offsetFromMaster is positive and large (say, the slave is 1 second fast), the adjustment makes the local clock move backwards:

```
offsetFromMaster = +1 s (slave is 1 s fast)
current local time = 10:00:05
new local time = 10:00:05 − 1 s = 10:00:04
```

The time jumps from 10:00:05 back to 10:00:04. It went backwards.

This causes:
- log timestamps going backwards, hard to analyze,
- event ordering confusion,
- possible application crashes.

Problem 2: time jumping

Even without going backwards, the time jumps:

```
Before: local clock shows 10:00:00.000
After:  local clock shows 10:00:00.050
```

The 0.050 s in between was "skipped." Applications depending on time continuity may misbehave.

## How to avoid the problems?

### Method 1: limit the adjustment magnitude

Strategy: if the deviation is too large, apply many small adjustments.

Example:

```
offsetFromMaster = −1 s

Split 1 s into many small adjustments:
- 1st: adjust 100 ms
- 2nd: adjust 100 ms
- ...
- 10th: adjust 100 ms

Total adjusted: 1 s, but each adjustment is small and its impact is controllable.
```

### Method 2: set an adjustment threshold

Strategy: set a threshold. Adjust only above the threshold; below it, don't adjust (or use another approach).

Example:

```
threshold = 100 ns

offsetFromMaster = −50 ns
|offsetFromMaster| < threshold
Don't adjust (deviation too small to matter)

offsetFromMaster = −500 ns
|offsetFromMaster| > threshold
Apply a step adjustment
```

Rationale:
- Small deviation: likely just measurement noise; adjusting only adds noise.
- Large deviation: genuinely needs adjustment.

### Method 3: forbid time going backwards

Strategy: if the adjustment would move time backwards, refuse to adjust, or wait.

Example:

```
offsetFromMaster = +1 s (would move time backwards)

Option A: refuse the adjustment, log a warning.
Option B: wait until the local clock naturally reaches the target time (wait 1 s).
```

## Implementing phase adjustment

### Software clock adjustment

Principle: the local hardware counter is read by software, which adds an offset.

```
software time = hardware counter value + phase_offset
```

Step adjustment: directly modify phase_offset.

```
phase_offset_new = phase_offset_old − offsetFromMaster
```

Advantages: simple, flexible.

Disadvantages: accuracy limited by software latency.

### Hardware clock adjustment

Principle: use a programmable hardware clock and write directly to hardware registers.

Step adjustment: write the new time value directly.

```
hardware clock register = current value − offsetFromMaster
```

Advantages: high accuracy, no software latency.

Disadvantages: needs dedicated hardware.

## A complete phase-adjustment example

### Scenario

- The slave has just started.
- Initial deviation from the master: +1 ms (slave fast).
- Adjustment threshold: 10 µs.

### Steps

Step 1: measure the deviation

```
measured offsetFromMaster = +1 ms = +1000 µs
```

Step 2: decide whether to adjust

```
|offsetFromMaster| = 1000 µs > threshold (10 µs)
Needs adjustment.
```

Step 3: check whether it would go backwards

```
offsetFromMaster > 0 (positive)
Would move time backwards.

Check the backward magnitude: 1 ms.
Acceptable? Depends on the application's requirements.
```

Step 4: execute the adjustment

Assuming the backward jump is acceptable, apply the step adjustment:

```
new local time = current local time − 1 ms
```

Step 5: verify

```
Measure offsetFromMaster again.
Ideally, close to zero.
```

## Summary

Phase offset: the difference between the slave and master clocks at a given instant.

Phase adjustment: directly modifying the clock's time value to align the two.

Formula:

```
offsetFromMaster = t2 − preciseOriginTimestamp − meanDelay − correctionField
```

Step adjustment: directly modifying the clock value.

Potential problems:
- Time going backwards.
- Time jumping.

Counter-strategies:
- Limit the adjustment magnitude.
- Set an adjustment threshold.
- Forbid time going backwards.

Phase adjustment sets the clock to the correct time.

Setting the clock once only fixes the offset at that instant.

Suppose you align the slave exactly with the master. A while later, you measure again and find a deviation.

The two clocks may run at different rates. Even if aligned right now, they will separate again.

That is the frequency offset problem: you need to adjust the clock's "heartbeat rate" to keep it synchronized over the long term.

Section 2.10 covers frequency synchronization.

Alignment at one instant is not full synchronization.

Imagine two runners: you place them side by side now, but one runs fast and one runs slow.

A minute later they're 1 m apart. Ten minutes later, 10 m apart.

Phase adjustment handles "alignment"; frequency adjustment handles "rate."
