# 3.10 Management Protocol and pmc: PTP's Remote Control

## Why a management channel at all?

Configuration and introspection of a live PTP node happen through the management protocol:

- GET: read a data set (status).
- SET: change a parameter.
- COMMAND: execute an operation (e.g., INITIALIZE).
- RESPONSE / ACKNOWLEDGE: replies.

LinuxPTP serves management over a Unix-domain socket by default (UDS, `/var/run/ptp4l`), and the `pmc` tool is the client.

## The management message

Per msg.h (lines 171-179), after the 34-byte header comes:

```c
struct management_msg {
    struct ptp_header   hdr;
    struct PortIdentity targetPortIdentity;     /* 10 bytes */
    UInteger8           startingBoundaryHops;
    UInteger8           boundaryHops;
    uint8_t             flags;         /* high nibble reserved | low nibble actionField */
    uint8_t             reserved;
    /* TLVs follow */
};
```

Notes:

- `sequenceId` is in the common header, not the body.
- `targetPortIdentity` with an all-ones clockIdentity and portNumber 0xFFFF means "broadcast".
- `boundaryHops`: decremented by each boundary clock; 0 means the message is not retransmitted.

### The action field

```c
enum management_action {
    GET,         /* read */
    SET,         /* write */
    RESPONSE,    /* reply */
    COMMAND,     /* command */
    ACKNOWLEDGE, /* acknowledgement */
};
```

## Boundary-hop propagation

Per 15.3.3, a boundary clock retransmits multicast management messages:

- only those received on a port in MASTER, SLAVE, UNCALIBRATED, or PRE_MASTER;
- with `boundaryHops` decremented by one;
- and only if the result is > 0;
- retransmitted only via ports in those four states.

Practical effect: `-b 0` reaches the local device; `-b 1` crosses one BC; larger values reach further.

## pmc basics

`pmc` sends management messages to a ptp4l instance, over UDS locally or over the network.

Common options:

```
-u            use the Unix-domain socket (local)
-b 0          boundaryHops = 0 (local)
-i <if>       network interface
-t <hex>      transportSpecific
-s <path>     UDS server address (default /var/run/ptp4l)
```

Commands are the `[action] ID` style, case-insensitive and abbreviatable.

### Interactive mode

```
$ pmc -u
pmc> GET CURRENT_DATA_SET
	aabbcc.fffe.ddeeff-0 seq 1 RESPONSE MANAGEMENT CURRENT_DATA_SET
		stepsRemoved     0
		offsetFromMaster 0.0
		meanPathDelay    0.0
pmc> GET TIME_STATUS_NP
	aabbcc.fffe.ddeeff-0 seq 2 RESPONSE MANAGEMENT TIME_STATUS_NP
		master_offset              0
		ingress_time               0
		cumulativeScaledRateOffset +0.000000000
		scaledLastGmPhaseChange    0
		gmTimeBaseIndicator        0
		lastGmPhaseChange          0x0000'0000000000000000.0000
		gmPresent                  false
		gmIdentity                 aabbcc.fffe.ddeeff
```

`pmc> help` lists every recognized management ID.

## The management bytes (again)

A `GET CURRENT_DATA_SET` request:

```
type 0x0001  length 0x0002  id 0x2001
```

The response:

```
type 0x0001  length 0x0014  id 0x2001  stepsRemoved + offset + delay (18-byte data + 2-byte id)
```

Management errors come back as `MANAGEMENT_ERROR_STATUS` (see section 2.14); GENERAL_ERROR is 0xFFFE.

## Reading what matters

| Goal | Command | Look at |
|:---|:---|:---|
| Port state | `GET PORT_DATA_SET` | portState |
| Parent | `GET PARENT_DATA_SET` | parent/grandmaster identity |
| Live offset | `GET TIME_STATUS_NP` | master_offset, gmPresent, gmIdentity |
| Deviation & mean delay | `GET CURRENT_DATA_SET` | offsetFromMaster, meanPathDelay |
| Priority | `GET DEFAULT_DATA_SET` | priority1/priority2 |
| Intervals | `GET PORT_DATA_SET` | logAnnounceInterval, announceReceiptTimeout, ... |
| Extended port info | `GET PORT_PROPERTIES_NP` | portState, timestamping, interface |

Version note: on LinuxPTP 1.9.2 (Ubuntu 20.04), several `_NP` GETs that exist in newer linuxptp are not recognized (`PORT_STATS_NP`, `PORT_SERVICE_STATS_NP`, `SUBSCRIBE_EVENTS_NP`, `UNICAST_MASTER_TABLE_NP`), pmc reports `bad command`. They require LinuxPTP 3.x.

## Setting

SET requests are validated client-side. Two examples that work everywhere:

```
pmc -u "SET GRANDMASTER_SETTINGS_NP clockClass 6 clockAccuracy 0x21 \
    offsetScaledLogVariance 0x4e5d currentUtcOffset 37 \
    leap61 0 leap59 0 currentUtcOffsetValid 1 \
    ptpTimescale 1 timeTraceable 1 frequencyTraceable 1 timeSource 0x20"
```

and

```
pmc -u "SET PRIORITY1 100"
```

pmc rejects obviously invalid SETs *client-side*: `SET CLOCK_DESCRIPTION` would not reach the server, pmc itself reports `CLOCK_DESCRIPTION only allows GET`. So on 1.9.2 it's hard to trigger a server-side MANAGEMENT_ERROR_STATUS through pmc.

## What the outputs actually mean

- `portState: SLAVE` / `MASTER`, the FSM state (section 3.3).
- `master_offset` / `offsetFromMaster`, in nanoseconds (TimeInterval divided by 65536 was printed by older pmc).
- `meanPathDelay` (CURRENT_DATA_SET), the E2E mean path delay.
- `gmIdentity` / `grandmasterIdentity`, who you actually sync to.
- `stepsRemoved`, hops to the grandmaster.

## Common workflows

```bash
# diagnose "can't sync"
pmc -u "GET PORT_DATA_SET"          # portState?
pmc -u "GET PARENT_DATA_SET"        # grandmaster?
pmc -u "GET TIME_STATUS_NP"         # offset / gm present?

# monitor
pmc -u "GET TIME_STATUS_NP" | grep -E "master_offset|gmIdentity"

# promote a device
pmc -u "SET PRIORITY1 100"
```

## Summary

- The management protocol = management message + management TLV over UDS or UDP.
- `pmc` is the shell: GET/SET/COMMAND, interactive or batch.
- `_NP` management IDs extend linuxptp beyond the standard, and some of them require a newer version than 1.9.2.
- pmc filters invalid SETs before they reach the server.
