# 3.12 Unicast Negotiation: PTP's Private Line Service

## When a slave wants to be a "guest"

In PTP there is a guest relationship: a slave *requests* that the master send it unicast Announce, Sync, and Delay_Resp, per message type, at an agreed rate, for an agreed duration.

LinuxPTP implements both mechanisms:

- on the master side: `unicast_listen`, accept requests, grant unicast streams;
- on the slave side: a `[unicast_master_table]` describing candidate masters, and automatic REQUEST/GRANT handling.

## The negotiation TLVs (recap)

The TLVs from section 2.15 appear in code (`tlv.h` / `unicast_client.c`):

```c
struct request_unicast_xmit_tlv {   /* 0x0004, length 6 */
    Enumeration16 type;
    UInteger16    length;
    uint8_t       message_type;          /* the requested type, high nibble */
    Integer8      logInterMessagePeriod; /* 2^interval seconds */
    UInteger32    durationField;         /* seconds */
};

struct grant_unicast_xmit_tlv {     /* 0x0005, length 8 */
    Enumeration16 type;
    UInteger16    length;
    uint8_t       message_type;
    Integer8      logInterMessagePeriod;
    UInteger32    durationField;    /* 0 == denied */
    uint8_t       reserved;
    uint8_t       flags;            /* bit 0: GRANT_UNICAST_RENEWAL_INVITED */
};

struct cancel_unicast_xmit_tlv {    /* 0x0006 */
    Enumeration16 type;
    UInteger16    length;           /* 2 */
    uint8_t       message_type_flags;  /* type high nibble;
                                          bit1 G(maintainGrant), bit0 R(maintainRequest) */
    uint8_t       reserved;
};
```

LinuxPTP encodes the message type by shifting left four bits (`message_type << 4`), matching the standard's high-nibble placement:

```c
req->message_type = message_type << 4;        /* unicast_client.c */
```

so requests look like:

```
request Sync:        0x00
request Announce:    0xB0
request Delay_Resp:  0x90
request Pdelay_Resp: 0x30
```

## The configuration

Master (`[global]`):

```ini
hybrid_e2e               1
inhibit_multicast_service 1
unicast_listen           1
```

Slave (`[global]` + `[unicast_master_table]`):

```ini
[global]
unicast_req_duration 60

[unicast_master_table]
table_id 1
logQueryInterval 2
UDPv4 192.168.1.10
UDPv4 192.168.1.20

[eth0]
unicast_master_table 1
```

Key points:

- `unicast_listen` makes the master answer unicast REQUESTs.
- `[unicast_master_table]` lists a table of masters for the slave; entries are `<transport> <address>`, `UDPv4 <ip>`, `UDPv6`, or `L2 <mac>`.
- `unicast_master_table` on the port selects which table to use.
- `unicast_req_duration` is the requested grant length in seconds.

There is no `master_address` option and no `logDelayReqInterval`; the Delay_Req interval item is `logMinDelayReqInterval`. If you enable `inhibit_multicast_service`, the slave must get *everything* via unicast.

## The client flow (unicast_client.c)

For each configured master entry, the slave maintains a client state. The core loop:

1. Request: when no active grant exists for a type (or it's expiring), send `REQUEST_UNICAST_TRANSMISSION` for Sync / Announce / Delay_Resp.
2. Wait: mark the type as waiting, set a timeout.
3. Grant received: that type becomes *granted*; messages arrive unicast on the regular sockets.
4. Denied (grant with duration 0) or timeout: back off and retry.
5. Cancellation: when a grant expires, send `CANCEL_UNICAST_TRANSMISSION` (if you still want it, set the maintainRequest bit so the master knows to expect a fresh REQUEST).

The domain's aggregate types feed `port.c`'s normal RX path, so the rest of the stack (BMCA, servo) is unaware the deliveries are unicast.

## The master side (port.c / msg.c)

On `unicast_listen`, the master:

1. Tracks per-requester grants (message type, interval, duration, remaining time).
2. Runs a timer to send the granted unicast Announce/Sync/Delay_Resp at the agreed rate.
3. Honors RENEWAL_INVITED: on a fresh REQUEST for the same type, re-grants.
4. Enforces resource limits: grants are tracked per requester, and the number of servicable clients is bounded by available memory and the configured grant durations.

## Sending and receiving paths

- Unicast messages use the same `transport_send`/`transport_recv` machinery as multicast, but target a specific `struct address` instead of the multicast group.
- The negotiated mode still marks two-step Syncs; Announce carries the grandmaster attributes regardless of delivery mode.
- `hybrid_e2e` means exactly what it says: multicast for discovery, unicast for the negotiated streams.

## Troubleshooting

| Symptom | Likely cause |
|:---|:---|
| `bad command: GET UNICAST_MASTER_TABLE_NP` | linuxptp 1.9.2; the TLV is 3.x-only |
| Requests never granted | master lacks `unicast_listen`, or `hybrid_e2e`/`inhibit_multicast_service` mis-set |
| Grant duration long, stream short | `unicast_req_duration` too small on the slave |
| Two masters serving one slave | table order/duplicate addresses |

## Summary

- Unicast negotiation trades multicast for per-type grants negotiated via REQUEST/GRANT/CANCEL/ACK.
- The slave enumerates masters in `[unicast_master_table]`; the master advertises via `unicast_listen`.
- Message types ride in the high nibble; CANCEL/ACK carry maintainRequest/maintainGrant flags.
- It works with hybrid operation (multicast discovery + unicast streams).
