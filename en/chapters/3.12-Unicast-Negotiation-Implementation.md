# 3.12 Unicast Negotiation Implementation: PTP's Private Line Service

## Why unicast

PTP uses multicast by default, but some networks need unicast:

```text
Limitations of multicast:

1. Crossing subnets
   - Routers may block multicast
   - TTL limits how far it spreads
   - Requires multicast routing support

2. Network load
   - Every device receives every message
   - Wastes bandwidth
   - Needless processing

3. Precise control
   - Can't target a specific master clock
   - Can't control quality of service
   - Can't allocate resources on demand

Advantages of unicast:

1. Crosses subnets
   - Passes through routers
   - No multicast restrictions
   - Wider reach

2. Service on demand
   - Sent only to the requester
   - Saves network bandwidth
   - Precise control over the target

3. Quality of service
   - Send rate is negotiable
   - Duration is negotiable
   - Flexible parameter configuration

Where it fits:
- PTP across routers
- Telecom carrier networks
- Data center interconnects
```

## The unicast negotiation protocol

### Signaling messages

```text
Unicast negotiation uses Signaling messages:

Signaling message structure:
┌─────────┬─────────┬──────────┬──────────┐
│Header   │Target   │TLV       │TLV       │
│34 bytes │Port ID  │(Request) │(Grant)   │
│         │10 bytes │Variable  │Variable  │
└─────────┴─────────┴──────────┴──────────┘

TLVs involved:
- REQUEST_UNICAST_TRANSMISSION
- GRANT_UNICAST_TRANSMISSION
- CANCEL_UNICAST_TRANSMISSION
- ACKNOWLEDGE_CANCEL_UNICAST_TRANSMISSION
```

### The negotiation flow

```text
The unicast negotiation exchange (step 4 is optional):

Step 1: Request (slave → master)
The Signaling message carries:
- REQUEST_UNICAST_TRANSMISSION TLV
- messageType: the requested message type (Sync/Announce/Delay_Resp)
- logInterMessagePeriod: the send interval
- durationField: the requested duration (seconds)

Step 2: Grant (master → slave)
The Signaling message carries:
- GRANT_UNICAST_TRANSMISSION TLV
- messageType: the message type being granted
- logInterMessagePeriod: the actual send interval
- durationField: the granted duration
- flags: grant flags

Step 3: Transmission starts
The master sends unicast messages with the negotiated parameters
The slave receives and processes them

Step 4: Cancel (optional)
Either side can send CANCEL_UNICAST_TRANSMISSION
The peer answers with ACKNOWLEDGE_CANCEL_UNICAST_TRANSMISSION
```

## TLV structures in detail

### REQUEST_UNICAST_TRANSMISSION

```c
/* tlv.h:283-289 */

struct request_unicast_xmit_tlv {
    Enumeration16 type;              /* 0x0004 */
    UInteger16    length;
    uint8_t       message_type;      /* requested message type */
    Integer8      logInterMessagePeriod; /* send interval (log2 seconds) */
    UInteger32    durationField;     /* duration (seconds) */
} PACKED;
```

**message_type encoding**:

The standard puts the enum in the **high 4 bits (bits 7-4)** of the byte and leaves the low 4 bits reserved. linuxptp follows suit: on transmit it shifts the message type left by 4 and writes it into the field (`unicast_client.c:61`):

```c
/* unicast_client.c:61 */
req->message_type = message_type << 4;
```

```text
Enumerated values (same as messageType in the PTP header, msg.h:44-54):

SYNC        = 0x0
DELAY_REQ   = 0x1
PDELAY_REQ  = 0x2
PDELAY_RESP = 0x3
DELAY_RESP  = 0x9
ANNOUNCE    = 0xB

So the bytes on the wire are:
- Requesting Sync:        0x00 (SYNC=0x0 << 4)
- Requesting Announce:    0xB0 (ANNOUNCE=0xB << 4)
- Requesting Delay_Resp:  0x90 (DELAY_RESP=0x9 << 4)
- Requesting Pdelay_Resp: 0x30 (PDELAY_RESP=0x3 << 4)
```

`logInterMessagePeriod` is a signed `Integer8` (`tlv.h:287`). The send interval is 2^logInterMessagePeriod seconds:

```text
 0: send once per second
-3: send every 0.125 s (125 ms)
 3: send every 8 s
```

### GRANT_UNICAST_TRANSMISSION

```c
/* tlv.h:169-177 */

struct grant_unicast_xmit_tlv {
    Enumeration16 type;              /* 0x0005 */
    UInteger16 length;
    uint8_t message_type;            /* message type */
    Integer8 logInterMessagePeriod;  /* send interval */
    UInteger32 durationField;        /* granted duration */
    uint8_t reserved;
    uint8_t flags;                   /* grant flags */
} PACKED;
```

**The flags field**:

```c
/* tlv.h:150 */

#define GRANT_UNICAST_RENEWAL_INVITED (1 << 0)
```

```text
What the flags mean:

bit 0: RENEWAL_INVITED
- 1: the master invites the slave to renew
- 0: no renewal invitation

Renewal sequence:
1. The grant is about to expire
2. The master sets RENEWAL_INVITED = 1
3. On receipt, the slave can request renewal early
4. Service is not interrupted

The other bits are reserved.
```

### CANCEL_UNICAST_TRANSMISSION

```c
/* tlv.h:162-167 */

struct cancel_unicast_xmit_tlv {
    Enumeration16 type;         /* 0x0006 */
    UInteger16 length;
    uint8_t message_type_flags; /* message type and flags */
    uint8_t reserved;
} PACKED;
```

**The cancel flow**:

```text
When a cancel happens:

1. The slave no longer needs service
   - Disconnecting
   - Switching to another master clock
   - Stopping synchronization

2. The master can no longer serve
   - Out of resources
   - Device shutting down
   - Configuration change

Cancel message:
CANCEL_UNICAST_TRANSMISSION TLV
- message_type_flags: the message type to cancel

Acknowledgment:
ACKNOWLEDGE_CANCEL_UNICAST_TRANSMISSION TLV
- Confirms the cancel request was received
- Stops sending/receiving
```

## The LinuxPTP implementation

### The unicast client structure

```c
/* mtab.h:31-40 */

struct unicast_master_address {
    STAILQ_ENTRY(unicast_master_address) list;
    struct PortIdentity portIdentity;    /* target port ID */
    enum transport_type type;            /* transport type */
    enum unicast_state state;            /* state */
    struct address address;              /* target address */
    unsigned int granted;                /* bitmap of granted messages */
    unsigned int sydymsk;                /* Sync/Delay_Req request mask */
    time_t renewal_tmo;                  /* renewal timeout */
};
```

### Sending a request

The real code does not poke at `msg->management.suffix` directly. It first builds a Signaling message (`port_signaling_uc_construct()`, `port_signaling.c:55-70`; `:66` sets the UNICAST flag, `:67` writes `msg->address`), then appends the REQUEST TLVs one at a time, and finally sends the message down the common transmit path. The TLV constructor:

```c
/* unicast_client.c:48-66 (TLV construction, reflowed from the real code) */

static int attach_request(struct ptp_message *msg, int log_period,
                          uint8_t message_type, int duration)
{
    struct request_unicast_xmit_tlv *req;
    struct tlv_extra *extra;

    extra = msg_tlv_append(msg, sizeof(*req));
    if (!extra)
        return -1;
    req = (struct request_unicast_xmit_tlv *) extra->tlv;
    req->type = TLV_REQUEST_UNICAST_TRANSMISSION;
    req->length = sizeof(*req) - sizeof(req->type) - sizeof(req->length);
    req->message_type = message_type << 4;   /* messageType in the high 4 bits */
    req->logInterMessagePeriod = log_period;
    req->durationField = duration;           /* seconds */

    return 0;
}
```

A representative send function requests SYNC and DELAY_RESP together (the "sydy" subscription). The intervals come from the port's own `logSyncInterval`/`logMinDelayReqInterval`, and the duration from `unicast_req_duration` (`unicast_client.c:243-273`):

```c
static int unicast_client_sydy(struct port *p,
                               struct unicast_master_address *dst)
{
    struct ptp_message *msg;
    int err;

    msg = port_signaling_uc_construct(p, &dst->address, &dst->portIdentity);
    if (!msg)
        return -1;
    err = attach_request(msg, p->logSyncInterval, SYNC,
                         p->unicast_req_duration);
    if (err)
        goto out;
    if (p->delayMechanism != DM_P2P && p->delayMechanism != DM_NO_MECHANISM) {
        err = attach_request(msg, p->logMinDelayReqInterval, DELAY_RESP,
                             p->unicast_req_duration);
        if (err)
            goto out;
    }
    err = port_prepare_and_send(p, msg, TRANS_GENERAL);
    if (err)
        pr_err("%s: signaling message failed", p->log_name);
out:
    msg_put(msg);
    return err;
}
```

Note that byte-order conversion for TLVs happens in `msg_pre_send()` on the transmit path (`msg.c:442` → `suffix_pre_send(m)` at `:487` → `tlv_pre_send(tlv, extra)` at `:235`). You don't call `tlv_pre_send()` yourself. Call it once by hand and then run `msg_pre_send()`, and the bytes get swapped twice.

### Handling a grant

```c
/* unicast_client.c:433-525 (grant handling, real code, excerpt; P2P branch omitted) */

void unicast_client_grant(struct port *p, struct ptp_message *m,
                          struct tlv_extra *extra)
{
    struct unicast_master_address *ucma;
    struct grant_unicast_xmit_tlv *g;
    int mtype;

    ucma = unicast_client_ok(p, m);   /* match the table entry by source address */
    if (!ucma)
        return;
    g = (struct grant_unicast_xmit_tlv *) extra->tlv;
    mtype = g->message_type >> 4;

    if (!g->durationField) {          /* duration 0: the grant was denied */
        if (mtype != PDELAY_RESP) {
            ucma->state = UC_WAIT;
            clock_set_sde(p->clock, 1);
        }
        return;
    }
    if (abs(g->logInterMessagePeriod) > 30)
        return;                       /* drop an absurd interval */

    ucma->granted |= 1 << mtype;

    switch (ucma->state) {
    case UC_HAVE_ANN:
    case UC_WAIT:
        if (mtype == ANNOUNCE) {
            ucma->state = unicast_fsm(ucma->state, UC_EV_GRANT_ANN);
            ucma->portIdentity = m->header.sourcePortIdentity;
            unicast_client_set_renewal(p, ucma, g->durationField);
        }
        break;
    case UC_NEED_SYDY:
        if (mtype == SYNC || mtype == DELAY_RESP) {
            if ((ucma->granted & ucma->sydymsk) == ucma->sydymsk)
                ucma->state = unicast_fsm(ucma->state, UC_EV_GRANT_SYDY);
            unicast_client_set_renewal(p, ucma, g->durationField);
            if (mtype == SYNC)
                clock_sync_interval(p->clock, g->logInterMessagePeriod);
            else
                p->logMinDelayReqInterval = g->logInterMessagePeriod;
        }
        break;
    case UC_HAVE_SYDY:
        unicast_client_set_renewal(p, ucma, g->durationField);
        break;
    }
}
```

The four states are a linuxptp construct, not a state machine the standard defines: `UC_WAIT / UC_HAVE_ANN / UC_NEED_SYDY / UC_HAVE_SYDY` (`unicast_fsm.h:23-28`). The standard only requires renewal before the grant expires; the 60 s in the sample below is illustrative. linuxptp sets the renewal timeout to three-quarters of the granted duration (`unicast_client_set_renewal()`, `unicast_client.c:224-241`; the key line is `:235`: `duration = (3 * duration) / 4;`). The receive path has already converted TLV byte order in `msg_post_recv()` (`msg.c:431` → `suffix_post_recv()` → `tlv_post_recv(extra)` at `msg.c:218`), so the handler can read the fields directly.

### Sending unicast messages

Unicast and multicast share one transmit path. `port_prepare_and_send()` (`port.c:3307-3333`) chooses `transport_sendto()` or `transport_send()` depending on whether the message carries a unicast address:

```c
/* port.c:3307-3333 (send path, reflowed from the real code) */

int port_prepare_and_send(struct port *p, struct ptp_message *msg,
                          enum transport_event event)
{
    int cnt;

    if (port_has_security(p))
        cnt = sad_append_auth_tlv(clock_config(p->clock), p->spp,
                                  p->active_key_id, msg);
    else
        cnt = msg_pre_send(msg);      /* byte-order conversion happens here */

    if (cnt)
        return -1;

    if (msg_unicast(msg))
        cnt = transport_sendto(p->trp, &p->fda, event, msg);
    else
        cnt = transport_send(p->trp, &p->fda, event, msg);

    if (cnt <= 0)
        return -1;
    port_stats_inc_tx(p, msg);
    if (msg_sots_valid(msg))
        ts_add(&msg->hwts.ts, p->tx_timestamp_offset);
    return 0;
}
```

The destination is written into `msg->address` when the message is built (`msg->address = *address;` at `port_signaling.c:67`), so this path does not set it again.

## Configuration examples

### Slave configuration

```ini
# ptp4l-unicast-slave.cfg -- adapted from the official configs/UNICAST-SLAVE.cfg (not the original text)
[global]
# Duration of the requested unicast service, in seconds; the option defaults to 3600 (config.c:395)
unicast_req_duration 60

# Unicast master table: one [unicast_master_table] section per table, distinguished by table_id
[unicast_master_table]
table_id 1
logQueryInterval 2
UDPv4 192.168.1.100
UDPv4 192.168.1.101

# L2 unicast table
[unicast_master_table]
table_id 2
logQueryInterval 2
L2 00:11:22:33:44:55

[eth0]
# Use table 1 (UDPv4)
unicast_master_table 1
```

For P2P, add a separate table with `table_id 3` and a `peer_address` line. `hybrid_e2e` is E2E-only and is ignored for P2P.

### Master configuration

```ini
# ptp4l-unicast-master.cfg -- adapted from the official configs/UNICAST-MASTER.cfg
[global]
# Unicast master: hybrid E2E plus unicast listening
hybrid_e2e                1
inhibit_multicast_service 1
unicast_listen            1

# priority1/priority2 are global items and belong only in [global]
priority1 128
priority2 128
```

Put `priority1` or `priority2` in an `[eth0]` section and linuxptp rejects the entire file.

### Startup commands

```bash
# Start the slave
ptp4l -i eth0 -f ptp4l-unicast-slave.cfg -m

# Start the master
ptp4l -i eth0 -f ptp4l-unicast-master.cfg -m -S

# Check unicast status
pmc -u "GET UNICAST_MASTER_TABLE_NP"
```

## Unicast vs multicast

| Feature | Multicast | Unicast |
|------|------|------|
| Address | 224.0.1.129 | A specific IP |
| Coverage | Within a subnet | Can cross subnets |
| Network load | Every device receives | Only the target receives |
| Configuration complexity | Simple | More complex |
| Dynamics | Automatic discovery | Negotiation required |
| Delay measurement | E2E or P2P | E2E / P2P (plus hybrid E2E) |
| Where this applies | LAN | WAN, across subnets |

## Summary: Key points of unicast negotiation

**Core concepts**:
- Signaling messages
- Negotiation exchange: request → grant → transmission (+ optional cancel)

**TLV types**:
- REQUEST_UNICAST_TRANSMISSION
- GRANT_UNICAST_TRANSMISSION
- CANCEL_UNICAST_TRANSMISSION
- ACKNOWLEDGE_CANCEL_UNICAST_TRANSMISSION

**Negotiation parameters**:
- Message type
- Send interval
- Duration

**Where this applies**:
- PTP across subnets
- Service on demand
- Precise control
