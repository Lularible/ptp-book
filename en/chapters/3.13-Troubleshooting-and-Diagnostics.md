# 3.13 Troubleshooting and Diagnostics: PTP's Health Guardian

## Understanding the failure modes

PTP failures cluster into a few buckets:

| Bucket | Typical symptom |
|:---|:---|
| Network | no Announces at all (firewall, wrong VLAN, wrong domain) |
| Clock | offset huge or wandering (bad source, bad servo tuning) |
| Protocol | state flapping, master changes, UNCALIBRATED never resolves |
| Timestamping | poor accuracy (software timestamps, wrong PHC) |

Diagnosis starts from the state machine, the timers, and the two big counters.

## Timeout detection

LinuxPTP's port timers fire the events we met earlier:

```c
/* port.c, around line 3062 */

p->service_stats.announce_timeout++;   /* we stopped receiving Announces */
```

```c
/* port.c, around line 3060 */

p->service_stats.sync_timeout++;       /* we stopped receiving Syncs */
```

Config:

```ini
[eth0]
announceReceiptTimeout 3    # default
logAnnounceInterval 1       # announce interval = 2^1 = 2 s
```

Timeout = 3 × 2 = 6 seconds.

## Path-delay anomaly detection

```c
/* port.c, lines 716-721 */

if (tmv_to_nanoseconds(p->peer_delay) > p->neighborPropDelayThresh) {
    if (p->asCapable)
        pr_debug("%s: peer_delay (%" PRId64 ") > neighborPropDelayThresh "
                 "(%" PRId32 "), resetting asCapable", p->log_name,
                 tmv_to_nanoseconds(p->peer_delay),
                 p->neighborPropDelayThresh);
    ...

    p->asCapable = NOT_CAPABLE;
}
```

When the mean peer delay exceeds `neighborPropDelayThresh`, the port drops out of AScapable, it stops being usable for sync even if the FSM says SLAVE.

## The state machine, in fault terms

State transitions that matter when something breaks (`fsm.c`, `ptp_fsm`):

```
SLAVE → MASTER:
- announce timeout (the master died; an ordinary port takes over).
  (slaveOnly ports instead go back to LISTENING.)

SLAVE → UNCALIBRATED:
- synchronization fault (EV_SYNCHRONIZATION_FAULT).
- master changed (EV_RS_SLAVE with mdiff=1).

MASTER/GRAND_MASTER → FAULTY:
- a fault was detected.

any state → INITIALIZING:
- port initialize / power-up (EV_INITIALIZE / EV_POWERUP).
- fault cleared from FAULTY (EV_FAULT_CLEARED).
```

The full table is `ptp_fsm` at fsm.c lines 21-220; the slave-only variant is `ptp_slave_fsm` at lines 222-337.

## Reading the log

Normal operation looks like:

```
ptp4l[1234.567]: port 1: INITIALIZING to LISTENING on INIT_COMPLETE
ptp4l[1234.678]: port 1: LISTENING to UNCALIBRATED on RS_SLAVE
ptp4l[1234.789]: port 1: UNCALIBRATED to SLAVE on MASTER_CLOCK_SELECTED
ptp4l[1235.001]: master offset    -32768 s2 freq   -1000 path delay    12345
```

A master loss (ordinary port) shows the direct promotion:

```
ptp4l[1236.567]: port 1: SLAVE to MASTER on ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES
ptp4l[1237.001]: selected best master clock aabbcc.fffe.ddeeff
ptp4l[1237.002]: port 1: MASTER to UNCALIBRATED on RS_SLAVE
ptp4l[1237.100]: port 1: UNCALIBRATED to SLAVE on MASTER_CLOCK_SELECTED
```

Timeouts are visible as the `...to MASTER on ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES` transitions and the log line `announce timeout`.

## The pmc diagnostic toolkit

Problem 1: can't sync

```bash
# 1. connectivity
ping <master>

# 2. port state
pmc -u "GET PORT_DATA_SET"

# 3. master?
pmc -u "GET PARENT_DATA_SET"

# 4. logs
dmesg | grep ptp4l
journalctl -u ptp4l
```

Common causes: firewall blocking 319/320, wrong VLAN/subnet, master down, domain mismatch, `master_only` set.

Problem 2: poor accuracy

```bash
# 1. timestamp capability
ethtool -T eth0

# 2. PHC present?
ls -l /dev/ptp*

# 3. current deviation & path delay
pmc -u "GET CURRENT_DATA_SET"

# 4. PHC state
phc_ctl /dev/ptp0 -- get
```

Common causes: software timestamping, congested link, long/asymmetric path, poor clock quality.

Problem 3: master flapping

```bash
# 1. priorities
pmc -u "GET DEFAULT_DATA_SET"

# 2. announce interval & timeout
pmc -u "GET PORT_DATA_SET"

# 3. master info & offset variance
pmc -u "GET PARENT_DATA_SET"
```

Common causes: equal priorities across candidates, announce timeout too small, unstable master, unstable network.

## Service stats

On LinuxPTP 3.x, `GET PORT_SERVICE_STATS_NP` shows the counters:

```
announce_timeout          1
sync_timeout              0
delay_timeout             0
unicast_service_timeout   0
unicast_request_timeout   0
master_announce_timeout   198
master_sync_timeout       394
qualification_timeout     0
sync_mismatch             0
followup_mismatch         0
```

On Ubuntu 20.04 (linuxptp 1.9.2), pmc doesn't know `PORT_SERVICE_STATS_NP`, it reports `bad command`. Use `-S`/the log greps instead, or a newer linuxptp:

```bash
grep -iE "announce.*timeout|sync.*timeout" /var/log/syslog | tail
```

## A monitoring loop

```bash
while true; do
    STATUS=$(pmc -u "GET TIME_STATUS_NP" 2>/dev/null)
    OFFSET=$(echo "$STATUS" | grep master_offset | awk '{print $2}')
    if [ -n "$OFFSET" ]; then
        if [ "$OFFSET" -gt 100000 ] || [ "$OFFSET" -lt -100000 ]; then
            echo "[ALERT] Large offset: $OFFSET ns"
        fi
    else
        echo "[ERROR] Cannot get time status"
    fi
    sleep 5
done
```

## Better practices

- Pin a designated master (low `priority1`, `slaveOnly 0`).
- Pure slaves: `slaveOnly 1` + `clockClass 255`.
- Boundary clocks to isolate regions; TCs for jitter removal.
- Hardware timestamping wherever accuracy matters.
- Monitor `master_offset`, `gmIdentity`, and the `*_timeout` counters; alarm on state flaps.

## Summary

- Timeouts and path-delay anomalies are detected inside `port.c`; they show up as FSM transitions and `service_stats` counters.
- The FSM's fault paths: timeout → MASTER (ordinary) or LISTENING (slaveOnly); fault → FAULTY; master change → UNCALIBRATED.
- The pmc toolkit maps each symptom class to concrete commands; the linuxptp-1.9.2 `_NP` limitations still apply.
- A tiny monitoring loop turns PTP into a watchable service.
