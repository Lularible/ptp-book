# 3.13 Troubleshooting and Diagnostics: PTP's Health Guardian

## Failure types

A PTP network can fail in many ways:

```text
Network-layer failures:
- link down
- network congestion
- packet loss
- abnormal delay

Clock-layer failures:
- master clock failure
- time jump
- frequency drift
- hardware failure

Protocol-layer failures:
- configuration error
- version mismatch
- parameter error
- abnormal state

Timestamping failures:
- hardware timestamping failure
- inaccurate timestamps
- lost timestamps
```

## Failure detection mechanisms

### Announce Receipt Timeout

LinuxPTP implements the timeout check in port.c:

```c
/* port.c:3062 */

p->service_stats.announce_timeout++;
```

**Timeout handling flow**:

```text
Announce timeout detection:

1. Record the time the last Announce arrived
2. Check periodically: current time - last_announce
3. If it exceeds announce_timeout × announce_interval:
   - bump the counter: service_stats.announce_timeout++
   - treat the master clock as failed
   - trigger a BMCA re-election
   - possibly switch to a new master clock

Config (the two defaults are 3 and 1, see config.c:258 and :307; send interval = 2^logAnnounceInterval seconds):
[eth0]
announceReceiptTimeout 3
logAnnounceInterval 1

Timeout = 3 × 2 = 6 seconds
```

### Sync Receipt Timeout

LinuxPTP counts the timeout in port.c:

```c
/* port.c:3060 */

p->service_stats.sync_timeout++;
```

**Statistics**:

```bash
# Check the timeout counters
pmc -u "GET PORT_SERVICE_STATS_NP"

# Output:
	aabbcc.fffe.ddeeff-1 seq 0 RESPONSE MANAGEMENT PORT_SERVICE_STATS_NP 
		portIdentity              aabbcc.fffe.ddeeff
		announce_timeout          1
		sync_timeout              0
		delay_timeout             0
		unicast_service_timeout   0
		unicast_request_timeout   0
		master_announce_timeout   198
		master_sync_timeout       394
		qualification_timeout     0
		sync_mismatch             0
		followup_mismatch         0

```

These counters come from `PORT_SERVICE_STATS_NP`. Don't confuse them with `PORT_STATS_NP`, the per-message-type counters, or with `stats.c`/`stats.h`, which compute min, max, mean, and rms over a series of samples.

### Path-delay anomaly detection

The delay check lives in `port_capable()` (port.c:704-776):

```c
/* port.c:716-722 and :770-775 (the original uses goto not_capable; inlined here) */

if (tmv_to_nanoseconds(p->peer_delay) > p->neighborPropDelayThresh) {
    if (p->asCapable)
        pr_debug("%s: peer_delay (%" PRId64 ") > neighborPropDelayThresh "
            "(%" PRId32 "), resetting asCapable", p->log_name,
            tmv_to_nanoseconds(p->peer_delay),
            p->neighborPropDelayThresh);
    p->asCapable = NOT_CAPABLE;
}
```

The check applies only to 802.1AS / gPTP ports: when peer_delay exceeds the configured neighborPropDelayThresh, the port sets asCapable to NOT_CAPABLE and stops being usable for synchronization. Port state itself lives in `PORT_DATA_SET`; `PORT_DATA_SET_NP` carries only `neighborPropDelayThresh` and `asCapable`.

## State-machine failure handling

### State transition logic

State transitions are handled by ptp_fsm and ptp_slave_fsm in fsm.c:

```c
/* fsm.c:21-220 (ptp_fsm), excerpt */

case PS_SLAVE:
    switch (event) {
    case EV_FAULT_DETECTED:
        next = PS_FAULTY;
        break;
    case EV_ANNOUNCE_RECEIPT_TIMEOUT_EXPIRES:
        /* master clock failed, promote yourself */
        next = PS_MASTER;
        break;
    case EV_SYNCHRONIZATION_FAULT:
        next = PS_UNCALIBRATED;
        break;
    /* ... */
    }
    break;

case PS_MASTER:
case PS_GRAND_MASTER:
    switch (event) {
    case EV_FAULT_DETECTED:
        next = PS_FAULTY;
        break;
    /* ... */
    }
    break;
```

> **Note**: In ptp_fsm, a PS_SLAVE port that receives an Announce timeout enters **PS_MASTER** (the master failed, so the port takes over), not LISTENING (`fsm.c:194-195`). Only ptp_slave_fsm (`fsm.c:222-337`), used by slaveOnly ports, returns to LISTENING here (`fsm.c:314-318`).

The full transition table is the ptp_fsm function in fsm.c (lines 21-220).

**Typical failure transitions**:

```text
SLAVE → MASTER:
- Announce timeout (the master failed and the port takes over; slaveOnly ports go back to LISTENING)

SLAVE → UNCALIBRATED:
- synchronization fault (EV_SYNCHRONIZATION_FAULT)
- master clock changed (EV_RS_SLAVE with mdiff=1)

MASTER → FAULTY:
- fault detected (EV_FAULT_DETECTED)

any state → INITIALIZING:
- port initialize / power-up (EV_INITIALIZE / EV_POWERUP)
- fault cleared in FAULTY (EV_FAULT_CLEARED)
```

## Diagnosing common problems

### Problem 1: no synchronization

```bash
# Diagnosis steps:

# 1. Check network connectivity
ping <master_ip>

# 2. Check PTP port state
pmc -u "GET PORT_DATA_SET"

# 3. Check master clock information
pmc -u "GET PARENT_DATA_SET"

# 4. Look at the logs
journalctl -t ptp4l     # filter by syslog tag (ptp4l logs through syslog, see print.c:94-97)
journalctl -u ptp4l     # filter by systemd unit

# Common causes:
# - firewall blocks the PTP ports (319/320)
# - network misconfiguration
# - master clock not running
# - domain number mismatch
```

### Problem 2: poor synchronization accuracy

```bash
# Diagnosis steps:

# 1. Check the timestamping type
ethtool -T eth0

# 2. Check hardware support
ls -l /dev/ptp*

# 3. Check the current offset and path delay (offsetFromMaster/meanPathDelay)
pmc -u "GET CURRENT_DATA_SET"

# 4. Check PHC state
phc_ctl /dev/ptp0 -- get

# Common causes:
# - software timestamping (low accuracy)
# - network congestion
# - large path delay
# - poor clock quality
```

### Problem 3: frequent master clock changes

```bash
# Diagnosis steps:

# 1. Check the priority configuration (priority1 / priority2)
pmc -u "GET DEFAULT_DATA_SET"

# 2. Check the Announce interval and timeout (logAnnounceInterval / announceReceiptTimeout)
pmc -u "GET PORT_DATA_SET"

# 3. Check master clock information and offset jitter (observedParentOffsetScaledLogVariance)
pmc -u "GET PARENT_DATA_SET"

# Common causes:
# - identical priority settings
# - Announce timeout set too small
# - unstable master clock
# - unstable network
```

## Best practices

### Monitoring script

```bash
#!/bin/bash
# ptp_monitor.sh

while true; do
    # Get the current status
    STATUS=$(pmc -u "GET TIME_STATUS_NP" 2>/dev/null)
    
    # Extract the offset
    OFFSET=$(echo "$STATUS" | grep master_offset | awk '{print $2}')
    
    # Check whether the offset is too large
    if [ -n "$OFFSET" ]; then
        if [ "$OFFSET" -gt 100000 ] || [ "$OFFSET" -lt -100000 ]; then
            echo "[ALERT] Large offset: $OFFSET ns"
            # Send an alarm
            # logger -t ptp_monitor "Large offset detected"
        fi
    else
        echo "[ERROR] Cannot get time status"
    fi
    
    sleep 5
done
```

### Automated diagnosis

```bash
#!/bin/bash
# ptp_diagnose.sh

echo "=== PTP Diagnostic Report ==="
echo "Date: $(date)"
echo

echo "1. Network Interface:"
ip addr show eth0 | grep -E "inet |ether"
echo

echo "2. PTP Hardware Clock:"
ethtool -T eth0
echo

echo "3. PHC Devices:"
ls -l /dev/ptp*
echo

echo "4. Port Status:"
pmc -u "GET PORT_DATA_SET"
echo

echo "5. Current Time Status:"
pmc -u "GET TIME_STATUS_NP"
echo

echo "6. Parent Clock:"
pmc -u "GET PARENT_DATA_SET"
echo

echo "7. Time Properties:"
pmc -u "GET TIME_PROPERTIES_DATA_SET"
echo
```
