# 3.5 The Servo Controller: The Art of Making the Clock Catch Up with Its Master

## The core problem of synchronization

Once a PTP port enters SLAVE, the core question is:

**How do you adjust the local clock so it stays synchronized with the master clock?**

That's the servo controller's job.

---

## Servo overview

### What the servo does

```text
Servo inputs:
- offset: the local clock's deviation from the master clock (ns)
- local_ts: the local timestamp
- weight: the sample weight

Servo output:
- ppb: the frequency adjustment (parts per billion)

Servo goals:
- minimize offset
- bring the local clock's frequency in line with the master's
```

### Servo types in LinuxPTP

```c
/* servo.h, lines 33-39 */

enum servo_type {
    CLOCK_SERVO_PI,          /* PI controller (most common) */
    CLOCK_SERVO_LINREG,      /* linear regression filter */
    CLOCK_SERVO_NTPSHM,      /* NTP shared memory */
    CLOCK_SERVO_NULLF,       /* null filter */
    CLOCK_SERVO_REFCLOCK_SOCK, /* reference clock socket */
};
```

**What each type does**:

```text
PI controller:
- proportional-integral controller
- the classic control-theory approach
- tunable and adaptable
- suits most setups

Linear regression filter:
- statistical method (weighted least-squares fit)
- adaptive window size (4/8/16/32/64 points)
- suits high-accuracy setups

NTP shared memory:
- shares time information with NTP
- for hybrid deployments
- doesn't adjust the clock directly (always returns 0.0, state always UNLOCKED, ntpshm.c:117-118)

Null filter:
- always returns 0.0 ppb, never adjusts the frequency (nullf.c:46, :57)
- decides the state by threshold only: LOCKED / JUMP / UNLOCKED
- for "measure only, don't steer" setups

Reference clock socket:
- sends samples out over a Unix socket for an external program (such as chrony) to filter
- protocol structures copied from chrony-3.2's refclock_sock.c (refclock_sock.c:35)
- for external sources such as GPS
```

## The PI controller in detail

### How a PI controller works

```text
PI controller = proportional (P) + integral (I)

Control equation:
output = Kp × offset + Ki × ∫offset dt (in the source this accumulated integral is drift)

Where:
- Kp: proportional gain
- Ki: integral gain
- offset: the current deviation
- drift: the accumulated frequency drift

Proportional term (P):
- responds to the current deviation
- larger deviation, larger correction
- fast response

Integral term (I):
- responds to accumulated past deviation
- removes steady-state error
- stable over the long run
```

### The PI sample function

```c
/* pi.c, lines 64-155 */

static double pi_sample(struct servo *servo,
                        int64_t offset,
                        uint64_t local_ts,
                        double weight,
                        enum servo_state *state)
{
    struct pi_servo *s = container_of(servo, struct pi_servo, servo);
    double ki_term, ppb = s->last_freq;
    double freq_est_interval, localdiff;

    switch (s->count) {
    case 0:
        /* first sample: just record the data */
        s->offset[0] = offset;
        s->local[0] = local_ts;
        *state = SERVO_UNLOCKED;
        s->count = 1;
        break;

    case 1:
        /* second sample: estimate the frequency offset */
        s->offset[1] = offset;
        s->local[1] = local_ts;

        /* make sure the time order is correct */
        if (s->local[0] >= s->local[1]) {
            *state = SERVO_UNLOCKED;
            s->count = 0;
            break;
        }

        /* check whether the time interval is long enough */
        localdiff = (s->local[1] - s->local[0]) / 1e9;
        localdiff += localdiff * FREQ_EST_MARGIN;
        freq_est_interval = 0.016 / s->ki;
        if (freq_est_interval > 1000.0) {
            freq_est_interval = 1000.0;
        }
        if (localdiff < freq_est_interval) {
            *state = SERVO_UNLOCKED;
            break;
        }

        /* estimate the frequency offset */
        s->drift += (1e9 - s->drift) * (s->offset[1] - s->offset[0]) /
                                    (s->local[1] - s->local[0]);

        /* clamp the frequency range */
        if (s->drift < -servo->max_frequency)
            s->drift = -servo->max_frequency;
        else if (s->drift > servo->max_frequency)
            s->drift = servo->max_frequency;

        /* decide whether a step is needed */
        if ((servo->first_update &&
             servo->first_step_threshold &&
             servo->first_step_threshold < llabs(offset)) ||
            (servo->step_threshold &&
             servo->step_threshold < llabs(offset)))
            *state = SERVO_JUMP;
        else
            *state = SERVO_LOCKED;

        ppb = s->drift;
        s->count = 2;
        break;

    case 2:
        /* normal operation: PI control */
        
        /* check whether a reset is needed */
        if (servo->step_threshold &&
            servo->step_threshold < llabs(offset)) {
            *state = SERVO_UNLOCKED;
            s->count = 0;
            break;
        }

        /* PI control equation */
        ki_term = s->ki * offset * weight;
        ppb = s->kp * offset * weight + s->drift + ki_term;
        
        /* clamp the output range */
        if (ppb < -servo->max_frequency) {
            ppb = -servo->max_frequency;
        } else if (ppb > servo->max_frequency) {
            ppb = servo->max_frequency;
        } else {
            s->drift += ki_term;  /* update the integral term */
        }
        
        *state = SERVO_LOCKED;
        break;
    }

    s->last_freq = ppb;
    return ppb;
}
```

**The three sampling phases**:

```text
Phase 0 (count=0): initialization
- record the first sample
- state: UNLOCKED
- output: the previous frequency (no new adjustment)

Phase 1 (count=1): frequency estimate
- record the second sample
- compute the frequency offset between the two samples
- formula: drift += (1e9 - drift) × (offset[1] - offset[0]) / (local[1] - local[0])
- this estimates the local oscillator's frequency offset
- state: LOCKED or JUMP
- output: the estimated drift

Phase 2 (count=2): normal PI control
- PI control on every sample
- formula: ppb = (kp + ki) × offset × weight + drift
- state: LOCKED
- output: the PI controller's output
```

### Tuning the PI gains

```c
/* pi.c, lines 157-171 */

static void pi_sync_interval(struct servo *servo, double interval)
{
    struct pi_servo *s = container_of(servo, struct pi_servo, servo);

    /* adjust Kp automatically from the Sync interval */
    s->kp = s->configured_pi_kp_scale * 
            pow(interval, s->configured_pi_kp_exponent);
    if (s->kp > s->configured_pi_kp_norm_max / interval)
        s->kp = s->configured_pi_kp_norm_max / interval;

    /* adjust Ki automatically from the Sync interval */
    s->ki = s->configured_pi_ki_scale * 
            pow(interval, s->configured_pi_ki_exponent);
    if (s->ki > s->configured_pi_ki_norm_max / interval)
        s->ki = s->configured_pi_ki_norm_max / interval;

    pr_debug("PI servo: sync interval %.3f kp %.3f ki %.6f",
             interval, s->kp, s->ki);
}
```

**Why the gains adapt**:

```text
Why adjust the gains to the Sync interval?

Long Sync interval:
- more time between two samples
- a more accurate frequency estimate
- but a slower response
- needs larger Kp and Ki

Short Sync interval:
- less time between two samples
- the frequency estimate may be less accurate
- but the response is faster
- needs smaller Kp and Ki

Formulas (pi.c:161-167):
kp = kp_scale × interval^kp_exponent, then capped at kp_norm_max / interval
ki = ki_scale × interval^ki_exponent, then capped at ki_norm_max / interval

Defaults in config.c (note: both scales default to 0!):
- pi_proportional_scale   = 0.0      config.c:338
- pi_proportional_exponent = -0.3    config.c:336
- pi_proportional_norm_max = 0.7     config.c:337 (upper bound 1.0)
- pi_integral_scale       = 0.0      config.c:334
- pi_integral_exponent    = 0.4      config.c:332
- pi_integral_norm_max    = 0.3      config.c:333 (upper bound 2.0)

That means:
- by default Kp and Ki already adapt to the Sync interval: the longer the interval, the smaller Kp (×interval⁻⁰·³) and the larger Ki (×interval⁰·⁴)
- only when the user explicitly sets `pi_proportional_const` and `pi_integral_const` to enter fixed mode are the exponents forced to 0, and Kp/Ki stop varying with the interval
```

## The linear regression filter in detail

### The idea

```text
The linear regression filter's idea:
- collect several (offset, time) sample points
- fit a line with linear regression
- the line's slope = the frequency offset
- the line's intercept = the initial offset

Advantages:
- uses many samples, reducing noise (least squares smooths by itself)
- adaptive window size: picks one of five lengths, 4/8/16/32/64
- frequency estimate and phase pull-back are decoupled: the slope gives frequency, the intercept gives "how much is still left to pull"

Math:
given n points (x_i, y_i), the regression line is
y = slope × x + intercept

Closed form with equal weights:
slope = (n∑xy - ∑x∑y) / (n∑x² - (∑x)²)
intercept = (∑y - slope×∑x) / n

The source uses the **weighted version** (linreg.c:186-188), replacing ∑ with ∑(·×w) and n with ∑w:
res->slope = (xy_sum - x_sum * y_sum / w_sum) /
             (x2_sum - x_sum * x_sum / w_sum);
res->intercept = (y_sum - res->slope * x_sum) / w_sum;
When all weights are equal, the two expressions match the closed form above.
```

### Linear regression sampling

The real function is `linreg_sample()` (`linreg.c:216-287`). The call sequence is fixed, four steps: `update_reference → add_sample → regress → update_size` (`linreg.c:234-238`). The version below is **rewritten** from the source: the function names, call order, tests, and return-value semantics all match. Only the `pr_debug()` line (`linreg.c:248-249`) is left out, and the source's comments are replaced with annotations.

```c
/* linreg.c:216-287, rewritten from the source (pr_debug omitted) */

static double linreg_sample(struct servo *servo,
                            int64_t offset,
                            uint64_t local_ts,
                            double weight,
                            enum servo_state *state)
{
    struct linreg_servo *s = container_of(servo, struct linreg_servo, servo);
    struct result *res;
    int corr_interval;

    /* The source opens with a comment (linreg.c:226-232) that states an
       approximation: it treats "now" and "the moment the frequency is
       actually written into the clock" as the same local_ts (the local
       timestamp when the Sync arrived). As long as the difference between
       them is far smaller than the update interval, the loop stays stable
       enough. */

    /* Step 1: push reference forward to local_ts (the step most easily
       missed; it maintains all four fields reference.x / reference.y /
       x_remainder / last_update).
       y accumulates the raw local time interval;
       x accumulates the interval after removing the current clock_freq
       correction, i.e. x_interval = y_interval / (1.0 + clock_freq / 1e9)
       (linreg.c:116), with the fractional part stored in x_remainder for
       next time (linreg.c:117-118). */
    update_reference(s, local_ts);       /* defined at linreg.c:107-124 */

    /* Step 2: write into the ring buffer. Note the coordinates are not
       (local_ts, offset) but (reference.x, reference.y - offset) */
    add_sample(s, offset, weight);       /* defined at linreg.c:126-136 */

    /* Step 3: run a weighted regression internally for every window
       length, writing the results into s->results[size - MIN_SIZE] */
    regress(s);                          /* defined at linreg.c:138-190 */

    /* Step 4: pick the window length, result in s->size (returns void) */
    update_size(s);                      /* defined at linreg.c:192-214 */

    if (s->size < MIN_SIZE) {            /* linreg.c:240, not "MIN_POINTS" */
        /* not enough points: regress() breaks when n > s->num_points,
           so no window can be selected */
        *state = SERVO_UNLOCKED;
        return -s->clock_freq;
    }

    res = &s->results[s->size - MIN_SIZE];

    /* decide whether to jump: compares the fitted intercept, not offset itself */
    if ((servo->first_update &&
         servo->first_step_threshold &&
         servo->first_step_threshold < fabs(res->intercept)) ||
        (servo->step_threshold &&
         servo->step_threshold < fabs(res->intercept))) {
        move_reference(s, 0, -offset);   /* the clock is about to be stepped by offset, so reference moves with it */
        s->last_update -= offset;
        *state = SERVO_JUMP;
    } else {
        *state = SERVO_LOCKED;
    }

    /* Step 5: the slope is a dimensionless frequency ratio (≈1.0); convert it to ppb */
    s->clock_freq = 1e9 * (res->slope - 1.0);            /* linreg.c:265 */

    /* Step 6: add a correction that pulls the residual phase intercept back; longer windows pull more slowly */
    corr_interval = s->size <= 4 ? 1 : s->size / 2;      /* linreg.c:275 */
    s->clock_freq += res->intercept / s->update_interval / corr_interval;

    /* Step 7: clamp to ±max_frequency */
    if (s->clock_freq > servo->max_frequency)
        s->clock_freq = servo->max_frequency;
    else if (s->clock_freq < -servo->max_frequency)
        s->clock_freq = -servo->max_frequency;

    s->frequency_ratio = res->slope / (1.0 + s->clock_freq / 1e9);

    return -s->clock_freq;                               /* linreg.c:286 */
}
```

### Adaptive window selection

```c
/* choose the best window size */

static void update_size(struct linreg_servo *s)
{
    struct result *res;
    double best_err;
    int size, best_size;

    /* Find largest size with smallest prediction error */

    best_size = 0;
    best_err = 0.0;

    for (size = MIN_SIZE; size <= MAX_SIZE; size++) {
        res = &s->results[size - MIN_SIZE];
        if ((!best_size && res->slope) ||
            (best_err * ERR_EQUALS > res->err &&
             res->err_updates >= ERR_INITIAL_UPDATES)) {
            best_size = size;
            best_err = res->err;
        }
    }

    s->size = best_size;
}
```

**How the adaptation works**:

```text
The source comment states the criterion itself: Find largest size with smallest prediction error. It does not "take the window with the smallest error"; it takes the "longest" window that is good enough.

The test has two branches (linreg.c:205-207):
- (!best_size && res->slope)
    the first window with a regression result is selected unconditionally (res->slope stays 0 while there aren't enough points)
- (best_err * ERR_EQUALS > res->err && res->err_updates >= ERR_INITIAL_UPDATES)
    the current window's prediction error err is no more than 1.05 times the best selected so far
    (ERR_EQUALS = 1.05, linreg.c:39),
    and its error statistics have finished initializing
    (ERR_INITIAL_UPDATES = 10 updates, linreg.c:37)

The error err is a moving average of "predicted intercept vs measured value" (linreg.c:157-168):
- the first 10 updates accumulate and average
- after that, exponential smoothing with ERR_SMOOTH = 0.02 (linreg.c:35)

Benefits:
- with few points it falls back to short windows (regress breaks when n > num_points, so the corresponding results[] entry keeps slope 0 and is never selected)
- with enough points and decent prediction it prefers long windows (4→8→16→32→64), which are steadier
- no config file involved: MIN_SIZE / MAX_SIZE are compile-time #defines
```

### pi_reset vs linreg_reset: reset strength two orders of magnitude apart

The base class's fourth virtual function is `reset` (`servo_private.h:44`). The forwarding layer `servo_reset()` is just one line, `servo->reset(servo)` (`servo.c:157-160`). The two implementations differ wildly:

```c
/* pi.c:173-178 — minimal reset: only sends the sample phase back to 0 */

static void pi_reset(struct servo *servo)
{
    struct pi_servo *s = container_of(servo, struct pi_servo, servo);

    s->count = 0;
}
```

```c
/* linreg.c:296-310 — wipes all the history the regression accumulated */

static void linreg_reset(struct servo *servo)
{
    struct linreg_servo *s = container_of(servo, struct linreg_servo, servo);
    unsigned int i;

    s->num_points = 0;
    s->last_update = 0;
    s->size = 0;
    s->frequency_ratio = 1.0;

    for (i = MIN_SIZE; i <= MAX_SIZE; i++) {
        s->results[i - MIN_SIZE].slope = 0.0;
        s->results[i - MIN_SIZE].err_updates = 0;
    }
}
```

```text
Field            pi_reset                    linreg_reset
Counter/points   s->count = 0                num_points = 0, size = 0
Frequency est.   drift kept (not cleared)    each window slope = 0.0, err_updates = 0
Time base        local[]/offset[] untouched  last_update = 0 (reference resumes from it)
Frequency ratio  none: PI has no rate_ratio  frequency_ratio = 1.0
Applied offset   last_freq kept               clock_freq kept (untouched)
```

## Servo states in detail

### The four states

```c
/* servo.h, lines 44-67 */

enum servo_state {
    SERVO_UNLOCKED,       /* not locked */
    SERVO_JUMP,           /* needs a jump */
    SERVO_LOCKED,         /* locked */
    SERVO_LOCKED_STABLE,  /* locked and stable */
};
```

**What the states mean**:

```text
SERVO_UNLOCKED:
- the servo doesn't have enough data yet
- or the offset is too large and needs a reset
- can't adjust the clock reliably

SERVO_JUMP:
- the offset exceeds the threshold
- the clock needs a step
- for correcting a large offset quickly

SERVO_LOCKED:
- the servo is tracking
- the offset is in the normal range
- normal frequency adjustment

SERVO_LOCKED_STABLE:
- several offsets in a row below the threshold
- the servo is stable
- you can consider lowering the Sync rate
```

### State transitions

The complete source of `servo_sample()` is in "The sample function" above. Here is only the last branch, which carries a key comment from `servo.c`:

```c
/* servo.c:100-114, complete source */

static int check_offset_threshold(struct servo *s, int64_t offset)
{
    long long int abs_offset = llabs(offset);

    if (s->offset_threshold) {
        if (abs_offset < s->offset_threshold) {
            if (s->curr_offset_values)
                s->curr_offset_values--;
        } else {
            s->curr_offset_values = s->num_offset_values;
        }
        return s->curr_offset_values ? 0 : 1;
    }
    return 0;
}
```

**How stability detection works**:

```text
Configuration:
- servo_offset_threshold: the offset threshold
- servo_num_offset_values: the number of checks

How it works:
1. on each sample, check whether |offset| is below the threshold
2. if below, decrement the counter by 1
3. if above, reset the counter
4. when the counter reaches 0, enter LOCKED_STABLE

Example:
config: offset_threshold = 100ns, num_offset_values = 5

Sample 1: |offset| = 80ns < 100ns → count = 4
Sample 2: |offset| = 90ns < 100ns → count = 3
Sample 3: |offset| = 150ns > 100ns → count = 5 (reset)
Sample 4: |offset| = 70ns < 100ns → count = 4
Sample 5: |offset| = 60ns < 100ns → count = 3
Sample 6: |offset| = 80ns < 100ns → count = 2
Sample 7: |offset| = 90ns < 100ns → count = 1
Sample 8: |offset| = 85ns < 100ns → count = 0 → LOCKED_STABLE

This guarantees:
- N consecutive offsets below the threshold before declaring stable
- any single overshoot resets the count
```

## Step threshold configuration

### What a step is for

```text
When the offset is very large:
- adjusting gradually is too slow
- the clock needs a step

The step threshold decides when to step:
- step_threshold: the threshold during normal operation
- first_step_threshold: the threshold for the first synchronization

Why separate the first time from normal operation?

First synchronization:
- the device just started, so the offset can be large (milliseconds or even seconds)
- a larger first step is allowed
- it reaches synchronization quickly

Normal operation:
- the offset should be in the nanosecond range
- only small steps are allowed
- to avoid a service interruption
```

### Configuration example

```ini
# The config file is passed to ptp4l with -f <file> (ptp4l.c:57).
# The repository's samples are in configs/*.cfg (such as configs/default.cfg, configs/gPTP.cfg).

[global]
# step threshold during normal operation (seconds). Default 0.0 = disabled (config.c:362)
step_threshold 0.0

# step threshold for the first synchronization (seconds). Default 0.00002 = 20 µs (config.c:288)
first_step_threshold 0.00002

# upper bound on frequency adjustment (ppb). Default 900000000 ≈ "no extra limit" (config.c:316).
# The value actually in force is min(hardware capability, this item): servo.c:81-85.
# The line below is an example of "the user deliberately tightens it to 500 ppm", not the default
max_frequency 500000
```

**What actually happens**:

```text
Scenario: the device just started, offset = 1 second

Config: first_step_threshold = 0.00002 (20 µs, the default)
      step_threshold = 0.0 (disabled, the default)

Processing:
1. servo->first_update starts at 1 (servo.c:87), so stage 1's test takes the "first_update && first_step_threshold < |offset|" branch
   (pi.c:113-118)
2. |offset| = 1 s > 20 µs ⇒ SERVO_JUMP
3. clock_synchronize() calls clockadj_set_freq(-adj) first, then clockadj_step(-offset)
   (clock.c:2055-2061); after the step, step_window_counter is set if step_window
   is configured (clock.c:2069, :1982-1988), and the next few Sync ticks skip synchronization
4. first_update is set to 0 (servo.c:132), and the offset is wiped out in one go
5. afterwards step_threshold = 0, so however large the offset gets, the servo only adjusts frequency and never steps

Later, if you change step_threshold to 0.00001 (10 µs):
1. In stage 2 (count=2), |offset| = 20 µs > 10 µs ⇒ first return SERVO_UNLOCKED
   and clear count to 0 (pi.c:133-138); this tick does **not** step
2. The comment at pi.c:126-132 explains why: the step is left for "stage 1",
   so drift gets re-estimated as it did at startup
3. The next tick falls into stage 0 (record only), then the tick after into stage 1,
   where the step_threshold branch holds (pi.c:116-118) ⇒ SERVO_JUMP, one step
4. After the step the estimate runs again → back to stage 2, normal frequency adjustment
```

**Two configuration modes**:

```text
    kp_scale = 0.7, ki_scale = 0.3 (pi.c:214-215)

       but each is still capped by norm_max / interval (pi.c:162-163, :166-167)

    pi_proportional_scale     0.7
    pi_integral_scale         0.3      ← must be given as a pair (pi.c:220)

                                   ki's exponent comes from the default at config.c:332
```

## Practical tuning advice

### Hardware timestamping

```ini
[global]
# defaults suited to hardware timestamping
pi_proportional_scale 0.7
pi_integral_scale 0.3

# step threshold (seconds, 0.00001 = 10 µs)
step_threshold 0.00001

# stability detection (offset threshold in ns)
servo_offset_threshold 100
servo_num_offset_values 5
```

### Software timestamping

```ini
[global]
# software timestamping needs more conservative parameters
pi_proportional_scale 0.1
pi_integral_scale 0.001

# a larger step threshold (0.001 s = 1 ms)
step_threshold 0.001
```

### High-accuracy setups

```ini
[global]
# more aggressive parameters
pi_proportional_scale 1.0
pi_integral_scale 0.5

# smaller step thresholds (1e-6 s = 1 µs, 1e-4 s = 100 µs)
step_threshold 0.000001
first_step_threshold 0.0001

# a stricter stability requirement (50 ns)
servo_offset_threshold 50
servo_num_offset_values 10
```

## Summary: the design wisdom of the servo controller

**Object-oriented design**:
- the base class defines the interface
- derived classes implement the algorithms
- one uniform call path

**Three-phase sampling**:
- initialize → estimate frequency → normal control
- step by step into a stable state

**Adaptive parameters**:
- adjusted automatically from the Sync interval
- adapt to different network conditions

**Several algorithms to choose from**:
- PI controller: classic and reliable
- linear regression: robust
- null filter: for debugging
