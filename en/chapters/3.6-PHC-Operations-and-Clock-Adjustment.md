# 3.6 PHC Operations and Clock Adjustment: Talking to the Hardware Clock

## The two clocks

A Linux PTP node has (at least) two clocks:

- the PTP Hardware Clock (PHC), `/dev/ptp0`, the NIC's on-board timer, the clock PTP syncs;
- the system clock, `CLOCK_REALTIME`, what applications actually read, disciplined by `phc2sys`.

Section 3.11 covers phc2sys.

## The PHC interface (phc.c)

### Capabilities

```c
#include <linux/ptp_clock.h>

struct ptp_clock_caps {
    int max_adj;           /* max ppb the clock can be tuned over */
    int n_alarm;
    int n_ext_ts;
    int n_per_out;
    int pps;
    int n_pins;
    int cross_timestamping;
    int adjust_phase;      /* PHC supports phase (slew) adjustment */
};
```

`adjust_phase` comes from a newer kernel (linuxptp's `missing.h` marks it "from upcoming Linux kernel version 6.5"); in older headers the field is `int rsv[13]`. `phc_has_writephase()` reads this field.

The key ioctls:

| ioctl | Argument | Purpose |
|:---|:---|:---|
| `PTP_CLOCK_GETCAPS` | `struct ptp_clock_caps` | capabilities |
| `PTP_SYS_OFFSET` | `struct ptp_sys_offset` | cross-timestamp with the system clock |
| `PTP_PIN_SETFUNC` | `struct ptp_pin_desc` | pin configuration |

Frequency and time adjustment do not use PHC ioctls. They go through `clock_adjtime(CLOCKID, &tx)` with `ADJ_FREQUENCY`, `ADJ_SETOFFSET`, or `ADJ_OFFSET`, the same `struct timex` interface used for any clock.

### Opening a PHC

PHCs are exposed via `clock_gettime`/`clock_adjtime` on the fd. LinuxPTP derives a clockid from the fd:

```c
#define CLOCKFD 3
#define FD_TO_CLOCKID(fd)  ((~(clockid_t) (fd) << 3) | CLOCKFD)
#define CLOCKID_TO_FD(clk) ((unsigned long) ~((clk) >> 3))
```

`phc_open()` validates that the device really is a PHC by calling `clock_gettime()` and `clock_adjtime()` on the derived clockid.

### Frequency adjustment

`phc_max_adj(clkid)` reads `caps.max_adj`; the constant:

```c
#define MAX_PPB_32  32767999   /* (2^31 − 1) / 65.536 */
```

That's the largest ppb a 32-bit `timex.freq` supports at the 65.536 ppb-per-tick scaling.

### Step and phase

`phc_has_pps()` and `phc_has_writephase()` detect the additional features (`PPS` capability, `adjust_phase`). Phase is applied through `clockadj_set_phase()`.

## Adjusting the clock (clockadj.c)

`clockadj.c` wraps `clock_adjtime(CLOCKID, &tx)` / `adjtimex` for the target clock.

### struct timex (linux/timex.h)

```c
struct timex {
    int    modes;      /* what to modify */
    long   offset;     /* time offset (us or ns per ADJ_*) */
    long   freq;       /* frequency, scaled: 1 ppm = 65536 */
    long   maxerror, esterror;
    int    status;
    long   constant, precision, tolerance;
    struct timeval time;
    long   tick;
    ...
};
```

### ADJ_ modes

| Flag | Value | Meaning |
|:---|:---|:---|
| ADJ_OFFSET | 0x0001 | with ADJ_NANO → ns offset |
| ADJ_FREQUENCY | 0x0002 | freq scaled 65.536/ppb |
| ADJ_MAXERROR / ADJ_ESTERROR | 0x0004/0x0008 | error fields (refclock) |
| ADJ_STATUS | 0x0010 | status bits |
| ADJ_TIMECONST | 0x0020 | PLL time constant |
| ADJ_TAI | 0x0080 | set TAi offset |
| ADJ_SETOFFSET | 0x0100 | one-shot step |
| ADJ_MICRO / ADJ_NANO | 0x1000/0x2000 | units of offset/time |
| ADJ_TICK | 0x4000 | coarse tick |

### clockadj_set_freq (lines 51-70)

```c
/* clockadj.c, lines 51-70 */
int clockadj_set_freq(clockid_t clkid, double freq)   /* freq in ppb */
{
    struct timex tx;
    memset(&tx, 0, sizeof(tx));

    /* For the system clock, also set the coarse tick length. */
    if (clkid == CLOCK_REALTIME && realtime_nominal_tick) {
        tx.modes |= ADJ_TICK;
        tx.tick = round(freq / 1e3 / realtime_hz) + realtime_nominal_tick;
        freq -= 1e3 * realtime_hz * (tx.tick - realtime_nominal_tick);
    }

    tx.modes |= ADJ_FREQUENCY;
    tx.freq = (long)(freq * 65.536);         /* 65.536 per ppb */
    if (clock_adjtime(clkid, &tx) < 0) {
        pr_err("failed to adjust the clock: %m");
        return -1;
    }
    return 0;
}
```

### clockadj_step (lines 102-127)

```c
int clockadj_step(clockid_t clkid, int64_t step)
{
    struct timex tx = {0};
    tx.modes = ADJ_SETOFFSET | ADJ_NANO;
    tx.time.tv_sec  = step / NSEC_PER_SEC;
    tx.time.tv_usec = step % NSEC_PER_SEC;
    sign-correct tv_usec;
    return clock_adjtime(clkid, &tx) ? -1 : 0;
}
```

Note: the `tv_usec` member holds *nanoseconds* when `ADJ_NANO` is set, despite the name.

### clockadj_set_phase

Uses `adjtimex` phase offset (ADJ_OFFSET | ADJ_NANO) for a smooth slew.

## Why the PHC's freq range is so wide

`caps.max_adj` comes from the driver; hardware PHCs commonly support big ranges (±0.5 %, ±1 %, sometimes ±32 %). The `timex.freq ± 65.536/ppb` scaling spans ±(2^31−1)/65.536 ≈ ±32,767,999 ppb (≈ ±32,768 ppm) per 32-bit field; the driver clamps further.

## The tick dance (for CLOCK_REALTIME)

For the *system* clock, when the requested frequency exceeds the fine `freq` range, LinuxPTP falls back onto the coarse `tick` adjustment:

```
tx.tick = round(desired_freq / 1e3 / USER_HZ) + nominal_tick
(freq -= 1e3 * USER_HZ * (tx.tick − nominal_tick))
```

Example (USER_HZ = 1000, nominal tick 1000 µs, desired +10 % = 1e8 ppb):

```
tx.tick = round(1e8 / 1e3 / 1000) + 1000 = 1100 µs
freq -= 1e3 * 1000 * 100 → 0
```

So the coarse tick carries the whole +10 % and `freq` finishes at 0. That's the "two-part" adjustment: coarse `tick` plus fine `freq`.

## phc_ctl

`phc_ctl /dev/ptp0 -- get` prints the current PHC time; `phc_ctl /dev/ptp0 -- freq 100.0` applies a 100 ppb frequency offset. It's the debugging Swiss-army knife for PHCs.

## Summary

- The PHC is a clockid derived from `/dev/ptpN` fds; the core is `clock_adjtime()`.
- Capabilities (`max_adj`, `adjust_phase`, PPS) are read via `PTP_CLOCK_GETCAPS` ioctls.
- Frequency is scaled at 65.536 per ppb; steps use `ADJ_SETOFFSET | ADJ_NANO`; phase slew uses `ADJ_OFFSET`.
- The system clock gets an extra coarse `tick` correction for large offsets.
