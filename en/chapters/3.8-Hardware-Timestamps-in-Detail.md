# 3.8 Hardware Timestamps in Detail: The Magic of Nanosecond Precision

## Why timestamp accuracy matters

In PTP synchronization, accuracy depends on timestamp accuracy:

```text
Timestamp accuracy and synchronization accuracy:

Software timestamping:
- Stamped in the kernel protocol stack
- Passes through the network stack
- Delay is unpredictable (scheduling, interrupts)
- Accuracy: microsecond level
- Use: ordinary setups

Hardware timestamping:
- Stamped in the NIC's timestamping unit (in the MAC or the PHY)
- Closest to the physical medium
- Delay is fixed and tiny
- Accuracy: nanosecond level
- Use: industrial, telecom, and other high-accuracy setups

How big is the gap?
- Software timestamping: sync accuracy usually lands in the microsecond range
- Hardware timestamping: sync accuracy usually lands in the sub-microsecond range
- One to two orders of magnitude apart (in practice it depends on the network and configuration)
```

## Timestamp types

### The timestamp_type enum

```c
/* defined in msg.h (util.h only declares ts_str) */

enum timestamp_type {
    TS_SOFTWARE,     /* software timestamp */
    TS_HARDWARE,     /* hardware timestamp */
    TS_LEGACY_HW,    /* legacy hardware timestamp */
    TS_ONESTEP,      /* one-step clock (Sync) */
    TS_P2P1STEP,     /* one-step clock (P2P) */
};
```

**Five timestamp types**:

```text
TS_SOFTWARE:
- The kernel stamps the packet while the stack processes it
- Uses the system clock (CLOCK_REALTIME)
- Setting: SOF_TIMESTAMPING_TX_SOFTWARE
- Accuracy: microsecond level

TS_HARDWARE:
- The NIC's timestamping unit stamps the packet in hardware (in the MAC or the PHY)
- Uses the PHC clock
- Setting: SOF_TIMESTAMPING_TX_HARDWARE
- Accuracy: nanosecond level
- Needs hardware support

TS_LEGACY_HW:
- The old hardware timestamping implementation
- Some older NICs use it
- Setting: SOF_TIMESTAMPING_SYS_HARDWARE
- Accuracy: sub-microsecond level

TS_ONESTEP:
- One-step clock
- Rewrites the message timestamp when it sends a Sync
- No Follow_Up message needed
- Needs hardware support (HWTSTAMP_TX_ONESTEP_SYNC)

TS_P2P1STEP:
- One-step clock for P2P delay measurement
- Rewrites the timestamp when it sends a Pdelay_Resp
- Needs hardware support (HWTSTAMP_TX_ONESTEP_P2P)
```

### sk_timestamping_init in detail

```c
/* sk.c, lines 560-650 - simplified */

int sk_timestamping_init(int fd, const char *device, enum timestamp_type type,
                         enum transport_type transport, int vclock)
{
    /* the real declaration looks like this (sk.c:563-564): filter1/filter2/tx_type are all local variables */
    int err, filter1, filter2 = 0, flags, tx_type = HWTSTAMP_TX_ON;
    struct so_timestamping timestamping;

    /* set the flags by timestamp type */
    switch (type) {
    case TS_SOFTWARE:
        flags = SOF_TIMESTAMPING_TX_SOFTWARE |
                SOF_TIMESTAMPING_RX_SOFTWARE |
                SOF_TIMESTAMPING_SOFTWARE;
        break;
    
    case TS_HARDWARE:
    case TS_ONESTEP:
    case TS_P2P1STEP:
        flags = SOF_TIMESTAMPING_TX_HARDWARE |
                SOF_TIMESTAMPING_RX_HARDWARE |
                SOF_TIMESTAMPING_RAW_HARDWARE;
        break;
    
    case TS_LEGACY_HW:
        flags = SOF_TIMESTAMPING_TX_HARDWARE |
                SOF_TIMESTAMPING_RX_HARDWARE |
                SOF_TIMESTAMPING_SYS_HARDWARE;
        break;

    default:
        return -1;
    }

    /* hardware timestamping needs extra driver configuration (sk.c:588-622) */
    if (type != TS_SOFTWARE) {
        filter1 = HWTSTAMP_FILTER_PTP_V2_EVENT;   /* first choice: the most general PTP filter */
        /* tx_type follows type, filter2 follows transport (sk.c:590-618) */
        err = hwts_init(fd, device, filter1, filter2, tx_type);
        if (err)
            return err;
    }

    /* bind the virtual clock */
    if (vclock >= 0)
        flags |= SOF_TIMESTAMPING_BIND_PHC;

    /* set the socket options */
    timestamping.flags = flags;
    timestamping.bind_phc = vclock;

    setsockopt(fd, SOL_SOCKET, SO_TIMESTAMPING, 
               &timestamping, sizeof(timestamping));

    /* select the error queue: this passes the constant 1, not the flags above (sk.c:636) */
    flags = 1;
    setsockopt(fd, SOL_SOCKET, SO_SELECT_ERR_QUEUE, &flags, sizeof(flags));

    /* finally there's a sk_general_init(fd) (sk.c:645) */
    return 0;
}
```

### Transmit timestamp types

```c
/* transmit timestamp types (<linux/net_tstamp.h>, excerpt) */

enum hwtstamp_tx_types {
    HWTSTAMP_TX_OFF,            /* no transmit timestamp */
    HWTSTAMP_TX_ON,             /* ordinary hardware timestamp */
    HWTSTAMP_TX_ONESTEP_SYNC,   /* one-step clock (Sync messages) */
    HWTSTAMP_TX_ONESTEP_P2P,    /* one-step clock (P2P messages) */
};
```

**The transmit types in detail**:

```text
HWTSTAMP_TX_OFF:
- The NIC does not stamp transmit packets
- For receive-only timestamping
- Or for software timestamping

HWTSTAMP_TX_ON:
- The NIC stamps transmit packets
- The timestamp goes into the error queue
- Userspace reads it with recvmsg(MSG_ERRQUEUE)
- A Follow_Up message has to carry the timestamp

HWTSTAMP_TX_ONESTEP_SYNC:
- One-step clock
- The NIC edits the packet directly when it sends the Sync
- It writes the timestamp into the PTP message's originTimestamp field
- No Follow_Up message needed
- Very demanding on the hardware

HWTSTAMP_TX_ONESTEP_P2P:
- P2P one-step clock
- The NIC modifies the Pdelay_Resp timestamp
- It writes requestReceiptTimestamp; the turnaround goes into the correction field (responseOriginTimestamp semantics)
- No Pdelay_Resp_Follow_Up needed
```

### Receive timestamp filters

```c
/* receive timestamp filters (<linux/net_tstamp.h>, excerpt) */

    HWTSTAMP_FILTER_NONE,              /* no receive timestamps */
    
    /* general timestamp filters */

    /* PTP-specific filters */
    HWTSTAMP_FILTER_PTP_V1_L4_EVENT,   /* PTPv1 UDP */
    HWTSTAMP_FILTER_PTP_V2_L4_EVENT,   /* PTPv2 UDP */
    HWTSTAMP_FILTER_PTP_V2_L2_EVENT,   /* PTPv2 Ethernet */
    HWTSTAMP_FILTER_PTP_V2_EVENT,      /* all PTPv2 */
    
    /* other protocols */
    HWTSTAMP_FILTER_NTP_ALL,           /* NTP packets */
};
```

**The filter types in detail**:

```text
Why filter at all?

NIC timestamping resources are limited:
- The hardware timestamp buffer is finite (in the MAC or the PHY)
- Stamping every packet burns resources
- Stamping only PTP packets is more efficient

Filter levels:
HWTSTAMP_FILTER_NONE:
- Stamps no packet
- For transmit-only timestamping

HWTSTAMP_FILTER_PTP_V2_L4_EVENT:
- Stamps PTPv2 UDP event messages only
- EtherType=IPv4/IPv6, UDP port=319
- The most common setting

HWTSTAMP_FILTER_PTP_V2_L2_EVENT:
- Stamps PTPv2 Ethernet event messages only
- EtherType=0x88F7
- Raw Ethernet transport

HWTSTAMP_FILTER_PTP_V2_EVENT:
- Stamps every PTPv2 event message
- Covers both UDP and Ethernet
- The most general

HWTSTAMP_FILTER_ALL:
- Stamps every packet
- The most resource-hungry
- For debugging or special cases
```

### The hwts_init function

```c
/* sk.c, lines 59-136 */

static int hwts_init(int fd, const char *device, int rx_filter,
                     int rx_filter2, int tx_type)
{
    struct ifreq ifreq;
    struct hwtstamp_config cfg;
    int orig_rx_filter;    /* remember which filter we actually asked the driver for (sk.c:64) */
    int err;

    init_ifreq(&ifreq, &cfg, device);

    /* check for VLAN over bond support */
    cfg.flags = HWTSTAMP_FLAG_BONDED_PHC_INDEX;
    err = ioctl(fd, SIOCGHWTSTAMP, &ifreq);
    if (err < 0) {
        if (errno == EINVAL || errno == EOPNOTSUPP) {
            init_ifreq(&ifreq, &cfg, device);
        } else {
            pr_err("ioctl SIOCGHWTSTAMP failed: %m");
            return err;
        }
    }

    switch (sk_hwts_filter_mode) {
    case HWTS_FILTER_CHECK:
        /* check only, no changes */
        err = ioctl(fd, SIOCGHWTSTAMP, &ifreq);
        if (err < 0) {
            pr_err("ioctl SIOCGHWTSTAMP failed: %m");
            return err;
        }
        break;

    case HWTS_FILTER_FULL:
        /* full filtering */
        cfg.tx_type = tx_type;
        cfg.rx_filter = HWTSTAMP_FILTER_ALL;
        err = ioctl(fd, SIOCSHWTSTAMP, &ifreq);
        if (err < 0) {
            pr_err("ioctl SIOCSHWTSTAMP failed: %m");
            return err;
        }
        break;

    case HWTS_FILTER_NORMAL:
        /* normal filtering, with fallback */
        cfg.tx_type = tx_type;
        cfg.rx_filter = orig_rx_filter = rx_filter;    /* sk.c:104 */
        err = ioctl(fd, SIOCSHWTSTAMP, &ifreq);
        if (err < 0) {
            pr_info("driver rejected most general HWTSTAMP filter");
            
            /* try the fallback filter */
            init_ifreq(&ifreq, &cfg, device);
            cfg.tx_type = tx_type;
            cfg.rx_filter = orig_rx_filter = rx_filter2;   /* sk.c:111 */
            err = ioctl(fd, SIOCSHWTSTAMP, &ifreq);
            if (err < 0) {
                pr_err("ioctl SIOCSHWTSTAMP failed: %m");
                return err;
            }
        }
        /* when the driver will only report HWTSTAMP_FILTER_SOME, put our saved
         * orig_rx_filter back so the check below does not trip over "SOME" (sk.c:119-120) */
        if (cfg.rx_filter == HWTSTAMP_FILTER_SOME)
            cfg.rx_filter = orig_rx_filter;
        break;
    }

    /* verify the configuration: the source explicitly allows HWTSTAMP_FILTER_ALL (sk.c:124-127),
     * so a driver reporting ALL is not a mismatch; without that clause the semantics weaken */
    if (cfg.tx_type != tx_type ||
        (cfg.rx_filter != rx_filter &&
         cfg.rx_filter != rx_filter2 &&
         cfg.rx_filter != HWTSTAMP_FILTER_ALL)) {
        pr_debug("tx_type   %d not %d", cfg.tx_type, tx_type);
        pr_debug("rx_filter %d not %d or %d", cfg.rx_filter, rx_filter,
                 rx_filter2);
        pr_err("The current filter does not match the required");
        return -1;
    }

    return 0;
}
```

**The SIOCSHWTSTAMP ioctl**:

```text
SIOCSHWTSTAMP: set the hardware timestamping configuration

struct ifreq {
    char ifr_name[IFNAMSIZ];    /* interface name */
    void *ifr_data;             /* points to hwtstamp_config */
};

Call sequence:
1. Build hwtstamp_config
2. Set tx_type and rx_filter
3. ioctl(fd, SIOCSHWTSTAMP, &ifreq)
4. The NIC driver receives the configuration
5. The driver configures the timestamping unit (MAC or PHY)
6. The timestamping unit starts stamping the selected packets

Notes:
- A NIC has only one configuration
- Two processes cannot configure it at once
- Changing it takes another configuration call
```

**The fallback mechanism**:

```text
/* filter fallback (the source uses switch(transport); written here as a ternary for comparison) */

filter1 = HWTSTAMP_FILTER_PTP_V2_EVENT;      /* most general */
filter2 = transport == TRANS_IEEE_802_3 ?
          HWTSTAMP_FILTER_PTP_V2_L2_EVENT : /* Ethernet only */
          HWTSTAMP_FILTER_PTP_V2_L4_EVENT;  /* UDP only */

Try filter1:
- On success, use the most general filter
- On failure (driver does not support it), try filter2 based on the transport
  (UDP→PTP_V2_L4_EVENT, 802.3→PTP_V2_L2_EVENT)

Why fallback?
- NICs support different filters
- Some NICs support only L4 filtering
- Some NICs support only L2 filtering
- Pick what the hardware actually supports
```

## Reading timestamps

### The timestamp array

```text
/* SO_TIMESTAMPING returns three timestamps
 * In the real code ts is a pointer (sk.c:426: struct timespec *sw, *ts = NULL;),
 * and ts = (struct timespec *) CMSG_DATA(cm) points at the three elements in the control message (sk.c:474) */

struct timespec ts[3];

ts[0]: software timestamp (SOF_TIMESTAMPING_SOFTWARE)
- The time when the kernel stack processes the packet
- Uses the system clock

ts[1]: system hardware timestamp (SOF_TIMESTAMPING_SYS_HARDWARE)
- Legacy hardware timestamp
- Converted by the kernel

ts[2]: raw hardware timestamp (SOF_TIMESTAMPING_RAW_HARDWARE)
- Supplied directly by the NIC's timestamping unit
- Uses the PHC clock
- The highest accuracy
```

### How sk_receive parses timestamps

## Reading transmit timestamps

### The MSG_ERRQUEUE mechanism

```c
/* transmit timestamps come from the error queue (excerpt) */

if (flags == MSG_ERRQUEUE) {
    struct pollfd pfd = { fd, sk_events, 0 };
    res = poll(&pfd, 1, sk_tx_timeout);
    if (res < 0 && errno == EINTR)
        res = poll(&pfd, 1, sk_tx_timeout);
    
    if (res < 0) {
        pr_err("poll for tx timestamp failed: %m");
        return -errno;
    } else if (!res) {
        pr_err("timed out while polling for tx timestamp");
        errno = ETIME;
        return -1;
    }
}

cnt = recvmsg(fd, &msg, MSG_ERRQUEUE);
```

**How the error queue works**:

```text
How transmit timestamping works:

1. The application sends a packet
   sendto(fd, buf, len, 0, &addr, sizeof(addr))

2. The packet passes through the kernel stack
   → reaches the NIC driver

3. The NIC sends the packet
   → the NIC's timestamping unit stamps it (MAC or PHY)

4. The timestamp goes into the socket error queue
   → it isn't a real "error"
   → the error queue is just borrowed as a delivery path

5. The application reads it from the error queue
   recvmsg(fd, &msg, MSG_ERRQUEUE)

Notes:
- MSG_ERRQUEUE does not receive a new packet
- It reads the timestamp of a packet sent earlier
- The packet contents come back as the "error information"
```

### Waiting for the timestamp with poll

```c
/* after sending, wait for the timestamp to become available */

res = poll(&pfd, 1, sk_tx_timeout);
```

```text
Why poll?

Timestamp generation takes time:
- The hardware needs time to stamp
- The timestamp has to travel back to the kernel
- The kernel has to put it in the error queue

Typical delays:
- NIC transmit: a few microseconds
- Hardware timestamp: nanosecond scale
- Trip back to the kernel: a few microseconds
- Total: microsecond scale

sk_tx_timeout:
- Its compile-time initial value is only 1 ms (sk.c:42: int sk_tx_timeout = 1;)
- ptp4l overwrites it from the config option at startup:
  sk_tx_timeout = config_get_int(cfg, NULL, "tx_timestamp_timeout") (ptp4l.c:193)
- tx_timestamp_timeout defaults to 10 and has a floor of 1 (config.c:386); the unit is milliseconds (ptp4l.8:1028-1031)
  ⟹ the "default 10 ms" you see in practice is the value after the override, not the initializer in sk.c
- On a timeout the cause may be a driver bug: the source's hint is "increase tx_timestamp_timeout
  or raise the kworker priority, but it's probably the driver anyway" (sk.c:449-452)
```

## One-step clocks

### How one-step works

```text
Ordinary clock (two-step):
1. The master sends a Sync
2. The master records the transmit time t1
3. The master sends a Follow_Up carrying t1
4. The slave receives the Sync (at time t2)
5. The slave receives the Follow_Up and gets t1

One-step clock:
1. The master builds the Sync (originTimestamp=0)
2. The NIC rewrites originTimestamp in hardware as it sends
3. It fills in the actual transmit time t1
4. No Follow_Up message needed
5. The slave gets t1 and t2 straight from the Sync

Advantages:
- One fewer message
- Less network load
- Less delay (t1 is more precise)
- A simpler stack

Challenges:
- The NIC has to edit the packet at transmit time
- Needs hardware support
- The timestamp must be computed before the packet is sent
- Very hard to do
```

### One-step implementation

```c
/* port.c, lines 1831-1878 (simplified example) */

/* check whether the TWO_STEP flag is needed */
if (p->timestamping != TS_ONESTEP && p->timestamping != TS_P2P1STEP) {
    msg->header.flagField[0] |= TWO_STEP;
}

/* send the Sync */
err = port_prepare_and_send(p, msg, event);
if (err) {
    pr_err("%s: send sync failed", p->log_name);
    goto out;
}

/* one-step: the hardware handles it, no Follow_Up needed */
if (p->timestamping == TS_ONESTEP || p->timestamping == TS_P2P1STEP) {
    goto out;
} else if (msg_sots_missing(msg)) {
    pr_err("missing timestamp on transmitted sync");
    err = -1;
    goto out;
}

/* two-step: send the Follow_Up */
fup->follow_up.preciseOriginTimestamp = tmv_to_Timestamp(msg->hwts.ts);
err = port_prepare_and_send(p, fup, TRANS_GENERAL);
```

**The hardware edit**:

```text
One-step hardware operation:

1. The application builds the Sync message
   originTimestamp = 0 (or an estimate)

2. The packet goes to the NIC driver

3. The driver configures the timestamping unit (MAC or PHY)
   HWTSTAMP_TX_ONESTEP_SYNC

4. Before the packet is transmitted:
   - Read the PHC time
   - Rewrite the message's originTimestamp field
   - Compute the UDP checksum (if needed)
   - Send the packet

5. The packet leaves
   originTimestamp = the actual transmit time

Where the hardware edits:
- In the PTP message header
- The originTimestamp field (10 bytes)
- Seconds field (6 bytes) + nanoseconds field (4 bytes)
```

### UDP checksum correction

```c
/* udp.c:254-260: on the IPv4 side, 2 bytes are added only for one-step; comment copied from the source */

/*
 * Extend the payload by two, for UDP checksum correction.

```

```c
/* udp6.c:269-271: on the IPv6 side, 2 bytes are added unconditionally, regardless of transport event type */

addr->sin6.sin6_port = htons(event ? EVENT_PORT : GENERAL_PORT);

len += 2; /* Extend the payload by two, for UDP checksum corrections. */
```

```text
The one-step UDP challenge:

What the UDP checksum covers:
- The UDP header
- The UDP data (the PTP message)
- The IPv6 pseudo-header

After the PTP message is modified:
- The UDP checksum no longer holds
- It has to be recomputed

How the hardware handles it:
1. Reserve 2 bytes before transmit
2. The hardware computes the checksum correction (MAC or PHY)
3. It fills in the reserved bytes
4. Actual UDP checksum = original checksum + correction

PHY chips such as the DP83640:
- Support automatic UDP checksum correction
- Need the reserved space
- len += 2
```

## Virtual clocks

### The vclock concept

```c
/* missing.h, lines 70-79 (excerpt: the source also wraps this in #ifndef HAVE_VCLOCKS / #endif) */

enum {
    SOF_TIMESTAMPING_BIND_PHC = (1 << 15),
};

struct so_timestamping {
    int flags;
    int bind_phc;    /* virtual clock index */
};
```

**Virtual PHC**:

```text
Newer Linux kernels add virtual clocks (virtual clock, used with SOF_TIMESTAMPING_BIND_PHC):

Background:
- One physical NIC can have several virtual PHCs
- Each virtual PHC runs independently
- They serve multi-domain PTP

Virtual clock index:
- bind_phc = 0: the physical PHC (default)
- bind_phc = 1: the first virtual PHC
- bind_phc = 2: the second virtual PHC

What it does:
- Binds timestamping to the chosen virtual clock
- Transmit packets use that virtual clock's time
- Receive packets use that virtual clock's time

Configuration:
vclock = interface_get_vclock(iface);
if (vclock >= 0)
    flags |= SOF_TIMESTAMPING_BIND_PHC;
timestamping.bind_phc = vclock;
```

### Multi-domain PTP

```text
Virtual clock use cases:

Case 1: telecom networks
- One physical network carries several domains
- Domain 1: frequency synchronization (1588v2)
- Domain 2: phase synchronization (1588-2019)
- Each uses a different virtual clock

Case 2: data centers
- Several tenants share the network
- Each tenant has its own clock domain
- Virtual clocks isolate them

Configuration example (assuming the physical PHC is ptp0):
# create virtual clocks: write the count into the physical PHC's n_vclocks
$ echo 2 > /sys/class/ptp/ptp0/n_vclocks

# wait for udev to create the new /dev/ptp* devices, then list the virtual clocks under this physical PHC
$ ls -d /sys/class/ptp/ptp0/ptp*
/sys/class/ptp/ptp0/ptp1  /sys/class/ptp/ptp0/ptp2

# ptp0: the physical clock
# ptp1, ptp2: virtual clocks

# ptp4l uses a virtual clock (phc_index is both a config key and a command-line long option)
ptp4l -i eth0 --phc_index 1
```

## Timestamp latency compensation

### ingressLatency and egressLatency

```c
/* latency compensation in port.c */

p->rx_timestamp_offset = config_get_int(cfg, p->name, "ingressLatency");
p->rx_timestamp_offset <<= 16;    /* convert to nanoseconds_scaled */

p->tx_timestamp_offset = config_get_int(cfg, p->name, "egressLatency");
p->tx_timestamp_offset <<= 16;

/* subtract the latency on receive */
ts_add(&msg->hwts.ts, -p->rx_timestamp_offset);

/* add the latency on transmit */
ts_add(&msg->hwts.ts, p->tx_timestamp_offset);
```

**How latency compensation works**:

```text
Timestamp latency:

Receive latency (ingressLatency):
Timestamping unit (MAC or PHY) → MAC → DMA → kernel → application
The latency includes:
- Timestamping unit to MAC delay (when in the PHY)
- MAC processing delay
- DMA transfer delay
- Kernel stack delay
- Total: a few microseconds to tens of microseconds

Transmit latency (egressLatency):
Application → kernel → DMA → MAC → PHY
The latency is similar to receive

Compensation:
receive timestamp = hardware timestamp - ingressLatency
transmit timestamp = hardware timestamp + egressLatency

Configuration (both in nanoseconds, default 0; after reading they are <<= 16 into the port):
[eth0]
ingressLatency 0
egressLatency 0

Usually:
- Hardware timestamping needs no compensation
- ingressLatency/egressLatency = 0
- Only special cases need them
```

## Timestamp debugging

### Four ready-made tools


## Summary: the key points of hardware timestamping

**Timestamp types**:
- Software, hardware, one-step clock
- Choose by what you need

**Configuration flow**:
- SIOCSHWTSTAMP configures the driver
- SO_TIMESTAMPING configures the socket
- recvmsg fetches the timestamp

**One-step clocks**:
- The NIC edits the message in hardware
- Saves a Follow_Up message
- Needs special hardware support

**Virtual clocks**:
- Multi-domain PTP support
- A new Linux feature

**Latency compensation**:
- ingressLatency/egressLatency
- Compensate for system delay
