# 3.9 TLV Processing: The Swiss Army Knife of Extended Information

## What is a TLV?

TLV (Type-Length-Value) is a general-purpose data-encoding format:

```text
TLV structure:
┌─────────┬──────────┬───────────────────┐
│Type     │Length    │Value              │
│2 bytes  │2 bytes   │Variable           │
└─────────┴──────────┴───────────────────┘

Type: identifies the TLV type, telling TLVs apart
Length: length of the Value field (not counting Type and Length)
Value: the actual data

Advantages:
- Extensible: a new type doesn't affect old implementations
- Flexible: variable-length data
- Easy to parse: dispatch on Type
```

**Where PTP uses TLVs**:

```text
PTP uses TLVs heavily:

1. Management messages
   - GET/SET operations
   - reading and writing data sets

2. Signaling messages
   - unicast negotiation
   - event subscription

3. Extension TLVs
   - organization extensions
   - profile extensions

4. Optional TLVs
   - path trace
   - alternate time offset
```

**TLV type ranges**:

```text
The TLV type allocation table in IEEE 1588-2019 divides the space like this:

0x0000            : reserved
0x0001-0x0009     : defined standard TLVs (0001/0002 management, 0004-0007 unicast
                    negotiation, 0008 path trace, 0009 alternate time offset)
0x000A-0x1FFF     : reserved
0x2000-0x2003     : values used by the 2008 edition, now retired; the standard says
                    they must not be put to other uses, to avoid clashes with 2008 implementations
                    (not a "security TLV range"; linuxptp uses them to talk to old
                    implementations: TLV_AUTHENTICATION_2008 and three more at tlv.h:38-41)
0x2004-0x202F     : experimental
0x2030-0x3FFF     : reserved
0x4000-0x4001     : ORGANIZATION_EXTENSION_PROPAGATE / ENHANCED_ACCURACY_METRICS
0x4002-0x7EFF     : reserved for the IEEE 1588 working group to assign propagating TLVs
0x7F00-0x7FFF     : experimental (linuxptp's TLV_SLAVE_DELAY_TIMING_DATA_NP = 0x7F00
                    lands here, tlv.h:53)
0x8000-0x8009     : defined non-propagating TLVs (including L1_SYNC, SLAVE_RX_SYNC_TIMING_DATA,
                    CUMULATIVE_RATE_RATIO, PAD, AUTHENTICATION)
0x800A-0xFFEF     : reserved for the working group to assign non-propagating TLVs
0xFFF0-0xFFFF     : reserved

Propagation (the rightmost column of the allocation table — don't treat the ranges as uniform):
- 0x0008 PATH_TRACE and 0x0009 ATO propagate; 0x0001-0x0007 do not
- 0x4000-0x7FFF all propagate; 0x8000 and above do not

By category:
- standard TLVs: 0x0001-0x0009
- security TLVs: 0x8009 AUTHENTICATION in 2019; 0x2000-0x2003 are 2008 leftovers
- organization extensions: three anchors (0x0003, 0x4000, 0x8000); OUI + subtype give the actual meaning
- profile extensions: built on organization extensions — 802.1AS Follow_Up_Info uses ieee8021_id + subtype 1
  (port.c:450-451); C37.238 2011/2017 use ieeec37_238_id + subtype 1/2
  (port.c:473-474, :487-488)
```

**How path trace works**:

```text
The Path Trace TLV records the path a message has taken:

master clock A sends an Announce:
Path Trace = [A]

boundary clock B forwards:
Path Trace = [A, B]

boundary clock C forwards:
Path Trace = [A, B, C]

the slave clock receives:
Path Trace = [A, B, C]
and knows the path: A → B → C → slave clock

Uses:
- fault diagnosis
- topology discovery
- path verification
```

```text
┌─────────┬──────────┬──────────┬──────────┬──────────┐

┌─────────┬──────────┬──────────┬──────────┬──────────┬──────────┐

│0x0005   │0x0008    │SYNC      │0         │300       │0         │
└─────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
Granted: authorized with the requested parameters
(lengthField=8: message_type(1)+logInterMessagePeriod(1)+durationField(4)+reserved(1)+flags(1))

3. Cancel unicast:

The slave clock sends CANCEL:
┌─────────┬──────────┬──────────┬──────────┐
│Type     │Length    │MsgType   │Reserved  │
│0x0006   │0x0002    │SYNC      │0         │
└─────────┴──────────┴──────────┴──────────┘

┌─────────┬──────────┬──────────┬──────────┐
│Type     │Length    │MsgType   │Reserved  │
│0x0007   │0x0002    │SYNC      │0         │
└─────────┴──────────┴──────────┴──────────┘
```

## Byte-order conversion

### Why byte-order conversion is needed

```text
Network byte order: big-endian
Host byte order: little-endian (x86/ARM)

The PTP protocol requires:
- all message fields in network byte order
- before sending: host order → network order
- after receiving: network order → host order

Example:
host value: 0x12345678
network order: 12 34 56 78 (big-endian)
host order: 78 56 34 12 (little-endian)

Conversions:
htons: host to network short (16-bit)
htonl: host to network long (32-bit)
ntohs: network to host short
ntohl: network to host long
```

### TLV byte-order macros

```c
/* tlv.c, lines 29-32 */

#define HTONS(x) (x) = htons(x)
#define HTONL(x) (x) = htonl(x)
#define NTOHS(x) (x) = ntohs(x)
#define NTOHL(x) (x) = ntohl(x)
```

### 64-bit byte-order conversion

```c
/* tlv.c, lines 97-113 */

static int64_t host2net64_unaligned(void *p)
{
    int64_t v;
    memcpy(&v, p, sizeof(v));
    v = host2net64(v);
    memcpy(p, &v, sizeof(v));
    return v;
}

static int64_t net2host64_unaligned(void *p)
{
    int64_t v;
    memcpy(&v, p, sizeof(v));
    v = net2host64(v);
    memcpy(p, &v, sizeof(v));
    return v;
}
```

**Why memcpy**:

```text
The alignment problem:

Some platforms (ARM, for example) require aligned memory access:
- 32-bit access: address aligned to 4 bytes
- 64-bit access: address aligned to 8 bytes

PTP messages may not be aligned:
- messages are packed tight
- a field can sit outside an alignment boundary

Accessing an unaligned address directly:
- x86: works (a little slower)
- ARM: can crash with SIGBUS

Using memcpy:
- handles unaligned addresses safely
- the compiler optimizes it well
```

## TLV receive processing

### The tlv_post_recv function

```c
/* tlv.c, lines 1145-1224 (excerpt) */

int tlv_post_recv(struct tlv_extra *extra)
{
    struct management_error_status *mes;    /* tlv.c:1147 */
    struct TLV *tlv = extra->tlv;
    struct management_tlv *mgt;
    int result = 0;

    switch (tlv->type) {
    case TLV_MANAGEMENT:
        /* management TLV: check length, cast, then convert the ID */
        if (TLV_LENGTH_INVALID(tlv, management_tlv))        /* tlv.c:1154-1155 */
            goto bad_length;
        mgt = (struct management_tlv *) tlv;
        mgt->id = ntohs(mgt->id);    /* convert the ID */
        if (tlv->length > sizeof(mgt->id))
            result = mgt_post_recv(mgt, tlv->length - sizeof(mgt->id), extra);
        break;

    case TLV_MANAGEMENT_ERROR_STATUS:
        /* error TLV: same length check */
        if (TLV_LENGTH_INVALID(tlv, management_error_status))   /* tlv.c:1162-1163 */
            goto bad_length;
        mes = (struct management_error_status *) tlv;
        mes->error = ntohs(mes->error);
        mes->id = ntohs(mes->id);
        break;

    case TLV_ORGANIZATION_EXTENSION:
        /* organization extension TLV: after the check, org_post_recv() flips the OUI and subtype (tlv.c:1168-1172) */
        if (TLV_LENGTH_INVALID(tlv, organization_tlv))
            goto bad_length;
        result = org_post_recv((struct organization_tlv *) tlv);
        break;

    case TLV_REQUEST_UNICAST_TRANSMISSION:
    case TLV_GRANT_UNICAST_TRANSMISSION:
    case TLV_CANCEL_UNICAST_TRANSMISSION:
    case TLV_ACKNOWLEDGE_CANCEL_UNICAST_TRANSMISSION:
        /* unicast negotiation TLV */
        result = unicast_negotiation_post_recv(extra);
        break;

    case TLV_PATH_TRACE:
        /* path trace TLV */
        if (tlv_array_invalid(tlv, 0, sizeof(struct ClockIdentity))) {
            goto bad_length;
        }
        break;

    case TLV_ALTERNATE_TIME_OFFSET_INDICATOR:
        /* alternate time offset TLV */
        result = alttime_offset_post_recv(extra);
        break;

    case TLV_AUTHENTICATION:
        /* authentication TLV */
        result = auth_post_recv(extra);
        break;

    /* ... other types ... */
    }

    return result;
bad_length:
    return -EBADMSG;
}
```

**The receive flow**:

```text
TLV receive flow:

1. Receive the raw byte stream
2. Check the TLV type
3. Dispatch to the handler for that type
4. Validate the length
5. Convert byte order
6. Parse the data fields
7. Return the result

Key points:
- validate the length first, to prevent buffer overruns
- use memcpy for unaligned fields
- pick the handler by type
```

```c
            flip16(&cd->protocolAddress->addressLength);
        }
        break;

    case MID_DEFAULT_DATA_SET:
        dds = (struct defaultDS *) m->data;
        dds->numberPorts = htons(dds->numberPorts);
        dds->clockQuality.offsetScaledLogVariance =
            htons(dds->clockQuality.offsetScaledLogVariance);
        break;

    case MID_CURRENT_DATA_SET:
        cds = (struct currentDS *) m->data;
        cds->stepsRemoved = htons(cds->stepsRemoved);
        cds->offsetFromMaster = host2net64(cds->offsetFromMaster);
        cds->meanPathDelay = host2net64(cds->meanPathDelay);
        break;

    case MID_TIME_STATUS_NP:
        tsn = (struct time_status_np *) m->data;
        tsn->master_offset = host2net64(tsn->master_offset);
        tsn->ingress_time = host2net64(tsn->ingress_time);
        tsn->cumulativeScaledRateOffset = htonl(tsn->cumulativeScaledRateOffset);
        tsn->scaledLastGmPhaseChange = htonl(tsn->scaledLastGmPhaseChange);  /* tlv.c:595 */
        tsn->gmTimeBaseIndicator = htons(tsn->gmTimeBaseIndicator);          /* tlv.c:596 */
        scaled_ns_h2n(&tsn->lastGmPhaseChange);                              /* tlv.c:597 */
        tsn->gmPresent = htonl(tsn->gmPresent);
        break;
    }
}
```

**The send flow**:

```text
TLV send flow:

1. The application fills in the data (host byte order)
2. tlv_pre_send runs
3. Handle it by ID type
4. Convert multi-byte fields to network byte order
5. Send

Note:
- single-byte fields need no conversion
- string fields need no conversion
- numeric fields need conversion
```

## TLV memory management

### The tlv_extra structure

```c
/* tlv.h, lines 469-476 */

struct tlv_extra {
    TAILQ_ENTRY(tlv_extra) list;    /* list node */
    struct TLV *tlv;                /* points to the TLV */
    union {
        struct mgmt_clock_description cd;    /* clock description */
        struct nsm_resp_tlv_foot *foot;      /* NSM response tail */
    };
};
```

**Why tlv_extra exists**:

```text
TLV messages can hold complex structures:
- variable-length fields
- nested structures
- extra parsing work

What tlv_extra does:
- keeps the parsed pointers
- avoids parsing twice
- manages the extra memory

Example:
CLOCK_DESCRIPTION holds several PTPText fields:
- physicalLayerProtocol
- productDescription
- userDescription

After parsing, tlv_extra->cd holds the individual pointers.
```

### The memory pool

```c
/* tlv.c, lines 41-42 */

static TAILQ_HEAD(tlv_pool, tlv_extra) tlv_pool =
    TAILQ_HEAD_INITIALIZER(tlv_pool);
```

```c
/* tlv.c, lines 1117-1143 (alloc 1117-1127, cleanup 1129-1137, recycle 1139-1143;
 * the order below is alloc → recycle → cleanup, but the source puts cleanup
 * before recycle) */

struct tlv_extra *tlv_extra_alloc(void)
{
    struct tlv_extra *extra = TAILQ_FIRST(&tlv_pool);

    if (extra) {
        /* take it from the pool */
        TAILQ_REMOVE(&tlv_pool, extra, list);
    } else {
        /* pool empty, allocate a new one */
        extra = calloc(1, sizeof(*extra));
    }
    return extra;
}

void tlv_extra_recycle(struct tlv_extra *extra)
{
    memset(extra, 0, sizeof(*extra));
    TAILQ_INSERT_HEAD(&tlv_pool, extra, list);
}

void tlv_extra_cleanup(void)
{
    struct tlv_extra *extra;

    while ((extra = TAILQ_FIRST(&tlv_pool)) != NULL) {
        TAILQ_REMOVE(&tlv_pool, extra, list);
        free(extra);
    }
}
```

**Why pool the objects**:

```text
PTP handles messages constantly:
- several messages per second
- each message may carry TLVs
- frequent alloc/free hurts performance

Pool optimization:
1. don't free after use; put the object back in the pool
2. take it from the pool next time
3. avoid frequent malloc/free
4. reduce memory fragmentation

Where this applies:
- objects created and destroyed often
- fixed-size objects
- short-lived objects
```

## Worked examples

### Building a management request

```c
/* Example: build a GET CURRENT_DATA_SET request
 * Adapted from the real code: pmc_common.c:580-606 (pmc_message) + :724-750 (pmc_send_get_action);
 * the server side that builds the response is port.c:3439-3475 (port_management_construct) */

struct ptp_message *msg;
struct management_tlv *mgt;
struct tlv_extra *extra;
struct PortIdentity target;         /* target port identity */
int datalen = 0, pdulen;

/* allocate a message */
msg = msg_allocate();
if (!msg)
    return -ENOMEM;

msg->hwts.type = TS_SOFTWARE;

/* Set the header: messageType and transportSpecific share the single tsmt byte (msg.h:91),
 * so there is no header.messageType field; reading it means msg_type() for the low 4 bits (msg.h:348-351) */
msg->header.tsmt               = MANAGEMENT;  /* port.c:3453 also ORs in transportSpecific */
msg->header.ver                = PTP_VERSION;
msg->header.messageLength      = sizeof(struct management_msg);
msg->header.domainNumber       = 0;
msg->header.logMessageInterval = 0x7f;

/* Set the target port: the real code assigns the whole struct at once (pmc_common.c:600) */
msg->management.targetPortIdentity = target;

/* Set the action: the management action is the low 4 bits of flags (msg.h:176);
 * read it with management_action() (msg.h:248-251); there is no header.actionField */
msg->management.flags = GET;

/* Build the TLV: it sits at the suffix zero-length array of management_msg */
mgt = (struct management_tlv *) msg->management.suffix;
mgt->type = TLV_MANAGEMENT;
datalen = 0;                       /* a GET request carries no data field */
mgt->length = 2 + datalen;         /* 2 = sizeof(mgt->id) */
mgt->id = MID_CURRENT_DATA_SET;

/* Accumulate messageLength by hand: hdr_pre_send() only htons the existing length, it does not recompute it (msg.c:91-98) */
pdulen = msg->header.messageLength + sizeof(*mgt) + datalen;
msg->header.messageLength = pdulen;

/* Attach tlv_extra: suffix_pre_send() at the end of msg_pre_send() walks msg->tlv_list,
 * calls tlv_pre_send(tlv, extra) for each TLV, and htons type/length (msg.c:228-239, :487) */
extra = tlv_extra_alloc();
if (!extra) {
    pr_err("failed to allocate TLV descriptor");
    msg_put(msg);
    return -ENOMEM;
}
extra->tlv = (struct TLV *) msg->management.suffix;
msg_tlv_attach(msg, extra);

/* Pre-send processing: this one call, and no other, does all the byte-order conversion (msg.c:442-489) */
msg_pre_send(msg);
```

### Parsing a management response

```c
/* Example: parse a CURRENT_DATA_SET response
 * Real path: transport_recv() → msg_post_recv() (msg.c:344-440, MANAGEMENT branch :426-428)
 *             → suffix_post_recv() (msg.c:184-226) calls tlv_post_recv(extra) for each TLV (:218)
 *             → a successful TLV is attached to msg->tlv_list by msg_tlv_attach() (:223) */

struct ptp_message *msg;
struct management_tlv *mgt;
struct currentDS *cds;
int cnt, err;

/* Post-receive processing: cnt is the byte count the transport read; this one call turns
 * the header, body, and TLVs all into host order (see port.c:3178-3179, nsm.c:353-354 for
 * the real call shape: it returns err, not a length) */
err = msg_post_recv(msg, cnt);
if (err)
    return err;

mgt = (struct management_tlv *) msg->management.suffix;
if (mgt->id == MID_CURRENT_DATA_SET) {    /* mgt->id was already ntohs'd by tlv_post_recv (tlv.c:1157) */
    cds = (struct currentDS *) mgt->data;
    
    /* by now the data is in host byte order (tlv.c:306-313) */
    printf("stepsRemoved: %hu\n", cds->stepsRemoved);                        /* UInteger16 */
    printf("offsetFromMaster: %lld ns\n", (long long)cds->offsetFromMaster); /* Integer64 */
    printf("meanPathDelay: %lld ns\n", (long long)cds->meanPathDelay);
}
```
