# 4.6 Troubleshooting and Optimization

## Common problems

### Problem 1: no messages arrive

```bash
# firewall — PTP uses UDP 319/320
sudo iptables -A INPUT -p udp --dport 319 -j ACCEPT
sudo iptables -A INPUT -p udp --dport 320 -j ACCEPT

# multicast membership
ip maddr show eth0
```

Common causes: firewall, multicast disabled on the switch, wrong interface, wrong subnet.

### Problem 2: time never settles

```bash
# is the system clock being stepped by NTP concurrently?
timedatectl status
# if managed by NTP/chrony: disable it for the test
timedatectl set-ntp false
```

Also check that only one discipline source is active (ptp-lite + NTP = fight).

### Problem 3: accuracy is poor

The dominant limiter in ptp-lite is software timestamping: `clock_gettime()` runs in user space, so every t1/t2 has scheduling delays behind it. Options:

- Reduce interference and CPU frequency scaling noise.
- Use hardware timestamping where the NIC supports it (extension).
- Keep the network quiet; prefer direct links.

## Optimization

### Make the scheduler deterministic

```c
#include <sched.h>
struct sched_param param = { .sched_priority = 99 };
sched_setscheduler(0, SCHED_FIFO, &param);

cpu_set_t cpuset;
CPU_ZERO(&cpuset);
CPU_SET(2, &cpuset);
sched_setaffinity(0, sizeof(cpuset), &cpuset);
```

Pin the process to one core and give it real-time priority, this cuts user-space timestamp jitter dramatically.

### Prefer high-resolution reads

Read `CLOCK_MONOTONIC_RAW` or `CLOCK_REALTIME` via `clock_gettime()` (vDSO), never `gettimeofday()` with its coarse fallback. On modern kernels the vDSO read is a few tens of nanoseconds.

### Tune the servo

- Lower the step threshold → fewer jumps, longer convergence.
- Raise it → faster initial alignment, risk of jumps.
- On stable links, larger `kp` tightens the loop; on jittery links, smaller.

### Later: move to hardware

With a PHC-capable NIC the same program can latch timestamps at the MAC/PHY, moving from ~µs jitter to ~ns jitter, everything else in the book then applies.
